# The development gateway

`pnpm dev-gateway` runs a real OpenClaw gateway that exists only for development. It has its own state folder and ports, and a scripted model stands in for every model provider, so no account or key is ever used. Clawtrate is built and tested against it. The rules for working with it are in [CONTRIBUTING.md](../../CONTRIBUTING.md#the-development-gateway), and the tool's own reference, with the account checks, is [`tools/dev-gateway/README.md`](../../tools/dev-gateway/README.md).

## Starting it

```bash
pnpm dev-gateway start
```

This runs `openclaw --dev gateway run` on `ws://127.0.0.1:19001` with its state in `~/.openclaw-dev`, so it never touches a gateway you use day to day. It talks only to a scripted model server on `127.0.0.1:19091`; no model provider account is used. It then seeds four sample bots, each with its own instructions, eleven conversations with reasoning and tool calls, and seven finished examples of the live situations (see [Scenarios](#scenarios)). Each seeded run is checked against its script. `pnpm dev-gateway up` does the same.

Every start is a fresh, seeded gateway. It stops the gateway this checkout started before, deletes `~/.openclaw-dev` and creates it again empty. OpenClaw keeps credentials in the same SQLite stores a clean profile has, so the tool never reuses state rather than trying to prove old state clean. If `~/.openclaw-dev` was not created by this tool, or is a symlink, `start` refuses and changes nothing. The tool records every process it starts by PID and start time, and it deletes a state folder only with proof that nothing runs on it: every recorded process is gone and nothing listens on the instance's ports. A process counts as gone only when the system says there is no such process, or shows it as a zombie. When the tool cannot tell, for example because `ps` fails or prints something it cannot read, it treats the process as running, signals and deletes nothing, and says what it could not determine. So if the folder's gateway may be running and this checkout cannot prove it started it, `start` and `reset` refuse, say which instance is in use, and change nothing. `stop` signals only processes it can prove this checkout started; anything it cannot prove, it reports and leaves alone. A process `stop` ended counts as stopped only once the port it listened on is closed too, since a gateway killed while busy can show as a zombie while its last threads still hold its socket: `stop` waits up to 10 seconds for the port, then names the process and the port and keeps its records. An instance's development browser and its helper processes, which can outlive the gateway and leave its process tree, are found by their arguments naming the instance's own browser folder: `stop` and `reset` wait for them to exit, stop by PID any still running after 10 seconds, and `reset` deletes nothing until none is left. A state folder made by an older version of the tool is refused for good; see [Migrating from an older version](#migrating-from-an-older-version). Because the gateway is new each time, preview hosts and the desktop app pair again after a start. The generated config must match one closed contract (only the scripted model, token auth on loopback, workspaces inside the instance, the tool allowlist and the rest; see `docs/decisions.md`); any other key or value stops `start` before the gateway runs. That contract covers the configuration only; a plugin loaded with `--with-plugin` is code that runs with your own access (see [Plugins of this project](#plugins-of-this-project)).

Other commands: `pnpm dev-gateway status`, `stop`, `seed` (verify the running gateway's seed), `approve`, `reset` (stop, then delete the instance's state folder), `list`, `prune`, and on a named instance `lock` and `unlock` (see [Scripted provider accounts](#scripted-provider-accounts)). Commands that talk to the gateway refuse to run unless the gateway this checkout started on that state is still running.

## Instances

What is described above is the default instance. One machine can run several development gateways at once, for example a long-lived preview and an end-to-end run in another checkout. Each is an instance, named with `--instance <name>` on any command or with `CLAWTRATE_DEV_INSTANCE`:

```bash
pnpm dev-gateway start --instance review
pnpm dev-gateway approve --instance review
CLAWTRATE_DEV_INSTANCE=review pnpm dev-gateway status
pnpm dev-gateway list       # every instance on this machine, its folder, ports and gateway
pnpm dev-gateway reset --instance review
pnpm dev-gateway prune      # machine-wide: remove every idle named instance, any checkout's
```

A name is 1 to 24 lowercase letters, digits and inner hyphens. The instance runs `openclaw --profile clawtrate-dev-<name>` with its state in `~/.openclaw-clawtrate-dev-<name>`, and `start` picks free ports for its gateway and scripted model between 19200 and 19999 and records them. Every rule above holds per instance: its own fresh folder and marker, its own run files in `tools/dev-gateway/.run/instances/<name>`, and no command for one instance acts on another instance's folder, gateway or processes. `reset` removes only the named instance. `start`, `stop`, `reset` and `prune` take a lock per instance, and port choice a lock for the machine, so no two of these commands act on the same instance at once. `start` holds its lock until the gateway is healthy, its exec policy checked and its bots seeded; a `stop` or `reset` issued meanwhile waits for it (up to ten minutes) and then acts on the finished instance. `status`, `seed`, `approve` and `list` take no lock. `list` and `prune` cover every instance on the machine and refuse `--instance`; `prune` is deliberate maintenance, removes only instances proven idle, and never the default one.

## Plugins of this project

A named instance can load this checkout's own OpenClaw plugins, from `plugins/`, by name:

```bash
pnpm dev-gateway start --instance review --with-plugin <plugin> [--with-plugin <another>]
```

**A plugin loaded with `--with-plugin` is trusted code.** It runs inside the gateway with your full access to files, processes and the network. The guard constrains the gateway's configuration and the tools bots are given, not what plugin code does. Load only plugins from this repository that you have read. `start` prints this every time it loads a plugin.

What the guard does check:

- **Where it comes from.** The plugin's real path must be a direct child, by exactly that name, of the real path of this checkout's `plugins/`. Neither folder may be a link, and nothing inside the plugin may be one. `start` reads the folder once, writes that copy into the instance's state folder, records its digest, and the gateway loads only the copy. `seed` checks the copy against the digest again.
- **What it may set.** Beside its manifest, each plugin has a `clawtrate-dev-contract.json` that lists the exact config keys it sets and the exact tools it turns on, each with a declared kind:
  - a setting is a `flag`, a `count`, a `loopback-url` (parsed, with a loopback host), an `instance-path` (plain names, resolved inside the instance's state folder) or a `scripted-model-url` (a plain path, given as that path on the instance's own scripted model);
  - a tool is a `plugin-tool`, and may not be one the gateway provides itself;
  - there is no kind for free text, a command, an argument list, a credential or a model provider, and any other key or kind is refused.
- **What its manifest may declare.** Providers and sign-in methods only for the scripted account providers (`acme`, `globex`), and then only on an instance started with `--with-accounts`; no provider aliases, catalogues or endpoints.

One plugin of an instance may also declare `botBrowsers`: which seeded bots get a browser of their own, and two timings, each from a closed set. The tool then writes the whole browser setup itself and the guard refuses any other browser setting. [`plugins/clawtrate-computer`](../../plugins/clawtrate-computer/README.md), the plugin for watching and taking over a bot's browser, does this for Marlow and Pip, whose browsers can open only the instance's scripted pages on loopback:

```bash
pnpm dev-gateway start --instance browse --with-plugin clawtrate-computer
```

[`plugins/clawtrate-tool-rules`](../../plugins/clawtrate-tool-rules/README.md), the rules plugin (what each bot may do without asking, after asking, or never), declares no setting and no tool, so it adds only its entry and its load path; every bot keeps the development config's denies:

```bash
pnpm dev-gateway start --instance rules --with-plugin clawtrate-tool-rules
```

Its rules are set from a connection with admin access (`clawtrate-tool-rules.set`), and its cards are the gateway's plugin approvals, answered from a client with `operator.approvals`. `pnpm scenarios` runs the rules checks on an instance of their own started this way, with an admin connection, Clawtrate's interactive tier, another device with approvals, one with read and write and a read-only one: rules lost with and without a copy (the check spoils the instance's own rules file and restores it), the methods' tiers and the empty event, an Ask's card and who receives it, Allow once and Deny, a Never, an Allow that does not pass an Ask, "Ask when nothing else decides", the limits, a Never on another spelling of a file's name, a card with approval forwarding on (to no destination) and with `cardDetails: "full"`, a routine's call, a setting changed while a card waits, the plugin turned off in the middle of a run, and a call in a run another bot's message started (`#message-read`). [The plugin's page](../../plugins/clawtrate-tool-rules/README.md#on-a-clawtrate-development-gateway) lists what each asserts. Turning the plugin off and on again, setting its `cardDetails`, or turning approval forwarding on, as the checks do, takes the config outside the contract until it is back.

The default instance and `pnpm e2e` load no plugins. [The opening](../decisions.md#development-gateway) is described in `docs/decisions.md`.

## Scripted provider accounts

```bash
pnpm dev-gateway start --instance acct --with-accounts --with-plugin clawtrate-dev-signin
pnpm dev-gateway lock --instance acct --agent <bot> --provider acme acme:home
```

A named instance can carry scripted provider accounts: two scripted providers on its own scripted model, labelled accounts of both in the shared store and one kept by Otto alone, a record of which account's credential reached the scripted model for every request, failures scripted per account, and scripted sign-ins (a link and a code, a browser sign-in with the code pasted back, an API key) through the gateway's own `models.authLogin`. `lock` and `unlock` set and clear a bot's one-account order through the gateway's command line. [`tools/dev-gateway/README.md`](../../tools/dev-gateway/README.md) explains all of it, the account checks and what the gateway did.

## Local pairing at the gateway's default

```bash
pnpm dev-gateway start --instance pairing --default-local-pairing
```

Every instance sets `gateway.nodes.pairing.autoApproveLocal` to `false`, so a device's first pairing waits for approval even on loopback. `--default-local-pairing` leaves that one setting out of a named instance's config, at the gateway's own default, for research into what a first pairing on the gateway's own computer does when nobody has changed it ([`docs/research/setup-flow.md`](../research/setup-flow.md)). The contract follows: such an instance refuses the setting, and an ordinary instance still requires it. The default instance refuses the option.

## A paired machine

```bash
pnpm dev-gateway start --instance machines --with-node
```

A development gateway has no paired machine, so Settings, Machines and a bot's "Where it runs" would have nothing to show. `--with-node` (named instances only) starts the gateway's own headless node host, `openclaw node run`, on this computer, on loopback, under the instance's profile, recorded and stopped like the gateway (`status` lists it as `node`). It is called media-box and declares only the two commands that read and write its exec approvals file, so no bot's command can run on it. Its state, its approvals file included, is a folder of its own inside the instance's folder, so its file is not the gateway machine's. `start` approves its pairing request and its command request by id once each is exactly what it must be. `pnpm e2e` starts its accounts instance with it. [The decision](../decisions.md#where-a-bot-runs-and-machines) says what the gateway returned for each method these pages use.

## A stand-in image provider

```bash
pnpm dev-gateway start --instance pictures --with-images
```

`--with-images` gives a named instance an image provider, so a bot's `image_generate` tool can be tried. The stand-in (`tools/dev-gateway/src/scripted-images.ts`) is a third process of the instance, beside the gateway and the scripted model. It listens on `127.0.0.1` on the last port of the instance's block, the gateway's port plus 19. It is recorded in the instance's marker as its `image` process, and `stop` and `reset` stop it like the others. Its log is `image.log` in the instance's run folder, and a new start keeps the previous one as `image.previous.log`. A request whose body cannot be read, or is not a JSON object, gets a 400 answer and leaves the stand-in running. It answers the OpenAI-style image endpoint that the gateway's bundled LiteLLM image provider calls (`POST /v1/images/generations` with a bearer key), always with the same picture. That picture is a 1024 × 1024 PNG of a sun over a hill in solid colours, drawn by the stand-in's own code. `GET /scripted/images/requests` lists every request it received and what it answered, and, for one it left unanswered, when the gateway closed it. A reference picture at an outside address (the tool's `image` or `images`) is refused: by the gateway's own hostname and IP checks, or, for a name that passes them, at the instance's egress proxy.

The option adds three things to the config, and the contract holds each one exactly. It adds `models.providers.litellm` (the stand-in's address on loopback, the made-up key `example-image-key` and no models), and `agents.defaults.mediaModels.image.primary: "litellm/scripted-image-1"`. It also moves `image_generate` from `tools.deny` to `tools.allow`, for every bot. Use the `#image` directives below with it. A marker in the picture's prompt (`[scripted: refuse]`, `[scripted: fail]`, `[scripted: hang]`) makes the stand-in refuse with a content-policy error (400), fail (500) or never answer. The default instance refuses the option, and only `start` and `up` take it. [`docs/research/image-generation.md`](../research/image-generation.md) records what the gateway did with it.

## Migrating from an older version

Earlier versions of the tool recorded no process start times, so this version cannot prove anything about the state they left and refuses it for good: it never signals its processes, starts it over or deletes it. Move it aside once, by hand, from the checkout that started it. For the default instance:

1. Look up the old gateway's and scripted model's PIDs. That checkout's `tools/dev-gateway/.run/state.json` records them as `gatewayPid` and `providerPid`. Check that each is still that process with `ps -o pid,lstart,command -p <pid>`, then stop it with `kill <pid>`. Stop anything they started too (`pgrep -P <pid>` lists it).
2. Check that nothing listens on the instance's ports any more: `lsof -nP -iTCP:19001 -iTCP:19091 -sTCP:LISTEN` prints nothing.
3. Move the old state folder aside by renaming it: `mv ~/.openclaw-dev ~/.openclaw-dev.old`.
4. Delete that checkout's old run file: `rm tools/dev-gateway/.run/state.json`.
5. `pnpm dev-gateway start` now creates a new folder and succeeds.

For a named instance it is the same with `~/.openclaw-clawtrate-dev-<name>`, `tools/dev-gateway/.run/instances/<name>/state.json` and the ports its run file records. The tool never adopts, lists or deletes the folder you moved aside. Delete it yourself once you no longer need it.

## Scenarios

The scripted model can put a run into every situation the live conversation has to show. Start a task with any bot and send a directive such as `#steps`, or a phrase from the table anywhere in a message ("Please show your work"). Several directives in one message run one after the other, so `#think #mcp #ask` reasons, calls the coding agent, then asks you a question. A number after `#slow`, `#stream`, `#slow-tool`, `#sleep` or `#mcp-slow` sets its length in seconds. `#help` lists them all. Directives take precedence over phrases; with several phrases, the longest wins. The `#image` directives have no phrase, so no ordinary sentence asks for a picture. A turn the gateway starts on its own with one of the prompts it writes for that (a heartbeat or a wake with a queued system event, a turn that is only runtime context, a command that completed after its turn ended, a scheduled event with no content) gets `NO_REPLY`, the gateway's "nothing to say", so it leaves nothing in the task, whatever the event's text says. Two continuations are meant to be seen and are answered: another bot's reply arriving in the task after a `#message-slow` gets a short acknowledgement, and a reminder the gateway asks to relay is relayed (the scheduler is off here, so none runs). A turn started some other way, by a hook or a plugin for instance, with a prompt of its own, is not recognized; like any other message outside the table it gets a short reply saying the scripted model has none written for it.

Where it matters which bot you ask:

- **Shell commands** run only for Otto, and only after you approve each one. Every other bot's shell is denied, so `#approve` sent to Pip shows a denied step instead. Otto's scripted model only ever asks for the commands in the table. An approval with "allow always" lets that exact command run in Otto's workspace without asking again, until the instance is started over. [What can run](../decisions.md#what-can-run) says exactly what is allowed.
- **Bot-to-bot messages** go only between Marlow and Pip. A bot outside the pair asks Marlow, and the gateway refuses. A message goes to the other bot's main task ("Notes for Pip" in Marlow's list), and a bot may ask its user a question only in a task a person has written in, which the seed's example does.
- **Files** stay in the bot's own workspace: the gateway is configured to refuse file tools outside it.
- **Web search** goes to the scripted model server on loopback, through the gateway's bundled Ollama search provider, and returns three fixed results on the reserved `search.example` domain. Bots are offered only the tools these scenarios use; fetching web pages, the browser, tools that manage the gateway or its installation, and tools that reach the network or another device are switched off for every bot.
- **Browsers** (`#browse` and the others): only on an instance started with `--with-plugin clawtrate-computer`, and only for Marlow and Pip, each in a browser of its own that reaches nothing but the scripted pages. Elsewhere the browser tool is off and these directives answer that the instance has no scripted pages.
- **Pictures** (`#image` and the others): only on an instance started with `--with-images`. Elsewhere `image_generate` is denied, and the bot answers that it has no image tool. When a picture is ready, the gateway starts a turn of its own in the task. The scripted model answers that turn with a caption and the picture's `MEDIA:` line, and on a failure with a short sentence. The scripted model recognizes a plain completion only when the current runtime context contains its matching inter-session header. It also recognizes the protected runtime-context form.
- **Routines** (`#schedule`): the gateway offers its `automations` tool only in runs started as its owner, which the scenario check does through the CLI. Sent from a paired client, the run reports "Tool automations not found".
- **Questions and approvals** need a client with the right scopes. The read-only preview does not show them yet; answer from a client with `operator.questions` or `operator.approvals`.

After `start`, the seed has left finished examples, played through a paired client called "Clawtrate seed" that answers and approves as the user and is unpaired afterwards: Juniper's "Show your work" (reasoning and steps), "A step that fails" and "Hand off to the coding agent" (an MCP call); Pip's "Ask Marlow about the plan" (a bot-to-bot exchange) and "Which route on Saturday" (an answered question); Marlow's "Notes for Pip", where Pip's message arrived; and Otto's "List the workspace (approved)" (a resolved approval).

### Scheduled jobs

`pnpm dev-gateway routines --instance <name>` adds the [sample routines](../../tools/dev-gateway/src/routines.ts) when their names are absent. The development gateway's scheduler is off. To run a sample immediately, use `openclaw --profile clawtrate-dev-<name> gateway call cron.run --params '{"id":"<id>","mode":"force"}'`.
