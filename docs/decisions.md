## Connecting to the gateway

- **Client identity.** `connect` sends `client.id: "gateway-client"` and `client.mode: "ui"`, with a `displayName` of "Clawtrate Desktop" or "Clawtrate Web". The gateway accepts only ids from its registry, and the other ids name OpenClaw's own products. `gateway-client` with mode `backend` is a reserved trust path for internal helpers, so we use mode `ui`.
- **Scopes, in tiers.** A device starts read-only: every `connect` requests exactly `operator.read`, and reading bots, tasks, transcripts and live streams needs nothing more. The first time the user sends, stops or answers something, the client asks once, through `device.scopes.requestUpgrade`, for the interactive tier: `operator.read`, `operator.write`, `operator.approvals` and `operator.questions`. Write does not imply the other two, and a read+write device receives no question events and is refused every `question.*` call, so they are asked for together and the gateway's owner approves once. `connection.upgrade` shows the pending request id and the approve command, chosen by the host as for pairing. On approval the client stores the rotated device token from `device.scopes.waitUpgrade` (through the pinned `GatewayScopeUpgrade`) and reconnects. `operator.admin` and the narrower `operator.sessions.*` scopes are never requested.
- **Requested is not granted.** The token record keeps the gateway's grant in `grantedScopes` and what the client means to hold in `heldScopes`. Only `heldScopes`, normalized to read plus whichever interactive scopes were granted, is ever requested; a record without it means read. The pinned device-auth lifecycle would otherwise reuse a stored token's grant as the request, so the token store reports the held scopes to it, and the client refuses to send a plan whose scopes differ.
- **Capabilities.** `caps` is `["tool-events"]`, without which the gateway sends no tool lifecycle events. A connect that asks for `operator.approvals` adds `approvals`, `exec-approvals` and `plugin-approvals`: without the first two the gateway auto-denies exec approvals as `no-route`, and the third routes plugin approvals. A read-only connect claims none of them, so the gateway never waits for a connection that cannot see approvals. Question events need a scope, not a cap.
- **Pairing.** The core waits for `connect.challenge` and signs the v3 device payload through the host's signer. It sends `connect` with the shared gateway token as bootstrap auth. On `PAIRING_REQUIRED` it shows the request id and an approve command chosen by the host: `pnpm dev-gateway approve` for the development gateway, otherwise `openclaw devices approve <requestId>` with a line saying the gateway's owner runs it on the gateway's machine. An unqualified `openclaw` command is never shown for the development gateway, because it would address the default profile. It retries every 3 seconds, which keeps the same request id, so the app connects by itself once someone approves. After pairing the client saves the device token and uses it for later connections. It then tries to remove the shared gateway token from this device's settings. If that write fails, the file still holds the shared token and the client retries cleanup on the next successful handshake.
- **What a sign-in is given is scrubbed from what comes back.** A key, a pasted code or a pasted address is held for the life of its sign-in (or of a direct key save), as typed, trimmed and decoded, and, for an address, its query values while there is room; every string from the gateway that enters the accounts state or the host's log while it lasts is taken out of it, and at every end of the sign-in, the safety stop after 64 steps included, the values are forgotten. A value shorter than 4 characters is not a credential and is not scrubbed: taking it out would cut into ordinary words. An account's id is the gateway's own durable name for it and is not scrubbed: a gateway that names an account after its key publishes that to every client on every read. Closing the last window does not end a sign-in; it ends with its connection.
- **Device tokens are scoped to one gateway URL.** The token store key includes the URL, so a token issued by one gateway is never offered to another.
- **A credential never crosses gateways.** Each connection gets its own token store and device-auth lifecycle, bound to its gateway URL and connection generation. Every read and write names that URL, and every write, including the rotated token of an approved step-up and the dropping of a bootstrap token after pairing, is checked again after each wait and dropped once the connection is no longer current. A handshake or step-up that finishes after a switch writes nothing.
- **Routes, when the setup flow's SSH package is built** (`docs/design/setup.md` §15, `docs/research/setup-flow.md` §5). Until then the two statements above hold as written. Then "one gateway URL" becomes "one route": a URL for an address; the OpenClaw profile and its port for this computer; for SSH, the pinned host key, the resolved SSH target and the gateway's port on that computer, never the forward's local port. Each route keeps its own token, offered only on that route; no two routes share one, and on a route whose gateway can't be authenticated before the token is sent, the token isn't sent automatically. After every hello the client reads `gateway.identity.get`; routes reporting the same identity are shown as one gateway, which never moves a token; a route that reports a different identity than before has its token dropped and is not used until it is paired again. The generation checks above stay through every wait. A credential still never crosses gateways.
- **Losing access.** A call refused for a missing scope, an action or a list read, drops that scope from the connection's effective scopes, and `canWrite`, `canAnswer` and `canApprove` follow from them together; the next use asks for access again rather than repeating the refused call, and read access is kept. A dropped connection clears all three until the next hello. When the gateway stops accepting the device, or reconnecting stops, every operation waiting for access is refused, and one started after that fails at once, since no hello will come: a send fails visibly with retry and delete, a Stop goes back to how the run was, a question or approval keeps its error and stays answerable. The user's retry reconnects. At most `MAX_ACCESS_WAITERS` (512) operations wait for access at once.
- **A viewer that goes away takes its requests with it.** Each bridge session names itself to the client; on dispose, every task creation, Stop, answer or approval resolution it started that is still waiting for access is withdrawn at once, before the gateway is asked, and nothing of it is kept. The viewer's token is checked once more just before each of these asks the gateway, so one whose access was already held, or settled a moment before, is withdrawn too. Outgoing messages belong to the task, not the viewer, and are not withdrawn. A second answer to the same question or approval while one is on its way is refused.
- **Session list.** `sessions.subscribe` with list parameters gives the subscription and the snapshot in one call, and is re-established after every reconnect. The list is read in pages of 200 (`hasMore`, `nextOffset`) until the gateway reports no more, up to 50 pages; reaching that ceiling sets `discovery.partial` and the task list says so. Changes that arrive while the snapshot is in flight trigger a trailing re-read. `sessions.changed` deltas are merged field by field into cached rows: present fields replace, `null` clears, omitted fields stay. Event rows follow the same membership rules as the list query (`excludeCron`, `excludeSubagents`, archived), mirrored from the gateway's own filter: a known row that stops qualifying is dropped, and an unknown row is never inserted from an event, because its payload cannot prove membership; the filtered list is re-read instead. Nothing polls.
- **Discovery.** After hello, bots and tasks load independently. A failed read sets `discovery.status: "error"` with a message, keeps whatever loaded before, and the status strip offers a retry, which reloads without reconnecting.
- **Reconnecting.** Once a connection has reached hello, every later drop and failed attempt is `reconnecting`, never `connecting`, and reopening the same gateway keeps the cached bots, tasks and transcripts. The interface keeps the shell mounted whenever it has data.
- **Viewers.** The host keeps one client; each Electron window and each browser tab gets its own bridge session. Transcripts are reference-counted across sessions, so one viewer closing a task does not close it for another, and a closed tab releases what it held. A browser that reconnects is a new viewer to the host; its bridge (`createRemoteBridge` in core) remembers the tasks it has open and opens them again after every hello.
- **Closing a task keeps the user's words.** When the last viewer closes a task that still holds unsent, accepted-but-unconfirmed or failed messages, or a run this client started, the task is kept and followed until that work is done, confirmed or deleted; reopening shows the same queue. Switching gateways drops it: a message is never sent to another gateway than the one it was written for.
- **Transcripts.** Opening a task subscribes with `sessions.messages.subscribe` and reads `chat.history` (200 rows). `session.message`, terminal `chat` events and the `agent` lifecycle end reload history. Earlier pages (`hasMore`) are not loaded yet.

## Live runs

- **One engine, pure.** `packages/core/src/runs.ts` turns `chat` and `agent` events, `question.*` events, the user's own sends and stops, and `chat.history` into each open task's `runs`, `outbox` and `questions`. Run states and transitions follow the table in `docs/research/grok-bot-flows.md` §5.6. The client feeds it and owns the timers and requests.
- **Text from one projection per run.** The capability map says a run's text comes as `chat` deltas or as `agent` assistant events and that consuming both double-counts it. Each run takes its text from whichever arrives first and ignores the other. `chat` deltas, which carry the whole message or only what to add (`deltaText`, `replace`), are followed by the client's own `ChatTextBaselines` (`chat-text.ts`), which keeps only each streaming run's text, not the client package's `GatewayChatStreamProjection`, which kept the whole message.
- **Steps.** A step is a tool call (`tool:<toolCallId>`, the gateway's own id) or a reasoning segment, which has no gateway id. A reasoning step's id is derived, never matched: it is a pure function of its place in its run, `reasoning:<runId>:<anchor>:<n>` (`reasoningStepId`), where the anchor is the nearest tool call before it in the run (`t.<toolCallId>`), or `s` for the run's start, and `n` counts the reasoning blocks since that anchor. The live stream and history compute the same function, the run keeping its current anchor and count (`reasoningAnchor`, `nextReasoning`), so a resync has nothing to align and the raw payload behind a step is found under the same id. Its text plays no part. Promised: no id is used twice in a task; tool steps keep the gateway's id; on a resync of the same history window a reasoning card keeps its id whenever the reasoning blocks before it since its anchor are the same in number; a card the live stream showed as one, that history holds as several blocks (the gateway joins a message's thinking blocks with a newline on the live stream), keeps its id and shows the first of them, and the others follow with their own ids. Not promised: when history shows a reasoning block, since the same anchor, that the live stream never showed on its own, the cards after it there shift by one; when history reveals a tool call the live stream missed, the reasoning after it takes that call as its anchor and a new id; and nothing across a reopening or a different history window. So each run carries `reasoningRevision`, which increases whenever a reconciliation with history removes, adds or re-anchors any reasoning id in that run (steps retention dropped and history brings back, older than every step still shown, do not count). View state keyed by a reasoning id of a run is valid only while that run's `reasoningRevision` is unchanged. A page that does not reach the transcript's start (`hasMore`) and begins inside a run numbers that run's reasoning before its first visible tool call from the anchor `c`, so it never takes the ids a window that sees the run's start gives. A segment ends at a `lifecycle` `model` phase, at a tool item, at reply text, or at a cumulative frame that does not continue it. Bot-to-bot sends and MCP tools are ordinary tool steps with their exact names. Titles are derived from the tool name, the same live and from history; the gateway's English `item.title` is not used. Text on a step is cut to `MAX_STEP_BODY_CHARS` (2,048 JSON characters), and the cut is named in its `cut` at the first cut, whichever cap made it. The exact payloads stay in a raw table in the host process, inline on the step only when their JSON is at most `MAX_INLINE_RAW_CHARS` (2,048), otherwise read with the bridge command `readStepRaw`. That keeps the 16 ms state snapshots small however long a tool's output is.
- **What `readStepRaw` promises.** A step's whole text is read from the raw table while it fits there (`MAX_RAW_ENTRY_CHARS`, 262,144, and the table's total, oldest first) and no history row it came from was cut, and otherwise from the gateway's history once that step is in history. `chat.history` cuts every text to 8,000 characters unless asked for more (`maxChars`, at most 500,000), and flags the row `__openclaw.truncated`. So a whole read asks for the length it needs: the step's known whole length, or 500,000 when a history row already cut it. A reasoning id is a place, which history can give another block, so what was fetched counts as the step only when it shows so: for a tool, the gateway's own call id; for reasoning, a fetched text that begins with the text the step already holds. This check only ever withholds `available`. It answers `{status: "available", raw}` only when that is established and the row the gateway returned is not flagged; `{status: "cut-by-gateway", raw, receivedChars, reason}` when it is flagged, `raw` being what was received, the beginning of what the gateway stored followed by its own marker, and `receivedChars` the length of the longest text the rebuilt step exposes; `{status: "too-large-for-gateway", reason}` when the gateway replaced the message holding the step with its placeholder (`__openclaw.reason: "oversized"`: a single message above 131,072 bytes is replaced whatever `maxChars` asks, so asking again does not help); `{status: "not-established", reason}` when history holds something else at the step's place; and `{status: "not-available-yet", reason}` when history did not return the step, which may be because it does not hold it yet or because its page was too large to include it, so trying again later may help. It answers null only for a step the task does not have. Reasoning rows carry the gateway's cut in `Step.truncated` as tool rows do. `readHistoryItem` asks for 500,000 too. An item any of whose rows the gateway cut has `truncated: true`: the item kept in state, read at the gateway's default length, says so when that cut it; the item a whole read returns says so only when the gateway still cut it at 500,000 characters or replaced a row above its 131,072-byte limit with its placeholder.
- **Sending.** `chat.send` always carries a `queueMode`: `followup` for a new run, `steer` into the active run. With none the gateway steers. A steer's own run id is settled at once by the gateway with an empty final, so it is remembered as an alias and its events are ignored while the run it joined is active. The idempotency key is the message id; a retry reuses it. A refusal from the gateway fails the optimistic run as "Couldn't start"; a send whose outcome is unknown drops it, and its events or history bring it back if it did start. Deliveries for one task go out one at a time in the order they were made. Messages leave the outbox only when an identifier ties them to a history row: the row's idempotency key (under `__openclaw` or on the row), or the `messageSeq` `chat.send` returned when the row carries no contradicting key. Text is never evidence. Acceptance is not confirmation: a `sent` message whose run has ended, and that the history read after it does not tie to a row, becomes `unconfirmed`, with a note that it may not have been delivered, and can be retried with its own idempotency key (so the gateway delivers it at most once) or deleted. Its files are kept until history confirms it or the user deletes it. An acknowledgement that names no run assumes none: the optimistic run is dropped, and the next history read confirms the message or finds it unconfirmed. A `/stop` the gateway handles as a command answers `{ok, aborted, runIds}` before any run or turn is recorded (`chat-send-handler` in OpenClaw 2026.10.6); the message is then `handled`, starts no run, is never made unconfirmed, and can be dismissed. A request nobody answers is given up locally after `REQUEST_TIMEOUT_MS` (60 s), and its outcome is unknown, never failed: the message becomes `checking`, its optimistic run is dropped, and history reads decide it, tying it to a row or, once nothing does, making it `unconfirmed`, to retry with the same key. Only a refusal from the gateway, or a request that never left, fails it. Nothing is sent again on the client's assumption. Waits the gateway answers late by design (`device.scopes.waitUpgrade`) take no deadline.
- **Creating a task.** `sessions.create` is idempotent per device and key with the same parameters: the gateway keeps a success for 300 s, a repeat waits on work still in flight, and a refusal frees the key (OpenClaw 2026.10.6). The request is kept with its key, counted against `MAX_CREATIONS` and holding its task slot from the moment it is asked, before anything is awaited (access included), in `state.creations`; the same request asked meanwhile joins it, and one withdrawn or refused before it was sent takes those who joined with it. A refusal makes it `failed`, offered again with the same key (`retryCreation`) or dismissed. No answer makes it `checking`, never failed. It is asked again automatically, with the same key and parameters, only of the gateway start that holds the key, and only within `CREATION_KEY_WINDOW_MS` (240 s) of sending: the hello's `server.bootId` is a random id the gateway draws at each start (2026.10.6 sets it in `createGatewayKernel`), and the idempotency record lives in that start's single request context, so the same `bootId` means the same record. The client keeps the `bootId` the request went to and asks again, with backoff and at once after a reconnect, only while the current hello carries the same one; the gateway then brings back the original outcome, the task is kept with its first message in its outbox, and the creation shows `created` with its key. Start times estimated from `snapshot.uptimeMs` are not used: a fast restart can match them after the record was lost. A hello without a `bootId`, another `bootId`, or the end of the window makes it `unknown`: nothing establishes whether the task exists, so it is never sent again automatically. Its `error` says that retrying may create a second task; the user can dismiss it once they have checked the task list, or retry it (`retryCreation`, the same key), which is their own decision. The same request asked while one is out or being checked joins it; asked once it was created, it opens that task; asked while unknown, it is refused with that warning.
- **Queue and hold.** "Queue after this turn", and any send while a run is stopping, is held by the client and sent when the run is terminal; the gateway's own queue is not used. A send while a question is pending is held too: the gateway would take a plain message as the answer and fail the asking run. It goes out as a steer once the question is answered or dismissed. Whether a question is pending is read from the question records as well as the run's cards. When it settles, every held message is claimed at once and delivered once each, in the order sent.
- **Pending cards and steering.** A steer does not close cards or move a waiting run back to running; the map shows a steer leaving approvals pending. This is where the engine departs from §5.6, which closes approval cards on a steer.
- **Reasoning segments are best effort.** The `thinking` stream has no segment id. A segment ends at a model call, a tool item, reply text, or text that does not extend the last; the last of these cannot tell a rewrite from a new segment. So a reload never adds history reasoning to a run still in flight, and once history holds the finished run its `thinking` blocks replace the live segments, each under the id its place gives it. A fresh opening of a run in flight whose last persisted content is a `thinking` block keeps that segment open, as the live view has it. Whether the next cumulative frame continues it is judged against the length and digest of the segment's whole text so far (`continuation`), live or persisted, not against the text kept, which may be cut, nor the raw payload's shape: a frame continues it only when it is at least that long and its prefix of that length has the same digest. One that does not starts the next segment and leaves the earlier one done, with its text and raw payload. A segment without that evidence starts a new one rather than being assumed to continue. No reasoning text is shown twice or dropped.
- **Run endings.** A lifecycle `error` ends a run only when the gateway marks it definitive (`executionSettled`, `fallbackExhaustedFailure`, or a classification other than a plain failure); otherwise it is an attempt error kept in `attemptErrors`, and the run goes on to its fallback. Terminal events are classified as the gateway does (completed, cancelled or aborted, timed out, blocked, failed). A run keeps the terminal event's own `stopReason`, `timeoutPhase`, `providerStarted` and `status`, and a `chat` error's `errorKind`; nothing is read from error text. In history, the gateway's injected aborted-partial row (`openclawAbort`) means stopped; only a final reply row establishes completion, and a run history shows ended without one has `outcomeKnown: false`. The gateway's own run timeout pauses while waiting for an approval; Clawtrate's turn limit is wall-clock time from the send.
- **Tool results.** Both shipped shapes are read: `result: {content, details}`, and the native one with the text in `output` and the details in `result`. Command output is matched by its `toolCallId`, or by exec's `command:<toolCallId>` item. A result marked `replaceable` takes a later `replace` frame for the same call, even after the run ended, and history's copy wins over it on reload; either bumps the step's `correction`, so a view that keeps state across renders starts again from the facts. Errors are capped like other step text.
- **Timers.** Timers are capped at 2³¹−1 ms, which `setTimeout` cannot exceed, and re-armed when they wake early.
- **Not done for the conversation.** These are known and left open:
  - After a reconnect that missed a run's end, the earlier run stays shown as active and Stop is withheld until its end is learned.
  - The gateway may run a steer it accepted after the run it was meant for was stopped.
  - An assistant's reply is threaded only when each gateway row carries its own reference.
  - The phone, light, run-question screenshot check and the approval reconnect unit case are intermittent: the screenshot's follow-to-end failure stays with the open scroll issue, and the reconnect case's earlier timeouts at its wait for a connection are not explained by its passing alone.
  - In the isolated F-163 approval regression run the settled approval's Raw region once disappeared before the last assertion; this branch changes neither that card nor that check, and why it collapsed is open.

## Approvals

- **Origins.** An approval keeps who asked: agent, session, run and tool call. It is shown once, in one task: where it already is; its own session's task; the task holding its run; the task that spawned its session, a helper (`spawnedBy` on events, `relation: "helper"`); or the task whose `sessions_send` result named its run, or, for an approval naming no run, its session (`relation: "messaged"`). Messaging an existing bot does not make it a helper, so only the send's own result ties the two. Either kind carries `parentSessionKey`, and `runEnded` follows the asking run, which the client follows as a foreign session. One that arrives before any of these ties is known is kept in `unroutedApprovals` (at most `MAX_UNROUTED_APPROVALS`, 16; past it new ones are counted in `unroutedApprovalsOmitted`, not kept) and placed once its spawn, its send result or its own task appears. A helper's spawn is known only from its events, so after a fresh opening its approval waits there until the helper's next event.
- **Sources.** On opening a task and after every reconnect, `exec.approval.list`, `plugin.approval.list` and `openclaw.approval.list` load what is pending for it; `exec.approval.*`, `plugin.approval.*` and `openclaw.approval.*` requested and resolved events keep it current. All three kinds' requests and list items are `{id, request, createdAtMs, expiresAtMs}` envelopes (the requested event adds `approvalKind`); a system-agent request carries `title`, `description`, `command`, `proposalHash`, `allowedDecisions`, `agentId`, `sessionKey` and `runId`. Only `approval.get` and `approval.resolve` return an `ApprovalSnapshot`. Each list is read against a revision per task and kind and against the task's opening: a response older than one already applied, or from an earlier opening or connection, changes nothing. A failure, a timeout or a refusal is that revision's answer too: it changes only what it establishes (the kind's access is `error`, or a lost scope), and an older list arriving after it adds or settles nothing. A pending approval no longer listed after a reload is `closed` (`no-longer-listed`), but only if it was already pending when the list was asked for. Question lists follow the same rules. Each kind's access is kept in `approvalSources`; `approvalAccess` is `ready` only when all three loaded and `partial` when some failed. Without `operator.approvals` it is `unavailable`, which the interface must not show as "no approvals".
- **Outcomes are kept apart from the cards.** Every resolution the gateway reports is kept by id (at most `MAX_APPROVAL_OUTCOMES`, 512, oldest first; cleared when switching gateways), whether or not a card has arrived. A request or list entry that arrives after its resolution, or is replayed after its settled card was trimmed, shows settled, never actionable. A closure this client inferred (`expired` at the expiry time, `closed` when no longer listed) is marked `inferred`, and the gateway's own outcome replaces it, decision, reason and resolver included. Once the gateway has settled an approval, nothing reopens it; only a later application result is added.
- **Legacy denials are not assumed to be denials.** Exec and plugin resolved events read `deny` whether a reviewer denied the approval or the gateway cancelled it when its run was stopped or let it expire (`publishAppliedApprovalResolution` adds `terminalStatus` only for system-agent approvals). Such a deny is a lossy outcome: the approval shows `closed` with `outcomeUnknown` and reason `settled-cause-unknown`, never as a denial, and the client reads its snapshot with `approval.get`, under the `operator.approvals` it already holds (at most `MAX_OUTCOME_LOOKUPS`, 16, at once). The snapshot's exact outcome (`cancelled` with `run-aborted`, `expired`, or `denied` with its reason and resolver) replaces the lossy one; an exact outcome, this client's own included, is never replaced by a lossy one. If the snapshot cannot be read the approval stays closed with its cause unknown.
- **What it carries.** Every field the map and schema give: for exec the command, argv, cwd, host, node, security, ask, resolved path, warning and command analysis; for plugin approvals the title, description, detail, severity, plugin and tool; for the generic kind its title, description and proposal hash. Also the scope, the session, agent, run and tool call, created and expiry times, and the record as received. What an interactive exec approval will run is its request's `command` and `cwd`; a node's run plan (`systemRunPlan`) is kept apart, and `runsOn` says whether the command runs on the gateway or a node, whose own rules govern it. `allowedDecisions` holds exactly the decisions the request offers, plus `deny`. Without a list each kind takes the gateway's own default: exec requests always list theirs, so allow once less any `unavailableDecisions` is the safe reading; a plugin request gets the plugin default of allow once, allow always and deny; system-agent changes offer allow once and deny. A terminal snapshot's typed `resolver` (`device`, `channel`, `runtime` or `system`, with its id) is kept apart from the legacy events' `resolvedBy` label, and its `source` gives its session and agent. A system-agent resolution's `terminalStatus` (`cancelled`, `expired`) is the outcome, not the deny its decision field projects, and its later `applicationStatus` is kept as `applicationStatus`. A saved rule does not bypass a host that always asks, so an approval for an already allowed command is not an error.
- **Cut text.** A field cut to its bound is named in the card's `cut`, a diagnostic list of at most eight paths in which later cuts can displace earlier ones, so it is never the safety fact. That is `decisionCut`, set on each card when it is admitted (bounded) if what the reviewer is asked to allow was cut (an exec command, its argv or cwd, a plugin or system-agent approval's text), and never cleared. While it is set only deny is accepted, except from a viewer the host itself gave the whole text to: `readApprovalText` lists the approvals again, returns that text with its digest, keeps nothing of the text, and records per approval and per viewer the digest it gave (at most `MAX_APPROVAL_READERS`, 8, viewers per approval, only while the approval is pending). An allow is accepted only from a viewer with that record, naming that digest (`shownDigest`); the digest alone, which every snapshot carries, proves nothing. A viewer whose channel cannot carry the whole text (the web host's result cap) is not given it, so nothing is recorded and that approval stays deny-only there. The check is made again after waiting for access, against the approval as it then is. The digest is over the whole text as the gateway sent it, so an approval changed under the same id is not allowed as the one shown. Deny is always accepted.
- **A step's waiting status.** An approval naming a tool call is that step's own `waiting` status while the step runs, and links to it by `stepId`; one that names no step is its own card. The run's state follows only the run's lifecycle events: exec can return an `approval-pending` result and wait on its own, so a pending approval does not mean the run is blocked. An approval is never settled because its run ended. It stays pending, with `runEnded`, until the gateway resolves it, it expires, or a reload no longer lists it; withdrawing it means denying it.
- **Resolving.** Allow once, deny, or a standing allow (`allow-always`) through `exec.approval.resolve`, `plugin.approval.resolve` or `approval.resolve` for the generic kind. The legacy methods answer `{ok: true}` once the decision is applied, and the card settles as asked. `approval.resolve` answers `{applied, approval}` with the approval as it actually ended, which is what the card shows, even when another reviewer settled it first (`applied: false`, with a note). A standing allow may carry `grantExpiresInDays` (1 to 3650) for exec and the generic kind; plugin approvals take no duration. No protocol field says which bots a standing allow covers, so the engine offers none.
- **Expiry.** A pending approval expires at its `expiresAt`, and the lists are re-read to confirm. The expiry is an inference; the gateway's outcome, if it differs, replaces it.

## Message cards

- `selectMessageCards` (`packages/core/src/cards.ts`) is a view over steps; it changes nothing in the store. It draws a Messaged card for each `sessions_send` call and an MCP card for each external MCP call. Two events belong to one card only when they share the call's id.
- **Delivery is not inferred from a start.** A tool start, or a `toolCall` in history, is the model's request; the gateway may never execute it. A started call is `started`, delivery not established. A Messaged card reaches Sent and later states only from the result's own `details.status`; an MCP card is `returned` once its result arrives, which does not mean the external work is done. A call that closed without a result is `unknown`. A returned error stays `failed` with its text, before, during or after Stop, on Messaged and MCP cards alike; only a result that itself says it was aborted (`details.aborted`, or for MCP `details.status` `aborted` or `cancelled`) makes the card `unknown`, still with its error. `deliveryUncertain` says whether the recipient or external server got it. A Messaged result with a delivery status (`sentBeforeError` included) keeps the delivery it establishes. "Work may continue" is shown only after an MCP call returned.
- **Times.** `requestedAt` is the tool's start, the model's request, which may precede approval or execution by minutes. `resultAt` is when this connection saw the result. The gateway reports no delivery time, so `sentAt` is always null.
- **Recipient.** From the result's `sessionKey`, else the arguments' `sessionKey`, `agentId` or `label`. Its run state comes from the recipient run's events when this connection receives them: the client follows a few recent runs of sessions no viewer has open, and copies the ones a task's results name into `linkedRuns`, with `outcomeKnown`. A recipient run that ended without saying how is `recipient-outcome-unknown`, never "no reply yet" or "recipient stopped".
- **Late replies are not attached.** An inter-session reply names its source session and tool, not the send it answers, and several sends to one bot can be outstanding. Such rows are returned as incoming messages.
- **MCP names are opaque.** The gateway sanitizes, shortens and de-duplicates MCP tool names, so they are never parsed. A call is recognized from its result's `details.mcpServer` and `details.mcpTool`, or before a result from a caller-supplied map of exact tool names. A configurable list of server names marks the coding agent; no product name is built in.
- States move only forward, with the precedence of §6.1 and §6.2, when the caller passes the previous cards, except after an explicit correction of the call's result (`correction` differs), which starts again from the facts.

## Attachments

- Files do not travel in bridge commands: the web bridge's frames are capped at 64 KB. A renderer adds a file first and `sendMessage` names it by id. The web host takes it on `POST /attachments?name=…&type=…`. The path is treated as internet-facing: it needs the access cookie (the access link's `?token=` only establishes the cookie and is not accepted here) and an `Origin` that is exactly this plain-HTTP listener's own scheme, host and port; a browser always sends one with a POST, so one without it is refused, and the host terminates no TLS, so an `https` origin is refused too. It needs a declared length, refuses one over the ceiling for that type before reading the body, closes the connection on any refusal, and answers 408 to a body that has not arrived within `UPLOAD_DEADLINE_MS` (60 s), giving its room back. The Electron host takes the file's bytes over IPC, never a path, so a renderer cannot make the main process read a file of its choosing.
- Both put files in one host-side `AttachmentStore`: 6 MiB per image and 20 MiB per other file, checked before the bytes are encoded or kept, at most 20 files per message, at most 64 files and 32 MiB waiting in total, kept 15 minutes. An upload reserves its room before its body is read, so uploads arriving together cannot exceed those bounds. The whole `chat.send` frame is checked against `hello-ok.policy.maxPayload` (25 MiB) before it reaches the socket. Base64 grows a file by a third, so a single file near 20 MiB already exceeds the frame. A refused message leaves its files available, so the user can send fewer. Once a message takes its files they leave the store (`take`, with `restore` if the message is refused) and are kept by the client, counted against `MAX_RETAINED_ATTACHMENT_BYTES` (32 MiB across every outbox), until history confirms the message or the user deletes it; a cancelled message's files are dropped at once. A file is counted in one place at a time. A message past any of these is refused before anything is kept.
- **Stop.** `chat.abort {sessionKey, runId}`. The run is `stopping` until the gateway reports how it ended; a normal end first gives `completed` with `finishedBeforeStop`. Cards pending at Stop are held aside, closed when the stop takes. If the stop request itself fails, the run goes back to how it was, `waiting` with those cards restored if it had any, with `stopError`: the one transition outside the table. Questions of a run that ended are closed, and a late or repeated question event for an ended run is ignored.
- **Stop before the gateway has taken the send.** OpenClaw 2026.10.6 cancels only a run it has registered. Its `chat.abort` with a `runId` also cancels a send it has accepted but not yet registered (`writePreRegisteredChatAbort`), and without one it aborts the session's registered runs; an abort that arrives before the send is accepted at all aborts nothing, `{aborted: false, runIds: []}`, with or without the run id, and the turn then runs in full while the client shows Stopping (probed on a named instance: send and abort in the same tick, three of three). The gateway's run id for a send is its idempotency key (`clientRunId = p.idempotencyKey` in its chat-send handler), which is the message id. So Stop on a run the gateway has not named waits for the send's answer, then aborts that run by id. An abort that lands while the gateway admits the send makes its answer `{status: "timeout", summary: "aborted", stopReason, endedAt}` with no event of the run ever after, or refuses the send ("Chat admission ended or was cancelled; submit a new turn."); the first settles the run as `stopped`, the second fails the send with retry and delete.
- **A queued turn has two ids.** A send that waits in the gateway's queue runs under a run id of the gateway's own: `run_status` comes under that id, the turn's lifecycle, text and end under the send's id, and history stores its rows under the gateway's id; `sessions.changed` names both (`runId`, `clientRunId`). The gateway's id is kept as a queue alias of the send's run (`queueAliases`, at most `MAX_QUEUE_ALIAS_COUNT`, 16, the newest), for as long as either id can arrive: a late frame under it updates that run, and history rows under it are read as that run's. A reconnect that missed the pairing frame recovers it from history, where a user row keyed `<send id>:user` is followed by rows under the gateway's id. A `sessions.changed` `end` or `error` naming a run still shown active reads history again.
- **A stopped turn can come back.** Every stop, `chat.abort` or a typed `/stop`, marks the session `abortedLastRun: true` (status `killed`); a `/stop` with no run active does not. The gateway's main-session restart recovery resumes a session that is so marked and still holds a recovery claim (a run recorded for recovery and not yet recorded terminal, a delivery claim, or a pending final delivery): the next turn admitted there keeps the mark instead of clearing it, and the recovery dispatches a turn of its own whose user row is the gateway's prompt "[System] Your previous turn was interrupted by a gateway restart …" with `provenance: {kind: "internal_system", sourceTool: "main_session_restart_recovery"}`. A run's end normally records it terminal and clears the claim; on a lightly loaded instance it always did in these probes, so the resurrection two builders saw under heavy load was not reproduced, and which path left the claim is not established. The client cannot avoid it: any Stop sets the mark, and any later message is a turn. What it does is show it as what it is: a user row the gateway wrote itself is a system line ("The gateway resumed an earlier turn by itself", or "started a turn by itself"), never the person's message, and never settles an outgoing message; and the run is settled when the gateway reports its end, under whichever id.
- **Turn limit.** At the "Turn time limit" the client stops a run it started, the way Stop does: the run is "Stopping…" until the gateway confirms, the gateway's refusal puts it back as running with "Couldn't stop", an unanswered abort is sent again after a reconnect, and the limit is reached once per run. Nothing is marked failed and nothing queued is released on the limit alone; once the gateway confirms, the run is stopped (`Run.turnLimit`) and its card says that Clawtrate stopped it at the limit, worded apart from a turn the gateway ended at a time limit of its own (`timeoutPhase`). The limit is 50 minutes, Clawtrate's choice, until the person sets another in Settings, Conversation (`setTurnLimit`, whole minutes from 1 to 1,440, kept in the host's storage; a host option `turnLimitMs` overrides it). Only a run this host started has a timer: a run started by another device, by the gateway itself, or before this host started (one it only observes or reads from history) has no turn limit here. OpenClaw's `chat.send {timeoutMs}` is an execution budget that pauses while an approval waits, not a wall-clock limit, so the limit is the client's own deadline and `chat.abort` (F-100).
- **Size ceilings.** Before anything reaches the socket, a send is refused with `SendTooLargeError` when an image exceeds the smaller of 6 MiB and `hello-ok.policy.attachments.maxImageBytes`, a file the smaller of 20 MiB and `policy.attachments.maxBytes`, or the request frame `hello-ok.policy.maxPayload`; the gateway would otherwise close the socket with 1009 and no answer. OpenClaw 2026.10.6 advertises `maxBytes` as the smaller of its 20 MiB media setting and the decoded size whose base64 fits its 25 MiB frame less 256 KiB of envelope, 19,464,192 bytes (18.6 MB), so that is a file's real ceiling there (`chat-attachment-policy`). The connection state carries the three ceilings and the file count (`ConnectionState.sendLimits`), so the composer refuses a file, or a message too large once its files are encoded, as each is added, with the ceiling it exceeds (F-074, F-285). The bridge does not carry attachments: its web frame limit is 64 KB.
- **Typed "Stop now".** OpenClaw 2026.10.6 treats its own abort words ("stop", "please stop", `/stop` and others, `abort-trigger-text`) as a command, but not "Stop now", the words Grok Bot's guide gives. Typed during a run, "Stop now" (and "please stop now", "stop now please") is Stop: `chat.abort`, not a message (`stop-words.ts`, F-097).
- **Message actions.** Hovering, focusing or touching and holding a message shows react, reply and more beside it (one tab stop, Left and Right move). Reactions are `session.reactions.set` (`operator.write`); the gateway's author is the connection's signed-in profile, so on a connection with none it refuses ("identified reaction author required"), and the interface says so. A reaction also queues a system event for the bot's next turn ("Control UI reaction added: …"), which is the gateway's doing. A reply is `chat.send` `replyToId`; the gateway keeps it as a reference with a preview and no thread of its own, so the thread view is assembled here from each row's own reference: the message, your rows that name it (`__openclaw.replyToId`), and each bot bubble whose row names it (`openclawDelivery.replyToId`). A bot's turn is several rows, and the gateway reads a reply tag only on a row with no tool call, so only that row's bubble joins the thread, never the rest of the turn. "Reply sent" is said only once history holds the row the gateway stored under the reply's key (F-066, F-067, F-283).
- **The "/" and "@" menus.** "/" at the start of a message lists the bot's skills a person may run (`skills.status` `userInvocable` and `eligible`), tagged Skill, and the gateway's text commands that are not those skills (`chat.metadata` `commands`), tagged Command; no app's action is listed, since the gateway lists those separately (`mcp.app.discover`); one chip per message, since the gateway runs one command per message; the chosen one is a chip, sent first as its own text alias. "@" lists the bots and the gateway's routines (`cron.list`, not its heartbeat) and puts the name where it was typed: the gateway's structured `mentions` are human profiles only. Groups and apps are not listed: groups are F-077, and the capability map names no listing of apps to mention (F-070, F-071).
- **What Stop also ends.** When a run this client stopped (Stop, a typed `/stop`, the stop after three timeouts) ends as stopped, the client aborts the runs of other bots the run's messages started. It takes them from the run's own record, its `sessions_send` results, not from the abort's answer, so a lost answer, a reconnect that settles the run from history, and a `/stop`, whose answer comes before the run's end, reach them too. Each recipient still identified by a retained run ID and session key is asked; one whose result the task no longer keeps is not, and the note then says other bots' work may continue. The note names at most eight of each kind and counts the rest. A recipient whose abort the gateway refuses, or which gets no answer after one retry on the next connection, is named as that, never as stopped. No process is stopped with a run: OpenClaw 2026.10.6's `sessions.processes.list` rows (`readBackgroundProcesses` in `bash-process-observation`) carry a session scope and a start time but no run, so nothing the gateway returns ties a process to the stopped run, and choosing by session and time could stop the next run's process. F-297 waits for a process row that names its run (F-296, F-297, F-298).
- **Three timeouts.** After three of a run's tool calls in a row time out, the client stops it: the machine may not be responding (F-101).
- **Request id.** A failed turn's "Copy request ID" copies the id this client gave the `chat.send` frame that started the run (the protocol client's `onSent`), which Raw shows beside the error event as received (F-301).
- **Resync.** The protocol client closes the socket on a frame sequence gap; the reconnect reloads open tasks and sets `caughtUp: {reason: "gap"}`. Any other reconnect sets `reason: "reconnect"`, except the one that follows an approved step-up. A jump in a run's own `agent` seq is not loss: the gateway numbers frames before it coalesces assistant and thinking frames. A repeated or older frame for a run is dropped.
- **Reloads.** Reads of one task run one at a time, a further request runs once after, and a response is applied only to the same connection and the same opening of the task, so a slow read never overwrites newer state. History is rebuilt aside and merged by run id and step id; only the steps the merge takes from history bring their raw payloads, so a step and its raw lookup always agree, and the same history read twice gives the same state. The in-flight run is rebuilt from its rows plus its `inFlightRun` snapshot: the snapshot's progress events (tool, item and status events; it carries no thinking) are replayed into the run by step id, so a step the rows already finished is not repeated and the current step shows even when earlier iterations were persisted. The same snapshot applied twice changes nothing. A run that was active before the read and that the gateway no longer has in flight, with no row, has ended without saying how: it settles with `outcomeKnown: false`.
- **Retention is bounded by construction.** Every value the host keeps in its state has a named maximum and every collection a named count, declared once in `packages/core/src/state-bounds.ts` against the state's own types: a field added to a retained type without a bound does not compile. The unit throughout is the JSON character, the length in UTF-16 code units of a value's `JSON.stringify` form, quotes and escapes included, so a `"` counts two. The store applies the bounds to every write (`enforceState`): a string past its cap is cut and its path recorded in the nearest `cut` list; an id past its cap is replaced by a digest of itself; a value kept as received (a raw payload, an avatar) is kept whole or not at all; a list keeps its newest items; a value of the wrong shape is dropped. The engine applies first the counts that need judgment, oldest finished first, and says what it dropped (`omittedSteps`, `runsOmitted`, `questionsOmitted`, `unroutedApprovalsOmitted`). A question past `MAX_PENDING_QUESTIONS_PER_TASK` is not shown, and stays pending on the gateway. Nothing cut is kept anywhere else: the whole value is read again when asked for and returned without being kept (`readStepRaw`, within the promise above, `readApprovalText`, `readHistoryItem`), and what the gateway sent that failed a run is kept beside the step payloads, never in the state, and read with `readRunRaw` when its Raw is opened, and an answer names an option by its original place, never by the text shown: it is sent as that option's `value`, else its label, read whole from `question.list` at that place, and refused if the option there no longer begins with what was shown. A question keeps its first `MAX_QUESTION_OPTIONS` options, each with its place and the gateway's `value`; the rest are counted in `optionsOmitted`. Outside the state, every map, set and array the client, a viewer's bridge session and the waiting files keep is named in one registry (`packages/core/src/owners.ts`) with its count and the most each entry holds, including collections inside the values of maps, sets and arrays (`recipients.*.runs`). Two tests hold it to that. `owners.test.ts` reflects over the live objects, their own properties and the values of every collection, and fails for a collection the registry does not name, one past its count, or an object of a class the walk does not know. `owner-sources.test.ts` scans the source of the engine and its hosts, and fails for any `Map`, `Set`, `WeakMap`, `WeakSet`, array, or collection made by a factory call (`Array.from`, `Array.of`, `Object.fromEntries`) kept in a class field, at module level, or in a variable a later-running function captures, directly or inside an object literal written as that value (reported under its path, `box.kept`), that is neither a field the registry names nor on its allowlist, where each entry says in one line why it is bounded (static, weak, capped, or one read). What neither guard sees: a collection put into a plain object after the object was made (`box.list = []` on an object other than `this`), and one returned by any other function call, since the walk cannot reach objects held only at module level or in a closure and the scan reads only the value written where the variable or field is made. Such a container needs a review, not a test. The store's listeners are capped (`MAX_STORE_LISTENERS`, 32). Each of those keeps only the bounded representation, from the moment it is admitted: an unrouted approval and a task creation are the very objects the state holds, nothing whole beside them; ids used as map keys pass the id cap (`capId`), and a task key, bot id, label or file name past its cap is refused, never cut; the task list is cut to the rows and fields kept as each page arrives; only `hello-ok.policy`'s three ceilings (frame, image and file) are kept, and a foreign session's step payloads not at all. ## The reading of an action

- **Where it lives.** The reading of a tool call as an action (its kind, words, outcome and fold key, `docs/design/conversation.md` sections 7 and 8) and the grouping of a run's record into cards and folds are in the engine package (`packages/core/src/actions.ts`, `action-feed.ts`), not in the interface, because the iOS app uses the same reading. Section 22 of the design puts the words in `packages/ui` and has the core return only data; here the core composes the sentence, and every word comes from one catalogue in the core (`action-words.ts`), so the iOS app shares the sentences and a translation still replaces one module.
- **What a step keeps for it.** The reading needs fields of a call's arguments and result `details` that the inline raw payload does not carry once it passes 2,048 characters (a write's content makes its arguments large; a read's details hold the whole file). A step keeps projections of both: only the keys the reading reads, values cut until the whole fits `MAX_ACTION_FACTS_CHARS`; a diff is kept as its counts and its first lines. The reading reads a projection exactly as the whole payload.
- **Nothing is Done by default.** One function decides an outcome (`outcomeOf`): the event's status first; then an outcome the kind's adapter names more exactly than the general reading (Started, Partial, No change, Unavailable, a phone's refusal); then any signal of the general reading at either level of the payload (`details` or `details.result`), which outranks the kind's Done and its fallback; then a value the adapter shows as received; then a value the general reading shows as received. Done needs the kind's positive evidence (8.1, "Done needs"): content, a diff, a non-empty list of made media, a progress card's revision or the gateway's answer that it cleared it, and for "a result without error" a result that carries text or details beyond a tool server's identity. A general card is Done only on a value that says the work was done (`ok: true`, a success status). Anything else is Call made.
- **One reading, live and from history.** History keeps a result's text whole (up to its cut) but of its `details` only what the gateway's chat display projection keeps: `exitCode`, `durationMs`, `cwd`, `sessionKey`, `ok`, `changed`, `created`, a diff. So a call is read the same way on both paths (`withPayload`): the result's own JSON, whole or after a line of words (`jsonResult`; the progress card's and the question's words then their JSON), under whatever details were kept; never for kinds whose text is what the tool read, ran or wrote. A history block keeps the few kept facts itself (`ToolResult.facts`, `MAX_TOOL_FACTS_CHARS`), so a call whose step retention dropped reads as its step did. Where a tool answers in a sentence (`textResult`), the kind's adapter reads the installed tool's own sentence too: `read`'s no-contents diagnostics (Unavailable) and its optional-file absence (Not found), the PDF and image refusals, exec's pending approval and timeout, media's "Generated N …" and background admission, the voice clip's "(spoken)". `packages/core/test/live-history.test.ts` reads every kind's outcomes live, from history with its step, and from history's block alone, and requires one outcome and the same words. The gateway's own sentences for a call it blocked before launch read as Not run on both paths. A plugin's block keeps only the plugin's reason text in history, and nothing there says it was blocked: from history alone, such a call reads by its text.
- **Done is earned, kind by kind.** Each kind's Done, and each outcome short of it, is established only by the evidence in one table (`DONE_EVIDENCE` in `packages/core/src/actions.ts`, the same table in `packages/core/README.md`, "What establishes Done"; a test keeps them equal). Text is never evidence of content: the installed tools' own sentences for nothing returned (an empty file, no readable text, a binary document, an image omitted for the model), for a read cut at its own limit, or for a page asked for, are read as what they say. A result whose text is cut, by the gateway when it stored it (`__openclaw.truncated`) or by this app's bound, is read only for what its readable part establishes (the complete members of a cut JSON object) and its kept details: never Done on that text, and Call made, "Stored result cut", where nothing more is established. A count on a card is the gateway's, or none. A send the gateway reports as sent is Sent whatever then happened to its reply.
- **A fold's plural.** The done plural counts the Done members only ("Read 1 file · 1 failed", "Searched memory 1 time · 1 partial"); a partial member is counted as partial, never as done; with no Done member, the neutral plural. Screen changes fold only with the same change; a tool-server call folds by the server and tool it turned out to be, when the name map knew it at its start.
- **What retention drops is said, where it was, and only if it is missing.** Dropping a run's steps (`withoutSteps`) counts the tool steps on the run (`Run.omittedTools`) and on the next tool step kept (`Step.omittedBefore`), or at the run's end (`Run.omittedToolsAtEnd`). What the transcript says of them comes from one function, `retentionAccount(run, drawn)`, run after the live record and history are combined, over every call the transcript draws for the run in order: a call the engine dropped that history's rows draw is not missing. A gap line ("272 actions not kept here") is drawn only where calls are missing from what is drawn, and the run line counts the actions the gateway reported and, when some are missing, how many are shown ("400 actions · 128 shown"). Text written beside a call is anchored by that call's id (`Preamble.beforeCall`); when the call is dropped, by the next call kept.
- **History draws from the engine's record.** A history item keeps up to `MAX_BLOCKS_PER_ITEM` (now 300, the page's whole pool, so the documented totals do not change for it) blocks; calls of its run that no row holds are drawn from the engine's steps in the run's order. A finished run whose history is not shown yet is drawn from the engine's record too, actions and cards, not its cards alone.
- **Only reported durations.** A step built from history rows carries `rowTimes` (its times are when the rows were written), and a run whose end came from its rows `endFromRows`: no duration is read from either, and the run line reads only the lifecycle's start (`reportedStartAt`), never this app's send time.
- **The tool inventory and the workspace root.** With the name map, the engine keeps the built-in and plugin tools `tools.effective` lists (`Transcript.builtinTools`, at most `MAX_BUILTIN_TOOLS`): a general card of one of these folds by its name. It reads the bot's workspace root from `agents.files.list` (`workspace`, `operator.read`) once a task's history loads (`Transcript.workspaceRoot`). Without it an absolute path is never memory; a relative `MEMORY.md` or `memory/…` is.

## Core layout

- Core builds on `@openclaw/gateway-client/browser` (`GatewayProtocolClient` and `GatewayBrowserDeviceAuthLifecycle`), not on the Node `GatewayClient`. The browser entry takes an injected socket and uses no Node built-ins, so it can run in Electron, Node and Expo.
- The host passes in a WebSocket factory, a key/value store, a device signer and its client identity (`packages/core/src/host.ts`). The only globals core uses are `setTimeout`, `clearTimeout` and `URL`, declared in `src/globals.d.ts`.
- The Node implementations live behind a separate entry point, `@clawtrate/core/node`, instead of a separate package. They are a JSON file store, an Ed25519 key in a 0600 PEM file, and the built-in WebSocket. Electron's main process and the web host share them. ESLint stops shared core code from importing `node:*` or using Node and DOM globals.
- Hosts and the renderer talk through one bridge contract (`packages/core/src/bridge.ts`). The host pushes whole state snapshots, coalesced to one per 16 ms. The renderer sends a few validated commands; `invoke` also returns a command's answer (a sent message's id, a created task's key, a step's raw payload). Commands that act on a task are accepted only for tasks that viewer has open. Selection lives in the renderer.

## Apps

- `apps/desktop` holds the Electron main process, the preload script, the renderer entry and the web host. The interface itself is in `packages/ui`, so the desktop renderer and the browser load the same components.
- Electron runs with `contextIsolation` and `sandbox` on, and Node integration off; `app.enableSandbox()` extends the sandbox to any renderer. The preload script is CommonJS because sandboxed preloads must be, and it exposes three functions. The window never navigates, and links open in the system browser. The main process's further rules for a shipped app are under [Packaging](#packaging).
- `CLAWTRATE_SCREENSHOT=<path>` makes Electron render offscreen, save a PNG and quit. It is there so the app can be checked on a machine nobody is looking at.

## Packaging

- **Tool: electron-builder 26.18.1.** One configuration (`apps/desktop/packaging/config.ts`) produces the macOS `.app`, `.dmg` and `.zip` for arm64 and x64 and the Windows NSIS installer, and takes electron-vite's existing output as it is. Signing and notarization are driven by its standard environment variables, which is what lets the owner sign later without a code change. Electron Forge was the alternative: it wants to own the build (its Vite plugin would replace electron-vite), needs a maker package per format, and defaults to Squirrel on Windows. The cost of electron-builder is a large dependency tree, and at package time it downloads the Electron release for each architecture and its DMG and 7-Zip helpers from GitHub.
- **Commands.** `pnpm package:mac` and `pnpm package:win` run `electron-vite build` and then `apps/desktop/packaging/build.ts`, which refuses icons older than the logo (the same hash as `assets/brand/generated.json`) and refuses to build the macOS app anywhere but macOS or the Windows installer anywhere but Windows. Output goes to `apps/desktop/dist` (git-ignored); `publish` is off and no update feed is written. The Windows installer was first built on Windows 11 x64 (10.0.26200) with Node 26.13.1 and pnpm 11.9.0; it needed no change to the build script. Its unpacked app passed `pnpm check:packaged` there. The installer is run in CI (see the Windows job below), on a runner that is discarded afterwards, since running it installs into the user's profile.
- **Author "Clawtrate contributors".** `apps/desktop/package.json` names it, and electron-builder takes the Windows executable's company name and both platforms' copyright line from it. Without it the executable kept Electron's own company name, "GitHub, Inc.".
- **Bundle identifier `dev.clawtrate.desktop`.** It is a placeholder the owner may change before the app is ever signed. After the first signed release it should not change: macOS ties the app's preferences and permissions to it.
- **What ships.** The app archive holds only `package.json`, electron-vite's `out/main`, `out/preload` and `out/renderer`, and `resources/icon.png`, the window icon the main process loads on Windows and Linux. Everything the main process imports, including `@clawtrate/core`, is bundled, so no `node_modules` are shipped. The web preview's and the fixture mode's builds are never included; a unit test checks the file list. On Windows the archive holds the same files; `win-unpacked` has `Clawtrate.exe`, Electron's DLLs and paks, `resources/app.asar` and `resources/elevate.exe`, the helper NSIS uses when an install needs elevation.
- **Icons** are `apps/desktop/resources/icon.icns` and `icon.ico`, both generated from the logo by `pnpm brand:icons`. There is no other artwork; the DMG uses electron-builder's default window.
- **Fuses.** The packaged binary has `RunAsNode`, `NODE_OPTIONS` and the `--inspect` arguments turned off. It also loads only `app.asar` and checks it against the hash electron-builder writes into `Info.plist` on macOS and into the executable's resources on Windows. On Windows both were shown to work, each against a copy with that fuse turned back off: an archive repacked with one comment added to the main process stops the app before any window (`FATAL ... Integrity check failed for asar archive entry '<header>'`), while the copy without the integrity fuse opens it; with `app.asar` removed and a `resources/app` folder in its place, the app does not load the folder and exits, while the copy without `OnlyLoadAppFromAsar` runs it. Electron 45 looks for `app.asar` before `app`, so a folder beside an intact archive is never loaded either way. The launch check reads the fuse wire from the packaged binary (`apps/desktop/packaging/fuse-check.ts`, with `@electron/fuses`) and fails unless every fuse packaging sets has that state; an app whose fuses were never flipped starts just the same, so its starting is no evidence. Because `--inspect` is off, the launch check drives the app over the DevTools protocol (`--remote-debugging-port`) rather than with Playwright's Electron launcher.
- **Unsigned by default.** With neither `CSC_LINK` nor `CSC_NAME` set, electron-builder gets `identity: null`, so it never searches the keychain, and the `afterPack` hook signs the app ad hoc with `codesign --sign -` after the fuses are flipped. Ad hoc signing uses no certificate and no keychain; Apple silicon refuses to run code without a valid signature. With either variable set, electron-builder signs with the hardened runtime and notarizes when a complete set of `APPLE_*` variables is present ([Updates and release signing](#updates-and-release-signing) has the rules and the line the build prints). [Packaging](development/packaging.md) lists the variables and how to open an unsigned build.
- **Main process rules for a shipped app** (`apps/desktop/src/main/index.ts`):
  - one instance per data folder: a second launch focuses the window;
  - a packaged app never loads `ELECTRON_RENDERER_URL`, only its own `index.html`;
  - every web contents refuses navigation, new windows and `<webview>`, and links open in the browser only for `http` and `https`;
  - requests outside the renderer's own folder are cancelled, except `https` images: bots' pictures, which the page's policy allows as `img-src https:`. [Addresses a gateway hands the client](#addresses-a-gateway-hands-the-client) narrows this to the pictures the person allowed (#71);
  - every address a gateway hands the client, a picture, a link, a file, a page or a sign-in page, follows [that rule](#addresses-a-gateway-hands-the-client), in both apps;
  - permission requests are denied except clipboard writes for the copy buttons;
  - the data folder for the device key and tokens (`<userData>/gateway`, or for a person's packaged app `CLAWTRATE_DATA_DIR`) is created `0700` and kept so, and the core writes its files `0600`;
  - on Windows a packaged app sets its AppUserModelID to the bundle id, the id electron-builder's installer gives the Start menu and desktop shortcuts it makes (`apps/desktop/src/main/identity.ts`). Without it, Windows named the window's taskbar button after the executable's path until it linked the executable to the shortcut, and after the shortcut's id from then on: the Windows job saw the same installed app under `Appid: <install folder>\Clawtrate.exe` at its first launch and under `Appid: dev.clawtrate.desktop` a minute later, so a button pinned from one launch was not the next one's. A development build keeps Electron's own.
    The content security policy is the `<meta>` in `apps/desktop/src/renderer/index.html`, shared with the web preview.
- **The launch check** (`pnpm check:packaged`, `playwright.packaged.config.ts`, `e2e-packaged/`) starts the packaged app for the machine's architecture (`apps/desktop/dist/mac-arm64/Clawtrate.app`, or `apps/desktop/dist/mac/Clawtrate.app` on Intel) with `--user-data-dir` in a temporary folder and its environment stripped of `CLAWTRATE_*`, `ELECTRON_*`, `OPENCLAW_*` and `NODE_OPTIONS`. It starts an unseeded sentinel instance `e2e-<run>-other`, which it never touches, then a seeded instance `e2e-<run>`. It records both instances, the app and the folder in the same run records `pnpm e2e` uses, so either cleans up after a killed run. Two things it must leave alone are hard assertions: the processes listening on ports 19001, 19091, 5310 and 5311 (by PID, start time and address, from `lsof`), and the sentinel's gateway PID and ports. Other builders' instances start and stop on a shared machine, and a before-and-after snapshot cannot show this run caused a change, so a change to them is printed as a note and does not fail the run. `pnpm e2e` keeps its own, stricter rule. Its isolation comes from `--user-data-dir`, which moves all of Chromium's storage and the gateway folder; `CLAWTRATE_DATA_DIR` alone would move only the gateway folder. It fingerprints the real data folders (`~/Library/Application Support/Clawtrate` and `~/Library/Caches/Clawtrate`) before and after, and fails if they changed. macOS also writes the bundle id's preferences, `~/Library/Preferences/dev.clawtrate.desktop.plist`, outside any data folder, at every launch. The check saves that file's bytes, mode and times first and afterwards puts them back exactly, or removes the file if the run created it, telling the preferences daemon first (`defaults import` or `defaults delete`) because it caches the file. It fails if the file cannot be restored. It checks that every renderer the app started runs in the operating system's sandbox, from outside the renderer: its launch arguments as `ps` reports them carry `--seatbelt-client` and no `--no-sandbox`, and the kernel's `sandbox_check()` (called through Apple's Python, which the command line tools install) says the process is confined. A page without Node globals is not that evidence, since context isolation alone gives it. With `app.enableSandbox()` removed and `sandbox: false`, the renderer starts with `--no-sandbox` and `sandbox_check()` returns 0, and the check fails. It quits the app with SIGTERM, as the system does at logout, and fails if the app or a helper is still running 15 seconds later. That is how it found a real bug: a state snapshot sent to a window already destroyed during quit threw in the main process, and Electron's error dialog then blocked the quit. On both systems a second launch with the same data folder must exit by itself with status 0 and leave the first app with its one window.
- **The launch check on Windows** runs the same tests against `apps/desktop/dist/win-unpacked/Clawtrate.exe`, or against the installed app in the folder `CLAWTRATE_PACKAGED_APP` names, and skips, by name, the four that need a development gateway (see the Windows job below for why none runs there). It therefore starts no instances and writes no run record, and has no listeners to protect. What differs is how it asks Windows: process command lines, parents and window titles come from PowerShell (`Get-CimInstance Win32_Process`, `Get-Process`), and the sandbox evidence is each renderer's token, read from outside: a sandboxed renderer runs at untrusted integrity (0) and the main process at the user's own level. Unlike on macOS, this assertion has never been seen to fail: the packaged Windows app, started with the sandbox turned off (`--no-sandbox` or `ELECTRON_DISABLE_SANDBOX=1`), crashes at once with an access violation (0xC0000005) before any renderer exists, so no unsandboxed renderer could be produced to read. The real data folders it fingerprints are `%APPDATA%\Clawtrate` and `%LOCALAPPDATA%\Clawtrate`; Windows keeps no preferences file outside the data folder. The app is asked to close with `taskkill /PID` without `/F`, a close message to its windows as at sign-out, and the run fails if it or a helper is still running 15 seconds later; whatever is left is then ended by PID. Windows reports no title, and refuses that close message, until the window is shown, which the main process does on `ready-to-show`, so the title is polled. The unread badge is checked from outside too, on Windows only: after the page calls `setBadge(3)`, the app's taskbar button, found through UI Automation by its application id (the bundle id, which the packaged app sets), has the overlay's description "3 unread" as its help text, and after `setBadge(0)` an empty one. That reads the overlay's description, which the main process sets and clears together with the icon, not the icon's pixels.

- **The Windows job in CI** (`windows` in `.github/workflows/ci.yml`, on `windows-2025`) builds the installer with `pnpm package:win`, unsigned, and keeps it as a workflow artifact for three days, for inspection; it is never a release. It runs the installer silently for the current user into a folder of its own whose name has a space (`/S /currentuser /D=<folder>`), fails if it exits with anything but 0, and checks what it made: `Clawtrate.exe`, `resources\app.asar` and the uninstaller in that folder; one uninstall entry under `HKCU`, and its own key, `HKCU\Software\<GUID>`, naming the folder (electron-builder derives the GUID from the app id and names both keys by it); the copy of itself it keeps for an updater, `%LOCALAPPDATA%\@clawtratedesktop-updater\installer.exe` (found by its bytes, not its name); and the Start menu and desktop shortcuts. The silent install must not start the app. The Start menu shortcut is then checked as part of the app's contract: it must open the installed `Clawtrate.exe` and carry the AppUserModelID the app gives itself at startup (`APP_ID`, read from `apps/desktop/src/main/identity.ts`), read from the shortcut through the shell's `System.AppUserModel.ID` property, so the taskbar button of a window opened from the Start menu is the shortcut's. The packaged checks drive the app over the DevTools protocol without Playwright's test fixtures, so no trace is recorded. It runs on the same triggers as the other jobs and caches the pnpm store as they do; it takes about four minutes, two and a half of them building the installer.

No development gateway runs on Windows. Porting the controller to Windows is its own piece of work.

### Addresses a gateway hands the client

The gateway is the person's own, but what it relays is written by bots and by whatever the bots read. An address the client fetches by itself tells a third party that this person's app is open, from where and when, and an address on the person's own network is reached from the person's own machine. So the rule is about what the client does before the person has chosen anything, and it makes the client do as little as it can by itself. It is the same rule in the desktop app, the web preview and the iPhone app, decided in the shared core where it can be; where a platform differs, the table says so and why. The evidence is [Addresses a gateway hands the client](research/remote-content.md) (sections cited as §); building it is #71.

Three answers: **fetched without asking**, **only when the person chooses** (and what they see first), and **never**. "The host" is the process that holds the connection: Electron's main process, the web preview host, or the iPhone app's own JavaScript.

Beneath the table:

- **Schemes.** Leaving the app: `http` and `https` only. Fetching from anywhere but the gateway: `https` only. `data:` only for a picture of the four types above, and for bytes the host itself read. For gateway-supplied addresses, only the two grant paths above may resolve against the gateway origin. Other relative addresses and all other schemes stay plain text. The check sits in the core, so the web preview, which has no main process, applies it too; `openExternally` and `openableUrl` repeat it. (§2: today react-markdown keeps `mailto:`, `irc:`, `xmpp:` and relative links, which the desktop drops silently and the web preview opens.)
- **The person's own network.** A link preview uses only global unicast IP addresses. Apply the IANA special-purpose registries and refuse any entry that is not marked globally reachable. Apply the IPv4 checks to IPv4-mapped IPv6 addresses and refuse the `64:ff9b::/96` NAT64 prefix. Refuse `localhost`, its subdomains, `.local` names and unqualified names before lookup, ignoring one final DNS dot. For any other name, refuse the target if any lookup result fails the same IP check. Connect directly to one checked address and apply these checks to each hop and the preview image (§3.2, §4.1). Opening such an address in the browser is still the person's choice. When the parsed host is a loopback or other literal the preview check refuses, or is `localhost`, a subdomain of `localhost`, a `.local` name or a name without a dot (ignore one final DNS dot), choosing it always shows the confirmation, even where the address is the control's text, and the confirmation says "This address points to this device" for loopback and "This address may be on your own network" otherwise. This warning uses the written host only. Before opening a link, Clawtrate does no DNS lookup. After handoff, the browser or system handler decides how to resolve it and whether to follow redirects. An address the gateway issued as a grant, and a sign-in page, are exempt.
- **`http` against `https`.** A fetch from the gateway follows the connection's scheme. On a `ws:` connection a grant, which carries its ticket in its address, therefore travels with the same protection as the connection itself, which already carries its own credentials and every message. The fetch adds no exposure the connection does not have, so the rule does not refuse it. Whether a `ws:` address beyond loopback is acceptable is decided where the connection is set up, not here. Every other fetch is `https`, and a redirect from `https` to `http` is refused. Opening in the browser accepts both; the full address shows which.
- **Redirects.** A fetch from the gateway follows none. A preview and its picture share a limit of three redirects, all within the initial page's origin and over HTTPS. Every hop repeats the checks here. An allowed picture follows none. On desktop the request filter must refuse redirect hops even when the destination is allowed. The web preview's `<img>` and the iPhone's `Image` cannot refuse a hop, so neither shows a remote picture.
- **Credentials and cookies.** Clawtrate's fetches carry no ambient credentials: no cookie, no HTTP authentication, and none of the client's own (gateway token, device token, the web host's access cookie); a grant carries only itself. Where a client cannot leave its own credentials out and stop redirects, remote pictures are unavailable there: in the web preview, whose access cookie belongs to the host name with `Path=/`, so the viewer's browser sends it with a picture on any port of that host (§3.3, §4.3), and on the iPhone, where neither is established (§3.4). On desktop, remove `Cookie` and `Authorization` from image requests and `Set-Cookie` from image responses. Keep remote pictures off until a check with stored credentials, a response that sets a cookie and an HTTP authentication challenge shows that no cookie or HTTP credentials are sent, no cookie is stored and no authentication prompt or retry occurs. The desktop's pictures carry no `Referer` (§4.2), and the web preview's page sends `Referrer-Policy: no-referrer`. Once a link or a sign-in page is open, the browser or the system's handler decides its credentials and redirects.
- **User names and passwords in an address.** An address with userinfo (`https://name:secret@host/`) is refused on every fetch and open path: it is shown as text, never a link, never fetched and never opened, a sign-in page included.
- **One parsed address.** For each address the core chooses a canonical URL. The policy checks and destination display use that URL, and only its canonical serialization reaches a fetch or the system handoff. The receiving process may repeat its scheme and userinfo checks on that serialization. Address controls that require confirmation expose no direct link before confirmation.
- **Size and type.** What the host fetches is bounded and typed: an item 5 MiB, a thumbnail 2 MiB, a preview's page its first 512 KB, a preview's picture 512 KB and PNG, JPEG, GIF or WebP, within one 8 s deadline for the entire preview, including DNS, redirects and its image. An allowed remote picture is decoded only as an image, by an image element; its size is not bounded: no bound on an image element's download was found in Electron's documentation.
- **A bot's picture.** The client fetches a remote picture only after the person allows it, because the gateway does not fetch one for it: its avatar route answers a remote picture's address as metadata and fetches nothing, and it serves only the Control UI (§1.1). The allowance is the person's, kept in the app on the device, per gateway, bot and exact address, and it is not written to the gateway: an admin connection, or a bot with the `gateway` tool, can change the address at any time.
- **Scopes.** This rule applies at every operator tier. The gateway decides which replies the connection can read. Sign-in uses its own tier, and allowing a picture writes nothing to the gateway.
- **What is the same and what differs.** The classification and every choice are the same in both apps, decided in the core. The web preview has no main process: the viewer's browser opens links itself, it shows no remote picture, and the host's fetches (items and previews) happen on the web host's machine. The iPhone app has no request filter, no page frame and no preview, and shows no remote picture, for the reasons in the table.
- **What the rule does not promise**, because nothing here holds it: a size bound on an allowed picture; that a name resolving to the person's own network is caught before the browser opens it.

## Updates and release signing

Electron's main process owns the update service and the download folder. Starting or quitting the app, reading its status and choosing a track make no update request. Check fetches the selected feed. Download fetches the file named by that check.

- **Download is offered only where this build can install what it downloads.** A transfer the person cannot use costs them bandwidth and leaves a file the app cannot hand them. The page still shows the offer and explains the build or system restriction.
- The validated running version determines the running track. A saved selection applies while its source is configured. Otherwise the host selects the running track if configured, then Stable if configured, then Beta if configured. With no source the selection is null. The screen passes the track it displayed to Check. A stale selection makes no request. A command replies with its outcome and the current snapshot. The screen can order replies and events by their process-local revision.
- Choosing another configured track immediately retires the offer and its file record, cancels the transfer and publishes the pending choice. Further commands are busy while the host drains the transfer, clears the directory and saves the choice. The running host publishes the new selection after the save succeeds. If folder cleanup fails first, the host reports a folder notice and keeps the previous selection. A failed save reports a track-save notice and leaves the previous selection active. A fresh check is needed for another offer.
- The host stores the selected track and the track and UTC time of the last complete feed read. It accepts that read in memory before saving. A bounded notice distinguishes a settings read, track save, last-check save or download-folder failure. It appears alongside the current operation state. The preferences reader caps input at 1 KiB before parsing. An atomic write keeps only the validated fields. Each displayed source is a hostname of at most 253 characters.
- Each check binds its offer to a private directory and a fixed file entry. The service clears old downloads at startup and before checking. It checks the canonical parent path and relies on the account's permissions on the app data folder. On macOS and Linux it checks owner and mode and creates the download directories with owner-only permissions. On Windows it sets a protected access list on the new directories. Native Windows verification is pending. Another account with rights granted by the machine's owner can have access to these folders.
- Progress counts bytes received and hashed. After renaming the file, the host opens the target without following links and checks the regular file's size and SHA-512 again. Verified means this download matched the feed when checked after writing. Main binds the checked file identity and digest to its offer. Another check, a track change or shutdown retires that record. A missing, changed or replaced file discovered on reinspection gives `artifact-changed`. Restart availability reflects the last inspection. Filesystem notifications are asynchronous. The host withdraws Restart when it observes a change. Restart takes the displayed verified offer ID. A new check always makes a new ID, including on the same track. Restart checks the file again, reserves the operation before notifying the screen and accepts only one handoff.

- **Download engine and platform updater.** The engine uses Node (`node:http`, `node:https`, `node:crypto`). Electron's built-in updater behaves differently by platform.
  - Clawtrate packages Windows builds with NSIS. Electron 45.3.2 supports Squirrel.Windows and MSIX updates, and neither mechanism updates this NSIS installation. On macOS, Electron uses Squirrel.Mac. Its feed entry can supply a ZIP URL, a SHA-256 digest and a byte count. When the feed supplies either check, the updater discards a mismatching download before unpacking. [Electron 45.3.2 updater documentation](https://github.com/electron/electron/blob/v45.3.2/docs/api/auto-updater.md#macos)
- **The feed** is one JSON document at one HTTPS address, read whole and at most 64 KiB (`MAX_FEED_BYTES`):

  ```json
  {
    "format": 1,
    "track": "stable",
    "version": "0.2.0",
    "releaseDate": "2026-11-01T00:00:00.000Z",
    "files": {
      "mac-arm64": {
        "url": "https://updates.example/clawtrate/Clawtrate-0.2.0-mac-arm64.zip",
        "size": 21,
        "sha512": "d/PXtFfUwaIXGZVkl0V6/BiLoriUAcWJNit6KD0cRzUHkPhQl0a2vkZZzpFaI/Ptrhun0lKbq/DXp0Yf9W9nlw=="
      }
    }
  }
  ```

  The host reads the feed as JSON. A repeated key takes its last value. The supported file keys are `mac-arm64`, `mac-x64` and `win-x64`. A file is the build's own artifact: the macOS `.zip` and the Windows NSIS installer. `node packaging/feed.ts <address of the folder>` in `apps/desktop` writes `dist/update-feed.json` from the artifacts in `dist`, hashing them; it uploads nothing. The owner publishes the feed and the files on one HTTPS host of their choosing. Stable uses `X.Y.Z`. Beta uses `X.Y.Z-beta.YYYYMMDD.N`. The three numbers compare first. Stable sorts above a beta at the same three numbers. Betas then compare by calendar date (years 1000 to 9999) and numeric run. Both the track in the feed and the version must match the selected track. Equal and older versions yield no offer. `releaseDate` is an ISO time in UTC. Any other field is ignored and never shown. Invalid required fields or invalid artifact entries give `malformed-feed`. An artifact URL that is unreadable, or neither on the feed's origin nor a [release download](#where-a-betas-files-live), gives `address-refused`. The current platform's artifact may be absent.

- **How a build finds it.** The build independently fixes the optional Stable feed in `CLAWTRATE_UPDATE_FEED_URL` and the optional Beta feed in `CLAWTRATE_NIGHTLY_UPDATE_FEED_URL`. Electron Vite substitutes both in the main bundle. With both addresses unset, the packaged host has no update source. The build requires HTTPS without credentials and rejects the parsed hostnames `localhost`, names ending in `.localhost`, `::1`, and names starting with `127.`. It does no DNS or connection-time address filtering. It accepts HTTPS addresses on private networks. A missing feed address or a placeholder host ending in `.example` gives `not-configured`. The production constructor gets its address from the build alone.
- **The build's own release date** comes from `SOURCE_DATE_EPOCH` (seconds) when set at build time, otherwise the time of the build. For a later F-010 implementation, the engine's age helper tests whether a newer version exists and the running build's own date is more than 14 days old. The desktop service exposes no required-update decision. The owner should give the build and `packaging/feed.ts` the same `SOURCE_DATE_EPOCH`.
- **The engine's rules**, each with a unit test that fails without it:
  - the feed and every file are read over `https`. Plain `http` is allowed only to `127.0.0.1` on the port a test names in the `loopbackHttpForTests` option; the production constructor does not pass it, and nothing outside the code can;
  - every file's address has the feed's own origin, or is a download of this repository's own GitHub releases, exactly `https://github.com/sidebandstudio/clawtrate/releases/download/<tag>/<file>` with no query, fragment or credentials (`GITHUB_RELEASE_ASSETS` in `address.ts`);
  - the feed follows no redirect. A file follows one, and only from such a release download, with a 301, 302, 303, 307 or 308, to `https://release-assets.githubusercontent.com` on the default port with no credentials or fragment. Any other redirect, a second redirect, a relative one that stays on github.com, or one without `Location` is `redirect-refused`, and the refused address is never requested. [Where a beta's files live](#where-a-betas-files-live) says why;
  - only a version greater than the running one becomes `available`; the same or an older one is `up-to-date`, and a download starts only from `available`;
  - the engine joins overlapping operations. The service refuses an overlapping Check or Download with a busy outcome before it reaches the engine;
  - a check first forgets the last check's offer: while it runs and after it fails, `newer` is null, so nothing is "required" from an earlier answer and `download()` starts nothing;
  - a download is written to a `.partial` file created exclusively with mode `0600`, counted and hashed as it arrives, stopped as soon as it passes the feed's size, and kept only when its size and SHA-512 are the feed's. A mismatch is reported as `size-mismatch` or `hash-mismatch`. On failure the engine tries to remove the partial file. A rename into place refused with `EBUSY`, `EPERM` or `EACCES` is tried again for about 1.5 seconds, since a virus scanner can hold a just-written Windows file for a moment. Once every byte is in, the downloading state carries a `step`, `moving` and then `verifying`, so a download that stops there shows where. The kept file's name is built from the checked version and the platform, never from the feed's address;
  - bounds: the feed at 64 KiB and 15 seconds (`FEED_TIMEOUT_MS`); a file at 512 MiB (`MAX_DOWNLOAD_BYTES`, refused as `too-large` from the feed's own `size`, or from `Content-Length`, before any byte is written), a 30-minute transfer deadline (`DOWNLOAD_TIMEOUT_MS`) and a 60-second idle deadline (`IDLE_TIMEOUT_MS`) end when the response and file write finish. The separate file proof follows;
  - nothing from the feed leaves the engine except the checked version, the release date re-written by `Date`, sizes it counted, and the path it made. Release notes and names are never read. The feed is read with `JSON.parse`. On Windows a fixed local helper inspects the downloaded file through an open handle;
  - a write to the download file that fails is `write-failed`, also while the server is still sending, so a screen can say to free space; a connection the server drops without a filesystem failure is `unreachable`;
  - every failure is one typed state: `address-refused`, `unreachable`, `timed-out`, `http-status` (with the status), `redirect-refused`, `too-large`, `malformed-feed`, `wrong-track`, `no-file-for-this-system`, `size-mismatch`, `hash-mismatch`, `write-failed`.
- **What the download checks.** On both systems, by the engine: the file's size and SHA-512 equal the feed's, and the feed came over HTTPS from the address fixed at build time. The request sets `rejectUnauthorized: true` and `ca: tls.rootCertificates`, so the certificate is verified even with `NODE_TLS_REJECT_UNAUTHORIZED=0` in the environment, and only against the Mozilla certificate authorities bundled with the Node.js inside Electron (Node 24.22.2 in Electron 45.3.2): `NODE_EXTRA_CA_CERTS`, `NODE_USE_SYSTEM_CA` and the system's own store add nothing. A host whose certificate chains only to a private or corporate authority cannot serve the feed. `apps/desktop/test/update/certificate.test.ts` shows both with a throwaway certificate `openssl` makes for the test. That proves the file is the one the feed names; it proves nothing the feed's host did not. There is no signature over the feed.
- **What the release-download check proves.** `apps/desktop/test/update/release-assets.test.ts` checks the production release-download rule address by address, and drives the engine through the one redirect against a stand-in that plays both GitHub hosts on `127.0.0.1`: a matching file is kept, a tampered one is `hash-mismatch`, and a second redirect, another host or port, a missing `Location`, a redirect from any other path and a redirect of the feed are each refused without a request to the refused address.
- **macOS installation.** The build flag records packaging intent. An unsigned or ad hoc build made without update signing reports `build-not-signed`. For a signed build, an independent inspector checks the running app against the Apple Developer ID Application requirement. It reads a private, unlinked copy of the verified ZIP. The inspector caps the expanded file bytes and the total scratch entries, including implicit directories. It admits one top-level Clawtrate app and the listed Electron helper apps. The bundle identifier, architecture and full release version must match. The inspector requests strict validation of the bundle, nested code and all architectures against the running app's designated requirement and passes Apple Security its no-network flag. The signed trial checks actual trust behavior and system-service traffic. A bundle built with the signing flag but without a certificate signature reports `build-not-signed` at its first inspection; its archive is not read.
- **Confirmation on macOS.** “If macOS stages the update, it can install the next time Clawtrate quits.” Download alone starts no native staging. After confirmation, the host rechecks the download and writes the attempt. The host opens a one-use URL on IPv4 loopback with a random path and serves the held archive with its length and SHA-256 if requested. The host selects Electron's default feed mode. Stand-ins exercise the feed and archive requests. Native requests remain part of the signed trial. The listener closes on completion, error or its two-minute deadline. When Electron reports that it staged the update, Clawtrate says ‘Clawtrate handed the update to the macOS updater. After restart, Clawtrate reports the version that is running.’ If the updater stops before it requests the archive, it cannot have staged this update, for example on a Mac running Clawtrate from a read-only disk image ([Squirrel's read-only volume check](https://github.com/Squirrel/Squirrel.Mac/blob/fffea30e4a339a7f7d69a3391314b72548d209bd/Squirrel/SQRLUpdater.m#L255-L275)). Clawtrate then reports `mac-updater-refused` and says ‘The macOS updater refused the update before receiving it. Nothing was installed.’ Check and the track stay available, and Download follows a new Check. Once the archive has been requested, staging cannot be ruled out: if Electron does not confirm it, Clawtrate keeps the attempt, says so, and keeps Check, Download and the track locked until it quits.
- **What the Mac handoff establishes.** Squirrel checks the staged bundle’s designated requirement. ShipIt checks its copy again. Those checks establish developer identity at each check. They cannot establish that the exact archive became the installed app. ShipIt can finish the authorized attempt at a later quit and retry on its own. Clawtrate never stages again automatically. Closing the listener cannot revoke a handoff. [Squirrel staging](https://github.com/Squirrel/Squirrel.Mac/blob/fffea30e4a339a7f7d69a3391314b72548d209bd/Squirrel/SQRLUpdater.m#L1076-L1096), [ShipIt copy and signature check](https://github.com/Squirrel/Squirrel.Mac/blob/fffea30e4a339a7f7d69a3391314b72548d209bd/Squirrel/SQRLInstaller.m#L249-L266).
- **Windows installation.** Windows x64 can check for updates. The Updates page withholds Download and Restart. Builds without update signing report `build-not-signed`. Signed builds report `windows-install-pending-trial`. The installer retains ordinary NSIS setup behavior. Before enabling handoff, the owner must establish cache-only Authenticode trust for the expected leaf, the signed setup's product and full version, protection through all setup reads, and a scoped install after the initiating app exits.
- **Attempt and recovery.** Before handoff the host atomically saves one target, track, starting version, UTC time and phase. A failed save stops the handoff. Startup reads the bounded settings once before cleaning the download folder. A corrupt attempt has its own notice and leaves valid settings readable and writable. Each launch compares its running version with the record. For example, “Clawtrate 1.2.0 is running.” A later manual downgrade changes that observation. The journal records neither which installer produced the current build nor a history of installations.
- **Signed trial.** Host tests use fixture bytes and stand-ins. The packaged launch check reads build capability with no verified offer. Stable and Windows stay closed until the owner tests consecutive signed releases on Windows x64, Apple silicon and Intel, including signer continuity, actual location and preserved data. The owner authorized the Mac Beta track, whose first two signed builds are that trial on Apple silicon and Intel ([Beta for macOS](development/releases.md#beta-for-macos)).
- **Signing hooks** (`apps/desktop/packaging/signing.ts`). `signingPlan` and `signingProblems` run before electron-builder. On macOS, `CSC_LINK` or `CSC_NAME` requests certificate signing. Supply a Developer ID Application identity for releases. Without either variable the app is signed ad hoc. The build notarizes only when signing is on and one complete set of `APPLE_*` credentials is present (an API key, an Apple ID with team, or a keychain profile), and `notarize` is `false` otherwise; Windows signs when `WIN_CSC_LINK` or `CSC_LINK` is set. The certificate and its password are read with electron-builder 26.18.1's own precedence (on Windows `WIN_CSC_LINK`, else `CSC_LINK`, and `WIN_CSC_KEY_PASSWORD`, else `CSC_KEY_PASSWORD`, where a variable set to an empty string still wins) and go together: a certificate without a password, a password without a certificate, a blank certificate variable, or a blank `WIN_` variable hiding a generic one stops the build, naming the variable. A certificate without a password needs its password variable set empty on purpose. A partial set (an `APPLE_ID` without its password, say), a notarizing variable or `CSC_NAME` set but blank (electron-builder counts spaces as a value), or notarizing credentials without a signing identity stops the build before it starts, naming the variables, not their values. Before electron-builder starts, Clawtrate prints the signing plan. On macOS it checks both app bundles after packaging. The build fails if it cannot read a bundle's signature or if the signature differs from the plan. Keep the entire output of a signed build private. Clawtrate's plan, preflight and signature-kind lines omit input values. The build passes through electron-builder's output, which can include identity names, hashes, paths and signing input values in errors. A build without the variables is configured exactly as before. Tests cover the decision and the configuration with made-up values; no test signs anything.

### The Beta track

The pre-release track is called Beta wherever a person reads it: in Settings → Updates, in the version (`0.1.1-beta.20261120.1`, which About shows), on GitHub's release page and on the site. The version suffix changed from `-nightly.` to `-beta.` before any build was published, so no installed app or saved setting carries the old one, and the engine now refuses it. The track's identifier in code stays `nightly`: in `UpdateTrack`, the saved preference, the feed's `track` field, the IPC replies, `CLAWTRATE_NIGHTLY_UPDATE_FEED_URL` and the candidate workflow's `TRACK` value, to which its `track` input `beta` maps. No person reads it, and renaming it would touch most of the update service and its tests while #204 rewrites them. A beta takes the checked-in version, raises its patch and adds the UTC day and a run number, the next one that no tag or staged release has used.

### Where a beta's files live

The Mac apps are assets of a GitHub prerelease, tagged `v<version>`. The Beta feed and `latest-mac.json` are served by the website, at `https://clawtrate.dev/updates/beta/feed.json` and `…/latest-mac.json`. The beta build is compiled with that feed and no Stable feed.

- **Why GitHub releases.** A beta's zips are 118.8 MB (Apple silicon) and 124.7 MB (Intel), measured from an unsigned `pnpm package:mac` of 0.1.0; signing and stapling add a few kilobytes. GitHub Pages refuses files over 100 MB from a repository, caps a site at 1 GB and has a soft limit of 100 GB of transfer a month, so it cannot hold the apps. A release asset may be 2 GiB, GitHub does not limit its downloads, and it costs nothing. Another host would cost money and add credentials to the release.
- **The one redirect.** GitHub answers a release download with a 302 to `release-assets.githubusercontent.com`, with a signed, short-lived query (observed on November 20, 2026). The engine follows exactly that hop, and only for a file the feed names at this repository's release download path. The feed itself follows none. The file's size, `Content-Length` and SHA-512 are still the feed's, and the feed still comes only from the address compiled into the build, so following the hop does not change what is installed. It adds GitHub's storage host as a party that sees the download. If GitHub moves its asset host again, a download fails as `redirect-refused` and nothing is written. A newer build with the new host is then installed from the site. The rule judges the request URL as the URL parser normalizes it, so dot segments that resolve back to the same release path and an explicit `:443` are the same request and are accepted.
- **How the site gets the feed.** `pnpm release:beta --publish` attaches `feed.json` and `latest-mac.json` to the release. The Site workflow (`.github/workflows/site.yml`) is the site's one deploy. It deploys only from `main`, the one ref the repository's `github-pages` environment allows; a tag rule would let anyone who can push a `v*` tag deploy that tag's own copy of the workflow. It runs on pushes to `main` that change `site/` or the assembler, and when `pnpm release:beta --publish` or `--withdraw` starts it on `main` after GitHub lists the release's new state; release events do not start it. `apps/desktop/packaging/site-feed.ts` refuses to assemble anything without `site/index.html`, so before the website lands the workflow fails and deploys nothing. It also refuses a `site/updates/beta/`: that folder only ever holds the generated files. It copies `site/`, takes the newest published beta that carries both Mac zips by their canonical names, `feed.json` and `latest-mac.json`, requires each of the two files to be the bytes GitHub's digest of it names, checks them against each other and the tag (`beta-files.ts`), requires each zip to be fully uploaded at its own release address with GitHub's size and SHA-256, reads each zip from that address, following only the one redirect the app follows, to require the SHA-512 the feed names (what the app checks) and the SHA-256 `latest-mac.json` names (what the install script checks) of that one download, and only then writes them under `updates/beta/`. From the same beta it fills the Mac download page, `site/download/mac/index.html`, a template whose `__CLAWTRATE_BETA_VERSION__`, `__CLAWTRATE_ARM64_ZIP__`, `__CLAWTRATE_X64_ZIP__` and `__CLAWTRATE_RELEASE_PAGE__` become the version, `latest-mac.json`'s two addresses and the release's tag page. It fails, so nothing deploys, without a published beta, while any `__CLAWTRATE_…__` token is left in the site, or while `site/install.sh` pins the placeholder `APPLE_CLAWTRATE_TEAM_ID` or another team than that `latest-mac.json`. Each deploy serves the newest beta still published. Withdrawing the newest one (making its release a draft) makes the next deploy serve the newest one left; withdrawing an older one changes nothing served. Withdrawing the only one deploys nothing, so the last deployment stays. The deploy job checks that the beta the build job assembled is still published, so a beta withdrawn between the two jobs is not deployed. How soon GitHub stops serving a withdrawn release's files is for the signed trial to observe. A feed is never written by hand.
- **`latest-mac.json`** is for the site's install script. `uname -m` names each entry: `{"teamIdentifier", "arm64": {"version", "url", "sha256"}, "x86_64": {"version", "url", "sha256"}}`, each SHA-256 in lowercase hex. `teamIdentifier` comes from the signatures of both apps, which must agree, so the script can require that team.

### Pairing and tasks across an update

An update in place keeps everything a pairing needs, because none of it depends on the version or the bundle's location:

- the bundle identifier is `APP_ID` (`apps/desktop/src/main/identity.ts`), which `packaging/config.ts` gives electron-builder;
- the data folder is Electron's `userData`, `~/Library/Application Support/Clawtrate`, named from `productName` in `apps/desktop/package.json` and `app.setName("Clawtrate")` in `src/main/index.ts`; a release changes only `version` in that file (`candidate-build.ts`);
- the device key is `<userData>/gateway/device-key.pem`, and the saved connection and device token are in `<userData>/gateway/state.json` (`createNodeHost` in `packages/core/src/node/index.ts`), plain files that need no keychain entry tied to the signature;
- the tasks are the gateway's sessions, which the reconnected app reads again.

The launch check's last test (`e2e-packaged/launch.spec.ts`) shows it with a packaged app: after pairing, it makes a copy whose archive and Info.plist carry only a higher version (`packaging/newer-copy.ts`), quits the app, starts the copy on the same data folder, and requires the seeded bots and a task with no connect screen or approval, the newer version from the running app, the same device key and saved connection, and a device token still saved for each gateway (the test checks that the entries are there, not that their values are unchanged). It quits the first app within the teardown's own 15 seconds, and the copy is in the run record, so the run's cleanup stops it if the test cannot. The copy is signed ad hoc, so it proves the paths. Only two consecutive Developer ID builds can prove that Squirrel.Mac hands one to the other.

### Cutting a beta

`pnpm release:beta` (`apps/desktop/packaging/release-beta.ts`) runs on the maintainer's Mac, never in CI, so the Developer ID certificate and the notary key never leave that Mac except to Apple. It reads both from the maintainer's vault at run time, builds both apps with `candidate-build.ts`, and checks each app as it ships, unpacked from its zip; every check's tool must succeed and print what is expected. Without `--publish` nothing is published. [Releases](development/releases.md#beta-for-macos) is the runbook. Its tests replace the vault, git, gh, the build and Apple's tools with stand-ins; no test signs anything.

- **Secrets go only to Apple's tools, on their standard input.** The release Mac runs other processes of the same user, and any process can read another's arguments with `ps`. electron-builder 26.18.1, given a `.p12`, imports it with `security import -P <password>`, and `@electron/notarize` 2.5.0 passes the key's id and issuer to `notarytool` as arguments. So the script gives electron-builder neither. It feeds `/usr/bin/security -i` the commands that create a keychain in a private temporary folder (with a random password that exists only in the script), import the certificate and allow `codesign` to use it, one command per call: `security -i` exits 0 after a batch whose earlier command failed, so each status is checked, and `show-keychain-info` must report the lock settings. It feeds `/usr/bin/xcrun notarytool store-credentials` the key's path, id and issuer, which it stores in that keychain as a profile; absolute paths, so no entry in `PATH` receives them. The build then gets an allowlist of ordinary variables (`PATH`, `HOME`, the locale and caches) and the keychain's path, the identity's hash and the profile's name, which electron-builder reads as `CSC_KEYCHAIN`, `CSC_NAME`, `APPLE_KEYCHAIN` and `APPLE_KEYCHAIN_PROFILE`. None is a secret, so neither the build, pnpm, Electron Vite and git under it nor its log holds one. That is why the script prints only the log's path when a build fails, and keeps no redaction step.
- **What a killed run leaves.** The certificate's file is deleted as soon as its import returns, and the key's file (`notary.p8`) as soon as `notarytool` has stored it, which keeps the key itself in the keychain; the script checks both are gone before the build starts, since the build runs as the same user. A normal exit, an error, Ctrl-C and SIGTERM remove the folder. A run killed outright leaves it: killed during the import or the credential store, with that raw file readable by that user, and at any point with the keychain, unlocked until it locks itself after an hour or when the Mac sleeps. The next run, first of all, removes each such folder whose recorded run has ended, and leaves one with no recorded run for the maintainer to inspect. [Releases](development/releases.md#if-a-run-is-killed) says how to remove one by hand.
- **Publishing checks what it publishes.** The staging folder can be edited, and a whole replacement can be made consistent with itself, so preparation verifies private copies of the zips, stages and records those, and prints the SHA-256 of the exact `release.json` it wrote. `--publish` requires that value, compares `release.json` with it before reading anything in it, and then checks the folder holds exactly the four files of the requested version plus its notes and record, that `release.json` names that version, tag, a full commit and a team, that every file still has its recorded hashes, that the feed and `latest-mac.json` name those two zips by size and digest under that tag and team, and that `notes.md` is the text its record makes. It asks GitHub's compare API whether the commit is on the repository's own `main`, not this checkout's `origin`, which can be a fork or stale, and refuses when it is not or GitHub cannot say. It compares the team with every earlier beta's `latest-mac.json` on GitHub, drafts included, and refuses when one cannot be read; only a listing with no earlier beta counts as the first. It creates the release as a draft with the notes as checked text, makes it public only after GitHub's own SHA-256 digest of each of exactly those files and the draft's notes match, and reads it back afterwards rather than trust the command's status.
- **Withdrawing reports what it saw.** It reads the release back from GitHub to report that it is a draft, then reads the feed's own address, with no redirect followed and each request with its own deadline, until it serves the feed of the beta GitHub still lists, or, with none, answers 404. A feed of any other version, a redirect, a failed connection, another status or a body that is not a feed is reported, never taken as no beta.

## Continuous integration

`.github/workflows/ci.yml` has read-only permissions and uses no secrets. It runs on pushes to `main`, on pull requests and by hand (`workflow_dispatch`). Its artifacts are what a failed check saw, and the Windows job's unsigned installer, each kept three days. It runs four jobs:

- lint, typecheck and unit tests on Linux;
- `pnpm e2e` on Linux, with `openclaw@2026.10.6` installed from npm (it needs Node 26.12.1 or later, which `setup-node` provides);
- `pnpm visual` and an unsigned `pnpm package:mac` on `macos-15`, the release the baselines were taken on;

## Web preview host

- The host binds `0.0.0.0:5310` by default and keeps the gateway connection, the device key and pairing in Node. Browsers on other machines usually reach it over plain `http`, which is not a secure context, so signing could not happen in the browser anyway.
- Access token: 24 random bytes, generated at each start and printed once. A request carrying the valid token gets a `HttpOnly; SameSite=Strict` cookie and a redirect that removes the token from the URL. Every asset request and the `/bridge` WebSocket need the cookie. The WebSocket also checks that `Origin` matches `Host`. Comparisons are constant time. Static files are confined to the build directory.
- The development endpoint belongs to the selected dev-gateway instance (`--instance` or `CLAWTRATE_DEV_INSTANCE`, default instance otherwise), and only while it is proven (`tools/dev-gateway/src/endpoint.ts`): the instance's folder is the tool's own and not a link, its marker is valid and names the instance, the marker's run id, instance and checkout agree with this checkout's run file, the run file's port is the instance's (19001 for the default instance), the connection file is a regular file naming the same URL, instance and run id, and the recorded gateway is the live process the tool spawned, by PID and start time. Two files agreeing is never enough: a stale pair whose port another process has since taken is refused. The hosts import the tool's own name validator and proof, so they apply the same rules.
- `--no-access-token` is accepted only when that proof holds at startup. The client is then told to open nothing but the selected instance's endpoint, and the proof is run again before every connection, saved, typed or retried. It runs where the socket is created (`createSocket` in `packages/core/src/client.ts`), because `GatewayProtocolClient` schedules its own retries without going back through `connect`. A refusal there opens no socket, shows `GATEWAY_NOT_ALLOWED` and ends the retries, so a gateway that stops, is restarted with a new token, or whose process cannot be checked, is not reopened without a token. The desktop app and a web host with a token apply the same proof to the development gateway's address; connections the user makes to other gateways are not affected. The default instance's endpoint is refused like any other when a named instance is selected. If the host's data directory remembers another gateway, the host refuses to start rather than resume it without a token. The pairing screen shows `pnpm dev-gateway approve --instance <name>` for a named instance.
- Unauthenticated upgrade requests are untrusted input: a malformed cookie is an invalid credential, and any parsing failure is answered with 400 or 401 instead of reaching the process.
- **Viewers are bounded.** At most `MAX_WEB_VIEWERS` (8). A viewer's snapshot carries only the tasks it has open. A snapshot is written only once the socket has accepted the one before (`bufferedAmount` back to 0), and only while fewer than `MAX_SNAPSHOTS_IN_FLIGHT` (2) viewers hold one unaccepted; until then the viewer keeps a reference to the newest state, not a copy, so no older snapshot is held. A socket that does not accept its snapshot within `SNAPSHOT_DRAIN_TIMEOUT_MS` (30 s) is dropped at once with what it left buffered, not left to flush. A command result is at most `MAX_RESULT_CHARS` (262,144 JSON characters); a longer one is answered with an error, so text too long for it is read whole only in the desktop app, and an approval it belongs to can still be denied. A viewer that leaves more than `MAX_UNACCEPTED_RESULTS` (16) results unaccepted is dropped the same way.
- The development gateway's bootstrap token stays in the host. **Use the development gateway** sends a command, never the token.
- The web host doesn't look on its own computer unless it is started with `--setup-look`, and then only in a sandbox, with its data in that sandbox's folder, never resuming a saved gateway, and it never pairs ("Setting up on this computer").

## Setting up on this computer

The first package of `docs/design/setup.md` (§19, "Order", item 1): the first screen, the look on this computer, Connect with nothing typed, and the form under Advanced. The host's part is `apps/desktop/src/setup/`; the interface's is `packages/ui/src/setup/`.

- **What the look runs, and when it runs nothing.** OpenClaw's launcher is not a read-only entry point. In 2026.10.6, `openclaw.mjs` replays pending package-lifecycle work (`dist/infra/package-lifecycle.js`) whenever `.openclaw-lifecycle-pending` or `dist/openclaw-install-guard` is in its package, before it handles `--version` (lines 649–715), and the same launcher fronts `gateway status`, `config get` and `qr`; before that, a Node it doesn't support starts a runtime recovery that may install one (lines 37–80). No command but the browser extension's native host skips that branch, and no runtime-recovery or compile-cache variable turns it off. So the look never runs an installed OpenClaw whose version isn't on a list of versions verified to have a read-only path (`READ_ONLY_VERSIONS` in `apps/desktop/src/setup/look.ts`), and that list is empty. Its version is read instead, never run: the program must resolve to the launcher `openclaw.mjs` beside its package's own `package.json` named "openclaw". For any version, the look then declines with "can't tell" (`read-only`): "This version of OpenClaw can change its own installation whenever one of its commands runs, so Clawtrate doesn't run it to look. Use Advanced with the gateway's address and token." Nothing below this paragraph runs on a real computer until a version is verified; a sandbox's stand-in, the host's own code, answers the commands instead (`apps/desktop/src/setup/sandbox.ts`), so the screens and Connect are still exercised in development and tests. Each probe's path today: the program's presence and its file identity are file checks; its version is a read of its `package.json`; the status, the deep status, the auth mode and the code are not run. Each program from the fixed list of §4 is a regular executable file or is skipped, and the file checks share the design's 2 s limit. In a version verified read-only, the first program found runs one of the exact commands the runner accepts (`isLookCommand` in `apps/desktop/src/setup/programs.ts`), each an argument array with no shell:
  - `[--profile <p>] --version` (10 s, 4 KiB);
  - for each profile looked at, `gateway status --json` (20 s, 256 KiB) and `config get gateway.auth.mode --json` (10 s, 4 KiB);
  - in production only, once, `gateway status --json --deep` (20 s, 512 KiB), read for `extraServices` only.

  The environment holds only `HOME`, `LANG`, `NO_COLOR` and a `PATH` of the program's own folder and the system's. The working folder is the home, never the app's. A sandboxed look runs no program at all (below). Standard error is read and dropped. Standard output is parsed in memory into typed facts and dropped. A program that ignores the request to stop is killed after 2 s. The default profile is always looked at; Clawtrate's own, `--profile clawtrate`, only when `~/.openclaw-clawtrate` exists.

- **What OpenClaw's status inspects.** In OpenClaw 2026.10.6, status reads the profile's service state, configuration and service environment. The default installation can use the native service command's arguments and environment for the probe. A named profile uses its own environment/config for that choice. The port comes from the applicable service arguments, environment or config. The probe uses TLS when configured and chooses its host from the bind rules. It inspects network interfaces, the listener and service/config diagnostics, and may resolve credentials through configured secret references before it sends a gateway probe. On macOS both status forms query the profile's service and list the whole launchd job table. They inspect eligible foreign OpenClaw jobs and, where applicable, read their owned definitions and program or shell-script files. The foreign-job pass excludes the default, node and own labels only after listing the jobs. Status may inspect a local TLS certificate, service layout, last gateway error, installed plugin records and host-desktop status. Deep status also checks the state database and fuller config/plugin validation, stale update jobs, system service folders, restart/last-shutdown records and established clients. Linux uses its service-manager and port diagnostics. Gateway status, config get and qr can load cwd and state dotenv and resolve config includes; the root --version path skips dotenv. The qr command takes the explicit loopback URL before network discovery, can resolve configured auth inputs and issues a bootstrap token into OpenClaw's own pairing store. It makes no gateway RPC for the normal named development config. Clawtrate's automatic path retains only the projected facts and the one-time pairing credential while connecting. So **a sandboxed look never runs the real program**, for status or anything else (below).
- **Connect goes to an exact local endpoint whose listener was rechecked before Connect.** The endpoint is `ws://127.0.0.1:<port>`, kept as that string. The address the status probed (`gateway.probeUrl`) and the one its RPC answered on (`rpc.url`) must both equal it, after taking off at most one terminal slash, and the port the status checked (`port.port`) must be the gateway's: `localhost`, IPv6, TLS, a path, a query, a user or another port is "can't tell". So is a gateway with no single process listening on exactly `127.0.0.1:<port>`, a listener that isn't running, a service config file other than the program's (`config.daemon.path`), and two profiles that report the same port. A version alone is not a gateway. The look keeps, in the host only, the listener's PID and the system's start time for it, the program file's identity (device, inode, size and times, read before the program is first run and again at the end, within the file checks' limit; a file changed between is not offered), both config paths and the service's identity (label, role, PID, state, unit). After the dialog, after the earlier connection is let go and after the check for an earlier pairing, it reads the status and the auth mode again, each run finished in time, within its limit and exited 0 before its output is read, and goes on only if all of these are unchanged and the consent's two minutes haven't passed, on every branch. It reads them again after the code is made, and the client asks the host before every socket of the setup connection, retries included, until the bots are first read on it, whether the same process still listens; if not, it opens none and shows "changed". Once each of those sockets opens, and again just before the frame that carries its credential (the one-time code, or this device's token), the host reads the endpoint's listener again: the status's own report of the port's listener, its PID and start time, the endpoint and the program file, against what the look found. Any difference closes the socket with nothing sent and shows "changed". The remaining window is a listener swapped out and swapped back between the last of those reads and the credential frame, or between two of them; the reads can't see that. Clawtrate narrows that window rather than verifying the socket's peer: a plain local WebSocket can't prove that the process that receives the code is the one that was checked, so nothing says so; route identity is later work. From then on the connection is the saved gateway's, reconnected by its address as every saved gateway is.
- **Where the gateway differed from the design.** `gateway status --json` doesn't report the auth mode, so the look reads it with `config get gateway.auth.mode --json`, which prints the mode and nothing secret; an unset mode is "can't tell". `--deep` doesn't list another profile's own service; the look also names the other `~/.openclaw-<profile>` folders in the home folder, folders only, by name, without opening them, as "Other OpenClaw services or profile folders reported here". A profile folder proves no service. The configured bind is "Configured for loopback" or "Configured for LAN" only for those two values; `auto`, `tailnet` and a custom address can each resolve to loopback, so they are "Not reported". A service is named, as "LaunchAgent" or "systemd user service" with ", stopped" when the status says so, only when the status associates it with this gateway; a development instance's status calls its service `diagnostic-only`, so its service is "Not reported", and a status that reports no unit says "No matching service reported". With nothing answering and nothing listening, the stopped card names the installed program's version and says "No gateway answered on port …". A status or auth command that can't start gives the card for a program that couldn't run.
- **Too old.** A reported version below 2026.7.0 (`OLDEST_OPENCLAW_VERSION`, Clawtrate's choice) is not offered for automatic Connect: "OpenClaw <version> is below the version this Clawtrate offers for automatic setup (2026.7.0)", with how to update and Look again. Another version at or above it is "untested" and says to use Advanced to try connecting. The cards claim nothing about a protocol; a setup hello on another protocol writes nothing and shows the protocol notice.
- **The host's confirmation.** Connect is `setupConnect` with no parameters. The host prepares the pairing from its own last look and shows its native dialog. Connect asks for read access, always, and the card's button says "Connect read-only". For a device without a saved pairing for that address the dialog asks "Pair this device read-only with the default gateway on this computer?" with "Clawtrate asks for read access. The gateway may ask its owner to approve this device."; the card says the same. A device with a saved pairing for that address is asked "Connect this device read-only to …?" with "This device has a saved pairing for this address.", and nothing claims what that pairing can do: the look found it by address, not by gateway. An answer after two minutes, a second use, or two minutes passing before a code is made or a socket is opened runs nothing. Nothing is minted before the answer. The consent is to what the dialog named: a saved pairing that went, or one that appeared, after it (found when Connect checks, or when the socket asks for its credential) mints and sends nothing (`SETUP_PAIRING_GONE`, `SETUP_PAIRING_APPEARED`), and the card asks again with the words for what is there now.
- **The one-time code.** After the dialog the host runs `openclaw [--profile clawtrate] qr --json --voice-node --url ws://127.0.0.1:<port>` and reads its output only when it ran to its end in time, within its limit, and exited 0. It accepts the code only when its address is exactly that URL, its token has a bootstrap token's shape, and it expires in the next ten minutes. It hands `{url, bootstrapToken, expiresAtMs}` to `ClawtrateClient.connectWithSetupCode` and drops it. The client keeps it in memory only, sends it as `auth.bootstrapToken` asking for `operator.read` alone, and forgets it at the first hello and on every terminal path: a refusal, a pairing that ended or that the gateway says not to wait on, a socket that couldn't start, another connect and a disconnect. Only while the gateway waits for its owner's approval does it keep it, until it expires.
- **What a setup connection publishes.** From its first socket through its first hello and the first read of bots and tasks after it, a setup connection (a code redeemed, or this device's token reused) publishes typed outcomes only: `AUTH_BOOTSTRAP_TOKEN_INVALID`, `PAIRING_REQUIRED`, `PROTOCOL_MISMATCH` with its two protocol numbers, the client's own `SETUP_GRANT_REFUSED`, `SETUP_ENDPOINT_CHANGED`, `SETUP_PAIRING_GONE`, `SETUP_PAIRING_APPEARED` and, for anything else the gateway answers, `SETUP_CONNECT_REFUSED`, each with fixed words. Never the gateway's own code, message, hint, scopes, device id, request id or close reason. A pairing shows this device's id, the scopes this client asked for, and the gateway's pending-devices instruction (`openclaw devices list`) without a request id; the client keeps only a short digest of the id to tell that the request ended. The gateway's version is shown only as a date version, otherwise not at all. A failed first read of bots says "Could not load your bots." Every other error, hint and pairing field the client publishes or logs has every credential it holds taken out, a token the gateway replaced on a later reconnect included. So the one-time code and the gateway's shared token are in no renderer state, snapshot, app log line, program argument or environment, or file the app creates. The app keeps the device token the gateway approves, deliberately, in its private device-token store. OpenClaw reads its own gateway credentials internally when its commands run, and keeps the code it issued until it is redeemed or expires; Clawtrate never asks it to print either. These are statements about Clawtrate's own logs, snapshots and files: the code is in the host process's memory while it connects, and a native crash dump of that process is outside them. The shared token is never asked for; only Advanced takes a token, typed. Once setup is over, the gateway is an ordinary saved one, and its refusals publish the pinned protocol's named codes (`ConnectErrorDetailCodes`) as they are and the client's own `CONNECT_REFUSED` for any other, so a code the gateway made up never reaches viewer state.
- **Back during Connect.** Back closes the connection setup opened, by its address, behind any change already queued for it; another gateway selected since is left as it is. The connection stays setup's own until the client has forgotten it: if its saved settings can't be deleted it stays connected, the screen says "Clawtrate couldn't close the connection it started.", and Back, or Connect, tries the same cleanup again before anything else. A cleanup under way is shared, and its answer changes the screen only for the attempt that asked.
- **No grant wider than the request.** The pinned device-auth lifecycle stores the device token from `acceptHello`, before the client's `onHello` sees the grant. For a setup connection the client's token store stages that token in memory instead and keeps it out of `load`. After `acceptHello` it writes the token only when the hello's protocol is this client's, its role is `operator` and its scopes are exactly `["operator.read"]` (`setupGrant`). Another role, no scopes or more scopes write nothing, close the connection and end in `SETUP_GRANT_REFUSED`. A device with a saved pairing reconnects for setup with `connectForSetup`, which asks for `operator.read` alone in the signed request and in the token store's answer to the lifecycle, on that socket and its retries until setup ends with its first read of bots, whatever the saved record holds or comes to hold; wider access the device already holds stays saved for later ordinary connections, and the gateway is saved once that hello is in. If the saved token is gone when the socket asks, nothing is sent (`SETUP_PAIRING_GONE`) and the card asks for a new consent. On every connection the signed request is the ceiling: an asked scope that the grant implies is held (write supplies read), and an unasked scope never is, so `canWrite` and the rest follow the request. A replacement token is stored with its grant held to the request, and an access upgrade keeps only the scopes it asked for or that they imply: a pairing-only upgrade adds pairing and nothing else.
- **What must be sandboxed, and the sandbox.** A run must be sandboxed when the app is not packaged, when any of `CLAWTRATE_E2E_RUN`, `CLAWTRATE_AUTOMATED`, `CLAWTRATE_SCREENSHOT`, `CLAWTRATE_SETUP_SANDBOX`, `VITEST` or `CI` is present at all, or when any of the debugging or sandbox switches is (`mustSandbox`). The desktop app decides it before its single-instance lock and its host runtime start (`resolveSetupLaunch` in `apps/desktop/src/setup/sandbox.ts`). A packaged app started with none of these is a person's and looks at the real computer, so nothing may automate a packaged app without the sandbox switch; `pnpm check:packaged` passes it on every launch, which `test/sandboxed-launches.test.ts` checks. A sandboxed or refused run never resumes a saved gateway (`start({ resume: false })`), and never resolves the development gateway or the ordinary data folder (`desktopStartup` and `webStartup` in `apps/desktop/src/setup/startup.ts`): the desktop app's data folder is the sandbox's checked `app-data`, or for a refused run the folder its launch named with `--user-data-dir`, else a fresh private temporary folder, set before the single-instance lock, and the web host's setup look keeps its data in that `app-data`. A gateway chosen in Advanced still connects. It looks only in the sandbox it names, and no development, test, screenshot or preview run starts a program of OpenClaw's to look:
  - **The description.** `sandbox.json` names a development instance, that instance's run id and a scenario from a closed set (`recorded`, `untested-version`, `not-found`, `program-missing`, `pairing`), and nothing else: no program, folder, facts file or port. It comes from `--clawtrate-setup-sandbox=<file>`, or, when that switch has no value, `CLAWTRATE_SETUP_SANDBOX`.
  - **Its folder.** The description lies directly in a folder below one of the system's temporary roots (`/private/tmp` and `/private/var/folders` on macOS, `/tmp` and `/var/tmp` on Linux, whatever `TMPDIR` says), whose path is its canonical path, outside the account's home, owned by this account and closed to others, with `home`, `work` and `app-data` folders of the same kind. Nothing binds the folder to the launch that wrote it: any such folder of the account is taken, and what its description can select is confined by the instance's proof. It is read without following a link, with one link, at most 1 KiB. The look's home and working folder are the folder's `home` and `work`, the web host's data its `app-data`.
  - **Its instance.** The account's home comes from the account, never from `HOME`, and an account that can't be read refuses. Inside it the only path used is the instance's own state folder, the canonical `~/.openclaw-clawtrate-dev-<name>`, a real folder of this account's. The run is proven with the dev-gateway tool's own records, bound to the launcher's checkout (the development build's own, or the one `--clawtrate-setup-checkout` names for the packaged launch check), never to anything in the description: the marker, read without following a link and trusted by the tool's rules, names the instance and the description's run; the checkout's run record agrees on run, instance, checkout and port; the port is the first of an instance's block; a config file, if there is one, is a regular file with one link; and the recorded gateway is alive by PID and start time, or proven gone, which reads as stopped. Nothing past a failed step is read, and no process is asked about before the last one.
  - **The stand-in,** chosen in host code, answers the look's exact commands for that instance's profile alone, in the host's process: the version and the auth mode from the scenario's fixtures, the status from the proven run, proven again for each status. It starts no program, loads no OpenClaw config, opens no socket, and never answers the deep status.
  - **Pairing.** A development instance is never paired with through "This computer": after the dialog, Connect is refused. The `pairing` scenario's gateway is the host's own synthetic one (`synthetic-gateway.ts`), on loopback, on a port the system chooses, which accepts only the codes the stand-in's fixture mint made for it and grants exactly read. It proves the app's side of pairing, not OpenClaw's. A launcher-owned mint on a real instance was not built: it would start the installed program in a test run.
  - **Checked again at every step.** The description the launch validated is the one every later step compares to: the start of each look and Connect, each command the stand-in answers, after each wait (the folder checks, the commands, the dialog, letting go of an earlier connection, the check for a saved pairing, the code), and in the client before the token read, after signing, before each socket and before a token is kept. Once it is gone or changed, the run refuses from then on, whatever is put at that path later. In the pairing scenario the synthetic server's own socket must still listen on 127.0.0.1 at the endpoint the look found, asked of the server itself.
  - **Refusal.** A missing description, or one that doesn't pass, refuses before any marker is opened or anything is started: one fixed line in the log ("The look on this computer refused to start: …") and fixed words on the card, for a missing sandbox, the description's place or shape, the home, the instance's state, ownership or config, and a pairing the scenario doesn't offer. An error's own text is never logged.
  - On Windows the look starts nothing, so no description is read.
- **The checks' launchers.** `e2e/setup.spec.ts` starts its own instance, `e2e-<run>-setup`. It records the instance in a run record of its own before starting it, so only the shard that runs the file starts it. It gives every launch of the development build a sandbox of that instance, written by `e2e/setup-sandbox.ts` (the same writer a developer uses), and checks that a launch without one is refused. `pnpm check:packaged` gives the packaged app a sandbox of its run's instance and names its checkout. The visual tests use the fixture and no host, and the web host's checks start it without `--setup-look`.
- **The web preview is not the person's computer.** A browser viewing the web host is on another device, so "This computer" would mean the host's. The web host keeps the address-and-token form as its first screen, as before; a host started for a development gateway connects to it as before. `--setup-look` shows the new first screen. It looks only in the sandbox `--setup-sandbox` names, since the web host is a development and review host, keeps its data in that sandbox's `app-data` (`--data-dir` is refused beside it), never resumes a saved gateway, and refuses to start without a sandbox that passes. It never pairs, because it has no native dialog to ask first, and it says to use Advanced.
- **Not done in this package.**
  - "Another computer" leads to a screen that says reaching another computer over SSH isn't in this version and offers Advanced (package 2).
  - "Have a setup code?" is not on the first screen until the code entry exists (package 4).
  - The stopped card offers "Look again", not "Start OpenClaw" (F-497).
  - The not-found card offers "Look again" and OpenClaw's own install instructions, not "Set up OpenClaw here" (package 3).
  - The first screen's hint says "Clawtrate says what it finds there" until setting up is offered.
  - The Electron checks need Electron's binary and a display. CI's e2e job downloads Electron and runs under `xvfb-run`; on Linux the app starts with `--no-sandbox`.

## Development gateway

- **Instances.** `openclaw --dev` means one state folder and one port per machine, but a long-lived preview and several end-to-end runs in other worktrees need gateways at the same time. So every `pnpm dev-gateway` command addresses one instance. With no name it is the default instance: `--dev`, `~/.openclaw-dev`, ports 19001 and 19091, as before. With `--instance <name>` or `CLAWTRATE_DEV_INSTANCE=<name>` it is `--profile clawtrate-dev-<name>`. Names are 1 to 24 lowercase letters, digits and inner hyphens, `default` and `dev` are refused, and the check runs before any path is built, so no name reaches the default profile, the `--dev` profile or a profile without the `clawtrate-dev-` prefix. Both set to different names is an error.
- **How a profile maps to a folder and a port.** Read from the installed OpenClaw 2026.10.6: `--profile <p>` sets `OPENCLAW_PROFILE=<p>` and resolves the state folder to `$HOME/.openclaw-<p>` (`resolveProfileStateDir` in `profile-utils`), with the config at `openclaw.json` inside it. The gateway port is `OPENCLAW_GATEWAY_PORT` if set, then `gateway.port` in the config, then a hash of the profile name (`resolveGatewayPort`); only `--dev` defaults to 19001. The tool sets the environment variable, writes `gateway.port`, and passes `gateway run --port`, all to the same recorded port. The gateway's lock lives inside the state folder, so instances do not share one. OpenClaw derives its sandbox host (port + 1) and browser control (port + 2) ports from the gateway port, so those are kept free too.
- **Ports for named instances** come from 19200 to 19999 in blocks of 20: the gateway on the first port and the scripted model ten above it. `start` picks the first block, starting from one derived from the name, whose ports are free and not recorded by any instance folder, and records them in the new folder's marker, all under the machine-wide port lock, so concurrent starts never pick the same block. The run file records the same ports, and the runner refuses a marker whose ports are outside the range or differ from the run file's.
- **Profile.** Every OpenClaw command passes the instance's profile option (`--dev` or `--profile clawtrate-dev-<name>`), and also sets `OPENCLAW_PROFILE`, `OPENCLAW_STATE_DIR`, `OPENCLAW_CONFIG_PATH` and `OPENCLAW_GATEWAY_PORT` for that instance. Callers cannot pass `--dev` or `--profile` themselves. `reset` deletes only the instance's own folder, after checking the path is exactly `~/.openclaw-dev` or `~/.openclaw-clawtrate-dev-<name>`.
- **State is never reused.** OpenClaw loads a profile's own `.env` and auth stores at startup, after the environment allowlist has been applied, and keeps credentials in SQLite stores (`agents/<agent>/agent/openclaw-agent.sqlite`, `state/openclaw.sqlite`) that a clean profile also has with empty tables. No inspection of an old folder could prove it clean, so there is one way to start the gateway: `start` (and its alias `up`) stops the gateway this checkout started, deletes the instance's folder, creates it again empty with a `.clawtrate-dev-gateway` marker holding a new random run id, then configures, starts and seeds. The folder counts as the tool's own only if, checked without following links, the path is a real directory and the marker is a regular file written by the tool. Anything else is refused untouched; the tool never deletes a folder it does not own.
- **Process identity.** The marker records the instance name, its ports, the checkout whose tool created it and every process a start spawned on it: the start command itself, the scripted model and the gateway, each by PID and by its start time from `ps -o lstart`. The marker is always written whole and renamed into place. A look at a process has three outcomes. It is alive with a start time; it has exited, which needs positive evidence (the kernel answers `ESRCH` to signal 0, or `ps` shows it as a zombie); or it is unknown, which is every other result: `ps` could not be run, timed out, exited non-zero or printed something unreadable, or signal 0 failed for another reason. A recorded process counts as gone only when it has exited or a live process has its PID with another start time (a reused PID). Unknown is never gone: it refuses every signal and every deletion and is reported with its reason. A record missing either half, or naming a PID below 2, cannot identify a process, so the marker is not trusted. The run file in this checkout records only the run id, instance, checkout and ports.
- **Recorded before it can run.** A spawn followed by a file write is not atomic against the spawner being killed. So `start` first writes to the marker that it is about to spawn the scripted model (`providerPending`), then spawns it behind a gate: `/bin/sh` waiting for a line on a pipe from `start`, which then `exec`s the real command under the same PID and start time. `start` records the PID and start time, and only then opens the gate. If `start` dies before that, the pipe closes, the shell exits without running anything, and the pending record remains. A pending process therefore counts as running while its `start` runs, unknown while that is unknown, and gone once that `start` has exited. The gateway is spawned the same way, and so is the e2e preview host (`hostPending` in the run record).
- **Signals need proof.** Run files are per checkout and can be stale or edited, so `stop` signals a process only when the folder is the tool's own, its marker is valid, the marker's run id, instance and checkout agree with this checkout's run file, and the live process has the recorded PID and start time. The identity is checked again right before every SIGTERM and SIGKILL. If a process's state is unknown, `stop` signals nothing. After SIGTERM it waits for proof of exit, also through lookups that fail for a moment while the process exits (macOS `ps` shows such a process as `?E`), sends SIGKILL only to a process still proven alive, and if it cannot confirm that a process ended it keeps the run file and says so. A gateway's direct children are listed, with their start times, while it is still the proven parent, and each is signalled only if it is still that process. Anything that disagrees is refused and reported, and nothing is signalled. A run file whose folder is gone or holds another run proves nothing and is discarded without signalling. No PID of 0, 1, a negative PID or a process group is ever signalled.
- **Deletion needs proof that nothing runs.** `start`, `reset` and `prune` delete a folder only when its marker is valid and names the instance and folder it sits in, every recorded process is proven gone, and nothing listens on the instance's ports (19001 and 19091 for the default instance). Before deleting, `start` and `reset` also refuse, name the instance and the other checkout, and change nothing when something on the folder may run and this checkout's run file does not prove the run is its own. This is what protects a long-lived preview from builders in other worktrees. A marker without a recorded start time was written by an older version of the tool. It is never trusted, whether or not its processes still run, and the tool never deletes or adopts it. The README gives the one-time manual migration: stop the old processes by PID, rename the old folder aside, delete the old run file, then `start` on the now absent folder.
- **Locks.** Each instance has a lifecycle lock, held by `start`, `stop`, `reset` and `prune` from before their ownership checks until after the change they make, and port choice has a machine-wide lock. `start` holds it through the health check, the exec policy check and seeding, so no other of these commands acts on an instance that is still starting; they wait up to ten minutes. `status`, `seed`, `approve` and `list` take no lock. A lock is an exclusive SQLite transaction on a file in `~/.clawtrate-dev-gateway/locks/`, through Node's built-in `node:sqlite`. SQLite takes an operating-system file lock, so ownership is atomic, the lock is released when its holder exits however it exits, nobody ever judges another process's lock stale, and release closes only the holder's own connection. Lock files are never deleted, since deleting one while a waiter has it open would let two processes hold it; named instances share 64 lock files by a hash of the name, which can only serialise two instances, never mix them. The lock folder and its parent must be real directories and a lock a regular file; a link there is refused. A command interrupted by SIGINT or SIGTERM ends at its next step; a command killed outright leaves only gated processes it never released, which exit on their own, or recorded ones.
- **One boundary for OpenClaw.** Every `openclaw` subprocess, including the health check behind `status`, `seed` and `approve`, goes through one runner in `tools/dev-gateway/src/env.ts`. Before spawning it checks that the state folder is the tool's own and either was created by the start in progress or belongs to this checkout's run, by the marker and the run file, whose recorded gateway must still be the live process the tool spawned. Otherwise it reports why and spawns nothing. OpenClaw always runs with the state folder as its working directory, so no `.env` in the caller's directory is read.
- **Environment.** OpenClaw and the scripted provider run with an allowlist: `PATH`, `TMPDIR`, `LANG`, `LC_ALL`, `TZ` and `USER`, plus `HOME` and the dev profile variables. Everything else is dropped, including provider keys, auth tokens, base URLs and `NODE_OPTIONS`. A unit test checks this against a shell that sets them.
- **The scripted model** (`tools/dev-gateway/src/fake-provider.ts`) speaks the OpenAI Chat Completions streaming API on `127.0.0.1:19091`. It is registered as a custom provider:

  ```json
  "models": {
    "mode": "replace",
    "providers": {
      "scripted": {
        "baseUrl": "http://127.0.0.1:19091/v1",
        "api": "openai-completions",
        "apiKey": "scripted-dev-provider",
        "models": [{ "id": "dev-1", "reasoning": true, "input": ["text"], "contextWindow": 128000, "maxTokens": 8192 }]
      }
    }
  },
  "agents": { "defaults": { "model": { "primary": "scripted/dev-1" }, "thinkingDefault": "low" } }
  ```

  `models.mode: "replace"` keeps bundled and discovered providers out. The `apiKey` is a placeholder; the scripted server ignores it. Reasoning is streamed as `reasoning_content` deltas, which the `openai-completions` adapter shows only when thinking is not `off`, so seeded turns use `--thinking low`. Tool calls are standard streamed `tool_calls`. Replies are chosen by the user's prompt and the number of rounds since it, so the same conversation always produces the same output. The gateway prefixes user text with a timestamp, puts a "Conversation info" block before text sent from a client, and appends a runtime line; the planner strips all three before matching. The runtime line (`Runtime: agent=<id> | session=<key> …`) is also how a scenario knows which bot it is answering for. Beyond the seeded scripts, the model plays scenarios selected by directive or phrase (see [Scenarios](#scenarios)). A failing step makes the server answer HTTP 400 instead of streaming.

- **Seeding** goes through the real gateway with `openclaw --dev agent --agent <id> --session-key agent:<id>:<task> --message …`. The command waits for the run's terminal outcome. The seeder requires `status: "ok"`, `summary: "completed"`, no abort, a `stop` stop reason and a final text that matches the script exactly. After each task it reads `chat.history` and checks the number of user turns, that every scripted tool call has a result and none failed, and that the session ends on a completed reply. Any mismatch fails the seed. Task titles are set with `sessions.patch` labels. Every start seeds its new gateway; running `seed` again verifies the existing sessions instead of duplicating them.
- **Seeded examples of the live situations** (`SCENARIO_EXAMPLES` in `seed-data.ts`, run by `examples.ts`) come after the scripted tasks, one at a time, through a paired client named "Clawtrate seed" with `operator.read`, `operator.write`, `operator.approvals` and `operator.questions` and the `tool-events`, `approvals` and `exec-approvals` caps. Its pairing request is approved by id, and its device is removed when the seed ends. It sends each example's prompt with `chat.send`, answers the question with `question.resolve`, resolves the approval with `exec.approval.resolve` (allow once, after checking the command is the scripted one), waits for the run's terminal `chat` event, and requires `final`, the scripted final text, the scripted tool calls in order with the expected number of failed results, an answered question or a command that ran, and for the bot-to-bot example a `status: "ok"` reply whose recipient run ended `final` in `agent:marlow:main`. Marlow's main task is opened by a person first, because a bot may only ask questions in a session a person owns. The seed prints each action it takes as the user. Running `seed` again verifies the examples from history.
- **Bots.** Four invented bots: Juniper (research), Otto (home server operations), Marlow (editing) and Pip (planning). Juniper is the gateway's built-in `main` agent, restyled rather than replaced. Every gateway has one, it is the system and heartbeat agent, and deleting it fights the gateway. Each bot gets its own `AGENTS.md`; the interface draws its avatar as a character. The seeded scripts use only `ls`, `read` and `write` inside each bot's workspace; the scenarios add the question tool, bot-to-bot messages, the coding agent's MCP tools and, for Otto only, the fixed shell commands in [What can run](#what-can-run). The bots are declared in the generated config (`agents.entries`, with `ownership: "explicit"` and each workspace where `agents add` used to put it), so their tool policy is part of the config the guard checks before the gateway first starts; the seed then writes their instructions and identities as before.
- **Sandbox config.** In addition to the provider settings above:
  - `gateway.nodes.pairing.autoApproveLocal: false`: loopback devices are approved like any other, so the pairing flow is exercised for real.
  - `tools.exec.mode: "deny"`: global, so every bot inherits it, including bots created later. Without a policy the gateway resolves `security: "full", ask: "off"`. The mode cannot be combined with `security` or `ask` in the same object; the gateway rejects that.
  - `agents.entries.otto.tools.exec: { mode: "ask" }`: the one exception, the shell bot. It asks a person about every command it has no approved rule for. See [What can run](#what-can-run).
  - `tools.agentToAgent: { enabled: true, allow: ["marlow", "pip"] }`, and per bot `tools.agentToAgent.send`: `["pip"]` for Marlow, `["marlow"]` for Pip, `[]` for Juniper and Otto. The global list requires both ends to match and the per-bot list names the only destination, so Marlow and Pip may message each other and no other bot may message anyone.
  - `mcp.servers.coder`: the stand-in coding agent (`tools/dev-gateway/src/coding-agent-mcp.ts`), run by the gateway as a stdio command: this Node binary, that one script, with the instance's state folder as its working directory, and no URL, headers or environment of its own. It keeps its threads in memory, makes no network request and writes no file. Its links use the reserved `.example` domain. Its tools reach the model as `coder__<tool>`.
  - The question tool, `ask_user`, is in the gateway's default tool set for every bot; nothing in the config removes it. Every bot gets it, since any bot may be asked `#ask`, and Marlow needs it to ask while answering Pip.
  - `tools.fs.workspaceOnly: true`: the file tools (`read`, `write`, `edit`, `ls`, `apply_patch`) refuse paths outside the bot's own workspace.
  - `tools.web.search: { enabled: true, provider: "ollama" }` and `plugins.entries.ollama.config.webSearch.baseUrl: "http://127.0.0.1:<scripted model port>"`: `web_search` uses the bundled Ollama search provider, which for a host that is not `ollama.com` posts `{query, max_results}` to `<baseUrl>/api/experimental/web_search` (and on a 404 to `/api/web_search` on the same host). The scripted model server answers there with three fixed results on the reserved `search.example` domain. The provider would add a hosted fallback only with an `OLLAMA_API_KEY`, which the environment allowlist drops, or with `models.providers.ollama.apiKey`, which cannot exist because `ollama` is not a configured provider. So search is configuration only, with no plugin to install, no credential and nothing past loopback.
  - `tools.web.fetch.enabled: false`: `web_fetch` cannot be restricted to loopback (its SSRF policy only adds private-host exceptions; public hosts stay allowed), so it is off.
  - `tools.allow`, global: the only tools any bot is offered, `read`, `write`, `edit`, `apply_patch`, `ls`, `exec`, `web_search`, `ask_user`, `sessions_send`, `sessions_list`, `progress_card`, `automations` and the stand-in's `coder__*`. A tool the gateway adds in a later version is off until it is listed here.
  - `tools.deny`, global, so that no change to the allowlist can bring them back: `gateway`, `plugins` and `openclaw` (self-management: they can update the shared installation, or search and install from outside, whatever the exec policy says), `web_fetch`, `x_search`, `code_execution`, `tts`, `image_generate`, `music_generate`, `video_generate` (reach hosted services), `browser`, `canvas`, `screen`, `computer` (drive a browser or a screen), `nodes`, `mobile_ui`, `node_inference`, `dir_fetch`, `dir_list`, `file_fetch`, `file_write` (act on a paired device), `message`, `conversations_send`, `conversations_turn` (send through a chat channel), `github_publish`, and `skills_read`, `skills_search`, `skill_workshop` (not needed; `skills_read` is offered outside the allowlist unless denied). A deny wins over the allowlist.
  - `cron: { enabled: false, triggers: { enabled: false } }`: a routine can be created and removed, but the scheduler never runs one, so no job can run a turn, a script or a delivery (webhooks included). Scheduled heartbeats stop with it ("scheduled heartbeats are disabled because the cron scheduler is disabled" in the gateway log); a wake that is not scheduled still runs a turn (see [What the scenario check observed](#what-the-scenario-check-observed)).
  - `session: { notifyOnCreate: false }`: no "Recent session creations" notice is queued in a bot's main task each time a task is created, so a turn the gateway starts there has nothing of the kind to carry. No config key turns the unscheduled wakes themselves off (only the runtime `set-heartbeats` method does), so the scripted model answers the turns the gateway writes itself with `NO_REPLY` (the prompts are listed in `GATEWAY_TURN_PROMPTS` in `scripts.ts`).
  - `tools.toolSearch: false`: tools are offered directly rather than behind `tool_search` and `tool_call` wrappers. The seeded tools were already offered directly, but later flows such as bot-to-bot messages need it.
  - `memory.search: { enabled: false, provider: "none" }`: memory search sits outside `models` and defaults to hosted embeddings.
  - `discovery.mdns.mode: "off"`, `update.checkOnStart: false` and the memory plugin's dreaming job off.
  - `proxy.proxyUrl: "http://127.0.0.1:<scripted model port>"`: the gateway's own egress proxy setting, so that everything the gateway fetches from beyond loopback goes to the scripted model, which answers a tunnel request with 403 and any other proxied request with a 403 body, and logs each as "refused a request beyond loopback" with its host. Loopback still connects directly (the proxy's default `loopbackMode: "gateway-only"`). Without it an instance is not confined to loopback: on start the gateway asks `catalog.openclaw.ai`, and `plugins.list`, every `plugins.catalog.*` method, `plugins.search`, `skills.search` and `plugins.install` ask `clawhub.ai` ([connectors research](research/connectors.md), section 1).
- **Enforcement: one closed contract.** `sandboxProblems` (`cli.ts`, with the comparison in `contract.ts`) holds the whole development config: exactly what `devConfig` generates for this instance's ports and folder, with any token, plus the identity fields and the `meta` stamp the CLI writes while seeding, and nothing else. Every key the contract does not name is refused with its path ("env is not allowed"), every value that differs is refused with what it must be, and every required key that is missing is refused. So an outside workspace, a real model, primary or fallback, weaker gateway auth, automatic pairing, importing the login shell's environment, another plugin entry or any unknown key all stop `start` before the gateway is spawned; a unit test refuses each, and one more for an unknown key. `start` checks the generated file; `seed` checks it again after configuring the bots, since the CLI rewrites it. `start` and `seed` also read the gateway's effective exec policy with `openclaw approvals get` and fail unless every bot's effective exec security is `deny`, except Otto's, which must be `ask`: security `allowlist`, ask `on-miss`, fallback `deny`.
- **The one opening: the project's own plugins.** A named instance may be started with `--with-plugin <name>`, repeatable (`tools/dev-gateway/src/dev-plugins.ts`).
  - **Trusted code.** A plugin loaded this way is trusted code. It runs inside the gateway with that user's full access to files, processes and the network. The guard constrains the gateway's configuration and the tools bots are given, not what plugin code does: a plugin can import Node's file, process and network modules directly, and no tool policy applies to that. Load only plugins from this repository that you have read. `start` prints this, with the plugin's digest, every time it loads a plugin.
  - **Location, held until load.** The plugin's real path must be a direct child, by exactly the requested name as stored, of the real path of the starting checkout's own `plugins/`. Neither folder may be a link, and nothing inside the plugin may be anything but files and folders. A `plugins/` that links elsewhere is refused, and so is a folder whose stored name differs only in case. The folder is read whole into memory when it is checked. That snapshot is written into the instance's state folder (`clawtrate-plugins/<name>`), checked against its digest, and is the only path in `plugins.load.paths`. A package entry outside the folder is refused. The names and digests are recorded beside the run file (`plugins.json`), and `seed` checks the copy against them again. So replacing the checked folder after the check changes nothing that runs. A unit test ports the reviewer's swap (the folder replaced by a link to other code after the check), and a live run of it on a named instance loaded the checked copy, never ran the replacement, and refused a copy altered afterwards at `seed`.
  - **A closed addition.** Beside its manifest, `clawtrate-dev-contract.json` is `{plugin: <the manifest's id>, settings: {<key>: {kind, value}}, tools: [{name, kind: "plugin-tool"}]}`, and nothing else.
    - Setting kinds are `flag` (true or false), `count` (a whole number), `loopback-url`, `instance-path` and `scripted-model-url`.
    - A `loopback-url` is parsed and must use http, https, ws or wss, with a literal loopback host (`127.x.x.x` or `[::1]`), no credentials, and the exact form the parser writes back, so `http:example.com`, `localhost` and `http://2130706433/` are refused.
    - An `instance-path` is up to eight plain names. It is given to the plugin resolved inside the instance's state folder (`clawtrate-plugin-data/<name>/…`), so `..`, absolute paths, `~` and `${…}` cannot be written.
    - No kind exists for free text, a command, an argument list, a credential or a model provider. Any unknown key or kind is refused, and so is a tool the gateway itself provides (`GATEWAY_TOOLS`, which the scenario check compares with the live `tools.catalog`).
    - The config entry the instance writes is `{enabled: true, config: {<key>: <value>}}`, the tools are added to `tools.allow`, and the closed contract includes exactly those. Unit tests refuse each of the reviewer's alternate forms (`{"url":"http:example.com"}`, `{"path":"../../outside"}`, `{"path":"../../.openclaw-other/agents"}`, `{"host":"example.com","port":443,"tls":true}`, `{"source":"${OPENAI_API_KEY}"}`, `{"run":"printf review"}`, `{"model_provider":"openai"}`), written raw and under every kind. A plain name such as `example.com` or `openai` is accepted only as an `instance-path`, where it is a file inside the instance.
  - **Order.** The contract is compared before `openclaw config validate`, which loads plugins, so nothing at all runs before a refusal.
  - **Sign-ins in a manifest.** A plugin's manifest may declare providers and sign-in methods (`providers`, `providerAuthChoices`, `setup.providers`) only for the scripted account providers, and the instance must be started with `--with-accounts`; `providerAuthAliases`, `modelCatalog` and `providerEndpoints` are refused. The setting kind `scripted-model-url` (a plain absolute path, given to the plugin as that path on the instance's own scripted model) is how such a plugin reaches the scripted side without knowing the ports a start chooses.
  - The default instance never loads a plugin, and `pnpm e2e`'s instances load none. Unit tests use a fixture plugin under `tools/dev-gateway/test/fixtures/plugins/` that registers no tool.
  - **Browsers of their own (`botBrowsers`).** The computer plugin needs the gateway's managed browser, and `browser` is otherwise denied here. So one plugin of an instance may add `botBrowsers: {bots, drainTimeoutMs, renewTimeoutMs}` to its addition: seeded bots only, each once, at most four; a drain of 2000, 5000 or 15000 ms and a renewal of 6000, 10000 or 20000 ms. Nothing else about the browser is the plugin's to choose. The tool writes the setup (`browserConfig` in `cli.ts`): `browser` allowed globally and denied per bot to every other seeded bot; one managed, headless profile per bot, on ports of the instance's own block (the scripted pages one above the scripted model, the profiles from the twelfth port on); Playwright's Chromium; `evaluateEnabled: false`, `allowSystemProfileImport: false`; and the plugin's `bots` map pointing at those ports on 127.0.0.1. The contract includes exactly that, so the guard refuses any other browser setting (`tools/dev-gateway/test/computer.test.ts`).
  - **Confined to loopback.** The gateway's configuration cannot allow only one origin: `browser.ssrfPolicy` can allow named hosts and private networks, not deny the public internet. So it does what it can (`allowedHostnames: ["127.0.0.1"]` and the strict policy for everything else: no private, link-local or special-use address, no hostname it cannot pin), and the tool does the rest with Chromium switches in `browser.extraArgs`: `--host-rules=MAP * 127.0.0.1:<pages port>` sends every connection, to any host, address or port, to the instance's scripted pages, which serve only their own origin; WebRTC may not send UDP around it. A proxy switch was not used: with one, the gateway refuses navigation unless private networks are allowed outright. A real-Chromium test and the computer checks in `pnpm scenarios` show an outside address and another loopback port refused.
- **Scripted provider accounts** (`--with-accounts`, named instances only; `tools/dev-gateway/src/accounts.ts`, explained in `tools/dev-gateway/README.md`). Two more providers, `acme` and `globex`, on the instance's scripted model with no key in their entries; four accounts saved before the gateway first starts by the gateway's own `models auth paste-api-key` and `paste-token`, their made-up credentials on stdin; labels in `auth.profiles.<id>.displayName`; and `logging.file` inside the instance so `logs.tail` serves only its log. The contract then holds `models.providers.acme` and `.globex` exactly, `logging` exactly, and `auth` as `profiles` (each entry a scripted account id with `provider`, `mode` `api_key`, `token` or `oauth`, and optionally a one-line `displayName` and `email`) and an optional `order` of scripted account ids: matchers, because the gateway itself writes these when a person signs in or labels an account, but closed ones. A credential names its account (`clawtrate-dev-key.acme.work`), which is how the scripted model records which account a request came from; it refuses a request with no credential with 401, as a real provider does. `lock` and `unlock` run `openclaw models auth order set|clear` on a named instance this checkout started, and before running anything refuse unless every account store the instance's current config names (every `agentDir`, the bot's own store and the shared one) is inside its state folder through no link; Clawtrate itself never does. The development sign-in plugin registers nothing outside a named instance the tool started (its marker names the gateway's process, and the plugin's code lies in its state folder), checks every request's address as loopback when it is made, and never follows a redirect. The development sign-in plugin (`plugins/clawtrate-dev-signin`) sets `setup.requiresRuntime: false`: without it the gateway treats `acme` as a provider with a key-less direct route and, after a locked bot's only account failed, sent one more request with no credential at all.
- **Processes.** `start` writes its run file, `tools/dev-gateway/.run/state.json` for the default instance and `tools/dev-gateway/.run/instances/<name>/state.json` for a named one, git-ignored, next to the logs and the connection file. `stop` sends SIGTERM to the proven processes, waits up to 15 seconds, then sends SIGKILL, and does the same for any proven direct child the gateway left behind. Nothing is ever stopped by name.
- **Housekeeping.** `list` finds instances from their state folders under the home (`~/.openclaw-dev` and `~/.openclaw-clawtrate-dev-*` with the tool's marker) and shows each folder, its ports, whether its gateway is running and which checkout started it. `prune` is deliberate machine-wide maintenance: it removes every named instance, whichever checkout created it, that the deletion rule proves idle, each under its lifecycle lock with the marker read again after the lock is taken, plus this checkout's run folder for it. It never removes the default instance. `list` and `prune` refuse `--instance` and `CLAWTRATE_DEV_INSTANCE` rather than ignore them, and every command validates the selector before it does anything.
- **End-to-end runs use their own instances.** `pnpm e2e` names one instance `e2e-<run id>` and a sentinel `e2e-<run id>-other`, and gives each a dev-gateway run id of its own (`start --run-id`). It starts the sentinel unseeded (`start --no-seed`), so another instance's gateway is always listening, then its own seeded instance, builds the web renderer into a temporary folder and starts a preview host on a system-chosen port. It checks it never uses 19001, 19091, 5310 or 5311, and that the default instance and its sentinel are still running with the same PIDs and ports; another named instance belongs to other work on the machine, and one that stops or restarts during the run is printed as a note, as the packaged check does. It keeps a run record in `tools/dev-gateway/.run/e2e/`: the runner's identity, each instance with its run id (written before that instance's `start`), each temporary folder (written as it is created) and the preview host, which is written as pending before it is spawned behind a gate and completed with its PID and start time before the gate opens (`e2e/run-record.ts`). Cleanup removes exactly those, resetting each instance with `--run-id`, and never runs `prune`. The host's folders are removed only once the host is proven to have exited. Cleanup runs from the teardown, from a setup failure, on SIGINT and SIGTERM and at process exit, synchronously, after letting an interrupted dev-gateway command exit. A run killed outright leaves its record, and the next run in the same checkout cleans it up once that run's runner has exited. If the runner or the host is alive or unknown, the record and the folders stay and the reason is printed. Each run also has its own Playwright output folder, so runs in one checkout do not delete each other's traces.
- **What the tool trusts.** It trusts its own local records, written by the same user account: the state folder's marker, this checkout's run file and connection file, and the e2e run records. A recorded start time protects against a PID the system has given to another process since. It does not prove which program started a process: someone who can rewrite the marker can point it at any process of theirs whose PID and start time they read from `ps`, and `stop` would signal it. The tool does not defend against that, since such a writer could signal the process directly. It does defend against stale and mismatched records: a run file alone, or a run file and a connection file that agree, never authorise a signal, a deletion or a token-free connection. The state folder, its marker, the run file and the lock folder are never read through a link, and neither is the connection file when an endpoint is proven.
- **Ports.** Default instance: gateway 19001, scripted model 19091. Named instances: 19200 to 19999, chosen at start. Web previews 5310 and 5311. The e2e preview host uses a port the system picks (loopback only). The fixture mode serves on 5341 (loopback only), or on `CLAWTRATE_FIXTURE_PORT` when another checkout's visual run holds 5341. The packaged app in the launch check opens its DevTools port on a loopback port the system picks.

### Scenarios

- **Selection.** `tools/dev-gateway/src/scenarios.ts` holds every scenario once: its directive, its phrase, a summary and its steps. The README's table is the same list. A message's known `#directives` run in order; without one, the longest phrase the message contains selects a scenario. Seeded prompts are matched first and exactly, so the scripted tasks are unchanged. A scenario is a list of steps; a model call ends after each tool call, and text before the next tool call goes into the call that leads to it, which is how directives compose. Steps after a tool call can read its result (the answers to a question, the coding agent's link, the other bot's reply), so the final text says what really happened.
- **Determinism.** Replies depend only on the conversation. Tool call ids are a hash of the session, the user turn and the round, so they are stable and do not repeat within a session. Slow steps set their own pace (250 ms per piece).
- **Why the slow tool is an MCP call.** It works for every bot without a shell. Otto has `#sleep` for a slow shell command.
- **Bot-to-bot.** A message names only `agentId`, so the gateway delivers it to the other bot's main session (`agent:<id>:main`) and creates it if needed. The message text carries a directive for the recipient (`#reply`, `#slow 15`, `#model-error`, `#ask`), so the recipient's run is scripted too. A reply that arrives later starts a new run in the sender's task, and the scripted model answers it with one line.
- **The scenario check** (`tools/dev-gateway/src/scenario-check.ts`) uses three paired clients, each with the scopes its checks need: read and write; read, write and `operator.approvals` with the `approvals` and `exec-approvals` caps; read, write and `operator.questions`. All advertise `tool-events`. Every chat and agent event of every run it drives is validated against `ChatEventSchema` or `AgentEventSchema` from `@openclaw/gateway-protocol`, and question and session approval events against theirs; top-level fields the published schemas do not declare are set aside and listed. `pnpm scenarios` runs it on an unseeded instance named `e2e-<run>`, recorded in the end-to-end run records before it starts, so an interrupted run is cleaned up like an interrupted `pnpm e2e`. In `pnpm e2e` it runs as `e2e/scenarios.spec.ts`, after the preview tests, on the run's seeded instance. The `#approve` check resolves with allow always and then checks that the rule is reused, which changes only that instance. Every run a check starts or sees has every tool call asserted in order with `RunView.expectCalls` (exact arguments, taken from the scenario definitions; the result's error flag, text and details, exactly or, for a value that varies such as a duration, an id or the home folder, by a check of that value; the item's title and end status) and its end asserted with `expectEnd` (terminal state and final text). `runCheck` collects every run that appeared on any client while the check ran and fails the check if any of them was left without both, so a call without an expectation cannot pass. Every task a check opens or submits to is recorded before the request goes out. When a check fails, for any reason including a run left unasserted, those tasks, every task that had a run event during it and the messaging pair's shared main tasks are drained: their runs aborted, and the gateway's history read, every 200 ms, until nothing has been in flight or waiting in any of them for a second and a half without a break. A send the gateway admits after a first idle reading (its request failed here, and the gateway took it later) is seen, stopped, and the quiet period starts again. If a task is still busy at the deadline, the next check does not start; it fails, naming the failed check and the tasks. Files a call wrote are read back with `agents.workspace.get`. To test the checks themselves, each one was recorded on a live gateway, replayed offline against the recording, and replayed again with one received payload altered at a time (arguments erased or changed, results, texts or details replaced, removed or changed key by key, error flags flipped, item titles and statuses, end states and final texts changed): 696 altered payloads across all 43 checks that make runs, and every one failed its check. The plain client also calls `sessions.subscribe`, so it receives `session.tool` for runs it did not start, such as the owner runs started through the CLI. A last check fails if any directive has no check that sends it.

### What can run

Only one bot, Otto (`SHELL_BOT`), may run shell commands, and only after a person approves each one. For every other bot, and every bot created later, exec is denied by the global policy, and the gateway refuses the call ("exec denied: host=gateway security=deny") without asking anyone.

Otto's policy is `mode: "ask"`, which the gateway resolves to security `allowlist`, ask `on-miss`, ask fallback `deny`. Otto's allowlist starts empty, so every command asks. An approval request reaches only a connection with `operator.approvals` and the approval caps; with none connected, or when the request expires, the fallback denies it. "Allow always" adds an allowlist entry bound to Otto, the exact arguments and the working directory, in the instance's own state database. After that the same command in the same folder runs without asking, until the instance is started over (every start deletes the state). A command run with per-call `ask: "always"` cannot be allowed always.

The gateway's config cannot both ask before every command and restrict Otto to a list of commands. Its allowlist mode runs listed commands without asking, and its ask mode runs any command a person approves. The task forbids a mode that runs commands without asking, so the restriction is in the scripted model: it only ever asks Otto to run these commands, built in `SHELL_COMMANDS` with no text taken from the message:

| Command                   | Scenario                       | Notes                             |
| ------------------------- | ------------------------------ | --------------------------------- |
| `ls`                      | `#approve`, the seeded example | lists Otto's workspace            |
| `echo 'Hello from Otto.'` | `#approve-once`                | per-call `ask: "always"`          |
| `ls missing-folder`       | `#exit-code`                   | exits 1 (BSD `ls`) or 2 (GNU)     |
| `sleep 5`                 | `#exec-timeout`                | with `timeoutSeconds: 1`          |
| `sleep N`                 | `#sleep N`                     | N is a whole number from 1 to 120 |

Each runs with `workdir: "."`, which is Otto's workspace inside the instance's state folder (`workspaces/otto`). They print text, list a folder or wait; none writes, deletes, reaches the network or reads outside the workspace. The gateway runs with the tool's environment allowlist, so the commands see no keys or tokens. A unit test checks that no scenario can emit any other command.

Beyond the shell, nothing a bot is offered reaches past the machine or the instance: only the tools in `tools.allow` are offered; file tools are confined to the bot's workspace inside the instance's folder; web search is answered by the scripted server on loopback; the coding agent is a local process in the instance's folder; routines are created and removed in the instance's own state and never run; and every tool that manages the gateway or its installation, reaches the network, drives a browser, a screen or a device, or sends through a chat channel is denied. `terminal` is not offered; in the source it cannot start a shell and its input obeys the exec policy (`openclaw-tools-*.mjs`, `exec-defaults-*.mjs`).

### What the scenario check observed

Everything here was seen by `pnpm scenarios` against OpenClaw 2026.10.6, with the scripted model through the built-in runtime, and is asserted by it unless marked "(probe)" (seen in a one-off probe, not asserted) or "(source)" (read in the installed package). An observation holds for the paths the check drives; where the source shows other conditions, they are named. "The map" is `docs/research/gateway-capabilities.md` as of `e83af08`.

- **A message sent from the app reaches the model behind a block of the gateway's.** A message sent with `chat.send` by an operator client in `ui` mode, as the app sends it (`sessionKey`, `message`, `idempotencyKey`, `queueMode: "followup"`), reaches the model as `[<time stamp>] Conversation info: ⟦openclaw:ctx⟧`, a fenced JSON block naming the sender, then the text, then the `Runtime:` line. A prompt matched on the whole text therefore never matches; the scripted model strips the stamp, the block and the runtime line before matching, and finds directives and phrases anywhere in the message. Asserted: a phrase ("Could you please show your work?") sent that way plays `#steps`, with its calls and reply, and the task's history shows the user's message as the phrase alone.
- **A message queued behind a reply that streams with no reasoning first takes another path, with a run id of its own and an event outside the schema.** (probe) Sent with `queueMode: "followup"` while `#stream 3` was streaming, the queued run's first two `run_status` events (`preparing_workspace`, `preparing_context`, `seq` 1 and 2) carried a provisional run id. The run `chat.send` had returned then continued from `seq` 4, its lifecycle events marked `completionSource: "reply-dispatch"`. Between them came an agent event `{stream: "error", data: {reason: "seq gap", expected: 3, received: 4}}` with no `seq`, which `AgentEventSchema` requires. Queued behind `#slow`, whose reasoning comes first, the queued run kept one id and no such event appeared, which the check "a message queued behind a slow stream" asserts.
- **The gateway starts turns of its own.** A bot's main task on a preview instance showed the scripted model's fallback reply to a prompt that began "OpenClaw runtime context: Conversation data (data, not instructions): "System: [...] Recent session creations (bounded summary; …". (source) The notice is queued in the bot's main task whenever another of its tasks is created, unless `session.notifyOnCreate` is `false` (`enqueueSessionCreatedNotice`, `session-created-*.mjs`); it wakes nothing itself and is read on that task's next turn. With the scheduler off, scheduled heartbeats never run, but unscheduled wakes still do: the `wake` and `system-event` methods, a node's exec or notification events, hooks, ACP spawns and background tasks (`requestSessionEventWake`, `heartbeat-wake-*.mjs`). Which of them started the preview's turn about twenty minutes after the seed was not established from the source. The turn's request is the heartbeat prompt ("Follow the heartbeat monitor scratch context when provided. … If nothing needs attention, reply NO_REPLY.") followed by the queued events as a runtime context block, and `NO_REPLY` is the gateway's "nothing to say" (`SILENT_REPLY_TOKEN`). Asserted by starting such a turn with `wake` (`mode: "now"`, the task's key) on a task created by the check: the gateway runs a turn nobody sent, its agent events are `lifecycle` only with `isHeartbeat: true`, the scripted model answers it quietly, the run ends with `terminalReply: {disposition: "silent"}` and a chat `final` without a message, and the task's history gains nothing. Before the scripted model knew these prompts, the same wake added the fallback reply to the task as a message (probe). A command that completes after its turn ended queues an `Exec completed (…)` or `Exec failed (…)` event, and the turn the gateway then starts has a prompt of its own: "An async command you ran earlier has completed. The command completion details are: … If no user-facing update is needed, reply NO_REPLY only." (`buildExecEventPrompt`, `heartbeat-events-filter-*.mjs`; with delivery off, "An async command completion event was triggered, but user delivery is disabled…"). Asserted the same way, with a wake carrying such an event, its output naming a scenario's phrase or not: the scripted server records that it saw the completion prompt, answers `NO_REPLY` without playing the scenario, and the turn ends as above. (source) A scheduled event's prompt is "A scheduled cron event was triggered, but no event content was found…" (answered `NO_REPLY`) or "A scheduled reminder has been triggered…", which asks to relay the reminder to the user and is answered with it; the scheduler is off here, so neither runs.
- **Which continuations after a bot's message are meant to be seen.** Not every turn that follows a bot's message without a person's new message is silenced. Another bot's reply that arrives later in the task (`#message-slow`) comes as an inter-session runtime block, also when the gateway starts the turn for it, and the scripted model acknowledges it ("Marlow's reply arrived. It is shown above."); asserted by "a message to a slow bot". The gateway's own request for a visible answer after a reply with reasoning and no text continues the same run (`#think-only`). A steered or queued message is a person's message. A reminder the gateway asks to relay would be relayed. Every other turn the gateway starts with one of the prompts above is answered `NO_REPLY`. A trusted plugin or a hook can start a turn with a prompt of its own; the scripted model does not recognize it, and it gets the fallback reply.
- **Agent events carry fields their published schema does not declare.** `AgentEventSchema` is closed (`additionalProperties: false`) with `runId`, `seq`, `stream`, `ts`, `spawnedBy`, `isHeartbeat` and `data`. Every agent event on the wire also has `sessionKey` and `agentId`; `lifecycle` events add `sessionId` and `lane`; `tool` events add the whole session row (`session`, `label`, `owner`, `createdActor`, `participants`, `unread`, token counts and about sixty more). A strict schema check rejects real events, so a client must ignore unknown top-level fields. The map lists `sessionKey`, `agentId` and `sessionId` and the session snapshot, but not that the schema rejects them. With those fields set aside, every chat, agent, question and session approval event matched its schema.
- **Assistant stream: snapshots and deltas.** Each `assistant` event carries `delta`, and some also carry `text`, the whole text so far. In the append-only streams the check drives, only the first event of a message carried `text`; later ones carried only `delta` and `itemId`. The map gives `{text, delta, itemId}` for every event. In the source (`assistantWireProjection`, `server-chat-*.mjs`) an event is sent as a full snapshot whenever it replaces the text (`replace: true`), has an empty or missing `delta`, or carries media, so later snapshots do occur. A client must treat an event with `text` as a snapshot that replaces what it has and append `delta` otherwise; the check rebuilds the text by that rule.
- **Text beside a tool call.** Text the model writes in the same message as a tool call does not appear on the `assistant` stream. It arrives as `agent stream:"item"` with `kind: "preamble"`, `title: "Preamble"`, phases `update` and `end`, and the text in `progressText`. Two reasoning pieces in one message arrive as one `thinking` text joined by a newline. The map does not mention either.
- **A reply with reasoning and no text.** The gateway does not end the run. It adds a user turn ("The previous assistant turn recorded reasoning but did not produce a user-visible answer. Continue from that partial turn…") and asks the model again, twice, in the same run (three `lifecycle start` events). If no text comes, it emits `lifecycle phase:"fallback_step"`, then `lifecycle phase:"error"` with `terminalReply.disposition: "empty"`, and `chat state:"error"`, `errorMessage: "⚠️ Agent couldn't generate a response. Please try again."`. The map does not describe this, and its list of lifecycle phases has no `fallback_step`.
- **A model error** (HTTP 400 from the provider): `lifecycle phase:"finishing"` with `error` and `errorObservation {provider, model, failoverReason: "format", providerRuntimeFailureKind: "schema"}`, `lifecycle phase:"fallback_step"` (`fallbackStepFinalOutcome: "chain_exhausted"`), `lifecycle phase:"error"`, then `chat state:"error"` with `errorMessage` ("LLM request rejected: …") and `errorDetail` with the same four fields, and no `errorKind`. History keeps an assistant row with `stopReason: "error"` and the error text.
- **History tool results do not always keep `details`.** `chat.history` `toolResult` rows carry `toolCallId`, `toolName`, `content`, `isError`, `timestamp` and `__openclaw`; `details` is kept for some tools and not others (the family table below says which). The map says rows carry `details`. A card rebuilt from history may have only the text and the error flag.
- **Who receives a run's tool payloads.** The client that sent the message receives `agent stream:"tool"` events with the arguments and the result. A client that has called `sessions.subscribe` receives the same payloads as `session.tool` events, for runs it did not start, including runs started by the CLI; in the source they go to session-event subscribers other than the run's own tool recipients, for runs shown in the control UI (`server-chat-*.mjs`). A client subscribed only with `sessions.messages.subscribe` receives the run's `item` events (title, status, `toolCallId`) and neither `agent` tool events nor `session.tool`. All three are asserted, with the arguments and result compared between the sender and the `session.tool` subscriber. The map mentions none of this. (An earlier version of this note said a non-sending client could not receive tool payloads at all; that was only the messages-only case.)
- **An unfinished plan makes the gateway continue.** A `progress_card` whose plan still has pending steps makes the gateway add a user turn ("This run’s latest successfully saved plan still has unfinished steps…") and ask the model again before the run ends (from a probe). `#plan` therefore sends a finished plan.
- **A queued turn's numbering.** For a turn it runs from its queue the gateway sends an `agent` event on stream `error`, `data: {reason: "seq gap", expected, received}`, without the `seq` its schema requires: its own note of a gap in the run's numbering across its two run ids. The check sets it aside and reports it only for a run it saw the gateway pair with an id of its own; anywhere else it fails the schema check.
- **Stopping.** `chat.abort {sessionKey}` returns `{ok: true, aborted: true, runIds: [runId]}`; the run ends `chat state:"aborted"`, `stopReason: "rpc"`, with the partial text in `message`, and `lifecycle end {status: "cancelled", aborted: true, stopReason: "rpc"}`, as the map says. Not in the map: history keeps the partial reply as an assistant row with `stopReason: "stop"`, so it looks finished there (note, from a probe). A stopped MCP call's `tool result` (`isError: true`, text "Aborted", empty `details`) arrives after the run's `chat aborted` and `lifecycle end` events.
- **Queue and steer**, as the map's row 19 says. `queueMode: "followup"` during a stream: the second message gets its own run, which starts after the first ends. `queueMode: "steer"` during a tool call: the steer's own run ends at once with a `chat final` that has no `message`; the tool finishes, and the steered message is answered inside the active run, whose history gains the user row between the tool result and the reply. The earlier abort the map warns about did not happen.
- **MCP results.** When the server returns `structuredContent`, the gateway puts a rendering of it first in the result, `"structuredContent:\n{…}"` with its keys sorted, and keeps the server's own text blocks after it, dropping only a text that repeats the structured content (`mcp-content-*.mjs`). The check asserts both: `send_message` returns a sentence of its own and the result holds the rendering then that sentence; `slow_task` repeats its structured content as text and the result holds the rendering only. `details` is `{mcpServer, mcpTool, structuredContent}`. An MCP error result is `isError: true` with the server's text and `details {mcpServer, mcpTool, status: "error"}`. A slow call sends nothing between `tool start` and `tool result`, as the map says.
- **Long output**, as the map says: the live result text is cut to 8014 characters ending "…(truncated)…"; the history row holds 8000 with `__openclaw {truncated: true, reason: "display-cap"}`; `chat.history {maxChars}` returns more (31 988 characters in a probe).
- **Exec approvals**, checked against the gateway source (`exec-approval-*.mjs`, `exec-approvals-policy-*.mjs`, `bash-tools-*.mjs`). `exec.approval.requested` is `{approvalKind: "exec", id, request, createdAtMs, expiresAtMs}` with `request {command, cwd, host: "gateway", security, ask, commandAnalysis {commandCount, nestedCommandCount, riskKinds, warningLines}, allowedDecisions, agentId, resolvedPath, sessionKey, runId, toolCallId, turnSourceChannel, …}`. The run shows `lifecycle waiting-approval {approvalId, toolCallId}` and `approval-resolved`. `session.approval` arrives with `phase: "pending"` and `"terminal"`, `sourceSessionKey`, and `approval.presentation.allowedDecisions`. `exec.approval.resolve` returns `{ok: true}`, and `exec.approval.resolved {id, decision, resolvedBy, request}` follows. Not in the map: which decisions are offered. An ordinary miss under `ask: "on-miss"` offers `allow-once`, `allow-always` and `deny`. A call with per-call `ask: "always"` offers only `allow-once` and `deny`, lists `unavailableDecisions: ["allow-always"]`, and `allow-always` is refused with `details.reason: "APPROVAL_ALLOW_ALWAYS_UNAVAILABLE"`. The source also makes it one-shot for commands with no reusable pattern and for mutable script files. After `allow-always` the same command in the same session runs with no request. A denial by the user is a tool result with `isError: true`, `details.status: "failed"` and the text "Exec denied (gateway id=…, user-denied): <command>", and an `agent stream:"approval"` event `{phase: "resolved", kind: "exec", status: "denied", title, itemId: "command:<toolCallId>", toolCallId, message}` (from a probe; the map lists that stream as not seen live).
- **Exec results**, as the map says: a non-zero exit is `isError: false`, `details {status: "completed", exitCode: 1, exitReason: "exit"}`, text ending "(Command exited with code 1)", and `command_output` with `phase: "end"` and `exitCode`; a command past its own limit is `isError: true` with `details {status: "failed", timedOut: true, failureKind: "overall-timeout"}`.
- **Questions**, as the map says: `question.requested` carries `id`, `questions` (each with `isOther: true`), `agentId`, `sessionKey`, `runId`, times and `status: "pending"`; `question.resolve {id, answers: {answers}}` returns `{status: "answered", answers}`; `question.resolved {id, status: "answered", answers}` follows; the tool's result `details` is `{status: "answered", answers: {answers: …}}` and its text starts with one "Header: answer" line per question before the JSON. A client with only `operator.read` and `operator.write` received no question event.
- **Bot-to-bot.** Not in the map: `sessions_send` with `label` only finds an existing session with that label ("No session found with label: …"), and with a `sessionKey` only an existing session ("No session found: …"); with `agentId` alone it uses that bot's main session, `agent:<id>:main`, and creates it. A send outside the per-bot list is `isError: true`, `status: "forbidden"`, "Agent-to-agent messaging denied by the requester agent tools.agentToAgent.send allowlist." A send answered in time is `{status: "ok", runId, sessionKey, delivery: {status: "skipped"}, reply}`; the recipient's run streams on the same connection under that `runId` and ends before the sender's tool result. A slow recipient gives `{status: "accepted", targetDisposition: "queued", delivery: {status: "pending"}}`; its reply later starts a new run in the sender's task, whose request carries a runtime context block "[Inter-session message] sourceSession=agent:marlow:main sourceTool=sessions_send isUser=false", and history gains an assistant row with `provenance {kind: "inter_session", sourceTool: "sessions_send", sourceSessionKey}`. A recipient whose run fails gives `isError: true`, `status: "error"`, `sentBeforeError: true`, and an `error` with the recipient's error text; the map shows `error: "agent error"` for a stopped recipient.
- **A recipient's question needs an owned, materialized session.** In the source (`question-*.mjs`), a bot's `ask_user` needs own-run access to a materialized ordinary session. A main session the gateway created for `sessions_send` is not one: there the recipient's `ask_user` fails at once with "Session-scoped questions require your own materialized ordinary session." and the recipient goes on without an answer (probe; the check prepares the session first and asserts only the successful side). A person's `chat.send` in that session is the way the check and the seed establish it; then the recipient's `question.requested` arrives with the recipient's `sessionKey`, `agentId` and `runId`, the sender's call returns `accepted` while it waits, and after the answer the reply arrives as a late reply. The map shows the question arriving with no such condition.
- **`chat.history` shows a bot's message to the recipient as an assistant row.** That is the history's display projection: the gateway builds the recipient's input as a user message, and `chat.history` shows it in the recipient's session as a row with `role: "assistant"`, plain-string `content` (the message text) and `provenance {kind: "inter_session", sourceSessionKey: <sender's task>, sourceChannel, sourceTool: "sessions_send"}`, not as a user turn. The map says the incoming turn is a user message, which is true of the input but not of what `chat.history` returns, and the app reads `chat.history`. The projection is asserted (role, provenance kind, `sourceTool`, sender and the exact message), and checked again whenever the seed is verified.
- **`sessions_list` shortens keys in `details`.** The result's `details.sessions[].key` is shortened for display (`agent:…3540`); the result's text JSON keeps the whole key.
- **Routines.** `automations` `add` returns the whole job (id, owner, schedule, payload, state, `configRevision`, `deliveryPreview`); `remove` returns `details {ok: true, removed: true}` live.
- **`chat.send` to a new key** of the form `agent:<id>:<name>` creates the session; the seed relies on this.

## Brand

- `assets/brand/logo.png` is the only hand-placed brand file. `pnpm brand:icons` (`tools/brand/src/make-icons.ts`) derives everything else from it with a small PNG codec, so no native image dependency is needed. The outputs are the Electron icons (`apps/desktop/resources/icon.png`, `icon-mac.png`, `icon.icns`, `icon.ico`), the favicons, and the in-app mark (`packages/ui/src/assets/logo-mark.png`). `assets/brand/generated.json` records the logo's hash, and a unit test fails when the icons are older than the logo.
- The logo must not carry provenance, text or camera metadata (`caBX`, `tEXt`, `iTXt`, `zTXt`, `eXIf` chunks). `pnpm brand:strip` removes them in place and copies every other chunk byte for byte, so the pixels do not change. `pnpm brand:icons` refuses a logo that still has them, and a unit test checks the committed file.
- Accent tokens come from the mark's mint. Dark theme: `--accent` `#3ee6c1`, hover `#6cf0d3`, text on accent `#04261f`. Light theme, where the raw mint is only 1.6:1 on white: `--accent` `#0a6e5c` (6.2:1 on white), hover `#06624f`, indicator line `#0d8f77` (above the 3:1 minimum for non-text).
- **Palette.** The chrome is neutral grey with no tint (`docs/design/visual-language.md`, section 2): two surfaces, the rail and the stage, and one raised fill for bubbles and cards. Selection and primary buttons are neutral too. The accent appears only on your own bubbles (`--bubble-user`, its own token so it can later be switched to neutral), on unread dots, on a working mark, on focus rings and on links. Colour otherwise belongs to the bots' avatars.
- **Avatars.** A bot without a picture is drawn as a character, a flat body and colour with a dark visor, chosen from a stable hash of its id (`packages/ui/src/Avatar.tsx`), so it looks the same on every device. A bot whose gateway identity has a picture shows the picture cropped to a circle. The development gateway no longer generates pattern pictures for its seed bots, so the preview shows characters.
- **Where the mark appears.** Inside the app the mark appears only on the connection and pairing screens, at 56 px. The rail has no product name.
- **Type.** One family, Figtree (`@fontsource-variable/figtree` 5.3.0), in two weights, with JetBrains Mono (`@fontsource-variable/jetbrains-mono` 5.3.0) for code. Both are under the SIL Open Font License 1.1, which allows bundling them in an MIT app as long as the fonts are not sold alone and their notice travels with them; the font packages carry it. The bundler includes the fonts from the packages, so the app loads no fonts from the network and no font file is committed. Instrument Sans and Instrument Serif are removed.

## Interface: the visual language

The shell follows `docs/design/visual-language.md`, built in the order of its section 14. What a later builder should know:

- **One test for each layout switch, shared with the stylesheet.** `packages/ui/src/layout.ts` holds the two widths: one pane below 688 px of `.app`, and Work docked from 960 px of `.main-pane`. The stylesheet's container queries use the same numbers, and the code measures the same elements with a `ResizeObserver`, so the layout and the behaviour that depends on it (the drawer's dialog role, focus, `inert`) cannot disagree.
- **Selection.** `packages/ui/src/selection.ts` keeps the selected bot, the remembered task for each bot (it wins over the most recent), the bots unfolded by hand and whether the open bot was folded by hand; the last two persist. A bot's row summarises all of its tasks with three independent signals (latest activity, unread, run state, failed before working).
- **May this connection write?** `canWrite` in `packages/ui/src/access.ts` returns false: the client asks for `operator.read` and the bridge has no command that writes. Nothing that creates or sends is rendered; the composer is the read-only pill.
- **The strip.** `packages/ui/src/StatusStrip.tsx` derives every state from what the shell already has. After a connection problem the shell is "dropped" until bots, tasks and the open task have loaded again, then "Synced" shows for four seconds. The core stamps each connect (`connection.connectedAt`) and each successful history load (`transcript.loadedAt`), so a transcript kept from before the drop, which still says "ready", does not count as in sync until it has reloaded; a reload that fails is "Couldn't sync this task", never "Synced". "Try again" for one task sends `closeSession` and then `openSession`.
- **Following the end of a transcript.** The view follows new output while the reader is at the end. A scroll the reader did not make, such as content growing when fonts arrive, keeps following; only the reader moving up stops it. Otherwise width changes keep the text at the reading line, just under the protected band, where it was: the character there when the engine's caret API can say which, or else the top of its paragraph, list item or row. The browser's own scroll anchoring is off on the transcript.
- **Focus.** On one pane, opening a conversation moves focus to its heading and Back moves it to the row that opened it. Closing Work returns focus to the control that opened it, if that is still visible and focusable, or else to the Work toggle. "Check now" stays focusable while it checks.

Where the build departs from the specification, and why:

- **Task rows show their time.** The specification says "With no mark, the title has the whole row." and puts the time of last activity only in the row's accessible description (`docs/design/visual-language.md`, section 7). `F-425`, the designer's corrected prototype screenshots and the review of this work ask for it in the row. Each task row shows it, right-aligned in 12 px tabular figures, followed by one fixed 12 px slot for its mark or unread dot, so times line up whether or not a row has a mark. The row stays 34 px, the title gives way with an ellipsis, the full title is still on hover and focus, and the time is still in the accessible description.
- **The title pill opens Work and does not close it**, as the specification says; the panel button toggles. Its name always ends "Show details."
- **A failed discovery in the strip** reads "Couldn't load bots and tasks" ("Couldn't load bots" on the phone), with the gateway's message as the explanation after the dot; "Can't reach <gateway>" becomes "Can't reach the gateway" on the phone. The strip's state may shorten after its explanation has, and never runs under its action; the whole line stays in the strip's text, which its live region announces, and in its tooltip.
- **A task with no messages** says "Messages between you and <Bot> in this task will appear here." The specification's "Say what you need" invites typing, which a read-only connection cannot do.
- **The development gateway's hint** ("127.0.0.1:19001, started with `pnpm dev-gateway up`") moved into the button's tooltip, so the connect screen has the one hint the design gives it.
- **A connection error** is titled "Could not connect"; the error's code stays visible, small, under the sentence, for support.
- **System messages** are centred event lines outside `.turn`, as before, so `transcript-turn` still counts user and assistant items only.
- **The gateway's name** is its address (host and port): the gateway does not report a name.
- **A task with nothing saved, while the gateway is away** (after a reload, for example) shows "Waiting for the gateway" instead of loading skeletons that could never finish.
- **The task-title tooltip** shows on any focus, not only keyboard focus, so a test can focus a row and see it.
- **Pins, sections, search, "+" and New task** are not rendered (section 14 says so). The `.pin*` and `.rail-section` rules, the composer's field and send button and the extra state marks were not brought over, On a read-only connection the rail's top holds no controls. The specification allows only a 12 px drag band there and keeps the product's mark and name out of the rail ("There is no product name in the rail and no heading above the bots."). The band is the full header height instead (56 px, 60 on touch), the same band the conversation's floating controls sit in, so both panes share one top edge and the list starts where it will sit once search and "+" exist; on macOS it also clears the window controls.

**Every figure is the gateway's.** A bot's totals and cost are `usage.cost` for the period, in the person's time zone (`mode: "specific"`), with `updatedAt` shown as its age. A cost is the gateway's estimate from its configured prices: `Partial` when `missingCostEntries` is not zero, `Unavailable` when nothing used has a price, never a zero then. The development gateway configures a price of zero, so its cost reads "About $0.00". By task is `sessions.usage`. By source adds the gateway's own numbers: a routine's tasks are Routines; in the other tasks, largest first and at most 32, each run's answers are added up, as a person's message (a `user` row keyed to the run), another bot's (an `inter_session` row, counted only when the sending task's `sessions_send` result names that run) or neither; the rest of the total is Not attributed. The tasks and the sources carry `sessions.usage`'s own `cacheStatus`: while it or the total is still being counted, the rest is not shown, being no figure of anything yet, and parts that come to more than the total (read at another moment) are not shown at all. `sessions.usage` lists at most the 200 most recently updated tasks while its totals cover every one, so when it lists 200 the page says the tasks and the count of more cover those listed, and the sources are partial. Settings says how many bots the state's bound of 32 left out. The design's "Your messages" reads "Messages from people": a row names its sender's profile, not whether that sender is the person looking.

**Budgets are one user preference with the gateway** (`clawtrate.budgets`, `users.prefs`), as the rail's arrangement is, so a person's other devices show the same budgets and a change on one reaches the others on `users.prefs.changed`. It is written with a compare-and-set at `operator.write`, carries its own revision, and fits the gateway's limit on one preference (the bounds are `MAX_BUDGETS`, `MAX_BUDGETS_BYTES` and the ids in `packages/core/src/usage.ts`). A budget is for a bot or for one of its routines (one each; `budgetId`), Daily or Weekly, a whole number of tokens within `MIN_BUDGET_TOKENS` and `MAX_BUDGET_TOKENS`, and records the time zone it was set in, so every device counts the same days. A Daily budget counts today, a Weekly one Monday to today, in the time zone it was set in (changing it keeps that zone), with the `usage.cost` request the Usage page makes for that period and zone. The page may show another period, or be read from another zone, so the budget and the figures each name their own days and zone, and nothing says they are one figure; a routine's counts its own tasks in `sessions.usage`. The engine counts every budget when budgets are read, again while any is kept (sooner while the gateway says it is still counting), and after a budgeted bot's run ends, once the gateway's 30-second cache can include it (`COUNT_EVERY_MS`, `COUNT_COUNTING_MS`, `COUNT_AFTER_RUN_MS` in `packages/core/src/usage-engine.ts`). A budget is a warning: past `BUDGET_WARN_PERCENT` a line in the bot's open task, at 100 percent a note above the composer. Nothing holds, stops or refuses a run or a send. Removing a budget is offered in its form; the design names no way to remove one.

**What is not built.** A system notification at 80 percent (F-396's second half): the desktop app's main process refuses the renderer every permission but clipboard writes, so one posted from the interface would never appear; it waits for the notifications design, where the main process posts it, at 80 percent only, held by quiet hours. Stopping a bot or a routine at its budget, a local send hold, "Pause" for a routine and the reset rules that depend on a hold (F-397, F-398, F-459: `controls.md` section 24). Per-turn and per-routine-run figures (F-232) and a per-turn breakdown (F-233): the design draws no place for them. A note when a run waits on a rate limit (F-236's `chat` `retry` with `reason: "rate_limit"`).

## Read-only flows: what the gateway gives, checked in its source

Read from `@openclaw/gateway-protocol` 2026.10.6 (`protocol.schema.json`, `connect-error-details`) and the installed OpenClaw 2026.10.6, and seen on a development gateway's `sessions.list` and `chat.history`.

- **A task row's last-activity time** is `SessionRow.updatedAt` (number or null), with `lastActivityAt` beside it. The core uses `updatedAt`, then `lastActivityAt`, then `createdAt`. `sessions.changed` carries the same fields, so rows stay current (F-017, F-425).
- **A message's time** is the `timestamp` on each `chat.history` message, with `__openclaw.recordTimestampMs` as a fallback (F-063).
- **Context use** is `SessionRow.totalTokens` out of `SessionRow.contextTokens`, which on 2026.10.6 is the model's context window (128000 for the scripted model), not the tokens used; `totalTokensFresh: false` marks a count from before the latest run. OpenClaw's own Control UI divides the same two fields. `sessionInfo` in `chat.history` repeats them, and `contextBudgetStatus.estimatedPromptTokens` is a pre-prompt estimate the client does not use. The header says "Context: unavailable" when either field is missing (F-059).
- **A bot's label.** `agents.list` agents carry `identity` with `name`, `theme`, `emoji`, `avatar` and `avatarUrl` only (the schema closes it with `additionalProperties: false`), and no `description`. The label pill shows `identity.theme`; reading a description would need `config.get` (F-019).
- **The primary bot** is `agents.list` `defaultId` (F-015).
- **Run state from rows.** `SessionRow.status` is one of `queued`, `running`, `done`, `failed`, `interrupted`, `killed`, `timeout`, with `hasActiveRun` beside it. Nothing on a row says "waiting for you", "blocked" or "done with failures"; those come from run events this read-only client does not take yet. `TaskStatus` has the three values so the interface can show them; the mapping never produces them today (F-057).
- **Pairing outcomes.** A client that is not OpenClaw's Control UI gets no result for its pairing request: the gateway waits on the request (`waitForDevicePairingResolution`) and sends `device.pair.resolved` only to Control UI, browser copilot and TUI connections (`isOperatorUiClient`). For `gateway-client` every attempt answers `PAIRING_REQUIRED` with the pending request's id, and each attempt refreshes that request. A rejected request is deleted, and so is one not refreshed for `DEVICE_PAIRING_PENDING_TTL_MS` (300000 ms); the next attempt then creates a new request with a new id. `PAIRING_REJECTED` and `PAIRING_EXPIRED` exist in the protocol's codes but the 2026.10.6 server never sends them. The client sees the same thing after a rejection and after an expiry, a new request id, and elapsed time does not settle it (a request can be rejected while the client is away for five minutes), so it does not guess: it records its own `PAIRING_ENDED`, says the request is no longer pending because it was rejected or expired, and that the gateway does not say which (`packages/core/src/connect-errors.ts`). It then stops retrying and offers "Try again", which sends a new request (F-009, F-227).
- **Protocol mismatch.** The gateway checks `minProtocol` and `maxProtocol` before authentication and answers `INVALID_REQUEST` with `details.code: "PROTOCOL_MISMATCH"`, `expectedProtocol: 4`, `clientMinProtocol`, `clientMaxProtocol` and `minimumProbeProtocol: 3`, then closes with 1002. The client reads `expectedProtocol`, stops retrying and sends nothing else; a `hello-ok` whose `protocol` differs from the client's is not used either (F-263). The end-to-end test sends a real handshake with protocol 99 to read this payload.
- **Scopes.** `agents.list`, `sessions.list`, `chat.history` and `models.list` are in the gateway's session read methods, all allowed for `operator.read`.

## Read-only flows: what the build does

- **One unknown is shown, not invented.** Where a row needs a write scope (sending, creating, renaming, archiving, deleting a task, marking read on the gateway, the scope upgrade), nothing is rendered for it. Those rows stay `todo`.
- **The rail's arrangement is this device's.** Pins, hidden bots, the sort order and the manual order are kept in local storage (`packages/ui/src/roster.ts`): storing them on the gateway (`users.prefs.set`) needs `operator.write`, and F-014 and F-016 wait for a storage decision. The sort control says "This device only" for the manual order (F-266). Hidden bots keep working; hiding sends nothing to the gateway (F-027). The arrangement is kept per gateway, because bot ids are the gateway's (every gateway has a `main`): under `clawtrate.roster:gateway:<id>`, where the id is the gateway's own device id from `gateway.identity.get` (`operator.read`, `{deviceId, publicKey}`, stable across addresses and restarts; `hello-ok` carries no stable identity, and its `snapshot.stateDir` is sent to `operator.admin` connections only). The core reads it with the bots and publishes both together, so the rail never shows bots before it knows whose they are. A gateway that does not answer it is kept under its address, `clawtrate.roster:address:<url>`. An arrangement kept under an address moves to the identity once the gateway gives one. Un-scoped state from before this change (`clawtrate.roster`, which names no gateway) is not carried over: nothing reads it and nothing deletes it.
- **The default order is recent activity** (F-031), as section 7 of the visual language said it would become once the sort control landed. Pinned bots come first, in their own order. Manual order starts from the gateway's order and is changed by dragging, Alt+Shift+Up and Down, or Move up and Move down in a bot's menu. Recent activity is a task's `updatedAt` from `sessions.list`, falling back to `lastActivityAt`, then `createdAt` (`packages/core/src/mapping.ts`), and a bot's is its latest task's. The capability map recommends `lastInteractionAt` for sorting a sidebar; `updatedAt` also moves when only a session's metadata changes, so such a change can move a bot up. Which of the two should order the rail is not decided yet.
- **The state avatar in the rail.** A bot's run state moved from a mark at the start of line two onto its avatar, as `conversation.md` section 18 says: the ring while it works (and the body bobs), a badge at the top right for waiting, blocked, failed and done with failures. A row's accessible name starts with the bot's name and its state, "Otto, working, 14 tasks, unread", the way assistive tools read a busy bot (F-020); the visual language's own example put the count first.
- **The primary bot's star** is a 16 px disc in `--bg-inverse` with a star in `--text-inverse` at the avatar's lower right. The teardown's badge is orange with a white star; the visual language allows no new colours, so the badge is neutral (F-015).
- **Your messages** keep the accent by default. A "Your messages" choice in the gateway menu switches them to neutral (`--bg-inverse`, black in the light theme), as `--bubble-user` was made its own token for. The teardown's default is the bot's colour; the visual language gives your bubbles the accent (F-064).
- **Wide tables** may make a bot's bubble as wide as the transcript column, while its text keeps the usual measure; wider still, the table scrolls inside the bubble. Table cells break between words only (F-065).
- **Find in the conversation** (Cmd/Ctrl+F) takes the title pill's place while open and uses the CSS Custom Highlight API, so nothing in the transcript's markup changes. Matches inside folded steps count, and their group opens when the match is current (F-076).
- **The dock badge** counts unread tasks other than the one on screen. macOS and Linux show the count on the app icon (`app.setBadgeCount`); Windows shows an overlay dot on the taskbar button with the count in its description (`apps/desktop/src/main/badge.ts`, F-023). The packaged-app check reads what the main process sets from outside the app: on macOS the dock label Launch Services reports (`lsappinfo`), which must show a count no larger than the gateway's unread tasks and follow them when another client marks one read and unread again; on Windows the taskbar button's overlay description, "3 unread" after a count of 3 and empty after 0. The macOS test needs a development gateway, so it is skipped on Windows. Linux has no packaged-app check.
- **Setting up** is a list of three steps on the connection screens: connecting, pairing this device, loading bots. On the pairing screen the second step is the waiting line. The core publishes bots as soon as `agents.list` answers, and the app opens then, with "Loading tasks" in rows whose tasks have not arrived (F-003).
- **The welcome screen's one action** reads "Connect a gateway" (F-001); the visual language had "Connect".
- **Settings** (Cmd/Ctrl+, or the gateway menu) is a dialog over either screen with a Gateway pane: address, state, this device's name and id, the scopes the gateway granted, the gateway's version and protocol, and the error for a pairing request that is no longer pending, an unreachable gateway or another protocol. Its state words come from the connection: "Connecting" while an attempt is under way (no retry scheduled), "Offline" while waiting for the next retry or stopped, "Pairing pending", "Disconnected" (F-227). An attempt nobody answers now records `UNREACHABLE` with the address, so Offline can say why (F-387).

The strip says "Disconnected" with "Reconnect". The gateway menu's Disconnect still forgets the gateway and returns to the connection screen; Settings calls that one "Use another gateway" (F-457). The choice is saved with the gateway, so a restart stays disconnected until Reconnect (F-457).

## Check-ins

A bot's check-ins are the gateway's heartbeat (`docs/design/automation.md` section 13; `packages/core/src/check-ins.ts`). Observed on OpenClaw 2026.10.6, on a named development instance, with an admin and a read-only client through `@openclaw/gateway-client` 2026.10.6:

- **What runs is a job.** Each bot that checks in has one `cron.list` job with `payload.kind: "heartbeat"`, `declarationKey: "heartbeat:<bot>"`, `schedule: {kind: "every", everyMs}`, `sessionTarget: "main"`, `enabled` and `state.nextRunAtMs`. A read-only connection lists it. The block's words come from this job, never from the config alone.
- **Who checks in: the gateway's enrollment rules.** Read in 2026.10.6's `resolveHeartbeatAgentIds` (`dist/heartbeat-config-*.mjs`) and each confirmed on a named instance: (1) if any bot in `agents.entries` has a `heartbeat` of its own, even `{}`, only those bots have a job; (2) else `agents.defaults.heartbeat.agentId` names the one bot that has (`main` on the development gateway, every 30 minutes); (3) else, when an `agents.defaults.heartbeat` block exists, every bot in the config has one (writing `agentId: null` gave all four seeded bots a job at 30 minutes); (4) else the gateway's ambient owner has one: `agents.defaults.systemAgent.agentId`, else (outside `ownership: "explicit"`) the one bot marked `default: true`, else the only bot (`tryResolveAmbientOwnerAgentId`). Clawtrate reads it from the config, not from the jobs: the job list is re-derived only when a heartbeat setting changes. With no default block and `systemAgent.agentId` changed from `main` to `pip`, main's job stayed listed; writing and then removing a setting for Marlow left Pip's job, not main's. A bot's cadence is its own `every`, else the default's `every`, else `"30m"`, parsed with minutes as the default unit: `every: "90s"` in the default gave each bot 90,000 ms. Writing `agents.entries.marlow.heartbeat {every: "1h"}` left Marlow's job only; then `heartbeat: {}` for main brought main's back at the default's 90 seconds, and a prompt-only setting for Otto brought Otto's back at 90 seconds too; removing every setting (`heartbeat: null` in a merge patch) brought main's back alone, under a new job id.
- **The catch, and what a save writes.** So a save that gives a bot its first setting of its own would stop every bot that inherits the default, including bots Clawtrate does not list. The engine works out those bots from the same `config.get` that supplies `baseHash`, never from the jobs' cadence or from the listed bots, and writes each in the same `config.patch` as `heartbeat: {every: <the default's every, exactly as the config gives it>}`. At most 32 such bots are kept, not counting the bot being saved; past that the save is refused, not cut, and the dialog says so before Save, which it turns off. A default `every` longer than 64 characters is never written back cut: 2026.10.6 accepted `"0s"` 32 times followed by `"90s"` (67 characters) as 90,000 ms for every bot, and a save that would have to write it to other bots is refused the same way. The dialog names the bots when it opens, keeps that list with its draft whatever a refresh shows meanwhile, and sends what it named.
- **A draft against a config that changed.** A save writes only the fields the person changed (a prompt for a bot that does not check in also writes `every: "0m"`, since any setting of its own enrolls it). A field counts as changed only once the person touched it and it differs from what the draft started from (`packages/ui/src/check-ins/draft.ts`). The dialog sends the bot's own setting it started from and the bots it said it would also write. The engine reads the config again; if a field the person changed was changed on the gateway meanwhile, the prompt there is now longer than Clawtrate edits, or the bots to keep differ, it writes nothing and reports a conflict ("Not saved"). Only then does the draft move to what the gateway has: fields the person left take the gateway's values, the person's edits stay (a prompt now too long to edit is dropped, after that conflict was shown), and the next save is against that. Every patch carries a non-blank `baseHash`. On 2026.10.6 a patch to these paths without one is refused (`INVALID_REQUEST` "config base hash required for agents.entries.pip.heartbeat.every; re-run config.get and retry with baseHash"); `"   "` is read as missing and refused the same way; `""` fails the schema ("must not have fewer than 1 characters"); a stale one is answered "config changed since last load; re-run config.get and retry", which is a conflict, shown before the list is read again.
- **Saved means read back.** "Saved" is shown only once one read shows both: the config holds every field written, the prompt included, and the job list shows each affected bot's job as it should be, disabled for Off and enabled at the cadence otherwise, for the bot and every bot kept. The bot's own job is required too, even when only its prompt changed: a bot whose setting is `{}` inherits the default's cadence, so its job's cadence is resolved from the config as the gateway does. The list is read through every page (`cron.list` answers `hasMore` and `nextOffset`, and each page `snapshotRevision`, `total`, `offset` and `limit`; `scheduleKind: "every"`, 200 a page, at most 50 pages). When the revision or the total changes between pages the jobs moved, and the read begins again, at most three times, as the gateway's own CLI does (`listCronJobsFromGateway`). Read every 500 ms for at most 20 seconds in all, each request given only what is left of them; past that, or when `config.patch` fails without a refusal that establishes it was not applied, the save is "not confirmed", never "saved".
- **One connection per save.** A read and a save are bound to the connection open when they start: its protocol client and a counter that changes on every hello and every close. A request after either changed is never sent, admin is checked again just before the patch, and a read that comes back after its connection ended, or after a later read began, changes nothing on screen. What is read carries the gateway's identity (`gateway.identity.get` `deviceId`, awaited on each connection before reading); it is cleared when the connection closes. A draft is bound to that identity, and a save names it: the engine refuses one for another identity before reading or writing, so a replacement gateway at the same address never receives an old draft. The dialog's draft lives in the section, not the dialog, so admin that ends and returns finds it again, for the same gateway and bot only. When `config.patch` gets no answer the save is "not confirmed"; the dialog then offers Check, which only reads, and moves the draft to what the gateway has; saving again is a separate act.
- **Off.** `every: "0m"` keeps the bot's job with `enabled: false`, no next run, and the `everyMs` it had before; `cron.run {id, mode: "if-enabled"}` on it answers `{ok: true, ran: false, reason: "disabled"}`.
- **What Off does not stop.** With `every: "0m"`, a `wake {mode: "now", text: "Exec completed …", sessionKey}` still reached the scripted model for that session, as `<openclaw>/docs/gateway/heartbeat.md` says ("A targeted event-driven wake can still run one agent turn"). The dialog says so under Off.
- **The job is not editable as a routine.** `cron.update` on it is refused: "system-owned monitor jobs cannot be edited by cron clients". `cron.run {mode: "force"}` on it was accepted (`enqueued: true`).
- **Reading the config.** `config.get` answered the read-only connection too; `config.patch` there is refused with "missing scope: operator.admin". Only the admin path offers a change.
- **"As needed" is not a gateway mode.** It is `every: "30m"`. Silence is what the gateway's built-in prompt asks for ("If nothing needs attention, reply NO_REPLY."), not something it guarantees, so no wording promises it. The words after a cadence, in the block and under Daily, As needed and Every…, follow the design's rule and say what is known of the prompt in effect, never what its wording seems to ask: "Its prompt asks it to stay quiet when nothing does." only for the built-in prompt (no prompt of the bot's own and no default prompt, both read from the config); "checks in with a prompt of its own" for any prompt of the bot's own, `NO_REPLY` mentioned or not; "checks in with the prompt the gateway sets for every bot" for a custom default; "checks in. Clawtrate can't read its prompt." when the config could not be read. An empty prompt means the default's prompt when `agents.defaults.heartbeat.prompt` is set (shown faint in the field), the built-in one otherwise. Any prompt typed gets a note that describes the built-in prompt and claims nothing about this one ("Whether Juniper stays quiet depends on what this prompt asks."). While a save is under way the dialog stays open and Escape waits for its answer. The gateway skips a scheduled attempt outside `activeHours` or while the bot is busy, and `isolatedSession` runs one in a fresh session (`<openclaw>/docs/gateway/heartbeat.md`; read, not observed), so the block says "Next scheduled attempt" and names no conversation; Off's words say a command started in the background still reports when it finishes.
- **Telling a check-in apart.** A heartbeat turn's `agent` events carry `isHeartbeat: true` (asserted by the scenario check, "a turn the gateway starts itself is answered quietly"). Nothing here labels a turn a check-in without that evidence; the conversation's "Checked in" line is not built (F-200).
- **Where it lives.** Check-ins opens from Routines, as the design places it: the chosen bot's block above its routines, and each bot's cadence beside its group in the all-bots list, once the check-ins are read. Settings keeps a "Check-ins" section with every bot's block. All of them use the blocks and dialog in `useCheckInsSection`. The dialog is mounted only while the connection holds admin, whatever opened it.
- **What is kept.** `ClawtrateState.checkIns` (`CHECK_INS` in `state-bounds.ts`): the IDs covered by the read, with one job and one setting per bot (`MAX_BOTS`), the default (the bots that inherit it, at most `MAX_CHECKIN_KEPT` + 1 (33, since the bot being saved is not kept), its `every` of at most 64 characters, marked cut past that, and its prompt), the gateway identity it was read from, prompts of at most `MAX_CHECKIN_PROMPT_CHARS` (4,000; a longer one is marked cut and never written back; the field takes no more), the scheduler flag and the one save under way. The engine keeps no collection of its own; the pages of jobs it reads are in flight only.
- **When it is read.** On entering the Check-ins section, whenever the connection comes back while it is shown and again when the bots are listed after it, after a save, and on the section's Refresh button, which stays offered after a read failed, for changes made elsewhere.
- **Not observed.** A check-in firing on its schedule: the development gateway runs with `cron.enabled: false` (`cron.status` `enabled: false`), and the view says that scheduled check-ins don't run then.

## Routines: what the gateway returns

Observed on a named development instance (OpenClaw 2026.10.6), through `@openclaw/gateway-client` 2026.10.6, with a paired admin client playing the other clients and a paired read-only client reading. The scheduler is off on a development gateway (`cron.status` `{enabled: false, nextWakeAtMs: null}`), so every run below was started with `cron.run {id, mode: "force"}`; nothing was observed firing on its schedule.

- **The list.** `cron.list {includeDisabled: true, limit, offset}` works at `operator.read` and pages with `total`, `hasMore` and `nextOffset` (at most 200 a page, protocol schema). The engine keeps 200 routines; past them it counts the rest from `total` without reading them, and the list says how many more the gateway has. Choosing a bot then reads that bot's routines with `agentId` (returned, not kept). A kept routine removed while others were left out reads the list again, so its place is filled. A routine whose bot the client does not hold (past `MAX_BOTS`) is listed under the bot's id and opens like any other. A job carries `id`, `agentId`, `name`, `enabled`, `schedule` (`{kind: "cron", expr, tz}`, `{kind: "every", everyMs, anchorMs}`, `{kind: "at", at}`), `sessionTarget`, `wakeMode`, `payload` (`{kind: "agentTurn", message}` or `{kind: "systemEvent", text}`), `delivery`, `state` and `updatedAtMs`. `state` carries `nextRunAtMs` and, once it has run, `lastRunAtMs`, `lastRunStatus`, `lastDurationMs` and `consecutiveErrors`; pausing removes `nextRunAtMs`. The gateway's own check-in job is in the same list (`payload.kind: "heartbeat"`, `declarationKey: "heartbeat:<bot>"`); the engine leaves it out (`packages/core/src/routines.ts`), since it is a bot's check-ins, not a routine.
- **Defaults it fills in.** A job added without `delivery` reads back `{mode: "announce"}`, and its forced run on a gateway with no channel ended `status: "error"`, `completionStatus: "failed"`, `error: "Channel is required (no configured channels detected). …"` after the bot had replied. `delivery: {mode: "none"}` ends `ok` and `succeeded`. A `sessionTarget: "main"` job is refused for any bot but the default: "sessionTarget "main" is only valid for the default agent".
- **The event.** Every connection receives `cron`, the read tier included, without subscribing: `{jobId, action: "added", job, nextRunAtMs}`, `{action: "updated", job}`, `{action: "started", job, runAtMs}` with `job.state.runningAtMs`, `{action: "finished", job, status, completionStatus, summary, runId, sessionKey, durationMs, usage, model, provider, runAtMs, nextRunAtMs}` with the job's new `state`, and `{action: "removed"}`. `started` and `finished` carry the same `runAtMs`, which is also the job's `state.lastRunAtMs` and the run's `cron.runs` `runAtMs` (observed). The engine reads the list on every connect and applies each event to it; nothing else of a routine is kept.
- **When events and reads cross.** The gateway sends `cron` with `dropIfSlow` (read in its source): a slow connection loses the event and the gap in `seq` forces a reconnect, which reads the list again, but only once another event arrives. So the engine does not trust one read or one event alone. A list read that an event overtook is not published (it may be older than the event) and is read again. A `finished` older than the `started` already applied (by `runAtMs`) does not clear it, and a `started` no newer than the last finished run marks nothing. While any routine is marked running, the list is read again every minute, so a dropped `finished` clears within a minute; after a failed read, it is tried again in 30 seconds, and the list says it could not refresh, with "Try again".
- **Runs.** `cron.runs {id, limit}` returns `entries` newest finished first (sorted by the record's `ts`, read in the gateway's source), each with `runId`, `runAtMs`, `status`, `completionStatus`, `summary`, `durationMs`, `model`, `provider`, `usage {input_tokens, output_tokens, total_tokens}`, `sessionId`, `sessionKey` and `jobName`; empty for a job that has not run. A forced run's id is `manual:<job>:<ms>:<n>`. A run of a `systemEvent` job in the main conversation has no `sessionKey`, `usage` or `model`, and its `summary` is the reminder's text. `cron.runs {scope: "all", limit, offset}` returns runs across jobs in the same order, with no date filter; the calendar reads pages of it until one reaches back before its first day, at most 1,000 entries, and says when that cap stopped it first ("Some runs on these days aren't shown"), so one busy routine cannot hide another's runs within that. The gateway's order is the contract for a routine's page (F-355): it shows the 20 runs that finished most recently, in that order, and says so; with overlapping runs, one that started earlier but finished later stays above one that started after it. A second forced run while one is in progress answered `{ok: true, ran: false, reason: "already-running"}`.
- **A run's conversation.** `cron.history {id, runId}` (or `{id, runAtMs}` for a run with no `runId`; observed) returns `{messages, activity, nextCursor?}`, the newest page first: a long run's first page does not start with the scheduler's message, so the engine follows `nextCursor` back, up to five pages of 200, and says the conversation is longer than it reads when that is not enough. The first message is the scheduler's: `role: "assistant"`, `provenance {kind: "internal_system", sourceTool: "cron", jobId, runId: <sessionId>, sourceSessionKey: <the run's sessionKey>}`, `senderLabel: "Forwarded from <name>"`, and as `content` the job's message as it was when the run started, then `\nCurrent time: …` and the gateway's instructions for unattended runs. After the job's message was changed with `cron.update`, the earlier run's history still held the earlier message. So the run's page shows that first message whole, as the gateway recorded it (the design's rule: it is not split, since nothing but the gateway's current wording marks where the job's text ends), never the routine's current instruction, and treats the history as the run's only when that first row names this job and this run's session. For a main-conversation run, and for a `runAtMs` with no run, the gateway refused with "The recorded cron transcript is unavailable. Refresh the run and try again."; that refusal and an empty history read as no conversation, and the page says Clawtrate can't show it, names retention as a likely reason only, and shows the run's `summary`. Any other failure (a timeout, a dropped connection) is "Couldn't load this run." with "Try again", never "no conversation". What a run older than `cron.sessionRetention` (24 hours by default, read) returns was not observed.
- **A run's session in the task list.** The run's session (`agent:<bot>:cron:<job>:run:<session>`) is not a `sessions.list` row; the job's own session (`agent:<bot>:cron:<job>`) is, and `isTaskSession` already leaves both out, as the gateway's `excludeCron` does. A routine's run is shown as a row under its bot from the routine's `state.lastRunAtMs` instead (F-193).
- **One-shot routines.** An `at` job reads back `deleteAfterRun: true`. A forced run of one left it listed, enabled and with its next run, so whether a scheduled run removes it was not observed. The gateway's source sends `finished` and then `removed` from the same commit when it removes one after a successful run. The engine says a routine "ran once, and the gateway removed it" only on that evidence: a `removed` that comes right after that job's successful `finished`. Any other removal, including a person's after an earlier run, reads "This routine was deleted."
- **Daylight saving.** The calendar computes times after the gateway's next run (which it draws as given, a staggered top-of-the-hour run included) the way the gateway's scheduler does, checked against its `computeNextRunAtMs`: a time the clock skips that day (2:30 AM on a spring-forward day in New York) does not run, and a time the clock passes twice runs once, the first time. Chips sit on the day's hour scale by the viewer's wall clock, so 8:00 AM is at 8 on a 23-hour day.
- **Retention.** The routine list is in the state (`ROUTINES` in `state-bounds.ts`, 200 routines, each instruction at most 4,096 characters, and the last routine removed with whether it removed itself). Runs (at most 20 per page, F-355), the calendar's runs (at most 1,000 entries read), one bot's routines (at most 200) and a run's conversation (at most five pages read, 160,000 JSON characters kept, later items counted, and the scheduler's message recorded with it up to 16,384 characters, `MAX_RUN_MESSAGE_CHARS`, the instruction's 4,096 plus the gateway's footer with room to spare; past it the run says the message is cut) are read when a screen asks and returned to it, never kept by the engine. A screen shows a read's answer only while it is for the same gateway, routine and revision it asked about.
- **F-191** is checked under its id for the read part (`e2e/routines.spec.ts`, `visual/routines-behaviour.visual.spec.ts`) and for the switch and "New routine" on an admin connection (`visual/routines-edit-behaviour.visual.spec.ts`, `e2e/routines-edit.spec.ts`).
- **The Routines button** is in the rail's top row on every connection that reads, so the empty state ("No routines yet") and a failed first read ("Couldn't load routines." with "Try again") can be reached. This adds the button to the rail in the existing visual baselines. Opening the view closes the Work pane (automation.md section 1); Back ("Back to conversation", or "Back to bots" on the phone) returns focus to the button.
- **A routine's run in the rail** (F-193) is an isolated agent routine that is running or whose latest run finished in the last 24 hours. A finished row opens that run, found by its start (`runAtMs`, the same as `state.lastRunAtMs`) and kept on screen after a later run finishes; a running row opens the routine, whose page shows the run in progress. The rows are kept apart from the bot's tasks: not counted, never unread, not in the tasks' order.

## Routines: changing them

Observed on a named development instance (OpenClaw 2026.10.6) with a paired admin client and a paired read-only client, through `@openclaw/gateway-client` 2026.10.6, and checked against the pinned `@openclaw/gateway-protocol` schema (`packages/core/test/routines.test.ts` validates every request the engine sends with the package's own `validate…Params`).

- **The tier.** `cron.add`, `cron.update`, `cron.remove` and `cron.run` on a read-only connection answer `FORBIDDEN` "missing scope: operator.admin". The engine checks admin just before each request, whatever asked for it (a button, the row's menu, the keyboard, or a bridge command from another viewer, which `e2e/routines-edit.spec.ts` sends), and answers `not-sent` without asking the gateway. The interface offers nothing that writes below admin; the view's foot is the access bar of `bots.md` §2, and admin is asked for only by its button.
- **`cron.add`** answers the job (with `deliveryPreview`). With a `declarationKey` it answers `{created, job, deliveryPreview}`, and a second add with the same key answers `{created: false, updated: true, job}` with the same id: no second routine. So each draft has its own key, `clawtrate:<uuid>`, kept for every try of that draft. A save whose answer never came is found only by that key (`cron.list`), never by name, bot or time, so another client's routine is never adopted; "Save again" is a separate action and reuses the key. `delivery` must be an object: `delivery: "none"` is refused ("at /delivery: must be object"). Clawtrate writes `{mode: "none"}` unless the person chose to announce.
- **One-time schedules.** The schema takes `{kind: "at", at}` with no zone. Sent with a `tz` beside it, `cron.update` accepted it, dropped the zone and read the wall time as UTC (`2035-01-01T09:00:00` with `tz: "America/New_York"` became `09:00Z`). With an offset (`…T09:00:00-05:00`) it stored `14:00:00.000Z`. Clawtrate writes the chosen wall time with its zone's offset at that moment; the gateway keeps the instant only, so the editor shows a saved one in this device's zone, and a change that leaves its date and time alone writes the gateway's own `at` back unchanged (it is not in the patch at all). Setting an `at` schedule also sets `deleteAfterRun: true`. A time in the past is refused ("schedule.at is in the past: …").
- **`cron.update {id, patch}`** answers the job. The patch merges: `{delivery: {mode: "none"}}` kept `bestEffort` and `failureDestination` already on the job, so Clawtrate sends only the fields the person changed, and delivery only as its mode. There is no revision to compare, so before writing, the engine reads the job (`cron.get`) and compares it with what the editor opened with; if any field the editor shows differs, nothing is written, the editor says the routine changed elsewhere, keeps the person's version to compare and reuse, and its saves still go through the form's checks. This narrows the window between the read and the write; it does not close it. "Saved" is said only when the gateway's answer shows the change.
- **Refusals** come back as `INVALID_REQUEST` with the gateway's words, shown as given: "invalid cron.update params: CronPattern: invalid configuration format ('99 * * *') …", "… Please provide a valid IANA timezone …", and for an expression that never fires, `invalid cron.add params: cron expression "0 0 30 2 *" has no upcoming run time and would never fire`. A job that no longer exists: "Automation not found: <id>. List automations and retry with a current job id. …" for `cron.update`, `cron.run` and `cron.remove`.
- **`cron.run {id, mode: "force"}`** answers `{ok: true, enqueued: true, runId: "manual:<job>:<ms>:<n>", processInstanceId}`; a second one while it runs answers `{ok: true, ran: false, reason: "already-running"}`.
- **`cron.remove {id}`** answers `{ok: true, removed: true}`; again, "Automation not found". The engine counts that as removed.
- **No run limit.** `cron.update` refuses `{patch: {maxRunsPerHour}}`: "unexpected property 'maxRunsPerHour'". That shows only that no such setting exists; whether the gateway limits runs internally was not found in the schema or the capability map. F-356 is `gap` with that evidence.
- **The scheduler, for F-354.** `config.patch {cron: {enabled: true}}` took effect without a restart (`cron.status` `enabled: true` within a second). A new routine every 5 minutes then had no run after several seconds and its next run 5 minutes after it was made. `tools/dev-gateway/src/routine-gateway.ts` turns the scheduler on for one check and off again whatever happens.
- **The gateway's hooks, for F-349 and F-358.** `config.patch {hooks: {enabled: true, token, path: "/hooks"}}` took effect without a restart; `config.get` then shows `token: "__OPENCLAW_REDACTED__"`. `POST <gateway>/hooks/agent` with the token answered 200 `{ok: true, runId}` and started a bot's turn; a wrong token answered 401. It is global and starts a bot, not a routine. With admin and hooks on, a routine's page shows that address with a copy button and says the key is kept on the gateway; Clawtrate never sees the key.
- **The five-minute floor (F-195)** is Clawtrate's; the gateway takes a one-second interval. A cron expression is read with croner 10.0.1, the library and version OpenClaw 2026.10.6 reads every cron schedule with, with the gateway's own options, and the floor is the shortest time between two consecutive runs over four years or 20,000 runs, so steps that cross an hour (`*/7 * * * *` fires at :56 and :00) or a day are caught and `0,59 8 * * *` passes. An expression croner refuses (an out-of-range field such as `99 * * * *`) gets croner's message before any request. Its runs are counted in UTC: a daylight-saving change can bring two runs closer for one night. `croner` is a new dependency of `@clawtrate/ui`, pinned to the gateway's version.
- **A save always ends.** While it is in flight the dialog stays (Cancel, Close and Escape wait), and after 30 seconds without an answer the editor says the gateway didn't answer and offers "Check now", which only reads (`cron.list` for a new routine's key, `cron.get` for a change) and compares each field that save sent, as sent, with what the gateway has. For a change it then says the routine reads as typed (which may be this save or the same change made elsewhere), or what the gateway has instead; a new routine found by its own key is saved. The foot has no Save meanwhile; "Save again" in the note is the only write, and it goes through the form's checks. An answer that comes later still settles it.
- **Reminders and commands keep their payload.** Following the design, only an agent turn's instruction is edited in the form; a reminder's text or a command is shown as written with a line saying to change it on the gateway, and a save never sends `payload` for them (a rename of a reminder was checked against the gateway: its `systemEvent` text stayed).
- **Where this follows the gateway over the design:** the design says `cron.add` has no request key, so a new routine found after a save in doubt can only be "one named so". The gateway's `declarationKey` is such a key (above), so a routine found by its draft's own key is that save.
- **Losing admin while editing** puts the access bar in Save's place and keeps the form; when admin is granted again, Save works. The editor closes, and its draft goes, when the gateway itself changes. A routine deleted while its page is open keeps what it showed and loses every control that changes it.
- **A bot's routines' time zone (F-196)** is a line under one bot's routines ("Mixed: New York, London" when they differ). "Change…" rewrites each routine's own `tz` with `cron.update`, one by one, through the same comparison as the editor, and names any that failed. Routines with no zone of their own or a schedule the form doesn't write are listed and left alone. New routines for a bot start in the zone most of its routines use.
- **F-194 and F-357 stay `todo`.** The away card belongs in the Routines view (automation.md section 14), not the conversation, but it needs a record of when Clawtrate was last opened, written to `users.prefs` by every client at launch, and a pause-all that runs only while Clawtrate is open with admin. It is left for a pull request of its own.

## Memory plugin on OpenClaw 2026.10.6

- The built-in memory search backend returned a file reference and excerpt without a file revision. The plugin reports the stored hash and leaves searchability unconfirmed. It never requests a reindex.
- The file-tool observation hook supplies the path argument and a success receipt for the built-in write and edit tools, without a canonical destination or file hash. The hook saves receipts through the gateway's bounded plugin store. The plugin records the hash of its own successful writes. The pinned filesystem SDK returns no publication identity for those writes, so reads omit saver attribution. The gateway runs tool observation outside the RPC event broadcaster. The service emits the empty change event for plugin RPC mutations that succeeded or may have succeeded.
- The gateway provisions local workspaces on first use. The plugin needs an existing workspace for writes and refuses a declared device-bridge workspace. It uses the caller-filtered bot roster and requires whole-roster access for shared folders, which have no session access key.
- The root writer shares a lock with the plugin's note writes. Other writers do not share it, so the final check and publication can race with outside writes. The pinned filesystem SDK's containment checks also depend on the platform's available filesystem primitives.

Nothing is added to `ClawtrateState` and the engine holds no collection (it is registered in `owners.ts` with none), so the state's and the host's worst cases are unchanged. Each answer is bounded so that the largest one fits a web host's result frame: 16 machines, 32 devices, 32 names of each inventory list, entries of an approvals file only for listed bots, names and ids of 128 characters (`machines.test.ts` builds the largest one).
- **Settings, not outcomes.** The pages show what the gateway's settings store and what the gateway reported, and infer nothing from them. The command machine is the stored `host` and `node` (the bot's own over every bot's, each read on its own, as the gateway reads them); a value the app doesn't know is shown as stored and marked unsupported; a stored node names a listed machine only by its exact id, because the gateway's own matching of names is its own. Nothing says where a command runs or what confines it: sessions, sandbox policy, elevated calls and approvals all decide that on the gateway. The browser is the stored tool lists, the gateway's `browser.enabled` and browser plugin switches, and the computer plugin's profile name. An approvals file is its settings: no "effective" outcome, since the gateway also weighs a task's permission mode, tool policy and availability.
- **Same setting, not sharing.** Two bots with the same stored node or the same reported workspace path have the same setting, and the pages say only that.
- **Saves are read back, then read again.** A command machine is saved with the revision the page showed (`baseHash`), said saved from the stored setting, and applied only when `config.get` reports the active revision equal to the saved one; a pending or failed application has its own words. A refusal whose code establishes that nothing was written (`INVALID_REQUEST` and the other codes `accounts-engine.ts` reads as not applied) is said as nothing saved, in the gateway's words. A failure that carries the saved config (`UNAVAILABLE` with `details.persistedConfig`: the gateway persisted the change, then didn't apply it or needs a restart for it) is read back like a receipt: saved when the setting agrees, with the gateway's words. Any other failure, a lost answer included, may have landed: the setting is read back and said as found, and the save as not confirmed, never as saved. A `config.get` answer of `valid: false`, which the gateway gives with an empty `config` when it can't read or parse its settings file, is no setting: that read fails, so a save read back that way says the setting couldn't be read, and so does the page when it reads again. A workspace is sent as typed, for the gateway's resolver to accept or refuse; a refusal is an unclear outcome, since files may remain, said with what the gateway reports after. A machine's defaults are written with the file's hash. A removal is done when the whole listing read back lacks the id. After any save, whatever its outcome, the page reads again.
- **Reads belong to their bot and access.** A read is drawn only for the bot and the connection's scopes it was made with, so nothing of another bot, an earlier connection or other scopes shows while a new read runs.
- **Device access** (`operator.pairing`) is a request of its own, `requestAccess {tier: "pairing"}`, for the scopes the connection holds plus pairing and nothing else; it is recorded with the token (`pairingHeld`) like admin, and asked for again only then. Nothing asks for it by itself. Renaming or removing another device's or a machine's record is offered with admin only, by the gateway's rule above; this device's own name with device access only when its record is operator-only; Remove only for a paired record, and a removal is confirmed only from a read-back that holds the whole list.

**A paired machine on a development gateway.** A development gateway has no node, so `pnpm dev-gateway start --instance <name> --with-node` starts the gateway's own headless node host, `openclaw node run`, under the instance's profile and recorded like the gateway (`tools/dev-gateway/src/scripted-node.ts`). It is closed like the config: one invented name, media-box, and it declares only `system.execApprovals.get` and `system.execApprovals.set` (`--commands`), not `system.run`, so no bot's command can run on it (the gateway refuses a command a node did not declare). Its state, approvals file included, is a folder of its own inside the instance's (`clawtrate-nodes/media-box`): an explicit `OPENCLAW_STATE_DIR` survives `--profile`, which only fills one in when none is set, so the node's file is not the gateway machine's. `start` approves its device request and then its command request, each by id and only when it is exactly what the node must be. `pnpm e2e` starts its accounts instance with it. What it cannot show, a command that ran on a node, stays unproven.

## SSH to another computer

The host side of "Another computer" (`docs/design/setup.md` sections 5, 8 and 19, issue #9) is a module of the desktop app's main process, `apps/desktop/src/main/ssh/`, with no interface. `SshTransport` (`transport.ts`) is what the setup screens and the host's confirmations will call: `prepareRoute`, `checkHostKey`, `trustCapturedKey`, `replaceTrustedKey`, `look`, `openForward`, `forget` and `closeAll`. Each returns a typed result: besides its own, `stale-route`, `app-files-unsafe`, `not-supported-here` and `failed` with fixed copy. Nothing calls it yet; the screens of "Another computer" are a later unit.

- **Its world is an input** (`world.ts`): the home folder, the person's SSH configuration and known-hosts file, the `ssh` program, the folder for the app's own files, the local user name, the agent, the platform and the app's environment. `productionWorld(appDir)` resolves them from the real environment: `~/.ssh/config`, `~/.ssh/known_hosts`, `/usr/bin/ssh` or `%WINDIR%\System32\OpenSSH\ssh.exe`, and the agent the app chooses: the socket `SSH_AUTH_SOCK` names, none without one, and on Windows no IdentityAgent directive unless the person explicitly disables agent use. Agent sign-in with the bundled client's default and an explicit pipe are both unverified. Tests pass a world they made in a temporary folder.
- **`ssh` runs with a minimal environment**: a fixed `PATH` on macOS and Linux, and on Windows the system's own variables (`SystemRoot`, `USERPROFILE`, `TEMP` and the like) and `System32` as `PATH`. Nothing else of the app's environment reaches it. On macOS and Linux the configuration names the selected socket or disables the agent.
- **The guard.** The guard rejects test paths that resolve into the developer's SSH directory when checked and rejects agent use. Test homes, keys, identity companions, Include files and app files must stay inside the fixture's private directories for the entire run. This check is a safeguard for fixtures. It cannot block filesystem changes after a path is checked.
- **The person's configuration is read as text** (`person-config.ts`), with `Include` followed outside any block and refused inside a matching one. From the blocks that apply to the typed name it takes `HostName`, `User`, `Port`, `IdentityFile`, `IdentitiesOnly`, `CertificateFile`, `IdentityAgent` and `PubkeyAuthentication`, first value winning as in OpenSSH, and checks each: a host name or user by the destination's pattern, a port by range, a path absolute or under `~/` and inside the home both by its spelling and as the file system walks it, with no `%` token, variable, `"` or backslash. `IdentityAgent` and `PubkeyAuthentication` are written as the person set them, off included; an agent outside the home or given as a variable is refused by name. Every setting section 5 lists is refused by name with that section's note. `Match` is refused wherever it appears, because its conditions can't be evaluated without running them. A setting the module does not know is refused by name too ("devbox's SSH settings use CanonicalizeHostname."); a short list of settings that run nothing and don't touch the key check (`AddKeysToAgent`, `ServerAliveInterval` and the like) is left out silently.
- **Keys are always named.** When the person's configuration names no key, the host writes OpenSSH's default key names that exist in the world's home (`id_rsa`, `id_ecdsa`, `id_ecdsa_sk`, `id_ed25519`, `id_ed25519_sk`) as explicit `IdentityFile` lines, and `IdentityFile none` when there are none: an empty list makes OpenSSH add the account's own defaults, even with `IdentitiesOnly yes`. Tests read every generated file back with `ssh -G`, which reads it and connects nowhere, and fail on any path of a home's `.ssh` beyond the keys named, or on an agent.
- **The configuration the host writes** (`route-config.ts`) is section 19's, one directive per line, plus the agent and `PubkeyAuthentication` above. Every path is written in double quotes with forward slashes, and may hold the characters profile and folder names use (spaces, apostrophes, parentheses, `&`, `,`, `#`, `[`, `]`, `=` and accented letters); a value with anything `ssh` would expand is refused. A route has a file for its looks and forward, and one for the prior-trust lookup, which has no `HostKeyAlias` and names the person's known-hosts file; a first contact has a file of its own, naming its empty capture file. `ssh` is always started with `-F` on one of them and an argument array, never through a shell.
- **A route is one endpoint.** Its alias, `clawtrate-route-<id>-<tag>`, and its files carry twelve hex digits of the SHA-256 of the resolved endpoint (`you@[devbox.example]:22`). Each `prepareRoute` makes a new generation, and every call refuses an older one as `stale-route`; a capture is bound to the generation and endpoint its probe ran with; a pin is trusted only with the endpoint recorded beside it. Preparing a route for another endpoint removes the old endpoint's files; `forget` removes all of a route's pins and files.
- **What it runs**, every one with `-F <file it wrote>`: `-v -N -T -o PreferredAuthentications=none -o NumberOfPasswordPrompts=0 -- <alias>` to check a pinned key, to look up prior trust, and (on the capture's file) to capture a key; `-- <alias> /bin/sh -s` with the LOOK on standard input; and `-v -o ClearAllForwardings=no -N -L 127.0.0.1:<free port>:127.0.0.1:<gateway port> -- <alias>` for the forward; and `ssh -V` once, which must exit 0. A probe ends as soon as its error output shows the key was written, or matched together with the file and line it was found at; a refused key is left to end by itself, so that its exit status 255 is read. Stopping it earlier lost those on Linux, where the reader can run, and stop ssh, before ssh writes its next line or exits. The forward runs with `-v`, which the design's line for it lacks, so that the host knows when it listens.
- **Host keys** (`known-hosts.ts`). A captured key is kept in memory, single use, for 2 minutes, and only its type and fingerprint are returned; `trustCapturedKey` pins exactly the captured bytes, never anything from the caller, and a test counts that first contact reads the key from one connection only. The fingerprint is computed in the process from the key bytes (SHA-256, as `ssh-keygen -l` prints it); the integration test compares the two. A pin is one line in the app's `known_hosts`, `<alias> <type> <key> endpoint=<endpoint> pinned=<time>`. A key already in the person's known-hosts file, hashed or not, is pinned only when `ssh -v` named that file and line for the resolved host and port, that line is a literal key (no `@cert-authority` or `@revoked`), and its bytes hash to the server key `ssh` reported. A changed key is never replaced by `checkHostKey`: it returns both fingerprints, and `replaceTrustedKey` is the separate call.
- **The app's own files** (`app-files.ts`). The host supplies a private app-data directory whose path remains under its control while the SSH route is in use. Before enabling SSH setup, the host must establish that its app-data directory and ancestors cannot be redirected by another account. Leaf creation is exclusive and replacement uses a private sibling. POSIX no-follow applies to the leaf of the open. OpenSSH reopens configuration and known-hosts paths itself. On Windows the host relies on the app-data directory's ACLs, which this module does not verify. A path the host cannot establish as private goes to Advanced.
- **The three failures** (`ssh-output.ts`) are told apart from the error output, read line by line into facts, without `-v`'s debug lines and a forward's channel lines; what is returned is the category, the cause in brackets for "can't be reached", and the exit status. `ssh` that can't be started is `spawn-failed`. `failureNote` and `forwardNote` give the fixed copy.
- **The LOOK** (`look.ts`) is a constant POSIX `sh` script whose one value is a request id the host makes. It prints a begin line and an end line carrying that id, so what a login start-up file prints before it is dropped, fake facts included; it closes its own standard input for every program it runs, cuts each program's output to 32 KiB in its pipe and sends it straight out as base64 with the exit status beside it, and ends itself after 30 seconds. The host reads at most `MAX_LOOK_OUTPUT`, counted in bytes: the largest whole LOOK the script can print (its version and both profiles' statuses each at 32 KiB, as base64, with the other lines: 132,493 characters) plus 16 KiB for what login files print before the begin line, which is bounded on its own. It needs the script's own exit 0 and every fact it always prints: a missing fact is `incomplete`. It returns only checked facts: the system's name, which fixed place holds the program (by index, never a path), the version, and from each `gateway status --json` the service's label, whether it is loaded and running and its process, the configuration path, port, bind, the running gateway's version, `rpc.ok` and the processes listening on the port. `gateway status --json` in 2026.10.6 has no auth mode field in the source read here, so the LOOK does not report one.
- **A found service** (`serviceOnPort`) comes only from a complete and consistent status: the command exited 0, the service is of a known kind, loaded and running with a known process, `rpc.ok` is true, and that process is every listener on the port. A service that reports itself stopped is `not-running`; anything less certain is `cant-tell`. `openForward` takes only a found service.
- **The forward** (`forward.ts`) is a state machine with its process, the probe, the LOOK and the clock passed in: `starting`, `verifying`, `up`, `waiting` with the cause, the failures in a row, the wait before the next try and whether two minutes have passed, and `closed` with `closed`, `key-changed` or `different-gateway`. It waits 1, 2, 4, 8 and 16 seconds, then every 30; `retryNow` tries at once, for wake and network changes. A lost race for the local port takes another at once, five times in a row. `openForward` goes through the same gates as every other call (the route as prepared, a supported client, a pin) and keeps one forward per route: the same route and service get the open one back, another is refused. After OpenSSH reports that it is setting up the local listener, Clawtrate probes the allocated loopback port with a credential-free HTTP request (`GET /healthz`, `http-probe.ts`). OpenSSH logs that line just before it binds the port, so a connection the local port refuses before any connection was made is tried again, every 50 ms, until the probe's 5 seconds are up; otherwise a probe that came too early would be reported as "can't tell". A complete status line establishes that the port answered as HTTP at that moment. The probe alone does not verify who owns that listener. A server that refuses forwarding is `forwarding-refused`; a forwarded connection the SSH server could not make is `gateway-not-answering` ("Nothing answered on the gateway port on devbox"), and "OpenClaw stopped" is shown only when the LOOK reports the service stopped (`gateway-not-running`). Then a LOOK on that connection's route must name the same gateway service on the gateway's port: the same profile, service label, configuration path and port. Another service there closes it; a stopped one keeps it waiting. The reader keeps at most 1,024 characters of the current unfinished stderr line so it can classify it across chunks. It discards each complete line after classification and exposes only typed facts. close() cancels the local probe and LOOK request, and waits for the local SSH clients that the forward started. closeAll() also joins the transport's local requests and clients. Closing an SSH channel does not confirm that the remote account has stopped the command or its descendants.
- **What the repeated LOOK does not close** (`docs/design/setup.md` section 15). A credential-free probe confirms that the forward's loopback port answered as HTTP, and a repeated LOOK confirms that the pinned SSH account still reports the expected service at that moment, while the listener's ownership and the gateway's identity remain unverified. Another account on that computer that takes the port while the gateway is stopped is caught when OpenClaw's own status no longer shows its service running there with its own process as the port's only listener. But the LOOK runs on its own connection: the gateway can stop and the port be taken between the LOOK and the client's connection, and the LOOK trusts what OpenClaw on that account reports. The identity check after hello stays the backstop, and it comes after the token was sent.
- **What it keeps, and its bounds.** In memory: at most `MAX_SSH_CAPTURES` (8) captured keys, expired ones dropped first; the latest preparation of at most `MAX_SSH_ROUTES` (16) routes; `MAX_SSH_FORWARDS` (8) forwards and `MAX_SSH_PROCESSES` (32) running `ssh` processes, past which it refuses; `MAX_FORWARD_LISTENERS` (8) listeners per forward. They are in the retention registry (`packages/core/src/owners.ts`) without a row of the host's worst case, since nothing on the bridge holds the transport yet; the unit that does gives the captured keys a row. On disk, in the app's folder: `known_hosts` and two configuration files per route; a capture's two files live only while its probe runs.
- **Windows** uses its bundled client from OpenSSH_for_Windows 9.5, the version the research ran; any other platform than macOS, Linux and Windows, a missing program, a version command that fails, Windows' older bundled 8.1, and OpenSSH before 8.4 elsewhere (which lacks `UserKnownHostsFile none`) are a typed "not supported here". The options and messages are the research's; the integration tests need an `sshd` the test can start as the current user and do not run on Windows.
- **Not done here.** The interface, the host's confirmations and the route store with one token per route; the `CODE`, `START` and `STOP` scripts; a live timeout of an unanswering address and a live "no such name" (each would reach something other than the test's own server; both are recorded outputs); IPv6 host names; an explicit agent pipe on Windows; an authoritative auth mode for the look; paths with consecutive or trailing spaces in the person's file beyond what the quoting covers; `Include` beyond one pattern in its last part; and a host certificate negotiated end to end. Also not done, from the closing review:
  - Required of the unit that builds the setup screens: before the setup host constructs a transport, it establishes that its app-data directory and its ancestors are private, and a host-boundary test gives it an app-data candidate whose parent resolves outside a private, synthetic root and expects Advanced, with no transport made.
  - A known-hosts read bounded before it is loaded, and one answer for parallel prior-trust lookups of the same route.
  - A strict recheck before "pinned" after a transient key change.
  - The HTTP probe cancelling its grace poll when it settles another way, with at most one grace poll per socket (its abort listener is removed when it settles).
  - Real sign-in with the Linux and Windows client versions the design supports: an explicit agent, host-bound public-key authentication and certificate authentication.
  - A LOOK where one profile's status can't be read and the other reports a healthy service is "can't tell", as the closing review asked; whether to offer the readable one while saying the other couldn't be read is for the setup screens, which show the person the choice.
  - Preparing a route again for another endpoint retires the old preparation before both new files are written, so a failed write leaves the route unprepared; it says so, and nothing connects on a half-written configuration. Staging both files first can follow.

## The rules plugin

`plugins/clawtrate-tool-rules` is built from the requirement lists of [the controls design](design/controls.md#21-the-plugins), section 21. Its page, [`plugins/clawtrate-tool-rules/README.md`](../plugins/clawtrate-tool-rules/README.md), says what it does and what it cannot.

- **One hook, every tool.** It registers `before_tool_call` with no matcher and the default priority, because "Ask when nothing else decides" can apply to any tool, and a matcher is fixed when the hook is registered while the rules change. The hook needs no conversation access. It reads the rules from memory, checks the rules file's size, times and inode on each call, and never waits, since the gateway fails a call closed when this hook throws or takes 15 seconds (`hook-runner-global-*.mjs`, `hooks-*.mjs`). It is an ordinary hook, not a trusted tool policy, which runs ahead of ordinary hooks and needs a declared contract.
- **The evaluator is a pure function** (`lib/evaluate.js`) of the rules and the call: a Never, then an Ask, the bot's own rules before every bot's, then the fallback, which an Allow from either scope keeps from asking. The hook only turns its answer into `block` or `requireApproval`, and never returns `params`.
- **What a call acts on** (`lib/targets.js`) is read only where it can be validated: a file tool's `path` (or `file_path`, when only one is given) as a path in the bot's workspace, and exec's `command` as words. A Never or an Ask on a path compares a folded spelling of the pattern and the path (case, Unicode spaces and the narrow space before AM or PM, curly quotes, composed and decomposed accents), which covers every name the gateway's file tools try when the exact one is missing (`path-utils-*.mjs`, `collectReadPathVariants`) and every name a filesystem that ignores case treats as one. An Allow compares the path as given, so it never lets through a spelling the other two catch. Links are not followed: the plugin does not look at the filesystem. Everything the gateway or a shell would change before the tool runs makes it unreadable, and an unreadable target acts on everything: a Never or an Ask applies, an Allow does not cover it. `apply_patch` (paths only hinted by the host) and `process` (no command) are always unreadable. The design's third kind, a tool server's tool, is a tool name pattern (`coder__deploy_*`), not a target.
- **The fallback lives in the scope**, so `set` takes `{scope, rules, fallback, expectedVersion}` and replaces the scope whole. The design names `set {scope, rules, expectedVersion}` and does not say where "Ask when nothing else decides" is kept.
- **Rule ids and versions.** The plugin gives each new rule a 12-hex id and version 1; a rule saved again with its id keeps its version unless what it says changed. A scope's version counts its saves and never repeats: a scope emptied is kept, with its version, so compare-and-set holds across a clear and a recreate. Only scopes that hold a rule or the fallback count against the 64 bots; at most 1,000 scopes are kept in all. Versions stop at the largest safe integer. Who saved a rule is a SHA-256 of the saving device's id, so a device can tell its own saves without the record naming devices.
- **The store** is a JSON file in a folder of the plugin's own in the gateway's state folder, written whole (every byte, or a failure before the rename) through a temporary file and a rename, and never larger than the 8 MiB the plugin reads back: a save is measured before anything changes. It is checked on every read as strictly as a `set`, envelope included.
- **Three states, never confused.** No rules file means nothing was saved, and nothing is decided. A file read and checked is enforced. A file that cannot be used, or one read earlier and gone since, is a lost policy, never an empty one: the plugin goes on enforcing the copy this process read last, and with no copy it asks before every call except `ask_user`, with a card saying the rules could not be read. Each change of state is logged as it is seen, and `status` reports the state, when a kept copy was read, and what is enforced (`enforcing`), apart from whether the hook is registered.
- **The decision record** is JSON lines beside it: one record per call the hook saw, metadata only, the call id hashed exactly as the gateway's audit log hashes it (`audit-recorder-*.mjs`), an ask's answer appended as its own line and joined by the record's id. 30 days and at most 50,000 records, oldest dropped first; the design gives the 30 days, and the cap is Clawtrate's. Expired records leave the file at start and on an hourly timer the plugin's service starts unreferenced, so an idle gateway drops them too and the timer never keeps it running. The file is compacted when it holds a fifth more lines than records, or when expiry or recovery needs a rewrite. An ordinary append does not compact it. One past 64 MiB is set aside at start rather than read. A line the cap evicts is remembered until a rewrite, so it too leaves the file thirty days after it was written; a record whose write failed is retried by the hourly maintenance as well as by the next record; and a record that could not be read at start (an I/O error, not a missing file) is read again before anything is appended or rewritten, so no new record joins a torn line and no rewrite is made from what memory alone holds.
- **`hook.registered`** is what the plugin can verify: a registration that had the gateway's hook interface registered the hook, and its service is running. The gateway gives a registration for setup only its methods, without `on`, so a method list alone says nothing of the hook (design section 20, row 34).
- **What a bot must be denied** is checked from the gateway's settings when the plugin starts, and written to the gateway's log, one warning per bot and reason. It reads the settings as the gateway does: an empty allow list restricts nothing, `write` in an allow list brings `apply_patch`, and a sandbox keeps commands off the gateway's machine only when the bot's exec host is not `"gateway"` (`tool-policy-match-*.mjs`, `exec-filesystem-policy-*.mjs`). A warning protects nothing. It is not a security audit finding: OpenClaw's `security audit` loads an installed plugin in validate mode, which never calls its `register`, so a plugin's audit collector does not run there (`audit-*.mjs`, `loader-runtime-load-*.mjs`).
- **A card's text can travel further than its WebSocket audience.** The gateway hands plugin approvals to its forwarder (`approvals.plugin`, to the originating chat or to configured targets) and to a channel's native approvals, with the plugin's title and description and the bot's id (`plugin-approvals-*.mjs`, `buildPluginApprovalRequestMessage`). So with `cardDetails: "auto"`, the default, the plugin redacts the description whenever `approvals.plugin.enabled`, an `approvals.plugin.<channel>` reviewer policy, or any chat channel is configured: the tool and the rule by id, version and action, and no path, command, pattern or bot id. It reads the current config for each card. `cardDetails: "full"` or `"redacted"` forces either; `status.cardDetails` says which is in force and why. The bot's id the gateway adds to a forwarded card is not the plugin's to remove.
- **The tiers are the gateway's.** `get`, `status` and `decisions.list` are registered with `operator.read` and `set` with `operator.admin`; the gateway refuses a caller below them before the plugin runs. The event is `plugin.clawtrate-tool-rules.changed`, `operator.read`, with an empty payload.

**What the gateway did that the design did not say**, on a development gateway with the plugin (OpenClaw 2026.10.6), asserted by the rules checks in `pnpm scenarios`:

- **Turned off in the middle of a run**, the plugin still decided that run's later calls, as if the run kept the plugins it started with. Its next call was asked, and Allow once ran it. Only a run that starts after the plugin is off runs its calls with no card. A plugin that stops therefore leaves calls running with no card from its next new run, not from the moment it stops.
- **With the plugin off**, a call to one of its methods from a connection below admin is refused "missing scope: operator.admin", and from admin "unknown method". The app tells a stopped plugin by its methods missing from `hello-ok.features.methods`, not by that refusal.
- **A run another bot's message started** has no one to ask: no card reached any device, the gateway answered the plugin's ask with `cancelled` at once, and the call failed with "Plugin approval required (gateway unavailable)". The design left this unsettled.
- **A routine's refused call** is counted `failed` (`tool_failed`) in the audit log, not `blocked`, and the routine run's transcript was empty, so the gateway's sentence for it ("Plugin approval unavailable: cron runs have no approval-capable initiating surface.") was not seen again. The plugin's record shows the ask answered `cancelled`.
- **Removing an entry from a bot's deny list** with `config.patch` needs `replacePaths`; with it, `null` removes the key.

## The website

The website lives in `site/` as plain HTML, CSS and one script, with no build step and no dependencies. It loads nothing from another host: no analytics, no trackers, no third-party scripts. Figtree's Latin file is committed under `site/fonts/` with its OFL licence beside it, because a static folder has no bundler to take it from the npm package the app uses. The screenshots use the app's fixture mode and sample data. Dark is the default; a visitor's choice of light is kept in `localStorage`, and each theme's screenshots are chosen in CSS so the first paint is right.

The site is published only together with the first signed beta, through the Site workflow (`.github/workflows/site.yml`), which copies `site/` and adds the newest published beta's `feed.json` and `latest-mac.json` under `updates/beta/`. From the same beta it must also:

- fill `site/download/mac/index.html`, a template, replacing `__CLAWTRATE_BETA_VERSION__` with the beta's version, `__CLAWTRATE_ARM64_ZIP__` and `__CLAWTRATE_X64_ZIP__` with `latest-mac.json`'s `arm64` and `x86_64` addresses, and `__CLAWTRATE_RELEASE_PAGE__` with the release's tag page, and deploy nothing while a token is left;
- deploy nothing while `site/install.sh` still holds the placeholder `APPLE_CLAWTRATE_TEAM_ID`, or names another team than the beta's `latest-mac.json`.

`site/install.sh` is for a first install: where Clawtrate is already installed it changes nothing and says so, because the site goes live with the first signed beta, which is built after #202 and #204 and installs its updates from Settings (Restart to Update). It is run as the site shows it: downloaded whole to a temporary file, with curl's exit status and an HTTP 200 checked, before `sh` runs it. Its body is functions, and its last line calls `main` with the one argument `main` requires, so a cut-off download runs nothing. It:

- pins Clawtrate's Developer ID team in `CLAWTRATE_TEAM_ID` and refuses to run while that is the placeholder;
- reads `updates/beta/latest-mac.json` (`{"teamIdentifier", "arm64": {"version", "url", "sha256"}, "x86_64": {…}}`) as a direct HTTP 200, strictly: JSON with no repeated key, exactly these fields and no others, the pinned team, one beta version in both entries whose date is a real calendar date, lowercase 64-character digests, and each address exactly `https://github.com/sidebandstudio/clawtrate/releases/download/v<version>/Clawtrate-<version>-mac-<arm64|x64>.zip`;
- takes the arm64 build on Apple silicon, also from a shell under Rosetta (`hw.optional.arm64`, `sysctl.proc_translated`), and the x86_64 build otherwise;
- follows at most one redirect from the release address, and only to `https://release-assets.githubusercontent.com`, checked before the second request, which is how GitHub serves release files (the app's updater follows no redirect); every curl call has `--globoff`, so the address checked is the address requested; the feed must arrive within 30 seconds, and a download that stays below 1 KB/s for 30 seconds fails. The feed is limited to 64 KiB and the ZIP to 2 GB even when the server omits its size;
- checks the SHA-256, then the archive before unpacking: only `Clawtrate.app`, no unsafe or repeated paths, the AppleDouble entries `ditto --sequesterRsrc` writes, and links only where an Electron framework has them, each link's target read from the archive and compared byte for byte with the one allowed (`Versions/Current` to `A`, a framework's top-level entry to `Versions/Current/<name>`); after unpacking it checks the tree again without following links;
- reads the app itself: bundle id `dev.clawtrate.desktop`, the feed's version, an executable for this processor; then `codesign --verify --deep --strict`, a readable signature with that identifier, a Developer ID Application authority, the pinned team and a code directory hash, and `spctl` reporting `source=Notarized Developer ID`, as the release script checks each app;
- copies the app to a private folder beside the target, checks that staged copy the same way and requires the same code directory hash, moves it into place with macOS’s exclusive rename, which preserves a destination created during the move, requires that the app at the target is the staged copy (its device and inode), and checks it in full once more, with the same hash, before reporting success. A copy that fails that last check is taken out again, only while the target is still the staged copy, and what was taken out is deleted only if it is that copy. If verification is interrupted or the moved item cannot be identified, the installer keeps the staging folder and reports its path. Anything else found at the target is left alone, and the output says where the staged copy is. INT, TERM and HUP remove only this run's private files.

`CLAWTRATE_FEED`, `CLAWTRATE_RELEASES` and `CLAWTRATE_ASSETS` point it at stand-ins on `http://127.0.0.1` for tests, and `CLAWTRATE_APPLICATIONS` at another folder to install into.

- The Work pane shows the task's details; its Files and Computer tabs are empty states until those flows exist.
- Read and unread is tracked per viewer in local storage. Marking a task read on the gateway needs a write scope.
- Re-pairing (F-456) needs the scope-upgrade methods, which belong to the write flows.
- The app does not page back through history beyond 200 rows.
- The macOS app is packaged but not signed or notarized. The desktop host can check and download a release on request. The screens, installation and the Windows Authenticode check are pending (see [Updates and release signing](#updates-and-release-signing)). The Windows installer is built and not signed; CI installs it, runs the launch check against the installed app without the four checks that need a development gateway, and uninstalls it.
- The launch check's fuse reader (`apps/desktop/packaging/fuse-check.ts`) hands the executable's path to `@electron/fuses`, which takes any path containing `.app` for a macOS bundle. A Windows install folder whose path contains `.app` (`Clawtrate.apps`, say) makes it look for a macOS Electron Framework and fail with `ENOENT`. CI's install folder does not.
- The Expo app has not been started; `apps/mobile` does not exist yet.
- The rules plugin has no interface yet: the permissions pages, the card's "Make a rule…", Activity's joins and the not-enforced note are other work, and it claims no parity row. It has not had a security review of its own, so it is for development gateways only.
- The rules plugin has no rules about addresses (web and browser), paths the host derives, or message recipients, and no Ask per recipient (design section 24). Its decision record is readable by every read connection, for every bot, and `get` returns notes, patterns and the saving device's hash at the read tier.
- The rules plugin sees an edit of its rules file made outside it at the next call, method call or hourly tick, not at once; a reader that holds rules from before keeps them until the event. Its stat, reads and appends in the hook are synchronous. It does not follow links when it matches a path. A pending card is lost if the gateway restarts, and the record keeps that ask with no answer. None of these was changed in the first review's fixes.
- The rules plugin's `status` loses the note that a decision file was set aside as oversized once a later append succeeds; the incident is not kept apart from current append health.
- The rules checks' Ask-precedence case uses one bot Ask beside local and global Allows, and its spelling case one difference of case; a global Ask fixture and harmless filename variants on a live gateway are not added.
- The rules plugin's validation messages quote what an externally changed rules file holds (a schema number, a scope id), which then reaches `status` and the gateway's log; fixed reasons are not used.
- The decision record's retention and listing assume records are appended in time order, so a clock set backwards can delay a record's removal or its listing by the size of the step; a time-ordered index is a larger change than this unit takes.
- At 50,000 records an append past the cap copies the list of record references, small beside a tool call; a ring buffer can follow.
- The rules store has no test, and no support, for a file whose identity changes while it is read: the plugin checks the file's metadata separately from opening it, so such a test would have to assert that the reader reports lost and keeps the prior verified policy, which needs a single-descriptor bounded read the store does not have.
