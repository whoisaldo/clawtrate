# Parity checklist

This is Clawtrate's definition of done. Each row is one behavior that a single automated check can verify. The behavior comes from the Grok Bot teardown in `docs/research/grok-bot-flows.md`; the section in the area column points to the evidence and the exact wording.

Columns:

- **id**: stable. Never renumber. New rows get the next free id at the end.
- **area**: the flow, with the teardown section that describes it.
- **platform**: where Clawtrate must pass the check: `desktop`, `iOS` or `both`.
- **Grok Bot behavior**: what Grok Bot does, in one or two sentences. For fine-grained control rows it says what Grok Bot lacks.
- **Clawtrate target**: `same`, or `better:` followed by what Clawtrate changes. A note after `same` narrows the scope; it does not change the behavior. Use Clawtrate's own names, art and branding, never Grok's.
  `not planned:` marks a behavior that needs a service only the vendor hosts. Builders skip `not planned` rows. The dependency pass has turned those the gateway cannot replace into `gap`, with the evidence in the gateway dependency cell; a `not planned` row that is still `todo` has a self-hosted equivalent, named in its cell.
- **gateway dependency**: what the gateway gives the row, from `docs/research/gateway-capabilities.md`. Each cell starts with a class: `client only` (nothing from the gateway beyond data another row already loads), `available` (methods and events the map names and describes cover every part of it), `partial` (they cover part, and the cell says what is missing), `plugin` (it needs a plugin from the capability map; the cell says whether the map demonstrated or only proposes it, and what works without it) or `none` (it cannot be done, and the cell says why). Then come the methods and events it uses, the operator scope, and any condition under which a call needs `operator.admin`. The scope is the tier Clawtrate requests for that behavior: `operator.read`, then `operator.write`, then `operator.admin`, plus `operator.approvals`, `operator.questions` or `operator.pairing` where a method needs them. Clawtrate does not use the narrower `operator.sessions.read` and `operator.sessions.write`, even where a method admits them, because they depend on sharing and on which sessions the caller owns, and a personal client must see every Bot and task on the gateway. "not in the capability map" marks a need the map does not yet cover, and **unverified** is carried over from the map. The capability map is the authority for this column: a builder who finds a dependency cell wrong corrects it in the same change.
- **status**: `todo`, then `done` with a passing check, or `gap` with evidence that it cannot be done without breaking a rule. A `both` row whose desktop check passes while its iOS check is still to come is `desktop done`; the value is used on `both` rows only. A check names the rows it covers at the start of its title (`F-013 F-015: …`), and `pnpm test` fails when a `done` or `desktop done` row has no such check.

Fine-grained control requirements (`FC-01` to `FC-15`, defined in the teardown under "What users say is missing") are tagged in the target column.

Where `docs/design/` specifies how an interaction looks and moves, that specification governs appearance, and this table governs what must be true.

Where a row says "Clawtrate's choice", the number or rule is Clawtrate's own acceptance boundary, not observed Grok Bot behavior. Rows that point to section 5.6, 6.1, 6.2 or the Clawtrate design proposals in sections 4.1 and 7 check proposed behavior described there.

A row whose behavior cell ends "(split from F-0xx)" was split out of that row; the original id keeps the first part.

Rows whose area says "beyond Grok Bot" are Clawtrate's own additions. There is no Grok Bot behavior to compare, so the target cell alone defines them.
