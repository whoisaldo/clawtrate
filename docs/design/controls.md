# Controls

What a person controls about each bot: what it may do with its tools, what it has been allowed, what it remembers, where it runs, and what it uses. This is the fourth part of the design, after `visual-language.md`, `conversation.md`, `bots.md` and `work-pane.md`, in the same language and with the same tokens. It is the part the reference product does not have: the teardown's "What users say is missing" (`docs/research/grok-bot-flows.md`, FC-01 to FC-15) says what people ask for, and the capability map (`docs/research/gateway-capabilities.md`) and the installed OpenClaw 2026.10.6 say what the gateway can do.

What must be true is in `docs/parity.md`: the tool-rule rows F-174 to F-180, F-222, F-328, F-330 to F-337, F-414 and F-416; the grant and audit rows F-166, F-167, F-178, F-324, F-326, F-327 and F-415; the default rows F-051, F-162, F-173, F-180, F-331, F-339, F-340 and F-365; the bot-to-bot rows F-130, F-309 to F-312 and F-436; the memory rows F-008, F-110, F-211 to F-216, F-375 to F-379, F-454 and F-455; the machine rows F-046, F-047, F-156, F-157 and F-272 to F-274; and the usage and budget rows F-131, F-232 to F-237, F-396 to F-398 and F-459. This document decides appearance, wording and input, and for every state it names the gateway fact the state rests on. Section 20 lists those facts with their sources, including what a probe plugin showed on a development gateway. Section 21 is the two plugins this needs, as requirement lists. Section 22 is the parity rows: each row's check, and the dependency cells that change. Section 23 is for builders.

One rule sits above the rest: **a screen states a guarantee only when something enforces it with nothing of Clawtrate's running.** That is the gateway's own code: its allow and deny lists, a bot's command policy, a bot's messaging list, a machine's approvals file. Anything a Clawtrate plugin adds holds only while that plugin runs: OpenClaw 2026.10.6 keeps the hook a run started with after the plugin is disabled, and new runs are governed by the remaining gateway policy, with no card for the calls the plugin would have asked about (row 33). So every line says which of the two holds it; a line that depends on a plugin says so on the line, and the page shows the plugin's state. Anything Clawtrate can only display or apply to its own sends says "Shown only". What is stored, what is loaded into a task, what is searchable, what is recorded and what is inferred are always told apart.

Model and effort per bot, the bot's account and its lock, and T3 Code are in `bots.md` sections 9 to 18 and are not redesigned here. Section 1 says where these pages sit beside them.

The prototype shows all of it: `prototype/controls.html` is the app with these screens added, and its address picks any state (section 23). The styles are in `prototype/css/controls.css` and the behaviour in `prototype/js/controls.js` (permissions, approvals, activity, messaging), `prototype/js/controls-memory.js` (memory) and `prototype/js/controls-usage.js` (usage, budgets, machines). `prototype/tools/checks/controls.mjs` checks them.

## 2. Shared rules

### What holds a rule

Every control on these pages is one of two kinds, and the design never mixes them on one line without saying so.

| Held by                      | What it covers                                                                                                                                                                                                                                                                                      | Holds when Clawtrate and its plugins are gone                                                                       | How the gateway shows it                                                                                                                                           |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **The gateway**              | A bot's own deny list (`tools.deny`), the gateway's lists and tool profile for every bot, a bot's command policy (`tools.exec.mode`), a bot's outgoing messaging list (`tools.agentToAgent.send`), the gateway's pair setting, a machine's approvals file, a routine's grant, a machine's allowlist | Yes                                                                                                                 | A denied tool is removed from what the bot is offered; a command is refused or asked about by the gateway's own card; a send is refused with `status: "forbidden"` |
| **Clawtrate's rules plugin** | Asking before any tool other than commands, rules about what a tool acts on (a path, a command, a server's tool), "Ask when nothing else decides"                                                                                                                                                   | **No.** Clawtrate cannot confirm these plugin rules are being enforced. The gateway's own restrictions still apply. | The plugin's card, or a refused call whose reason names the rule                                                                                                   |

The memory plugin is the same kind: what it adds holds only while it runs (section 12). This design has no budget plugin (section 17).

**The plugin's state** is shown wherever a plugin rule is: at the top of a bot's permissions page, on every line that depends on it, and in Settings, Permissions. It comes from the plugin's own status method (section 21), never from the method list alone, because a method can be listed while its hook is not registered (section 20, row 34):

| State                     | Established by                                                                                                                                | Shown                                                                      |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| Running                   | `clawtrate-tool-rules.status` answers with a version the rules need or newer, its hook registered, and the time its hook last saw a tool call | "Rules plugin answered at 5:46 PM. Last tool call seen 5:46 PM."           |
| Rules methods unavailable | Its methods are not in `hello-ok.features.methods`                                                                                            | "Rules methods unavailable on this gateway."                               |
| Stopped                   | Its methods are listed but `status` fails, or reports the hook not registered                                                                 | "Clawtrate's rules plugin isn't answering."                                |
| Old                       | `status` reports a version older than the rules need                                                                                          | "Clawtrate's rules plugin is version 0.9; Otto's rules need 1.0 or newer." |
| Not checked               | No answer yet in this session                                                                                                                 | "Checking Clawtrate's rules plugin…"                                       |

**When rules need a plugin that is not running** (rules methods unavailable, stopped or old), the page does not pretend. Clawtrate cannot confirm these plugin rules are being enforced. The gateway's own restrictions still apply.

**Which rules, and how Clawtrate knows them.** A plugin that isn't answering can't be asked for its rules, so Clawtrate lists them from its own last read of them (the plugin's `get`, read scope), which this device keeps with the time and the rules' version. That read holds everything that can apply to the bot: its own rules, the rules for every bot and "Ask when nothing else decides". From it the affected tools are, by their exact names:

- the whole tool group of each line with a plugin rule for this bot or for every bot (a rule about what a tool acts on is held only by denying the whole tool);
- `sessions_send`, when the bot's outgoing messaging Ask applies;
- when "Ask when nothing else decides" is on, every tool the bot is offered except `ask_user`.

If this device has no earlier read (the plugin never answered here), Clawtrate can't tell which rules aren't held: the note says "Clawtrate's rules plugin isn't answering, and this device has never read its rules, so it can't tell which aren't being enforced." and names no lines. In that case, and while "Ask when nothing else decides" is on, there is no bulk deny: the note says "To deny a tool, open its line below and choose Never." A plugin whose methods are unavailable and that was never seen has no rules to hold, and the page shows no note.

**The note**, on `--danger-soft`, short enough that the glance stays on the first screen at 390 px. The plugin's state is the line above it, so the note doesn't repeat it: "**Enforcement not confirmed.** Clawtrate cannot confirm these plugin rules are being enforced. The gateway's own restrictions still apply. Rules as last read on this device, 5:41 PM." and, for admin, "Denying them adds `write`, `edit`, `apply_patch`, `exec`, `process` and `sessions_send` to Otto's own deny list." with "Deny these in Otto's settings". Below admin: "Only a connection with admin access can deny these."

**The hold.** "Deny these in Otto's settings" is one `config.patch` adding those exact tool names to the bot's own deny list, a setting the gateway owns (row 40: with the plugin off, a tool added this way and read back was refused, "Tool ls not found").

- **Confirmed** only when `config.get` reads the entries back. Until then the lines stay "Not enforced now" and the note reads "Writing the deny…". Once confirmed the lines read "Never" with the gateway's mark, and the note reads "Denied in Otto's settings. Change files, Run commands and Message other bots are denied in Otto's own settings (read back 5:47 PM)."
- **After the plugin answers again** the denies stay until someone changes them. The note says "Clawtrate's rules plugin is running again. Otto's settings still deny Change files, Run commands and Message other bots, which Clawtrate added while it wasn't. Change them on each line." Each is changed with that line's own choice (section 5).

Clawtrate does not apply the hold by itself: the gateway runs nothing when a plugin stops, so an automatic hold would still leave the gap open until a client with admin noticed (section 24).

**What a plugin rule cannot cover**, said once on the permissions page under "For these rules to hold" (section 4), and never hidden:

- A bot that can manage the gateway or its plugins can change or remove the rules: its `gateway` and `plugins` tools must be Never.
- A bot that runs commands on the gateway's machine, as the gateway's user and outside a sandbox, can edit the gateway's settings and the plugin's store: Run commands must be Never there, or run on another machine or in a sandbox, for plugin rules to mean more than advice.
- A rule about a file tool is a rule about that tool, not about the file: commands and other tools can still reach the file where the bot may use them.

### Marks

Every rule, policy, saved approval, limit and budget carries one mark, in words with an icon, never in colour alone.

| Mark                                               | Icon                | Used for                                                                                                                        |
| -------------------------------------------------- | ------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| "The gateway enforces this"                        | shield              | A gateway-held control (table above). The only unqualified guarantee                                                            |
| "Only while Clawtrate's rules plugin runs"         | plug                | A rules-plugin control while the plugin is Running. The memory plugin has the same mark with its name                           |
| "Not enforced now: the rules plugin isn't running" | warning, `--danger` | A rules-plugin control while the plugin is absent, stopped or old                                                               |
| "Set on the gateway"                               | lock                | The gateway's settings for every bot, or a machine's approvals file: enforced by the gateway, shown, never changed by Clawtrate |
| "Shown only"                                       | eye                 | Something Clawtrate displays or applies to its own sends; nothing on the gateway holds it                                       |

The mark sits under a line's words in 12 px, `--text-faint` (the warning in `--danger`), with its icon; on a rule's page it is a fact row, "Held by", with the full sentence. A screen reader reads it as part of the line.

**Why Clawtrate does not change "Set on the gateway".** The gateway's settings for every bot and a machine's approvals file affect every bot and every person who uses the gateway. Clawtrate writes only a bot's own entries and its plugins' rules, and shows the gateway's with a padlock: "Set on the gateway. Clawtrate can't change it." (F-333)

### Four facts kept apart

Wherever a page shows a tool, a policy or a place, it keeps four facts apart and labels each, because they come from different records and can disagree (section 20, rows 1, 4 and 22):

| Fact                  | Means                                                                                                                                                                                                                                                                | From                                                                   |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| **Offered**           | The tool is in what the bot's latest task was offered                                                                                                                                                                                                                | `tools.effective {sessionKey}`, a cached listing, with its date        |
| **Default**           | A value for every bot that this bot inherits because it sets none                                                                                                                                                                                                    | `config.get`, the gateway's settings for every bot                     |
| **Effective posture** | What the gateway will do for this bot's next call: the bot's own setting when it has one, else the default, combined with a machine's approvals file (the stricter of the two, and the more asking; section 20, row 4), and a plugin rule only while the plugin runs | `config.get`, and the machine's file (admin) when it applies           |
| **Observed**          | Where a call actually ran, or what it actually did                                                                                                                                                                                                                   | The call's own result in a task (`work-pane.md` §16), or the audit log |

"Narrow, never widen" is said only of the tool allow and deny lists, where the gateway's layering really works that way. A bot's own command policy replaces the default for that bot: it can be wider (section 20, row 4).

### Input

- A choice is one radio group with one tab stop; arrows move and choose; Home and End go to the ends. Choosing saves at once, except where section 5 asks first, and the save is announced only once the gateway's read-back agrees.
- A page's Back returns focus to the line that opened it. A save keeps focus on the control saved. A background read never moves focus.
- Fields that take a pattern or a number say what they accept before anything is typed, mark themselves invalid with the reason, keep focus, and save nothing until they are right.
- One polite live region announces: "Saved. Change files: asks first", "Couldn't save", "Revoked", "Removed", "Memory saved", "Deleted", "Budget saved", "Exported 7 files", and the access request's own phrases.

## 3. What a rule means

### The order, strongest first

The gateway decides; Clawtrate never works out a verdict of its own and never implies a check that did not happen. A stronger one is never loosened by a weaker one. This is the rules plugin's own order (section 21) with the gateway's around it.

| #   | What applies                                                                                                                                                | Held by                                                                                             | What the person sees                                                                                                                  |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | The gateway's settings deny the tool for every bot: its deny list, its tool profile, its sandbox, its provider policy                                       | The gateway: the tool is removed from what the bot is offered, and no later layer can grant it back | "Never", with the lock. Never a card                                                                                                  |
| 2   | A deny for this bot: a whole tool in its own deny list                                                                                                      | The gateway                                                                                         | "Never". A call made anyway ends as a failed card (below)                                                                             |
| 3   | A Never rule about what a tool acts on, for this bot or every bot                                                                                           | The rules plugin, while it runs                                                                     | "Never" for those targets, with the plugin's mark                                                                                     |
| 4   | Matching P5 Ask                                                                                                                                             | The rules plugin, while it runs                                                                     | "Asks first": a card. Allow once passes this check.                                                                                   |
| 5   | Nothing above in the rules plugin                                                                                                                           | "Ask when nothing else decides" (the rules plugin), unless an Allow rule matches                    | A card, or nothing                                                                                                                    |
| 6   | For commands, a separate later check: the bot's command policy with the machine's approvals file, and the automatic review when it is Review first (`auto`) | The gateway                                                                                         | Commands on the machine's allowlist run; the rest are asked about, reviewed or refused as the policy says. Other tools: the call runs |

- **For every bot and for one bot.** A Never or an Ask applies wherever it is set; an Allow rule never undoes an Ask or a Never, for this bot or for every bot. (F-177, F-331)
- **What an Allow rule does.** It keeps "Ask when nothing else decides" from asking, and nothing else: it never passes an Ask rule or a Never. To stop an Ask rule asking, change that rule. (F-328)
- **The gateway's own standing approvals** (a machine's allowlist entry, a routine's grant) pass step 6 only; they never pass a rules-plugin Ask.
- **Words are not permissions.** The gateway's command reviewer is given a bounded part of the task's earlier messages as evidence (section 20, row 39); that is input to its verdict and nothing more. Earlier words never pass a call by themselves and never override an ask or a deny. (F-180, F-339, F-340, F-414)

### Two layers for commands

A command passes two checks in turn: the rules plugin first (steps 3, 4, 5), then the gateway's own command check (step 6). Neither can wave the other through: a plugin Allow rule never stops the gateway asking, and a command can meet two cards, each saying who asks.

### What "ask" shows, and to whom

**The card** is the approval card of `conversation.md` §12. For a plugin ask, its full request says "Asked by Clawtrate's rules plugin: Otto's rule 'Ask first · notes/**', version 1.", and for admin "Make a rule…" where section 6 permits it. It offers **Allow once and Deny, never Always allow**: the gateway tells the plugin only the decision, not which approval it was or who answered (row 35), so nothing trusted could tell the plugin whether the person may make a standing permission. A standing permission is a rule, made on the rules page with admin (section 6).

**Who sees it.** Shown live (section 20, row 30): the device whose message started the run receives the card and can answer it, and so does an admin connection; another device holding the approvals scope, and a read-only device, do not. A run started by a device with read and write only, while no approver was connected, had its call refused ("Plugin approval required (gateway unavailable)", row 32); with an approver connected that was not tried.

**How long it waits.** The plugin asks for its wait, and the gateway keeps it up to 10 minutes (row 31: 900,000 ms became 600,000; a 4,000 ms wait ended in about 4 s). Clawtrate's plugin asks for 10 minutes, so the card's footer says "The rules plugin asks for a 10-minute wait." The card reads Expired only from the approval's terminal state or the call's result ("Approval timed out"); a late answer is refused with "approval already resolved".

**When nobody can be asked.** Shown live: in a routine's run the gateway raises no card and refuses the call at once, "Plugin approval unavailable: cron runs have no approval-capable initiating surface." (row 32). The routine's own summary may still claim the work was done. So in a routine a rules-plugin "Ask first" means refused, and the page that sets such a rule says so wherever the bot has routines: "Otto has 1 routine, Weekly cleanup. There, Ask first means refused: a routine's run has no one to ask, and the call is refused with no card. The routine's own summary may still say the work was done." The gateway's own command card is different: a routine's command can run under that routine's grant (section 8). A run started by another bot's message can have no eligible reviewer, in which case its Ask is cancelled and the tool result says the gateway was unavailable.

### A change while a card waits

Two changes were tried while a plugin card waited (row 33): saving the bot's deny list, and turning the plugin off. In both the card stayed listed, an answer given afterwards was acknowledged, and the call then failed with "Plugin approval required (gateway unavailable)". A change to the plugin's own rules that was not a configuration change left the call to its card, and Allow once ran it. No other change was tried. So:

- An answer and what then happened are two facts, shown apart (section 18).
- Before a setting is saved while a request of the bot's waits, the line's page says so beside the choice: "A pending request may stay open after you change a setting. Its answer and its outcome are shown separately." with "Show the request".

Two plugin cards can be pending at once. OpenClaw 2026.10.6 accepted an answer to one of them and then cancelled the waiting call. Render the gateway's call result independently of the acknowledged answer.

### What a refused call looks like

A refused call never runs. In the transcript it is the action card's Not run outcome (`conversation.md` §7.3), shown as failed so it stays in view, and its opened view says what decided it, from what was reported at the time:

## 9. Activity

Activity lists the tool actions the gateway's audit log holds, newest first, and what caused each where a record says so (F-324).

**A row**: the time; the bot; the task; the action as the audit log names it (the tool, and a command or target only when an independently readable tool result in the task's own transcript has it); a tag, **Allowed**, **Asked**, **Denied** or **Blocked**; and on the second line its cause, labelled:

- **Recorded**: a record made with this call shares its run and call identity: the call's own result in a task this connection can read ("the gateway's sentence"), the rules plugin's decision record (read scope: "Recorded: Otto's rule 'never under secrets/**', version 1 (now version 2)"), or the gateway's approval history (approvals scope: "Recorded: answered Allow once"; "your answer" only when this reader is established as its resolver).
- **Inferred**: Clawtrate read something before the call that would explain it, and nothing contradicts it; the row says what and when ("Inferred: Marlow's messaging list didn't name Pip when it was read at 5:30 PM"). A call a routine's grant may have passed reads "Cause not recorded". An earlier read of a rule is never Recorded.
- **Cause not recorded**: nothing joins, or the gateway's answer names no cause ("Plugin approval required (gateway unavailable)", "Tool read not found" with no read naming the tool). The row shows the tool and the time.

A cause names the rule version the record names, which stays what it was when the rule is edited ("version 1 (now version 2)"). A cause is shown only to a connection that can read its source: below the approvals scope a cause from approval history reads "Needs approvals access", with no command, approver or title. The rules plugin's decision record is read scope.

**Filters**, in one band above the list that never covers it: a select for the bot and a select for the verdict (All, Allowed, Asked, Denied, Blocked). On the phone the band takes as many lines as it needs, always above the list.

**Opened**, a row shows its facts (run, tool, the record's id, retained until) and, when a task this device has loaded holds that call, "Show in chat", which opens that task with that step in view and focused. Otherwise: "This step isn't in a task this device has loaded."

**The foot**: "The gateway keeps 30 days of activity, up to 100,000 records, without arguments or results. A call to a tool the gateway removed leaves no record here." There is no Clear: the gateway has no method to clear its audit log, and Clawtrate keeps no history of its own here.

**States**: loading; couldn't load; empty; the gateway records none ("The gateway isn't recording activity: its audit log is switched off in its settings."); more than a page ("Show older"); a partial history ("Records before Oct 19 have expired.").

## 10. What a new bot starts with

`agents.create` takes only a name, a workspace, a model and a picture (row 36), so a new bot exists with the gateway's settings for every bot until a second write gives it its own. Clawtrate makes that second write restrictive, and loosens in a third, **to the command policy the person chose in New bot** (`bots.md` §3, "Approvals"). The sequence is the one of `bots.md` §3, "What Create does": step 1 advances only on `agents.create`'s confirmed reply, and steps 2 and 3 write only to the `agentId` it returned. Each later step is one hash-guarded write, and what the page shows after it is what the read-back has, never what was sent:

| After                 | Run commands                                                               | The bot's deny list                                                                                                                                 | Its model                 | Clawtrate sends to it |
| --------------------- | -------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------- | --------------------- |
| 1. `agents.create`    | Inherited from the gateway's settings; Clawtrate claims nothing about them | Empty: the gateway's lists for every bot apply                                                                                                      | As created                | No                    |
| 2. One `config.patch` | Never (`tools.exec.mode: "deny"`)                                          | `gateway`, `plugins`, `automations`, `browser`, `message`, and `<server>__*` for every tool server (`t3code__*` for T3 Code, `bots.md` §20, row 27) | `fallbacks: []`, explicit | Yes, once read back   |
| 3. One `config.patch` | What was chosen: Ask (`tools.exec.mode: "ask"`) or Full (`"full"`)         | `gateway`, `plugins`, `t3code__*`, written with `agents.entries.<id>.tools.deny` in `replacePaths`                                                  | unchanged                 | Yes                   |

Before each of steps 2 and 3, the host reads the config with `config.get` and sends the patch with that hash. It stops and refreshes, writing nothing, when the bot's entry is gone, when the id no longer identifies the bot Create returned, or when the hash has changed; it never writes an entry that is missing. Step 3 names the exact deny path in `replacePaths` because the gateway refuses a patch that removes list entries without it (row 12), and step 3 removes step 2's restrictive entries. Both choices keep the same order, Never first and then the chosen policy, and step 3's deny list is the same for both.

Clawtrate sends nothing to the bot and starts no task for it until step 2's read-back agrees. Between steps 1 and 2 the bot inherits the gateway's settings, whatever they are; New bot says so above Create: "Before Clawtrate sets Viral's policy, the new bot inherits the gateway's settings."

### The choice: "Ask before acting" or "Run without routine approvals"

New bot asks it on its own step, Approvals, after Account (`bots.md` §3). **Nothing is chosen at first, and Create stays unavailable until one is chosen.** The host also refuses a Create that carries no choice. The choice decides step 3's command mode and nothing else:

| Choice                            | Its line in New bot                                                                                                                           | Step 3 writes                                 |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| **Ask before acting**             | "Sets Viral's command policy to ask for approval when a command misses the machine's allowlist."                                              | `agents.entries.<id>.tools.exec.mode: "ask"`  |
| **Run without routine approvals** | "Sets Viral's command policy to run without routine approval. The machine, the task or a rule can still require approval or block a command." | `agents.entries.<id>.tools.exec.mode: "full"` |

It is not the whole outcome for a command: the approvals file of the machine the command runs on can tighten it, including with an entry for this bot, or deny commands entirely; a task's permission mode can ask; a plugin can ask or block on its own (research §2.2, section 14). A tool deny list bars the named tools; it says nothing about what a command can change.

When the file is absent, can't be read, or doesn't settle it, the general line stays. The file's defaults alone don't establish what a given bot gets, so nothing else is inferred from them.

## 17. Budgets

A budget is a number of tokens a bot or a routine may use in a day or a week (F-234). **A budget is a warning, everywhere, and says so ("Shown only").** Nothing in this design stops a bot at its budget: that would need a trusted identity for each model attempt, the period it counts in, and a rule for charges that arrive late, twice or never and for runs that start at the same moment, and the gateway's per-attempt usage summary is best-effort and carries no attempt id (row 27). So no state says a budget stops anything, and "Stop at the limit" is not offered (section 24).

**Setting one**, on the bot's Usage page: Daily or Weekly, a number ("Tokens", whole, 1,000 or more), counting the total the gateway reports for the bot (or the routine) in that period. "Save budget". A Daily budget is labelled and counted daily ("41k of 200k tokens today", "Resets at 00:00, your time"); a Weekly one weekly ("1.64M of 2.5M tokens this week", "Resets Monday at 00:00, your time").

- At 80 percent (F-396): a grey line in the bot's open task, "Otto has used 82% of its weekly budget: 1.64M of 2M tokens.", and a system notification on the desktop.
- At 100 percent (F-397): the composer says "Otto has reached its weekly warning budget. This is shown only: other apps, channels and Otto's routines aren't stopped." with "Raise budget". A local send hold is not implemented: it would hold only Clawtrate's own sends, and only once the period's count is complete. With admin, "Pause Weekly cleanup", which pauses the routine itself (`cron.update`), said as that and not as the budget.
- Resets daily at 00:00, weekly at 00:00 on Monday, in this person's time zone; raising it ends the warning; a local send hold, were it implemented, would be released at once and depend on a complete count for that period (F-398, F-459).

Kept as this person's preference with the gateway (row 29), so it is the same on their other devices.

**States**: none; under; warned; reached; Daily; an invalid number ("Enter a whole number of 1,000 or more.").

## 21. The plugins

Each plugin is written from its list, each item checked by a test or a review, and each gets its own security review before it is installed on any gateway that is not a development gateway. Both fail open when they are gone (row 33), so neither is presented as a guarantee (section 2).

### Clawtrate's rules plugin (`clawtrate-tool-rules`, P5)

**What it must do.**

- [ ] One hook for agent tool dispatches that call it; no conversation access.
- [ ] Decide in this order, the same as section 3: a matching Never (block, with the rule named); a matching Ask (`requireApproval`); "Ask when nothing else decides", unless an Allow rule matches (`requireApproval`); otherwise no decision. An Allow rule never passes an Ask or a Never.
- [ ] Match on the canonical tool name and, only for named tools whose parameter the hook receives and can validate, that parameter (a file tool's `path`; `exec`'s `command`; a server tool's name). A call whose parameter can't be read is treated as acting on everything.
- [ ] Ask with a title of at most 80 characters, a description of at most 512 characters, `timeoutMs: 600000`, and only Allow once and Deny. Full text names the rule and target. With forwarding or chat configuration, the default text names the tool and the rule by id, version and action. The gateway can add the bot id when it forwards a request. The explicit full-text override can send target details with the request.
- [ ] Refuse at every limit (section 6), counting each scope's Allow, Ask and Never rules; never evict.
- [ ] Keep a metadata-only decision record for 30 days: time, bot, task, run, call id hashed as the audit log hashes it, tool, decision, and its source (a rule id and its version at that moment, the fallback, or none), so a cause can be joined to an audit record by run and call identity.
- [ ] `clawtrate-tool-rules.status` (read): version, rules schema version, whether its hook is registered, the time its hook last saw a call, and which tools it matches; "Rules unavailable" if reading its rules fails.
- [ ] Methods `get`, `decisions.list` (read; newest first, paged by a cursor that goes on after the last record listed, with `before` as a time filter); `set {scope, rules, fallback, expectedVersion}` (admin, which the gateway checks when it registers the method), with `fallback` the boolean for asking when no other rule decides. An empty invalidation event; readers re-fetch on receipt.

**What it must never do.** Rewrite a call's parameters; get ahead of the gateway's own policy; ask or block for `ask_user`; let an Allow outrank a Never or an Ask; make a standing permission from a card's answer; put arguments or results into the plugin's decision record or its own log messages; put rule data into invalidation events; add targets or bot ids to automatically reduced approval text. OpenClaw may include arguments or results in its task data and may log arguments when a tool is denied or fails, and the gateway controls the forwarded request envelope.

#### As built against OpenClaw 2026.10.6

1. OpenClaw 2026.10.6 keeps the hook a run started with after the plugin is disabled, and new runs are governed by the remaining gateway policy.
2. With the plugin disabled, a direct `status` call returned missing `operator.admin` to the reader and unknown method to admin.
3. A routine's plugin Ask produces no card, records `cancelled`, and is audited as `failed` with `tool_failed`, even when its summary says the work was done.
4. A scope save requires `set {scope, rules, fallback, expectedVersion}`, with `fallback` the boolean for asking when no other rule decides.
5. Tool-server rules match OpenClaw's exposed tool name with `<server>__<pattern>`, without inspecting the server tool's arguments.
6. The plugin writes exposure warnings at startup, and OpenClaw's standalone security audit reads installed plugin metadata without running its service.
7. Removing an existing bot deny list with `config.patch` uses `null` and the exact array path in `replacePaths`.
8. A run started by another bot's message can have no eligible reviewer, in which case its Ask is cancelled and the tool result says the gateway was unavailable.
9. For known lost rules, the plugin keeps applying the last verified policy when available, and otherwise asks before every dispatch that reaches the hook except `ask_user`.

   While the rules are lost and no earlier copy is held, a person can allow once a call that a lost Never would have refused; the card says the rules could not be read.

10. For path rules, Never and Ask fold letter case, the specified Unicode spaces and apostrophes, and composed or decomposed accents after path parsing, while Allow compares the parsed path without those folds.
11. Auto redaction omits paths, commands and agent ids from plugin text when forwarding or chat configuration is present, and OpenClaw can add the agent id to the forwarded request.
12. The decision record removes expired metadata at startup and during hourly idle pruning, including after a failed disk rewrite becomes writable again.

### Clawtrate's memory plugin (`clawtrate-memory`, P2)

**What it must do.**

- [ ] `list`, `read` (read, only within what that connection may read); `write {path, content, expectedHash}`, `delete {path, expectedHash}` (admin) for notes and shared folders.
- [ ] **One root writer**, the only code in the plugin that writes a `MEMORY.md`: given a bot, the hash it expects and the new content, it holds that workspace's lock, checks the hash, writes a temporary file and renames it over the file, and reports the new hash or why it refused. The race with a write made outside the lock between its check and the rename is stated, not hidden. `copy` writes root memory only through it.
- [ ] `copy {item, agents[], expectedHashes}` (admin) for shared items: one root-writer call per bot, in turn, each reported on its own (`{copied, hash}`, `{refused, reason}`, or `{unknown}` when the write's result was lost); each copy marked with the item's source id, so `uncopy` can remove exactly that copy and "Check again" can find it. It is not all or nothing, and says so.
- [ ] Resolve a bot's workspace with `resolveAgentWorkspaceDir` and refuse a workspace the gateway reaches through a device bridge. Open with no-follow, refuse hard links, check after opening that the file is inside the root by its identity, and refuse a configured shared root that is a link or outside the gateway's state.
- [ ] Record a saver only for a successful write: its own writes, and an `after_tool_call` observation of a file tool whose result succeeded, with no revision unless the write reports one. The observation sees arguments and results; it keeps only the bot, task, time, path and hash.
- [ ] Report searchability only from a search that returned that revision; a read by name is not a search.

**What it must never do.** Write outside notes, shared folders and its root writer; move an item between two files; delete a folder; keep memory text anywhere but the files themselves; emit paths or text in a broad event; call a reindex the gateway's owner hasn't supported.

## 24. Not covered here

- A task's own permission mode and tool overrides: the task's Details.
- Rules typed as sentences: nothing on the gateway can evaluate one (F-174 now asks for rules built from choices, with an optional note).
- Editing the gateway's settings for every bot from Clawtrate: shown, locked.
- Proactive check-ins, notifications per bot, quiet hours, routines' pages and deleting a bot: other packages. Routine grants and budgets link to a routine by its id until that design exists.
- The phone's own permission requests and the Secure Form (`conversation.md` §24).
- The computer plugin's install (`work-pane.md` §19).
- Compaction (`conversation.md`); section 16 only reports context figures.
- A per-turn record of model and effort (F-044).
- A group conversation's approvals with several reviewers (FC-09): the card's reviewer rules here are the gateway's (row 6), and a group's are not yet designed.

Cut from this design because nothing proven supports them, each waiting for a capability the gateway doesn't have:

- **Always allow on a rules-plugin card, and the grants it would make** (a scope, a lifetime, every bot, revoking, expiry): waits for the gateway to give a plugin's approval callback the approval's id and the answering connection's identity and scopes (today it gives the decision alone, row 35). F-167's plugin part, F-326, F-327, F-331 (2, 3) and F-415 stay `todo`.
- **Clawtrate denying a stopped plugin's tools by itself**: waits for the gateway to fail closed for a missing plugin hook, or to run something when a plugin stops; a client can only act once it notices, and only with admin connected (row 40).
- **Stopping a bot or a routine at its budget**: waits for a per-attempt usage record with an attempt id the gateway vouches for, and an admission check that counts runs starting together. F-397 stays `todo`, and F-398 and F-459 cover only Clawtrate's own sends.
- **Which saved approval let a call run**: the gateway's records don't link a call to the grant that passed it, so such a cause is Inferred.
- **One all-or-nothing copy across several bots' root memory**: there is no transaction across workspaces; copies are per bot (section 13).
- **Rules about target types the hook can't validate**: addresses (web and browser), paths the host derives, and message recipients, whose resolution happens inside the tool. Incoming messaging rules and an Ask per recipient go with them; F-130's incoming part and the rules plugin's messaging rows stay `todo`.
