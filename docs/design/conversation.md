# Conversation components

How a running turn looks, moves and reads. This is the second part of the design; `visual-language.md` is the first and defines the tokens, type, surfaces, the rail and the plain transcript this builds on.

The behaviour these components must have is set out in the teardown's design proposals (`docs/research/grok-bot-flows.md`, sections 4.1, 5.6, 6.1, 6.2 and 8.8) and checked by `docs/parity.md`. This document decides appearance, wording, motion and input, and for every control it shows it says what the control does, how it is reached from the keyboard and what it is called. Parity ids are given beside each requirement. Section 22 says what each part starts from in the shell as it is built and what the builder changes there. Section 23 lists the parity rows whose wording has to change and why.

One rule sits above the rest: **no label claims more than the gateway has reported.** A card says "Sent" when an event says the message was accepted, not when the call started. An approval's outcome says the command can run, not that it ran. While the connection is down, nothing on screen looks live.

A second rule sits beside it: **the conversation reads at the level of what a bot did.** Every action is a plain-words card a person can follow without opening anything; reasoning stays folded away, and the raw call is one step further (section 7).

The prototype shows all of it: `prototype/gallery.html` has every component in every state, and `prototype/conversation.html` plays one scripted turn inside the shell, and three more runs that test the action cards (`?scene=short`, `?scene=long`, `?scene=thought`). The styles are in `prototype/css/conversation.css` and the markup in `prototype/js/components.js`, one function per component.

## 1. How the pieces fit

A turn in the transcript, top to bottom, in the order things arrive:

```
your bubble
  progress bubble            what the bot says as it goes, and text it writes beside a tool call
  action cards               one line per action, or per fold of one kind: "Read 6 files",
                             "Searched the web for …", "Messaged Marlow", "Messaged T3 Code"
  approval or question card  when the bot needs you
  "Thought for 8s"           when reasoning led to the reply; folded
  reply bubble               streams in
  status line                the avatar and a phrase; always last, leaves when the run ends
  run line                   "Worked for 1m 12s · 14 actions", once the run has ended
```

Calm by default: a finished turn is bubbles, a column or two of one-line cards, and one quiet line. A person can tell what the bot did from that alone. Complete on demand: every line opens in place, and every card, of every kind, can show what the gateway actually sent (section 9).

Everything that opens does so in place and grows downward. Nothing above an opened element moves. Folded content uses the browser's own disclosure (`details` and `summary`), so each has a keyboard path and find-in-page reaches folded text.

Text is never faded with opacity. A message that has not been sent uses the neutral raised fill with `--text` (section 6), not a dimmed version of your bubble.

### Motion

Motion says what state something is in. It never makes anyone wait: no enter animation delays content, nothing is held back to finish a transition, and removed elements go at once except the status line's 200 ms fade.

**Reduced motion** comes two ways, as in the shell: the system setting (`@media (prefers-reduced-motion: reduce)`) and the app's own (`[data-motion="reduce"]` on the root). Every rule for a still form is written under both. Every loop stops and every transition is instant. Each state keeps a still form that says the same thing, listed with each component below. (F-291)

**A lost connection** stops every motion that stands for the gateway's work, whatever the motion setting (section 19).

### Input

- **Pointer.** Hover shows full text for anything truncated, as a tooltip.
- **Touch.** Every hover has a tap or a touch-and-hold equivalent, listed with each component.
- **Keyboard.** Everything that opens is a `summary` or a button with `aria-expanded`: Tab reaches it, Enter or Space opens and closes it. Focus order follows reading order. New content never takes focus. When something that holds focus is replaced (a card resolving, an action finishing, a card becoming a fold), focus moves to the same control in what replaced it, or to the replacement's first control.
- **Shortcuts** are written for the Mac. On Windows and Linux, Ctrl stands for ⌘ and Alt for ⌥. A shortcut that belongs to a card applies while focus is inside that card and wins there over a window-wide shortcut with the same keys; outside the card the window-wide one applies. (F-072)

**Hit areas.** Sizes in this document are what is drawn. On touch, every control's hit area is at least 44 × 44 px, extended invisibly where the drawing is smaller. Desktop row heights are not touch targets and stay compact.

| Control                                                               | Drawn, desktop | Drawn, touch      | Hit area, touch |
| --------------------------------------------------------------------- | -------------- | ----------------- | --------------- |
| Copy button                                                           | 24 px          | 32 px             | 44 px           |
| Text buttons on a card ("Raw", "Show all")                            | 24 px tall     | 28 px tall        | 44 px tall      |
| The Readable and Raw tabs                                             | 26 px tall     | 36 px tall        | 44 px tall      |
| Buttons on a request card                                             | 36 px          | 48 px, full width | 48 px           |
| Jump to latest                                                        | 36 px          | 44 px             | 44 px           |
| Rows that open (cards, rows in a fold, the run line, "Thought" lines) | 30 to 40 px    | 44 px             | 44 px           |

### State marks

A 12 px mark, used in task rows, beside state words and as the avatar's badge. Shape carries the meaning, so colour is never the only cue.

| Mark             | Shape                                | Colour                                    |
| ---------------- | ------------------------------------ | ----------------------------------------- |
| working, sending | An arc travelling round a faint ring | `--accent-line` (sending: `--text-muted`) |
| waiting          | A solid dot that pings               | `--warn`                                  |
| blocked          | A disc with a bar                    | `--warn`                                  |
| failed           | A disc with an exclamation mark      | `--danger`                                |
| stopped          | A disc with a square                 | `--text-faint`                            |
| done             | A disc with a check                  | `--accent-line`                           |
| check            | A check alone                        | The text colour                           |
| unread           | A dot                                | `--accent-line`                           |
| queued, unknown  | A hollow ring                        | `--text-faint`                            |

The hollow ring means two things, so it never stands alone: the word beside it says which. Reduced motion: the arc holds still at one position; the ping becomes a fixed halo.

### Announcements

The conversation has one polite live region. It speaks changes a sighted reader would notice at a glance and nothing else:

- a run's lifecycle: "Otto is working", "Otto is waiting for you", "Stopping", "Stopped", "Otto finished", "Otto couldn't finish";
- the connection and access: "Reconnecting", "Connected", "Access requested", "You can now send, stop and answer";
- the result of an action the user took: "Copied arguments", "Couldn't copy. The text is selected.", "Queued", "Held until you answer".

It does not speak each phrase, each action or the elapsed time.

## 3. What the connection may do

A gateway grants a connection one of three tiers. The conversation is useful on every one of them, and each feature asks only for the tier it needs.

| Tier        | The conversation shows                                                                                                                                                                                                                       | The conversation offers                                                                                                                               |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| Read        | The transcript, live work as it happens (the status line, action cards, Messaged cards among them), and Raw for what the gateway sends. The gateway does not send pending approvals or questions on this tier, so they are not shown at all. | Reading, opening, copying. No composer, no Stop, no answers.                                                                                          |
| Interactive | Everything above, and pending approvals and questions                                                                                                                                                                                        | Sending, stopping, answering                                                                                                                          |
| Admin       | The same conversation                                                                                                                                                                                                                        | Management screens elsewhere: saved permission rules, a bot's own model. Requested the first time such a screen is opened, never by the conversation. |

One function answers "may this connection write?", the shell's `canWrite(connection)`. It is true on the interactive and admin tiers when the host offers the commands, and it decides the composer, Stop, the answers on cards and every "New" control.

**The access bar** takes the composer's place on the read tier. It is a shelf row on `--bg-bubble` at the foot of the column, the composer's width.

| State               | The bar says                                                                                                                                                                                                                                                                                                                                                              | Actions                                                             |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| Read-only           | An eye, "**Read-only.** You can follow Otto's work here. Approvals and questions aren't shown on this connection."                                                                                                                                                                                                                                                        | "Request access" (primary)                                          |
| Sending the request | "Asking the gateway…"                                                                                                                                                                                                                                                                                                                                                     | none                                                                |
| Requested           | The waiting state's words for where the request waits (`setup.md` §9, "**Waiting for approval on devbox.** …" and its siblings), then the command the host supplies in a `--bg-pane` line with a copy button, then "This changes by itself as soon as the owner approves or denies the request, or it expires.", then "Request 7c41d09e" in mono with its own copy button | "Check now" where the host can look, "Stop waiting" (`setup.md` §9) |
| Denied              | "**The request was denied.** Nothing changed. This device can still read."                                                                                                                                                                                                                                                                                                | "Request again"                                                     |
| Expired             | "**The request expired** before it was approved."                                                                                                                                                                                                                                                                                                                         | "Request again"                                                     |
| Couldn't ask        | "**Couldn't send the request.**" and the reason                                                                                                                                                                                                                                                                                                                           | "Try again"                                                         |

The gateway answers a request for more access by a continuous wait (`device.scopes.waitUpgrade`). Where the host can look at the gateway's computer (this computer, SSH) it also checks the pending list on a schedule, and the bar shows the next check and "Check now"; on an address route there is nothing more to look at, so that bar has no countdown and no "Check now" (`setup.md` §9). It has no "Cancel request" either: the gateway has no way to withdraw a request it holds, and only the owner's decision or its expiry ends one. While the connection is down the bar keeps its words and offers no action, since asking needs the gateway.

- One request covers sending, stopping and answering. The app makes it when the user chooses "Request access"; it is never made silently, and it never asks for admin.
- The command and the request id come from the host. The design never writes a command of its own.
- While requested, the bar keeps its place and the conversation stays live above it. Leaving the task and coming back shows the same state.
- **When access arrives**, the bar is replaced by the composer without moving the transcript, the status strip says "**Access granted** · you can send, stop and answer" for 4 seconds, and the same words are announced. If focus was in the bar it moves to the composer's field; otherwise it stays where it was. Approvals and questions that were pending arrive as cards under the ordinary rules: they do not take focus, the status line and the rail change to "Waiting for you", and Jump to latest reads "Needs you" when a card is out of view (section 14).

**A wait this device cannot see.** If the gateway reports that a run is waiting while the connection is on the read tier, the status line reads "Waiting for an answer" in `--text-muted` with the blocked badge, and a note sits above it: "Otto is waiting for an approval or an answer. This device can't see it on a read-only connection." with "Request access". Nothing is shown when the gateway does not report the wait.

**A request this device can see but not answer** (a tier or capability short of the one the request needs) is a card with the title and summary, the tag "Needs approval", no buttons, and one line: "You can read this request but not answer it from this device." with "Request access". Its full request and Raw still open.

**Keyboard and names.** The bar is a `region` named "Access". Its buttons are ordinary buttons in reading order; the copy buttons are named "Copy approve command" and "Copy request id". Nothing in it has a shortcut.

Where a gateway offers no way to step up at all, the bar says "**Read-only.** This gateway does not let this device send." and has no button.

## 4. The state avatar

The avatar is the first signal. Three layers say the state, so that no single one has to be seen:

- **The face** (characters only): where the eyes look and how the body moves.
- **The ring**: an arc that travels round the avatar while a tool is running. 1.5 px, 4 px outside the avatar, `--accent-line` on a faint track.
- **The badge**: a state mark at the top right, with a 2 px halo in the surface colour, for the states that need you or went wrong.

| State           | Entered when                                                                        | Eyes                             | Motion                                      | Ring          | Badge                                | Still form                                |
| --------------- | ----------------------------------------------------------------------------------- | -------------------------------- | ------------------------------------------- | ------------- | ------------------------------------ | ----------------------------------------- |
| idle            | No active run in any of the bot's tasks                                             | Round, looking the bot's own way | A blink every 5.6 s, staggered between bots | none          | none                                 | Eyes open                                 |
| thinking        | A run is active and no tool call is running                                         | Turned up                        | Sways 4° each way, 2.6 s                    | none          | none                                 | Eyes turned up                            |
| working         | A tool call is running                                                              | Straight ahead                   | Bobs, 0.6 s each way                        | Orbits, 1.2 s | none                                 | The arc held in place beside the avatar   |
| waiting for you | A card from the bot's runs is pending                                               | Wide, on the viewer              | Leans in: grows to 110% and back, 2.6 s     | none          | waiting, pinging                     | Wide eyes and the badge with a fixed halo |
| blocked         | The gateway or the bot's machine is unreachable, or the run needs a settings change | Half closed                      | None. Slumped 5°                            | none          | blocked                              | The same                                  |
| done            | A run completed and its task has not been opened since                              | Smiling                          | One nod, 420 ms, then still                 | none          | none; the row carries the unread dot | Smiling eyes                              |
| failed          | The latest run failed and its task has not been opened since                        | Half closed                      | None. Slumped 5°                            | none          | failed                               | The same                                  |
| stopped         | The latest run was stopped; until the next run or until the task is opened          | As idle                          | None                                        | none          | stopped                              | The same                                  |

**One order, everywhere.** When several states apply, to one run or across a bot's tasks, the most urgent wins, in this order: waiting for you; failed or blocked; done with failures; working; thinking; done; stopped; idle. Done with failures is the done face with the failed badge. A queued task counts as idle for the avatar. Section 20 uses the same order for the rail and gives its fixtures. When waiting wins while the machine is unreachable, the avatar shows waiting with the blocked badge. (F-086, F-422, F-426)

A bot with its own picture has no face to move. For it the ring also says thinking, as a full ring that breathes between 35% and 100% over 2.6 s (held at 50% under reduced motion), and the badge and ring carry everything else: done is the picture with no ring and no badge, told from idle by the row's unread dot.

Accessible name: the avatar is `role="img"` with the name "<Bot>, <state>", for example "Otto, working". Where it sits inside a control that already speaks the state, it is hidden from assistive technology. (F-020, F-086)

Sizes: 64 px in the Work pane, 56 px pinned, 40 px in the rail, 28 px in the status line, 22 px in the title pill and in a card's live status, 20 px in the Jump control. Below 28 px the ring sits 3 px out.

## 5. The status line

The last thing in a running turn: the bot's avatar at 28 px and one short phrase. No bubble. It is flush left with the bubbles, 10 px below whatever came last.

**Anatomy.** Avatar with state; phrase (14 px, `--text-muted`); elapsed time (12 px, `--text-faint`, tabular, `m:ss`). The whole line is one button, 40 px tall, with a pill hover.

**Lifecycle.**

| Moment                                       | What shows                                                                                                   |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| You send                                     | The avatar and the phrase "Thinking" appear at once. The phrase is never empty. (F-081, F-082, F-085)        |
| An action starts                             | Its card's running words replace "Thinking" at once, and the avatar is working. (F-082)                      |
| Bubbles and cards arrive                     | They render above the line. The line stays put. (F-081, F-089)                                               |
| A card is pending                            | "Waiting for you", in `--warn`; the avatar is waiting. (F-292)                                               |
| Stop is pressed                              | "Stopping…"; the avatar is idle; no shimmer. (F-097)                                                         |
| The run reaches completed, stopped or failed | The line is removed: it fades and lifts 4 px over 200 ms. No message says only that the bot is done. (F-089) |

**The phrase.** While an action runs it is that action's card in its running form, verb and object, as section 8 words it (7.8 says which, when several run). Otherwise it is "Thinking". The gateway's own status phases give it more to say when no action is running:

| Source                                                          | Phrase                                                                |
| --------------------------------------------------------------- | --------------------------------------------------------------------- |
| No action running                                               | Thinking                                                              |
| An action running                                               | Its card's running words, for example "Reading backup-2026-11-15.log" |
| The gateway is reviewing a command before it runs               | Reviewing a command                                                   |
| A message to another bot, once the gateway says it was accepted | Waiting for Marlow                                                    |
| Status phase preparing a workspace or environment               | Setting up the workspace                                              |
| Status phase preparing context or flushing memory               | Gathering context                                                     |
| Status with a retry                                             | Rate limited. Retrying, attempt 2 of 5                                |
| A pending card                                                  | Waiting for you                                                       |
| A wait reported on a read-only connection                       | Waiting for an answer                                                 |
| Stop pressed                                                    | Stopping…                                                             |
| The machine is unreachable                                      | Can't reach <machine>                                                 |
| The connection is lost                                          | Reconnecting. Last seen <last phrase, lower case>                     |

Phrases are in the user's language, have no bot name in front and no trailing ellipsis except "Stopping…". A tool the app has no kind for gets the general card's words, built from its name (8.3), so the phrase is never the gateway's English title. (F-082, F-083)

**Motion.** A light crosses the phrase while the avatar is thinking or working: a band of `--text` moving over `--text-faint`, left to right, every 2 s. It stops when the state is anything else. A new phrase rises 5 px and fades in over 200 ms; the old one is replaced at once. Reduced motion: plain `--text-muted` text, replaced at once. (F-084, F-291)

**Elapsed time** is the wall-clock time since the run's start as the gateway reported it, so it is right after a reload and on a second device. It is not shown when the gateway gave no start time, and it is hidden, not frozen at a number, while the connection is lost.

**Input.**

- Hover: the full phrase as a tooltip, for when it is truncated. (F-087)
- Click, tap or Enter: brings the running action's card into view and moves focus to its line, without opening it (7.8). With no action running, it does nothing and says so in its name.
- Accessible name: "Otto, working: Reading backup-2026-11-15.log. Show the action." With nothing running: "Otto, thinking. Nothing running to show."
- Screen readers hear lifecycle changes through the announcer (section 2), not every phrase.

## 6. Streaming text and message captions

- Reply text streams into its bubble as the gateway emits it. A caret follows the last character: 2 px wide, the height of the text, `--accent-line`, breathing between 100% and 35% over 1.2 s (steady under reduced motion). The bubble has `aria-busy="true"` until the message is complete. Text is never revealed more slowly than it arrives. (F-095, F-433)
- Progress messages the bot writes mid-run are ordinary bubbles, and so is the text it writes beside a tool call (section 7.6). (F-088)

A caption is a 12 px line under a bubble, on the bubble's side:

| Caption                          | Under                                                 | When                                                                                                                        |
| -------------------------------- | ----------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Incomplete                       | A reply                                               | The run failed or was stopped while it streamed. The text stays. (F-433)                                                    |
| Steer                            | Your bubble                                           | The gateway accepted it into a running turn. (F-096)                                                                        |
| Steer · restarted the turn       | Your bubble                                           | The gateway reports that the steer interrupted the turn and restarted it. Never shown on a guess.                           |
| Failed to send · Resend · Delete | Your bubble                                           | The send failed. The first part is `--danger`. "Resend" sends the same text again; "Delete" removes the bubble. (F-075)     |
| Sends when reconnected           | Your bubble, in the neutral raised fill with `--text` | Written while offline and held by the host. It is sent once when the connection returns and takes your colour then. (F-287) |

A message that has not been sent is never drawn in your colour and never dimmed: white on a dimmed accent falls to 2.7:1.

## 7. What a bot did: action cards

The conversation reads at the level of what a bot did (`AGENTS.md`, F-488). Every action a bot takes is a card in the transcript, at the moment it happened: one line with a verb, what it acted on, and its state. A person follows a run by reading those lines between the bot's own bubbles, without opening anything. Reasoning stays out of sight until it is opened, and the raw call is one step further, behind each card.

The Messaged card (section 10) and the Messaged T3 Code card (section 11) are two members of this family. Every other kind of action takes their form, and section 8 lists the kinds.

### 7.1 One model, three levels

An action is a card. A card opens to its detail. The detail has Raw. There is no second list of the same actions anywhere: the cards are the record of the run, the run line under them is only its summary (7.7), and reasoning lives inside the cards it led to (7.5).

| Level               | What is on screen                                                                                                                                                                                                                                                                                                                                                                                                                                | Reached by                                                         |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------ |
| 0, nothing opened   | Your bubbles. The bot's bubbles: what it says as it goes, the text it writes beside a tool call (7.6), and its reply. One card for each action, or for each fold of actions of one kind (7.4). Approval and question cards. A "Thought for 8s" line over a reply that reasoning led to with no action after it. The run line, once the run has ended. The status line, while the run is active. No reasoning text, no arguments, no raw payload. |                                                                    |
| 1, one thing opened | A card's readable view: what it acted on and what came back (section 8). A fold's list of its actions, one row each. A Messaged card's exchange. The text behind a "Thought" line over a reply. The run line's record: model, effort, run id.                                                                                                                                                                                                    | Click, tap or Enter on the line                                    |
| 2, one step further | Raw, what the gateway sent (section 9), as the second tab of an opened card. The reasoning that led to an action, behind the "Thought for 4s" line at the top of its opened card. One action of a fold, opened from its row, with its readable view.                                                                                                                                                                                             | The Raw tab; the "Thought" line inside a card; a row inside a fold |

A fold puts one level between its line and its calls, so an action inside a fold has its Raw at level 3. That is the price of saying "Read 6 files" in one line, and the fold's rows name every file at level 1.

**Why the cards are shown without opening anything.** The first version of this design folded every step of a run behind one line ("Worked for 1m 12s · 9 steps") and showed only the Messaged cards outside it. To learn what the bot did, a person had to open the line and read a step list of tool calls and reasoning segments: a trace, not an account. Grok Bot shows the account (a grey "Messaged" line with the recipient's avatar and name, "Created routine" with a clock and the routine's name) and the owner asked for that ease for every kind of action. So the cards are always shown, the trace is gone as a separate view, and the step row designed before survives in two places: as the row inside an opened fold, and as the detail with Readable and Raw behind every card.

### 7.2 The card

Folded, a card is one line: the Messaged card's line from section 10, with the same grid, sizes and surface.

```
Read  ▤ backup-2026-11-15.log   96 lines                              0.6s  ›
Ran   ▹ du                      du -sh /srv/media/*                   1.2s  ›
Searched the web for  ⌕ "cold climate heat pump"   5 results          2.1s  ›
Messaged  ● Marlow   Write a two-line entry for the house log.    ✓ Replied  ›
```

| Part    | Look                                                                                                                                                                                                                                              |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Verb    | 14 px, `--text-muted`. It changes tense with the state: "Reading", "Read", "Couldn't read".                                                                                                                                                       |
| Icon    | The kind's icon, 16 px, `--text-faint`, directly before the object, as the recipient's avatar sits before its name on a Messaged card and the clock before a routine's name in Grok Bot. While the action runs, the working mark takes its place. |
| Object  | 14 px, medium weight, `--text`: a file's name, a host, a query in quotes, a program, a routine's name, a bot. A path shows its last part; the whole path is the tooltip and is in the opened card.                                                |
| Detail  | 13 px, `--text-muted`, truncating: one short fact. "96 lines", "5 results", "+4 −0", a command line in mono, the first line of a message.                                                                                                         |
| State   | At the right. Done: the duration, 12 px, `--text-faint`, tabular. Any other state: its mark and word (7.3).                                                                                                                                       |
| Chevron | 12 px, turns when the card is open.                                                                                                                                                                                                               |

Size and surface: 40 px tall (44 on touch), `--bg-bubble`, radius 18, as wide as the column up to 640 px (560 px beside a docked Work pane), padded 14 px left and 12 px right, 8 px between parts. In a column narrower than 560 px the card has its own layout, given in 7.9: the verb and the object form one sentence that may take two lines, so that what the action acted on is always readable. The detail is never dropped, and the state word is never shortened.

**Cards in a row form a column.** Cards with nothing between them sit 2 px apart, and their touching corners are 6 px instead of 18, so the actions of a stretch of work read as one quiet column, the way the steps of Grok Bot's illustrated step list do. A bubble, a request card or a note between cards ends the column; the next card starts a new one, 8 px below what came before it. Messaged and T3 Code cards join a column like any other card.

**Name.** The line is a `summary` whose accessible name is the verb and object, the detail and the state: "Read backup-2026-11-15.log, 96 lines, 0.6 seconds". The icon is hidden from assistive technology. Hover shows the whole line as a tooltip when any part is truncated.

### 7.3 States

Every card's state is one the gateway can establish. A call's start is the first thing the gateway reports; it comes before the call is checked or allowed, and also for a call that is then skipped, so it is never proof that the call was made. There is no "sending" state anywhere. A result that is not flagged as an error is not, by itself, proof that the work the verb names was done either: some tools return as soon as the work is admitted, queued or refused for want of a setting, and say so in the result. So each kind reads its result through an adapter (8.2), and a card says only what that adapter establishes. The Messaged card (section 10) and the T3 Code card (section 11) keep their own tables, because what they claim reaches past the bot.

**While the call is open:**

**The general rule.** A result without an error flag is not, by itself, proof that the action happened. There is one reading of a result's payload, and **every kind goes through it**; a kind's own adapter (8.1, "Done needs" and "Other outcomes") only adds to it, and nothing reaches Done by default. The reading looks at the payload the gateway passes in `details` (the tool's own JSON), and at a nested `details.result` where a tool projects its outcome there, for these fields:

- `ok: false`, an `error` field, or a `status` of `error` or `failed`: **Failed**, even without the error flag, with the received `error` as the detail;
- a `status` of `forbidden`: **Not run**, with the received `error` as the reason;
- a `status` of `not_found`, or `removed: false`: **Not found**;
- `code: "confirmation_required"`: **Not run**, "Needs confirmation", with the received `target` and `proposedEffect`; a `status` of `approval-pending`: **Waiting for approval**;
- a `status` of `queued`: **Queued**;
- `effect` of `unverifiable` or `suspected_noop`: **Not confirmed**;
- an `outcome` (a string, or an object with a `code`), or any `status` or `code` value this list and the kind's adapter do not name: **Call made**, with the value shown as received.

A result is **Done** only when the reading finds none of these signals, and, where the kind's row names evidence of success ("Done needs"), that evidence is there. Values that say the work was done (`ok: true`, a `status` of `ok`, `completed`, `success`, `sent`, `accepted`, `answered`, `replied`, `removed: true`, `effect: "confirmed"`) are not signals against Done. A kind's adapter may name an outcome more exactly than the reading (Started for an admitted background task, Partial, Suppressed, Unavailable, No change, a phone's refusal codes, Not found for a memory read); where it does, its outcome is used. A tool with no row of its own (the general card) is read by this rule and nothing else.

**When the result arrives**, the kind's adapter gives one of these outcomes. Each row says what the result must contain; anything else is the outcome below it that the result does establish, and at worst "Call made".

- When the media that a Started card admitted arrives in a later turn, it arrives as that turn's own message and attachments; the Started card does not change, because nothing on the wire ties the later delivery to this call. ### 7.4 Folding

Actions of one kind in a row become one card with a count: "Read 6 files", "Searched the web 3 times", "Ran 5 commands". The rules below decide every fold, so that the live run, a reload and a second device draw the same cards.

**Which actions may fold.** An action may join a fold only when all of these hold:

- its fold key (8.1, "Folds with") is known **at its start**, from its name and arguments: a built-in name in the table, or a tool-server call that the gateway's name mapping identifies. A call known only from its result (an unidentified tool-server call, a general card whose name the gateway's tool inventory does not list as a built-in or plugin tool) never folds, because placing it would have to wait for its result;
- its key is not "never" (rows 15 except look-ups, 16, 18, 19, 23, and T3 Code launches);
- it is in the same run as the action before it, with nothing shown between them (below).

Every state may fold: running, waiting, done and every outcome of 7.3. A failure does not leave its fold; it is named on the fold's line instead. **A fold reads what a single card reads**: every member's state and outcome come from the same function a single card uses (7.3: the event's status, then the kind's adapter, then the general reading), whether the cards arrive live, through the engine's placement, or from history; there is no second path. So a member that a single card would show as Waiting for approval, including a call that returned `approval-pending`, makes the fold Waiting, and the fold then shows no duration.

**The fold key.** Two actions fold only when their keys are equal. The key is the row's "Folds with" value: for most rows the exact tool name (so `memory_search` and `memory_get` are separate, image and video generation are separate, `get_goal` never folds with `update_goal`); for rows 1 and 3 the kind (a fold of edits may hold `write`, `edit` and `apply_patch`); for row 24 the server and tool; for row 25 the thread (section 11). **Where a tool does several operations, the key includes the operation**: the tool and its `action` for rows 7 (`terminal`), 15 (the tool and each look-up action: `automations` `list` with `automations` `list`; `cron`, the alias the gateway still accepts, is another tool, so `cron` `list` does not fold with `automations` `list`; `next_check` never folds) and 21 (making media, listing its models and checking a task are three keys: listing generated media is not making it). Each operation has its own plural, given in 8.2 ("Looked at image models 2 times", "Checked image generation 2 times"); where an operation has no truthful plural, its calls do not fold. Rows 11 (`browser`), 12 (`computer`) and 13 (`mobile_ui`) fold all their actions because their plural ("Used the browser · 12 actions") claims only use, which every member's start establishes.

**What breaks a fold.** An action with another key; a bubble, including text the bot writes beside a tool call; an approval or question card; a note; your own message sent into the run; the run's end. Reasoning between two actions is not shown at level 0, so it does not break a fold. After a break, the next action with the key starts a new card.

**Becoming a fold.** The second action with the key turns the card into a fold in place. Its line changes to the plural ("Read 2 files"), and the first action becomes the fold's first row. Nothing moves: the line keeps its height and position. If the card was open, the fold opens with that first row open in the view it had (Readable or Raw), and focus stays on the same control inside that row.

**Counting.** A count that names objects counts **distinct objects** whenever the calls identify them: files from a path or a patch's named files (rows 1, 3, 4), documents and images from `pdf`, `pdfs`, `path` and `paths` (row 22), notes in memory by their path (row 4). When there are as many calls as objects, the line names the objects only: "Read 6 files". When there are more calls, it adds the number of times: "Read 2 files · 6 reads", "Edited 2 files · 3 edits", "Read 3 PDFs · 2 times" (two calls over the same three PDFs), "Saved 1 note to memory · 2 times" (two writes of `MEMORY.md`). When any member's objects cannot be identified (a patch with no named file), the line counts times only, and says so: "Made 4 edits", "Searched memory 3 times". A count of objects never silently counts calls. The run line always counts actions (7.7).

**The plural is never more complete than its least-established member.** The kind's done plural ("Made images", "Searched memory") is used only when every settled member is Done or Partial, whose past verb is true (a partial search did search). Otherwise:

- while a member waits for approval, the line uses the neutral plural below, whatever the others did, because the waiting call has done nothing yet: "Commands · 2 calls";
- when every settled member was **Started**, the line uses the started plural: "Started making images · 2 times";
- in every other mix (any member Queued, Call made, Not confirmed, No change, or members with different outcomes), the line uses the kind's **neutral plural**, a noun with the number of calls, which claims nothing: "Image generation · 3 calls", "Memory search · 2 calls", "Tool server linear · 2 calls". The noun names the operation, not its outcome ("Image generation", "Memory search", "Routine run", "Message on Telegram", "Tool server linear"); each kind's noun is part of the mapping (section 22), and the prototype's `neutral` for each kind in `js/kinds.js` is the reference list.

The settled outcomes that are not Done are counted on the right side (below), and the accessible state says the same words.

**The folded line, in every combination.** A fold shows two things at once that a single card shows one at a time: what is happening now, and what has gone wrong. They have separate places, so neither hides the other.

- **The detail slot** holds, in this order, the first that applies: the first problem's words, if any member has one (7.3, last column), "couldn't read backup-2026-11-08.log", led by the problem count ("1 failed: couldn't read …") while the right side is taken by a live state, in `--danger` when a failure or a block is among them, otherwise in `--text-muted`; else the running member's words in lower case, "reading notes.md"; else the members' objects in order, distinct, joined with commas and truncated, or for edits the summed change "+24 −6".
- **The right side** holds, in this order, the first that applies: "Waiting for you" with the waiting mark, when a member waits for approval; the working mark and the elapsed time of the running member (the latest to start), when a member runs; "Last seen running", still, when the connection is lost and a member was running; once the fold has settled, **the counts of every outcome that is not Done**, in one fixed order: failed, not run, unavailable, not found, suppressed, stopped, unknown, then started, queued, not confirmed, call made, no change, partial: "1 failed · 1 stopped", "2 started", "1 started · 1 call made"; the summed duration, only when every member is Done and reported both its start and its end; otherwise nothing.
- Problems lead that order and set the tone: `--danger` with the failed mark when a failure or a block is among them. The detail names the first problem among the rows, in their order.
- The accessible state of a settled fold is the same words: "2 started", "1 failed, 1 stopped"; it is "done" only when every member is Done.
- A duration is never a partial sum: if any member lacks a start or an end time, the fold shows no duration.

So a fold that holds an earlier failure and a later pending approval reads "Ran 3 commands · 1 failed: couldn't run mv · Waiting for you"; a fold whose members were all stopped reads "Read 3 files · stopped reading notes.md · 3 stopped"; two background image admissions read "Started making images · 2 times · 2 started"; two partial memory searches read "Searched memory 2 times · 2 partial"; and the fold is never drawn as a plain success when a member had a problem or an outcome short of Done.

**Opened** (level 1), the fold lists its actions as rows in order. A row is the step row the shell builds (section 22): 34 px (44 on touch), the kind's icon, the action in the singular ("Read backup-2026-11-15.log"), its detail, its own state, a chevron. A failed row is in `--danger`. A row opens to that action's readable view with its Readable and Raw tabs (8.6), and to the reasoning that led to it (7.5).

**A new action while the fold is open** is appended as the last row, rising 4 px over 200 ms; the count in the line goes up; rows that are open stay open, in their view; focus stays on the control that had it; nothing above the new row moves.

**Identity and reconciliation.** A fold is computed, not stored: the engine runs the same pure function over a run's ordered record (its actions, bubbles, request cards and notes, with each action placed by its start) after every change, live or from history, so the live run and a reload agree. A fold is keyed by its first member's tool call id; a single card by its own. View state is kept under those keys and under each member's tool call id: whether a card or fold is open, which rows are open, and in which view. When a reconciliation with history changes a fold's members:

- **A split.** A call of another key, or a bubble, now sits inside the fold. The fold becomes two cards, or a card and a fold, with the new item between. The part holding the first member keeps the key and its open state. The part after it is keyed by its own first member, and opens if the fold was open, so nothing the reader had open closes. Rows keep their own open state and view, and focus stays on the control it was on, wherever its row now is. The reading line holds (section 18).
- **A merge.** An item between two folds of one key disappears. They become one fold keyed by the earlier first member, open if either was open; rows keep their state.
- **A new member.** History restores a call the live stream missed: it takes its place among the rows; the count and the line are recomputed.

This is the same rule as section 19: after a reconnect nothing the reader had opened closes, except an open "Thought" line whose run's reasoning revision changed.

**Where there are no run boundaries.** History the gateway returns may not say which run each call belonged to. Then the conservative boundary is the history row: only calls carried by one assistant message (its tool call blocks, with their results) fold together, and a fold never crosses a user message, a bubble, or a row that the gateway marks with another run id. Such history has no run line.

### 7.5 Reasoning

Reasoning has no card. Its text is never on screen until the person opens it.

- **It belongs to what it led to.** A segment of reasoning belongs to the next action in its run; with no action after it, to the reply that follows; with neither, to the end of the run.
- **Inside a card.** An opened card whose action reasoning led to starts with one line, "Thought for 4s" (13 px, `--text-faint`, 30 px, a chevron). That line opens to the text (level 2): 14 px, `--text-muted`, at most 62 characters wide, each segment its own paragraph in order. Several segments before one action are one line, with their durations added. In a fold, each row carries its own.
- **Before a reply.** Reasoning that led to a reply, with no action after it, is one line directly above the reply's bubble: "Thought for 8s", the event-line form, flush with the bubbles, 4 px above the bubble. It is folded, always; opened, the text sits under the line and above the bubble.
- **A run that only thought.** The gateway does not end a turn on reasoning alone: when a reply has reasoning and no text, it asks the model again, twice, and then ends the run as an error. Such a run shows its "Thought for 12s" line above the turn's error card (section 17).
- **Durations** come from the segments' own times. Without them the line reads "Thought", never a zero.
- **No reasoning exposed.** When the model reports none, or its visibility is off, there are no "Thought" lines and nothing else changes.
- **After a reconnect.** A reasoning segment has no id of the gateway's; the engine derives one from its place in the run, and each run carries a revision that changes whenever a reconciliation with history shifts its reasoning steps. Whether a "Thought" line is open is kept under that derived id, and only while the run's revision is unchanged. When it changes, an opened "Thought" line closes and its text is read again. Nothing else closes: cards are kept under the gateway's tool call ids, folds under their first call's id, and the run line under the run id, none of which a reconciliation changes.

### 7.6 Text beside a tool call

Text the model writes in the same message as a tool call does not come on the reply stream. It arrives as an `item` of kind `preamble`, its text in `progressText`, with phases `update` and `end`. It is the bot narrating its work ("Reading last night's log first."), so it is shown as one of the bot's ordinary bubbles, placed directly before the card of the call it came with. Its updates replace its text in place; it has no caret once its item ends. It ends a column of cards and breaks a fold, like any bubble. It is not reasoning and is never hidden.

### 7.7 The run line

When a run with at least one action ends, one quiet line follows everything the run put in the transcript: 13 px, `--text-faint`, 30 px tall, with a chevron, flush with the bubbles.

| The run                    | Line                                                                                                                                                |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| Completed                  | Worked for 1m 12s · 14 actions                                                                                                                      |
| Stopped                    | Stopped after 40s · 4 actions                                                                                                                       |
| Failed                     | Failed after 12s · 2 actions                                                                                                                        |
| Any of these with problems | … · 1 failed, in `--danger`; then any of "1 unavailable", "1 not sent" (suppressed), "1 stopped", "1 unknown", in `--text-muted` (7.3, last column) |

- It counts actions, not cards: a fold of six counts six, and a Messaged card counts one. An approval that belongs to no tool call is not an action.
- Durations read `48s`, `1m 12s`, `1h 04m`, from the run's start and end as the gateway reported them. A duration the gateway did not report is left out ("14 actions"), never shown as zero.
- **Opened** (level 1), it shows the run's record on one line of 12 px text: the model, the effort requested for the task or turn ("low effort requested"; the gateway does not dependably report the effort a turn used, so the line never says "used"), "effort not reported" when there is none, and the run id with a copy button named "Copy run id". The model and effort are also the line's tooltip.
- A run with no action has no line. A run whose only steps were reasoning has its "Thought for 8s" line over the reply instead (7.5), and nothing more.
- While the run is active there is no run line: the status line carries the phrase and the elapsed time (section 5). A run that was mid-way when the connection dropped gets its line when the gateway reports its end.
- It is a `summary` whose name is its text.

### 7.9 Phone width and touch

- **The narrow layout.** In a column narrower than 560 px, which includes every phone, a card is a small block, not a single line. At the top right sit the state and the chevron, as wide as their words need; the state word is never shortened. To their left, the verb, the icon and the object are one sentence that wraps like text, over at most two lines, in the line's 15 px (17 on touch). Under it, the detail, one line, truncated at its end. Heights: about 60 px for a one-line sentence with a detail, about 80 px for two lines, never less than 44 px.
- **The object stays readable in every state.** The verb is never shortened and the object never loses its start: a long object, such as the query in "Couldn't search posts on X for "heat pump rebate 2026 experiences"", carries on to the second line, and only what does not fit in two lines is cut, at the end, with an ellipsis. Running, waiting, review, last seen, Failed, Unavailable and every other state use the same layout, so a longer state word ("Waiting for you", "Last seen running") takes room from the sentence's first line and never from the object. The whole sentence is the line's accessible name, and touch and hold offers it in full (below).
- The same holds at larger text sizes and in longer languages: the sentence wraps rather than truncating its object first.
- Columns, folds, levels and states are the same. A fold's rows are 44 px.
- Touch and hold on a card opens a sheet headed by the card's whole sentence and detail, untruncated, and offers "Copy result", which copies exactly the result text its readable view shows, and "Copy raw". On a fold it offers "Copy list", the singular lines of its actions, one per line. On a "Thought" line it offers "Copy reasoning". (F-431)
- Tapping the status line brings the running card into view, as a click does.

### 7.10 The read-only connection

A connection on the read tier sees the same cards. A client that did not start a run receives its tool events, with their arguments and results, once it subscribes to the session, so a card for a run started elsewhere, or watched on a read-only connection, is as full as one this device started. There is no reduced form of any card.

What the read tier changes is only what section 3 says: approvals and questions are not sent to it. So a call waiting for approval shows "Waiting for approval" from the run's own lifecycle event, without the approval card, and the question a bot asks shows as the action card "Asked you a question" (section 8) with its text from the call's arguments, and the note "This device can't answer it on a read-only connection." with "Request access".

## 8. The kinds of action

### 8.1 The list

Nothing in a tool event names the kind of action. Each event has the tool's name, an English title the gateway builds from the name and the arguments, a mark on shell commands (`commandBearing`), and, on a tool server's result only, the server's and the tool's own names (`details.mcpServer`, `details.mcpTool`). So the app chooses the kind from the tool's name, by this table, and writes the words itself in the user's language. Builders implement this table, its adapters and its fold keys as one mapping (section 22).

Names, arguments and result fields are those of the installed OpenClaw 2026.10.6: its tool catalog and each tool's own schema and result builder, and, for the families a development gateway can run, the calls the scenario check recorded (`docs/decisions.md`, "Tools a bot can be given" and "What the scenario check observed"). A name not in the table is the general card (8.3). The display table in the package also knows `bash` and `image`, and its policy layer knows `image`; neither is a tool in the 2026.10.6 catalog, so they have no row. `cron` is an alias of `automations` the gateway still accepts, and shares its row.

"Done needs" is the adapter's test for Done (7.3); a result without it gets the outcome the next column names, and otherwise "Call made". "Folds with" is the fold key (7.4): two actions fold only when their keys are equal. "Dev" says whether `pnpm dev-gateway` can produce the kind; the others are built and checked from fixtures in the gateway's own shapes (section 22).

### 8.2 Choosing the kind, and the words for each action

- **By the exact tool name first.** Names are compared whole; nothing is matched by prefix or by splitting a name, except as the next points say.
- **Memory is a path.** A memory note is an ordinary file write: `write` or `edit` whose path is `MEMORY.md` or under `memory/` in the bot's workspace. The path is normalized first: a leading `./` is removed, and an absolute path is compared after removing the bot's workspace root (`agents.workspace.get` names it); a path outside the workspace is never memory. Only the path says it is memory, so row 4 is chosen from the arguments' `path`, and every other write or edit is row 3.
- **Commands.** A call the gateway marks `commandBearing` is a command whatever its name. The object is the program: the first word of the command line that is not an environment assignment, `sudo`, `env`, `nohup` or `time`, without its path. When the line starts with anything else (a subshell, a heredoc, a variable, a comment) or is empty, the object is "a command": "Ran a command". `terminal` is not a command: it manages terminals a person opened, and is row 7.
- **A patch's files.** `apply_patch` names its files inside its `input`, on the lines `*** Add File: <path>`, `*** Update File: <path>`, `*** Delete File: <path>` and `*** Move to: <path>`. One named file is the object ("Edited weekly.sh"); several are "Edited 3 files"; none that can be read is "Applied a patch". Folds count these files with the others (7.4).
- **Documents and images.** `pdf` takes `pdf` or `pdfs`; `view_image` takes `path` or `paths` only, each a local path or a permitted URL. One is named; several are counted: "Read 3 PDFs", "Looked at 3 images".
- **Tool servers.** A tool-server tool's name in an event is the gateway's effective name, which it sanitizes, shortens and de-duplicates, so it cannot be split into a server and a tool, and it need not contain any particular separator. A tool-server call is identified only by its result's `details.mcpServer` and `details.mcpTool`, or before the result by the gateway's own name mapping, the map from effective names to server and tool that the gateway's tool configuration gives. Until one of those identifies it, the call is the general card (row 26) with words from its effective name; when its result names the server and tool, it becomes row 24, or T3 Code's card, in place (11.2).
- **T3 Code** is recognized per call, never per server: by its result naming one of T3 Code's seven tools, and before the result only on the evidence of the gateway's name mapping, which the result can overrule (section 11).
- **Tools a provider brings with an account** have a row when the app knows what they search or do, as `x_search` does: its words name the source the person knows, "posts on X". Any other such tool is the general card.
- **The object** is taken from the arguments the start event carries, so it is known from the start: a path's last part, a host from a URL, a query in straight quotes shortened to 40 characters, a routine's `job.name`. Where the arguments do not name it, the line says so plainly until the result does: a `conversations_send` names only an opaque `conversationRef`, so its object is "a conversation" until the result's `channel` gives "Telegram"; the line never shows the reference itself.
- **One rule for tense.** The running form is the present participle, the done form the past, the failed form "Couldn't" with the base verb. Rows whose effect leaves the gateway use a noun form with "Call started" while open (7.3). A form the tables do not give is built that way.

**By action.** Some tools do several things through an `action` argument. The words follow the action. Text a person or the bot typed is never on the closed line; it is in the opened card.

The browser's and the computer's action names are the gateway's (its display table and the computer's schema). A computer advertises its own set of actions; one this table does not name gets "Used the computer".

**A routine's schedule in words.** The job's `schedule` has a `kind` of `at`, `every` or `cron` (and `stream` where triggers are on). `at`: the date and time, "Dec 2 at 9:00 AM". `every`: "every 2 hours", from `everyMs`. `cron`: a weekly or daily expression with fixed minute and hour ("0 9 * * 1") becomes "Mondays at 9:00 AM"; any other expression is shown as written, in mono. The time zone is always said: `tz` when given ("Mondays at 9:00 AM, Europe/London"), and "gateway's time" when it is missing, because the gateway then uses its own host's zone, not the phone's.

### 8.3 The general card

Any tool with no row of its own gets the general card, and its words come from its name.

1. **The name.** Take the name exactly as the event gives it. For a tool-server call, use the server and tool from the result once it names them, and the effective name before that.
2. **Words.** Split it at underscores (single or double), hyphens, dots, spaces and a lower-case letter followed by a capital; drop empty parts; lower-case every part except one that is all capitals and two to five letters long ("PDF", "API"). `skills_search` gives "skills search", `github_publish` "github publish", `getWeatherNow` "get weather now".
3. **The line.** "Using skills search" while it runs, "Used skills search" when done, "Couldn't use skills search" when it failed. The object slot holds the words, in medium weight; the icon is the diamond.
4. **The detail** is the first value present in the arguments among the keys the gateway itself uses for a call's detail, in its order: `command`, `path`, `url`, `targetUrl`, `targetId`, `ref`, `element`, `node`, `nodeId`, `id`, `requestId`, `to`, `channelId`, `guildId`, `userId`, `name`, `query`, `pattern`, `messageId`. A path or URL is shortened as in 8.2; anything else is cut to 60 characters. With none of them, there is no detail.
5. **Opened**, it shows the arguments as label and value rows, the result, and one more row, "The gateway calls it", with the gateway's own English title for the call (`item.title`, for example "Skill Search"), shown as sent.
6. **Fold.** Calls of the same tool name in a row fold ("Used skills search 3 times") only under 7.4's restriction: when the name is known at the call's start as a built-in or plugin tool in the gateway's tool inventory. A name known only from its result never folds.

The gateway's English title is not used for the line, because it is English only and is built for a log ("Write to notes/scratch.md (34 chars)"), not for a sentence.

### 8.5 The automatic review

When the gateway reviews a command before anyone is asked, the card carries the review's record: in progress, approved or denied, with a risk level and a one-line reason once it has decided. It applies to commands only. The review does not itself ask anyone; what happens after it denies is the gateway's, and the interface shows whichever follows.

### 8.6 Opened: the readable view and Raw

**Open**, only that card opens. Others keep updating, new ones keep arriving, and nothing above it moves. (F-293) Every card of the 26 rows except the two Messaged cards and the question card has two views, switched by a tab list at the top (Readable, Raw), under the "Thought" line when there is one (7.5). The two Messaged cards and request cards have Raw as a button (section 9).

- **Readable.** The inputs as label and value rows, then the result, as the table in 8.1 says for each kind. A running action shows its output as the gateway streams it, with the streaming caret, under "Output so far". (F-432) An action with nothing to add says so in one line ("The gateway sent no result for this action.") and is never an empty box.
- **Raw.** What the gateway sent, as section 9 defines it. (F-093, F-094)

**Long output** shows eight lines in full and stops there, with "Show all 96 lines" under it. Nothing is drawn half-faded: the eighth line is as readable as the first. Shown in full, the block scrolls inside itself up to 280 px (60% of the height on a phone) and the button reads "Show fewer". The count is the number of lines there really are. Copy always copies all of it.

**Output the gateway cut.** The gateway shortens long results, and where it cuts depends on the path a result took and on its settings, so the app assumes no fixed size. A result is treated as cut when the gateway flags it or when its text ends with the gateway's own truncation marker, which is shown as received. The block then ends with a line on `--warn-soft`. When what was received is plain text, the line gives its real size: "Truncated by the gateway. 7,946 characters were received; the rest was not sent." When it is a structured result, whose text is not a simple prefix of the original, the line says only "Truncated by the gateway. The rest was not sent." "Show all" counts only the lines received, and Copy copies what was received and says so ("Copied what was received").

**Rebuilt from history.** A card rebuilt from `chat.history` may lack the result's `details`, which the gateway keeps for some tools and not others: a write keeps its diff, a read and a web search do not. The line then shows what the text gives and leaves out what only `details` held ("Read notes.md", with no line count), never a guess. It may also lack timing; the right side then shows nothing where the duration would be, never zero.

**Loading.** An action's detail is fetched when it is first opened. While it loads, the body is one line, "Loading this action…", with `aria-busy`. If that fails: "Couldn't load this action." with "Try again".

**Copy** follows section 9. On touch, touch and hold follows 7.9. (F-093, F-431)

**Keyboard.** Tab moves through the cards in order; Enter or Space opens one. Inside it, Tab goes to the "Thought" line when there is one, then the tab list, then the copy buttons, then "Show all". The tab list is one tab stop: Left and Right move between Readable and Raw and select, Home and End go to the ends. Each tab names its panel (`aria-controls`), and each panel is labelled by its tab. In an opened fold, Tab moves through its rows, each a `summary`.

### 8.7 Open points for the builder

The names, arguments and result fields in 8.1 and 8.2 are taken from the installed package's schemas and result builders, and from the scenario check's record. What is still open is listed here; until a point is settled, the card leaves the part out and the outcome is "Call made".

1. **Later tools.** A tool added after 2026.10.6 is the general card until a row is added for it.
2. **The `message` tool's result.** Its result depends on the channel's adapter and the action, and no published schema fixes it, unlike `conversations_send` and `conversations_turn`. Until the adapter's fields are read from the package for a channel, a returned `message` call is "Call made", never "Sent".
3. **Helpers after the start.** `sessions_spawn`'s accepted result names `childSessionKey` and `runId`; the results of `agents_wait` and of `subagents` `kill` and `steer` were not read for this design. Until their outcome fields are taken from their result builders, they end as "Call made".
4. **A media task's later status.** The `status` action of the media tools reports a background task; its fields were not read for this design, so its opened card shows the result text as received.
5. **The computer's advertised actions** depend on the computer; an action not in 8.2 is "Used the computer".
6. **The external-content markers** that `web_fetch` puts around a page's title and text are the gateway's own (`wrapExternalContent`); the builder strips exactly those markers from the title on the closed line, and shows the text as received when opened.
7. **The phone's done code.** A `mobile_ui` act that ran returns `{outcome: {code, message}, snapshot}`, and the `code` comes from the device, not from the gateway; the gateway itself names only refusals (`confirmation_required`, and `target_stale`, `target_not_found`, `secure_content`, `package_changed`). Until the device's code for a done act is fixed, an act that ran is "Call made" with its code shown, never "Tapped".
8. **T3 Code** is settled in section 11. What remains there is listed in 11.5.

Every action card, every row in a fold, every request card and every "Thought" line has Raw, on the desktop and on the phone. It is one component, so that two builders do not invent two.

Where the app shows something it sent (the answer to a question, a decision on an approval), the part is labelled as sent and holds the parameters as sent. The gateway keeps a readable record of tool actions with their time, bot, task, run, call and outcome, including actions that needed no approval; the link opens that record at this call. The record's own screen is not part of this design.

| Couldn't load            | "Couldn't load what the gateway sent." with "Try again"                                                                                                                 |

**Copy.** Every code block and every value in Timing and Identifiers has a copy button, and each is named for exactly what it copies: "Copy arguments", "Copy result", "Copy tool call id". It copies that text in full, including lines the view has folded, and never anything else.

- When the clipboard took it, the icon becomes a check for 1.4 s and the announcer says "Copied arguments".
- When it did not, the icon becomes a warning for 1.4 s, the text it would have copied is selected, and the announcer says "Couldn't copy. The text is selected." Nothing claims success.

## 10. The Messaged card

One card for each message a bot sends to another bot: the action card for `sessions_send` (section 8, row 16). It sits in the transcript where the message was sent and joins a column of cards like any other; it never folds, and the message appears nowhere else in the run. (F-119, F-439)

**Folded**, one line, 40 px (44 on touch): the word "Messaged", the recipient's avatar at 20 px and name, the first line of the message in `--text-muted`, and the state at the right with its mark. In a column narrower than 560 px it is two lines: "Messaged", the recipient and the state on the first; the message's first line on the second. The words "Messaged" and "Message from" are never dropped, and the state word is never shortened. (F-122)

**States.** Each state is something an event established. There is no state for something the gateway does not report.

| State                | Mark and colour     | Established by                                                                                                                                                                                                                                |
| -------------------- | ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Call started         | sending             | The gateway reported the start of the tool call. A start comes before the call is checked or allowed, and it is also reported for a call that is then skipped, so it is never proof that the call was made or that the message was delivered. |
| Waiting for approval | waiting, `--warn`   | A pending approval request names this tool call. The call had already started; it is held until the request is answered. (F-312)                                                                                                              |
| Sent                 | check               | The call returned and its result says the recipient accepted the message                                                                                                                                                                      |
| Working              | working, `--accent` | The result named the recipient's run, and that run's own events show it active                                                                                                                                                                |
| Recipient waiting    | waiting, `--warn`   | That run is waiting on its user: it asked a question, or it needs an approval                                                                                                                                                                 |
| No reply yet         | hollow ring         | That run finished, or the call returned, without a reply. This includes a result that reports a timeout and says the message was sent before the error: the message went, and a reply may still come.                                         |
| Replied              | check, `--accent`   | A reply arrived that an identifier ties to this message                                                                                                                                                                                       |
| Recipient stopped    | stopped             | That run ended as stopped or cancelled without a reply (F-434)                                                                                                                                                                                |
| Recipient failed     | failed, `--danger`  | That run ended as failed. The message was delivered; the failure is the recipient's.                                                                                                                                                          |
| Failed               | failed, `--danger`  | The call returned an error, and nothing in the result says the message was sent                                                                                                                                                               |
| Blocked by policy    | failed, `--danger`  | A messaging policy forbade the call (F-311)                                                                                                                                                                                                   |
| Not sent             | stopped             | The approval was denied or expired; or the call was skipped before it ran, because the run was steered or cancelled; or the sender was stopped and the gateway confirms the call was never made (F-436)                                       |
| Unknown              | hollow ring         | The sender was stopped before the call returned and the gateway cannot say whether it was delivered                                                                                                                                           |

**Transitions.** The card follows this graph, not a list order. The start is the first thing the gateway reports about a call, and there is no second start when a held call resumes.

```
Call started ─► Waiting for approval ─► Call started     (allowed: the same call goes on)
     │                   └────────────► Not sent         (denied or expired)
     ├─► Blocked by policy
     ├─► Not sent                       (skipped before it ran)
     ├─► Sent ─► Working ⇄ Recipient waiting
     │     │        │
     │     └────────┴─► Replied | No reply yet | Recipient stopped | Recipient failed
     ├─► No reply yet                   (a timeout that says the message was sent)
     ├─► Failed                         (an error, with nothing to say it was sent)
     └─► Unknown | Not sent             (the sender was stopped)

No reply yet ─► Replied          only on a reply an identifier ties to this message
Unknown      ─► whatever a later event that names this message establishes
```

- Replied, Recipient stopped, Recipient failed, Failed, Blocked by policy and Not sent are final. Nothing changes a final card.
- Working and Recipient waiting may alternate as the recipient asks and is answered. From either, the recipient's run ending as failed gives Recipient failed, so the sender's card never stays Working after the recipient failed.
- Where the result does not name the recipient's run, the card goes from Sent straight to Replied or No reply yet.
- **A late reply** is attached to its card only when an identifier ties it there. Otherwise the card stays as it was and the reply arrives as an incoming message, "Message from Marlow" (below).
- Two events belong to one card only when the gateway's identifiers say so. A replayed event updates the card it names and never makes a second one; an event older than the card's state is ignored. (F-309, F-435, F-469)

**Open**, in place (F-121):

- **What was sent**: the sender's avatar and name, "sent" and the time the call was issued, then the exact text on a `--bg-pane` inset. Attachments are chips under it. (F-123, F-128)
- **What came back**: one row for the recipient, led by its avatar, then what the state allows:

| State                | The recipient's row and what follows                                                                                                                                                                                   |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Waiting for approval | "This message waits for your approval. Nothing has been sent."                                                                                                                                                         |
| Call started         | "Otto began this call. Nothing yet shows that it was made."                                                                                                                                                            |
| Sent                 | "Marlow received it. No reply yet."                                                                                                                                                                                    |
| Working              | The recipient's state avatar at 22 px, its name and its current phrase on one row, updating as its actions change: "Marlow · Reading the house log". Nothing else: the folded line already says Working. (F-438)       |
| Recipient waiting    | "Marlow asked a question in its own task and is waiting for the answer.", or "Marlow needs your approval in its own task." Either has "Open in Marlow", which goes to that card.                                       |
| No reply yet         | "Marlow's run finished without a reply." or, after a timeout, "The message was sent, and no reply came in time." Then: "A reply that names this message appears here; any other arrives as a message from Marlow."     |
| Replied              | "Marlow replied" and the time, then the reply on an inset                                                                                                                                                              |
| Recipient stopped    | "Marlow's run for this message was stopped before it replied."                                                                                                                                                         |
| Recipient failed     | "Marlow received it, and its run for this message then failed.", then the reason when the gateway gives one                                                                                                            |
| Failed               | "The call failed.", then the error text                                                                                                                                                                                |
| Blocked by policy    | "A messaging rule stopped this: <the rule>. Nothing was sent."                                                                                                                                                         |
| Not sent             | "You denied the approval. Nothing was sent.", "The approval expired. Nothing was sent.", "Otto moved on before making this call. Nothing was sent.", or "Otto was stopped before the call was made. Nothing was sent." |
| Unknown              | "Otto was stopped before the call returned. The gateway cannot say whether Marlow received it."                                                                                                                        |

- **Actions**, in this order, each present only when it can do something:

| Action               | Present when                                                    | Does                                                                                                                                                                        | Name                                                    |
| -------------------- | --------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| "Show the approval"  | Waiting for approval                                            | Scrolls to the approval card and focuses it                                                                                                                                 | Show the approval for this message                      |
| "Open in Marlow"     | The result named the recipient's task                           | Selects the recipient's task, scrolled to its "Message from Otto" card, which is open and focused                                                                           | Open this message in Marlow's task                      |
| "Show full exchange" | The two bots have exchanged more than this message in this task | Replaces the two rows above with every message between them in this task, oldest first, read-only. It reads "Show only this message" while open. Focus stays on the button. | Show every message between Otto and Marlow in this task |
| "Raw"                | Always                                                          | Section 9: the send call's name, arguments, result, timing and identifiers                                                                                                  | Raw                                                     |

**Coming back.** "Open in Marlow" records where the reader was. On the receiving card, "Open in Otto" returns there: the sender's task, the transcript at the scroll position it had, the card still open, focus on "Open in Marlow". ⌘[ does the same.

**The receiving side.** The recipient's task starts the run with a "Message from <Bot>" card. It is the same component with the sender in the name slot, and its state is the recipient's own run. (F-120, F-437, F-469)

| State           | Established by                                | Opened                                                                                                                                      |
| --------------- | --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Working         | The run is active                             | The sent text and attachments; the recipient's own status line is at the foot of the transcript as usual                                    |
| Waiting for you | The run asked a question or needs an approval | The sent text; "Marlow asked you a question below." or "Marlow needs your approval below.", with "Show the question" or "Show the approval" |

- A message that no card on screen accounts for (one a bot did not ask for, or a late reply no identifier ties to a card) is an event line, "Message from" with the avatar and name. It opens to the message's text and "Raw".

**Elsewhere.** While the recipient works, its avatar in the rail is working and its row says so. (F-126)

## 11. The Messaged T3 Code card

The same component, for work a bot sends to T3 Code. It is drawn only from the bot's own tool events on the gateway, and the app never connects to T3 Code (F-138). Clawtrate has an optional T3 Code integration: a switch in settings, off by default, with which a person adds a T3 Code server to the gateway and gives it to chosen bots (F-482 to F-487). The cards do not depend on that switch: a bot's T3 Code calls are drawn whenever its tool events show them, with the switch on or off. (F-132, F-487)

**Identity.** The text "T3 Code" and a mark drawn for Clawtrate: code brackets in a 20 px rounded tile on `--bg-inverse`. No third-party logo.

**Each call's state.** Every call to T3 Code, whichever tool, has one of these states. They are the call's, not the work's.

| State                | Mark               | Established by                                                                                                                                                                                                                         |
| -------------------- | ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Call started         | sending            | The gateway reported the start of the tool call. That is never proof the call was made. While the call runs the gateway reports nothing more: no progress arrives.                                                                     |
| Waiting for approval | waiting, `--warn`  | A pending approval request names this tool call. The call is held until the request is answered.                                                                                                                                       |
| Call made            | check              | The call returned without an error. That means the call was made, not that the work is finished.                                                                                                                                       |
| Delivery unknown     | hollow ring        | The bot was stopped before the call returned, or the result says it was aborted or cancelled, and the gateway cannot say whether it was made                                                                                           |
| Failed               | failed, `--danger` | The call returned an error: `isError`, with T3 Code's `{code, message}` (F-314)                                                                                                                                                        |
| Not sent             | stopped            | The approval was denied or expired; a plugin refused the call (`details.status: "blocked"`, which is not an error result); the call was skipped before it ran; or the bot was stopped and the gateway confirms the call was never made |

**Transitions.** Call started, then Call made or Failed. A call that needs approval goes from Call started to Waiting for approval and, when allowed, back to Call started: it is the same call, and no second start is reported. A stop before the call returns leads to Not sent or Delivery unknown. Delivery unknown moves to Call made or Failed only when a later tool event carries an identifier that names this call. Call made, Failed and Not sent are final for the call. A thread, which many calls share, has a state of its own (11.2).

**When the bot is stopped** and a thread's latest sending call was made, the card adds a line in medium weight: "The call was made. Work handed to T3 Code may continue there." The stop note says the same. A call that had not returned when the bot was stopped gets no such line: it is Delivery unknown, or Not sent when the gateway confirms it. (F-137, F-470)

Touch and hold offers "Copy sent text" and "Copy raw" (the raw of the call whose item is open, or of the thread's first call). (F-444) The Work pane's Coding section lists these cards across the bot's tasks, one row per thread; its rows use this card's folded form. (F-136)

### 11.1 T3 Code's tools, and which calls are T3 Code's

T3 Code offers an outside client seven tools (`docs/research/provider-accounts-and-t3-code.md`, B.2 and B.3, from the installed T3 Code `0.1.8-nightly.20261109.4433`). Every one also takes an optional `environmentId`. Failures come back as a result flagged `isError`, with `{code, message}`, not as a protocol error.

**Which calls are T3 Code's.** A call is recognized per call, never per server. It is T3 Code's when its result names one of these seven tools in `details.mcpTool`, whatever the server is called in `details.mcpServer`: the person names the server, and one gateway can hold more than one T3 Code server. Other tools on the same server are not T3 Code calls. Before the result, a call is treated as T3 Code's only on the evidence of the gateway's name mapping (the map from effective names to server and tool that the gateway's tool configuration gives), and the result can overrule that evidence (11.4). Otherwise it is an ordinary tool-server call (section 8, row 26, then row 24) until its result names it.

**Reading a result.** The fields above are T3 Code's structured content, which the gateway passes on in `details.structuredContent`. The gateway's history keeps no `details` for tool-server results, so a card rebuilt from history reads the same fields from the result text, where the gateway writes the structured content first, as `structuredContent:` followed by its JSON with sorted keys. That rendering is the gateway's own and is parsed only in that form; when it cannot be parsed, the call has no known thread and is a card of its own (11.2).

### 11.2 Threads: one card for each, and its state

**A thread's identity** is three things together: the server, as the result's `details.mcpServer` names it; the `environmentId` argument, when the call gives one; and the `threadId`. A launch learns the `threadId` from its result; `t3_thread_send`, `t3_thread_read`, `t3_thread_wait` and `t3_thread_interrupt` carry it in their arguments, and their results repeat it. Nothing is matched by project, title, link, or nearness in the transcript. Two threads are two cards, even side by side.

**One card for each thread** in a task: the card of the first call on that thread that this task's record holds. Normally that is the launch. When the launch is not in the record (it was in another task, or older than the history the gateway returned), the first call that is becomes the thread's card, under the same title "Messaged T3 Code", and its opened view says so: "This thread was started before this conversation's record begins." or, when the Coding section knows the launch's task, "This thread was started in Weekly backup check." with that task as a link. No launch is invented. A call whose thread cannot be known (a launch that failed or was refused, a result that cannot be read) is a card of its own, as before.

**The listings** (`t3_project_list`, `t3_thread_list`) are ordinary lines in T3 Code's family: "Looked through T3 Code projects", "Looked through T3 Code threads", with "4 projects" or "6 threads" from the result. They fold with each other ("Looked through T3 Code 2 times") and never join a thread's card.

**The thread's state** is the right side of its card. Each call keeps its own state (the table above) on its own item; the thread's word is worked out from them, in this order:

1. **A call on the thread is open.** Waiting for approval, if one waits; else "Call started" for an open launch, send or interrupt; else "Checking", with the sending mark, for an open read or wait.
2. **Else, what T3 Code last reported.** The status in the latest returned, non-error result of any call on the thread (launch, send, read, wait, interrupt), in plain words: preparing, queued and starting are "Starting"; running "Running"; waiting "Waiting in T3 Code"; completed "Completed"; interrupted "Interrupted"; failed "Failed in T3 Code"; cancelled "Cancelled"; rolled back "Rolled back"; idle "Idle"; `interrupt_requested` "Stop requested"; `no_active_run` "Idle". A wait that `timedOut` reports its run's status, so "Running", never "Completed". A launch without a message reports no status, so it falls to step 3.
3. **Else, the latest sending call's state:** Call made, Failed, Not sent or Delivery unknown.

So a failed check, or a refused follow-up, shows on its own item and does not change the thread's word. The reported status is a snapshot, not a live state: it changes only when another call on the thread returns, and the opened card says when: "T3 Code reported Running at 5:41 PM." Keeping the card's word to what a call's result reported, rather than polling T3 Code, is a presentation decision: the results do carry T3 Code's status, and the card shows it with its time.

**The folded line** reads "Messaged T3 Code", the T3 Code mark, the first line of the latest message sent on the thread (the launch's `message`, else its `title`, or a follow-up's `message`), and the thread's state. When the thread holds more than one call, the detail ends with their number, "· 3 calls".

### 11.3 Opened: every call, each with its own Raw

Opened, the thread's card lists its calls in order, one item each, and every item can show what the gateway sent for its own call:

- **The item's head**: who and what, "Otto started the thread", "Otto followed up", "Otto read the thread", "Otto waited for a result", "Otto asked T3 Code to stop", with the call's time and its own state word.
- **What was sent**: the exact `message`, for a launch or a follow-up; under a launch, a chip for each target field its arguments contain (project, title, model, branch from `workspaceStrategy`). An absent field has no chip; nothing is filled in.
- **What came back**, as the result established it: for a launch, the thread and its first run's status; for a follow-up, its `delivery` in words ("Started a new run", "Queued", "Steered the running turn", "Restarted the turn") and the run's status; for a read, the thread's status and the latest run's assistant items on the page, with one line on how much was read: "Read to the end" only when `hasMore` is false and none of that run's items, of any type, has `textTruncated: true`; "First page only: the reply may continue" when `hasMore` is true; "Part of the reply only: its text was cut, and the rest was not read" when an assistant item's text is cut; "Part of the run only: an item's text was cut, and the rest was not read" when only another item of that run (a user message, a tool item) is cut (with or without more pages, the lines show together). Nothing says the end was read until both are complete; for a wait, the run's status, "The wait ended before the run finished" when `timedOut`, and the result run when `resultRun` names one; for an interrupt, its status in words. The state sentences of the per-call table apply: "This shows the call was made. It does not show that the work is finished." under any call whose result reports no final status.
- **"Raw"**, a text button at the end of every item, named "Raw for this call", opens that call's own panel (section 9): its tool name, arguments, result, timing and identifiers. Every call that joined the card keeps its Raw here, whether or not it also has a line of its own (11.4).
- **"Show where it happened"**, on an item whose call also has a line of its own, scrolls to that line (11.4).

Under the items: **Files**, as chips, only when a result or a gateway attachment carries them (F-135), and **"Open thread"**, only when a result carries a `link`, the latest one received. It is a link named "Open the T3 Code thread in your browser"; it opens the system browser when chosen, and nothing is fetched before that. (F-135)

A card that is one call on its own (no known thread) is opened as before: what was sent, what came back, Files, "Open thread" and "Raw".

### 11.4 Becoming the T3 Code card, joining a thread, and a line at each later moment

**The change in place.** A call that is T3 Code's but not yet known to be shows, while it runs, as the general card: "Using t3code thread launch", words from its effective name, the diamond, Call started. When its result names one of the seven tools, that same element becomes T3 Code's line, keyed by the same tool call id:

- **Place.** The line keeps its place in the transcript. At every width the two lines have the same structure (one line on a wide column; the sentence and the state on the first line and the detail on the second on a narrow one), so the height is the same; where a different height cannot be avoided (a longer sentence wraps), the reading line holds as section 18 says, and nothing above the reader moves.
- **What changes.** The icon becomes the T3 Code mark, the words become "Messaged T3 Code" or the operation's words below, the detail becomes the first line sent, and the right side the state. The change is a 200 ms cross-fade of the line's parts; under reduced motion it is instant.
- **What carries over.** If the line was open on its Readable tab, the T3 Code card opens with this call's item; if it was open on Raw, the item opens with its Raw panel open. Focus stays on the same control: on the line's heading if it was there; on the item's "Raw for this call" if it was on the Raw tab; on the same copy button inside the same Raw panel if it was there, since both are section 9's one component.
- **When the result overrules the name mapping**, the change runs the other way with the same carry-over. A call the mapping had shown as T3 Code's line, whose result names another tool, becomes that tool's card in place, keyed by the same tool call id. If the line was open, the card is open. If the call's item had its Raw panel open, the card opens on its Raw tab; otherwise on Readable. Focus stays on the corresponding control: the line's heading becomes the card's heading; the item's "Raw for this call" becomes the card's Raw tab; a control inside the Raw panel (a copy button) becomes the same control, by its name, in the card's Raw tab. Because a call joins a thread only after its result (below), an overruled call never has to leave a thread's card.

**Joining a thread's card.** A call on a thread that already has a card joins it only after its result names the tool and the thread, and then in one of two ways:

- **Directly**, when all of these hold: the thread's card is the item just above the call's line in the same column, with nothing arriving between them since the call started; the reader is following the end of the transcript (section 18); and the call's line is not open and holds no focus. Then the line closes up over 200 ms (instantly under reduced motion) and the call is an item of the thread's card, which updates its state. This happens only at the foot of the transcript, where the reader is, so nothing above the reader moves.
- **With a line of its own**, in every other case: the call keeps its line where it happened, in T3 Code's family, and is also an item of the thread's card. Its words: "Followed up with T3 Code", "Read the thread in T3 Code", "Waited for T3 Code", "Asked T3 Code to stop", each with the call's own state and, as its detail, the first line it sent or the status it got back. The line opens to that call alone (what was sent, what came back, its Raw) and has "Show the thread".

Either way, every call has its Raw on the thread's card, and a call with a line has it there too.

**Getting from a line to its thread, and back.** Destinations are found by identity, never by nearness.

- **"Show the thread"** (named "Show this thread's card") finds the card for the line's thread identity. In this task: it scrolls the card into view by the smallest scroll, opens it, opens this call's item, and moves focus to the item's head. In another task of the same bot (the Coding section's index of thread cards across a bot's tasks, F-136, knows where): it opens that task at the card in the same way, and records where the reader was, so that "Back" on the phone, ⌘[ on the desktop, or the card's "Back to where you were" returns to the line with focus on "Show the thread", as "Open in Marlow" does (section 10). Where no card for the thread is in reach, the control is absent.
- **"Show where it happened"** on an item (named "Show this call where it happened") finds the line by the call's tool call id, scrolls to it and moves focus to its heading.
- Nothing else moves focus. A line or an item never leads to a different thread, even one beside it.

### 11.5 What remains open about T3 Code

- **A failure's exact envelope.** That a failure is a result flagged `isError` with `{code, message}` is established; its exact JSON was not captured. Read `code` and `message` from the structured content, and show the result text as received when they are absent.
- **The name mapping before a result.** The engine accepts a map of exact effective names to server and tool, given by its caller (`docs/decisions.md`, "Message cards"). Where it comes from in the app (the gateway's tool inventory, or the server the integration added, F-482) is the builder's to settle; without it, every T3 Code call is recognized at its result.
- **Contract drift.** The fields above are those of the installed T3 Code build named in 11.1. T3 Code's public source has moved on (reads gain `beforePosition` and `earlierPosition`); a fixture names the build it mirrors, and a field this design does not read is ignored rather than guessed.

## 18. Following and Jump to latest

**Following.** The reader is following when the end of the transcript is within 96 px of the foot of the view. That is decided before each change, and then:

- a reader who was following stays at the end, whatever changed: new output, a card arriving or resolving, the shelf or the composer growing or shrinking, the standing-allow form opening, the Work pane docking;
- a reader who was not following keeps their place: the text at the reading line, just under the protected band at the top, stays where it is while things change above or below it. This is the shell's own rule for a change of width, extended to every change of content.

So when an approval arrives and the shelf row appears, or the standing-allow form opens, the status line is still the last thing in view, at any width.

One thing limits following: what the reader has just opened stays in view. If staying at the end would push the first line of a card, a row in a fold or a form the reader opened above the top of the view, that line is held at the top instead, and the reader is no longer following. Nobody is scrolled away from what they opened to keep the status line in view.

A reader who is not following and opens something whose content falls below the foot of the view (a Raw panel, the full request) has it brought into view by the smallest scroll that shows it, and never past its first line.

**Jump to latest** is the shell's `.jump-latest` control (see `visual-language.md`), with the states a run needs. It shows only while the reader is not following and its destination is out of view: centred 10 px above the foot of the transcript, a pill on `--bg-raised` with `--shadow-pop`, 36 px (44 on touch), at most 380 px wide. It rises 6 px and fades in over 200 ms.

| State              | Content                                                                           | Destination                                                                                              |
| ------------------ | --------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| A card is pending  | The waiting mark, "Needs you" in `--warn`, and an arrow                           | The oldest pending card. The arrow points up when that card is above the view and down when it is below. |
| A run is active    | The bot's avatar at 20 px in its real state, the current phrase, and a down arrow | The end                                                                                                  |
| New output, no run | "Jump to latest", or "3 new", and a down arrow                                    | The end                                                                                                  |

A pending card comes first, then a live run, then new output. Choosing the control scrolls to its destination; for a card it also moves focus to the card. The control leaves when its destination comes into view.

- What was missed is fetched again and merged in place, without enter animations. No message or card appears twice: each is matched by its identifiers and updates the one already on screen. - Nothing unmounts and nothing the reader had opened closes: an open card with its chosen view, an open fold and its open rows, an open card with its Raw panel all survive. The one exception is an open "Thought" line in a run whose reasoning revision changed (7.5): it closes, because the reasoning it showed may have moved. (F-104)
- The reader's place holds. New items below the fold bring up Jump to latest.
- If the fetch fails, what was on screen stays. (F-105)

In the prototype, "Drop the connection" in the bar shows all of this during the scripted run.

These depend on the gateway more than the rest:

- **What "started" proves.** A tool's start event is reported before the call is checked or allowed, and also for a call that is then skipped. It shows that the bot began the call and nothing about whether it was made or delivered. That is why both Messaged cards begin at Call started, and why a call can go from there to Waiting for approval and back.
- **The kind of an action.** No field of a tool event names it. The app chooses it from the tool's name by 8.1's table, so a tool the table does not know is the general card, and a tool server's call is ordinary until its result names its server and tool.
- **What history keeps.** `chat.history` tool results carry `toolCallId`, `toolName`, `content` and `isError`, and keep `details` for some tools only (a write's diff, yes; a read's or a web search's details, no). A card rebuilt from history shows only what the row holds (8.6).
- **The recipient's state on a Messaged card.** Working and Recipient waiting need the send's result to name the recipient's run. Where it does not, the card goes from Sent to Replied or No reply yet.
- **Rules.** An approval request says which decisions it offers and carries the command, its arguments, the folder, the host or machine, the bot and, for a routine's request, the scope of the grant. It does not carry the rule that "allow always" will save, and the confirmation does not return one. Standing grants are listed and revoked with the access that answers approvals; a host's allowlist needs admin.
- **Effort.** The gateway reports the effort requested for a task or turn. The effort a turn used is not a dependable field and is never shown.

**Replaced.**

2. **Reasoning as a step.** Reasoning no longer has a row or card. It belongs to the next action, the reply, or the run's end (7.5). ### Where the mapping lives

The table in 8.1, the action words in 8.2, the general card's rule in 8.3 and T3 Code's seven tools in 11.1 are one mapping, from a tool call to a kind and the parts of its line, and it lives in one place: a new module in the core, `packages/core/src/actions.ts`, beside `runs.ts` and `cards.ts`. It is pure: given a step's tool name, its arguments, its result's `details` when there is one, the gateway's name mapping for tool servers, and the configured list of T3 Code's tools, it returns the kind, the fold key, and the parts of the line (verb form for each state, object, detail) as data, not as English. The words themselves are strings in `packages/ui`, so that they can be translated; the core never builds a sentence. `toolTitle` in `runs.ts` stays for what it does today; the general card's words follow 8.3, which differs from it (lower case, camel case split, an acronym kept). Folding is a pure function over a run's steps and bubbles (7.4) in the same module, so that the live stream and history give the same folds. A unit test feeds it one call of every row of 8.1 and asserts the kind and the line.

### What needs a fixture scene

The development gateway runs only some tools (8.1, column "Dev"). Every card of the others is built and checked from fixture events: tool `start`, `update` and `result` events, and `chat.history` rows, in the shapes of the installed package's schemas and result builders, never in fields invented for a fixture. Each kind needs a scene that plays it through its open states and every outcome of 7.3 that its adapter can give, and a second action with the same key in a row, so that its fold is checked. Beside them:

- **Outcomes that are not done:** media admitted in the background (`async`, `status: "started"`) and media made, whose count is the result's, not the request's; a routine run that returned `enqueued: true` and one that returned a finished `run`; a channel send that was `sent`, `queued`, `suppressed` and `unknown`, and a turn that `replied` and one that timed out; a memory search that was `unavailable`, and one that was `partial`; an X search without credentials (`missing_xai_api_key`); a computer click whose `effect` is `unverifiable`.

- **Folds:** a fold that a failed action joins; one that a new action joins while it is open, with focus inside an open row's Raw; a fold with an earlier failure and a later pending approval; a fold whose members were all stopped; a fold with a member missing its times; a fold split and one merged by a reconciliation, with open rows; two reads of one file and one of another ("Read 2 files · 3 reads"); two calls of an unidentified opaque name, which do not fold.
- **Runs:** forty actions of mixed kinds (the prototype's `?scene=long`), and forty that alternate kinds; reasoning, a reply and no action; reasoning only, which ends as an error.
- **Tool servers and T3 Code:** an ordinary tool-server call identified only by its result; a T3 Code launch identified only by its result, while its line is open on Raw with focus inside it; one identified at its start by the name mapping and overruled by its result; two threads in one task; the same `threadId` on two servers; a thread whose launch is not in the record; an immediate wait that joins the card, a follow-up after a bubble that keeps its line, a failed read, and a stop that returns `interrupt_requested`; every joined call's Raw opened from the thread's card; "Show the thread" from a line in another task, and back.
- **History and reconnects:** history without `details` for a read, a web search and a tool-server result (whose thread is read from the rendered structured content); a reconnect whose reconciliation changes a run's reasoning revision while a "Thought" line and a card are open: the line closes and the card stays open; the same run received by a second client that subscribed to the session and did not start it: the same cards.

## 24. Not covered here

- Secure Form and Computer cards, and with them the order between the vault, a password manager and a Secure Form. They use the card frame here (`--bg-bubble`, radius 18, a 17 px title, a tag at the top right, buttons along the foot), and a run counts them among its pending cards, so a steer or an answer to another card never clears them.
- Requests for permissions on the phone itself: pending, timed out, granted and re-evaluated, resumed once, blocked by policy.
- Draft, file and link cards.
- The Permissions page, where standing grants are listed and revoked, a host's allowlist is shown to an admin, and the audit log and limits live. (F-178, F-324)
- Clawtrate's rules plugin and its rule form: rules the user shapes by hand, with a scope and a lifetime of their choosing, deny and ask rules for a bot, and saving a rule after a request expired. Sections 12 and 23 mark what depends on it.
- Question records that are forms, carry a resource or a link, or ask for a secret. Section 13 shows them readable and not answerable until they have a design.
- Changing the model or the effort. Both belong to the task and the turn; a bot's own default needs the admin tier.
- The Work pane's Coding section, beyond the card form its rows use. (F-136)
- A conversation shared by several bots.
- The gateway's record of tool actions, which Raw links to.
