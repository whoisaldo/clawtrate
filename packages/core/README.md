# @clawtrate/core

The gateway client and the live conversation engine. A host process (Electron main, or the web preview host) owns one `ClawtrateClient`, which holds the gateway connection, the device key and every task's runs. The interface never talks to the gateway: it reads state snapshots and sends commands through a bridge. This guide is for building the interface on top of it. The reasons behind each behaviour are in `docs/decisions.md`.

## The bridge

The interface holds a `ClawtrateBridge` (`src/bridge.ts`):

- `getState()` and `subscribe(listener)`: the latest `ClawtrateState` and every later one. Hosts coalesce store updates to one snapshot per 16 ms (`batchSnapshots`).
- `send(command)`: run a `BridgeCommand` and ignore its answer.
- `invoke(command)`: run it and resolve with its answer, typed by `BridgeResultFor<C>`.
- `attach(file)`: hand a file's bytes to the host for a later message; resolves with an `AttachmentInfo` (`src/attachments.ts`) whose `id` the message names.

The desktop renderer gets one over IPC (`apps/desktop/src/renderer/bridge-desktop.ts`), and a browser gets one over the web host's socket (`createRemoteBridge` in `src/remote-bridge.ts`, used by `apps/desktop/src/renderer/bridge-web.ts`). Each window or tab is its own viewer (`createBridgeSession`). Hosts validate every command (`parseBridgeCommand`) before it reaches the client. A command that acts on a task is refused unless this viewer has that task open.

There is no separate steer command. `mode: "auto"` starts a new run when the task has no active run, steers into the active run when it is running or waiting, and queues when it is stopping. `mode: "queue"` queues behind the active run whenever a run is active; with none it starts a run. While a question from the run is pending, every message is held, not sent, whichever mode it was sent with, until the last pending question is answered, dismissed or expires. A question counts as pending when the run waits on it, also when the task holds only its id: a run this client followed while nobody had its task open (a bot's recipient) keeps the question it waits on by id, carries it into the task when the task is opened, and settles it on `question.resolved` or when `question.list` no longer lists it. A run carried into its task that way, or any run of an open task another task's send names, goes back to being followed when that task is let go, so the sender's card keeps seeing it to its end; and while both tasks are open, a change to that run updates the sender's card at once, whether it comes from an event or is settled from a history read. A sender's task opened when nothing follows its recipient's run any more (the recipient's task was let go while the sender's was closed) reads the recipient's own history after its history read, and follows the run from what that establishes: in flight, or ended as its rows say. Opening a task takes over every run followed for it, so no copy left behind goes stale. When the gateway deletes such a session, its followed runs end with no known outcome (`cancelled`, `outcomeKnown: false`), the question they waited on with them, and nothing of the session is kept. A question that settled is not asked again by a repeated request. Held messages are then released in order as a message sent at that moment would go: a steer into the running run unless it was queued, queued while the run stops, and queued, one run each, once the run has ended by itself.

A question answer maps each question id to its answers. Each answer is either text as typed or `{ option: index }`, where `index` is the option's `QuestionOption.index`. At most 3 questions and 8 answers each are accepted.

An approval offers only the decisions in its `allowedDecisions`; deny is always among them. `expiresInDays` (1 to 3650) goes only with `allow-always`. When `decisionCut` is set, only deny is accepted until this viewer has called `readApprovalText` and passes the returned `digest` as `shownDigest`. Echoing the card's own `decisionDigest` does not count. A decision that failed sets `decisionError`: `refused` only when the gateway's answer establishes the decision was not applied (the list, with its sources, is `REFUSED_DECISION_ANSWERS` in `src/approval-refusals.ts`), `unknown` for every other answer or none after it was sent. While it is `unknown`, no allow is accepted, and no Deny either if a Deny's outcome is among the unknown (`unknownDeny`), until `checkApproval` (run once by itself, and again after a reconnect) reads the request back: still pending clears it, settled shows how it ended. `stillOpen` says a read-back found a refused request still pending. Every decision and every read-back takes the next number in `attempt`. A decision's response settles only its own attempt, so one refused or unanswered decision never releases another still on its way (`inFlight`). A read-back's pending answer counts only when no newer attempt began after it was sent, and clears only an unknown outcome established before it was sent (`unknownAt`); otherwise it is dropped and, unless a newer read-back is on its way (`readingAt`), another is sent. At most one decision is on its way, except that a Deny may follow an allow: while `submitting`, `submittingDecision` names the latest. `decisionRefusal(card, decision)` says why a decision may not be sent now. These attempts belong to the approval, not to the task showing it: while a decision or read-back is on its way or an outcome is unknown, the client keeps them apart from any task (at most 256 approvals; past that a decision on another is refused), across a task's release and a reconnect. A task that shows the approval anew while something is outstanding marks its outcome unknown until a read-back sent after that answers; no list loaded on opening clears it.

A step's text on the snapshot (`argsText`, `output`, `result`) is a `StepText`: up to 2,000 characters of `text` plus the whole length in `totalChars`. The exact gateway payload is `Step.raw`, a `StepRaw`, carried inline only when its JSON form is at most 2,048 characters; otherwise it is null, and `readStepRaw` reads it. `readStepRaw` answers one of: `{ status: "available", raw }`, only when it has established that what it fetched is the step shown (for reasoning, a text beginning with the step's own; for a tool, its call id); `{ status: "cut-by-gateway", raw, receivedChars, reason }`, when the gateway's history holds the step only cut to its display length (`raw` is what it sent: the beginning of the text with the gateway's own marker after it; `receivedChars` is the length of the longest text the rebuilt step exposes, not of `raw`; show it as cut, never as whole); `{ status: "too-large-for-gateway", reason }`, when the gateway replaced the step's message with its placeholder for a message above 131,072 bytes (it will not return the text, so do not offer to try again); `{ status: "not-established", reason }`, when history holds something else at the step's place; or `{ status: "not-available-yet", reason }`, when history did not return the step: it may not hold it yet, or its page was too large to include it, so trying again later may help. Show the `reason`. `Step.truncated` says the gateway cut a step's text, reasoning included. A `TranscriptItem` whose `cut` names fields is read whole with `readHistoryItem`. `truncated: true` on an item means the gateway cut one of its rows: the item kept in state is read at the gateway's default display length (8,000 characters), so it says so whenever that cut it; the item `readHistoryItem` returns is read at the longest length the gateway gives (500,000) and says so only if it is still cut, or if a row above the gateway's 131,072-byte limit came back as its placeholder text. The gateway's cut is not a clean prefix: a cut text ends with the gateway's own marker, and a placeholder replaces the text altogether. None of these whole reads is kept in state.

Writes need access the device may not hold. The first send, stop, answer, resolution or creation on a read-only device asks the gateway's owner for `operator.write`, `operator.approvals` and `operator.questions` in one request; `requestAccess` asks without acting. Admin (`operator.admin`, with the interactive scopes) is asked for only by `requestAccess` with `tier: "admin"`, which the account screens send when the person chooses "Request admin access"; no write asks for it by itself, and an account write below admin is refused before anything is sent (`AdminNeededError`). A grant the client asked for is recorded with the device token (`adminHeld`), and only then does connect ask for admin again; a stored grant that merely lists admin never makes it ask. While the request is pending, a message shows `awaiting-access` and the other actions wait. When the gateway refuses or the connection stops, they fail with an error the interface can show.

## The rail's actions

`src/task-actions.ts` manages a bot's tasks and `src/sidebar.ts` the rail's arrangement; both keep nothing beyond what the state shows. Every call stays at `operator.write`: the parameters are only those OpenClaw 2026.10.6's own policy admits at write (`session-method-scopes-base`), and `test/task-actions.test.ts` checks each against a copy of those rules. They act on any task the rail lists, open in the view or not, and a host pinned read-only refuses all of them. On a read-tier connection the first one asks for the interactive scopes, as a send does, and waits.

- `newTask` is `sessions.create {agentId, label?}` with no message: nothing runs until the person writes. The new row is listed at once from the answer. A task with no name is "New task"; a bot's `main` key is "Main".
- `renameTask` is `sessions.patch {key, label}`; labels are unique per bot, and a taken one fails as "Another task of this bot is already called …".
- `pinTask` is `sessions.patch {key, pinned}`; pinned tasks come first under their bot (`Task.pinned`).
- `markTask` is `sessions.patch {key, unread}`. With `opened`, it is the read of opening a task: made only while the connection already writes (never asking), only when the row is unread, one per task while one is on its way (`MAX_OPENED_READS`), and with `expectedMarkedUnreadAt` naming the marker it saw (`Task.unreadMarker`), so it never clears a newer "Mark as unread".
- `archiveTask` and `restoreTask` are `sessions.patch {key, archived, expectedSessionId}`. An active run is refused (`ActiveRunError`) unless `stop`: then `chat.abort`, and the archive waits, within `STOP_SETTLE_MS` (15 s), for the gateway's row to say nothing runs. A plain archive reads `runMark` (what the engine has seen of the task's runs) before and after describing the task, and sends nothing, refusing with `ActiveRunError`, if a run started meanwhile. The gateway has no guard that makes an archive refuse a run started while the request travels, so that last moment is not covered: in OpenClaw 2026.10.6 the archive first stops every run of the session (`prepareSessionLifecycleDrain` in `sessions-lifecycle-drain`), and its guards compare only `sessionId` and `lifecycleRevision` (`archiveTargetChanged` in `sessions-mutations`), which are set when the session is made and which a run does not change. A plain archive answers `{ stoppedRun }`: true when a run of the task was seen to end as stopped, on that run's own end event (`WaitingIndex.stopMark`), at or after the request, waiting up to `ARCHIVE_STOP_WAIT_MS` (3 s) for that end when a run started while the request was out. Its refusal for a working task carries `ACTIVE_RUN_MESSAGE`, which crosses the bridge as the error's message.
- `deleteTask` stops an active run the same way, archives, then `sessions.delete {key, archivedOnly: true, deleteTranscript: true, expectedSessionId}`, the only delete the write tier may make.
- `listArchived` reads `sessions.list {agentId, archived: true}`: at most `MAX_ARCHIVED_LISTED` (50), newest archive first.
- `newMainTask` is `sessions.create {agentId, key: "agent:<bot>:main"}`: the bot's canonical main, which the gateway never archives or deletes. A second create of the key while another is under way is refused with "session changed before sessions.create; retry the request"; the retry answers the same session, so every client adopts one Main.
- `changeSidebar` applies one `SidebarChange` (pin, hide, a one-bot `move`, section) to the `clawtrate.sidebar` user preference with a compare-and-set, applying it again to a newer value on a conflict (at most `SIDEBAR_WRITE_ATTEMPTS`, 4). When the gateway holds no arrangement yet, it starts from `base`, the device's own. `state.sidebar` is read at every connect and on `users.prefs.changed`; `status` is `unavailable` for a connection with no durable user, and the interface then keeps its arrangement per device. A change that would pass the gateway's 4,096 bytes (`MAX_SIDEBAR_BYTES`), or pin past 32, is refused with `SidebarFullError` in plain words. An answer older than the arrangement shown never replaces it. Every write raises the arrangement's `rev` under the compare-and-set: the gateway gives no version of a preference, so the arrangement carries its own, and an answer is shown only if its `rev` is not below the one shown (a tie goes to what was asked last).

`src/waiting.ts` says which tasks wait for the person, and whose latest run was stopped, across every bot. A task the engine follows is described by its runs (`fromActivity`), as the conversation shows them; any other by the gateway's events, by run identity: a run waits for an approval from its lifecycle's `waiting-approval` until `approval-resolved` or its end, and for an answer from `question.requested` until `question.resolved` (and `question.list` at a connect, with `operator.questions`). A task the gateway lists as running and waiting has `status: "waiting"`, `waitingFor` and `waitingSince`; a task listed with no active run waits for nothing. At most `MAX_WAITING_SESSIONS` (64) tasks are kept, `MAX_WAITING_MARKERS` (8) markers each.

## The Work pane's files

`src/files.ts` reads what the Files tab shows (`docs/design/work-pane.md`, Part 1), all at `operator.read`, and keeps none of it in the state. `listTaskFiles` reads `sessions.files.list` and the task's row (`sessions.describe`) together, so its `folder` says where the task works: the bot's configured `workspace`, a folder of its `own` (`spawnedWorkspaceDir`, `spawnedCwd` or a `worktree`), a `repository` the gateway keeps, or `unknown`. `folder.sameAsWorkspace` is true only when the row carries none of those four fields and the list returned a `root`; only then is a task's file read with `agents.workspace.get`, and a workspace file with the task's `sessions.files.assets`. That decision is bound to the read: the row is read again just before the other folder's reader is asked and again once it has answered, and when either shows the task no longer works in the bot's workspace, nothing that reader sent is used; the file is read once more from fresh facts, and a second change answers `failed`. `readTaskFile` follows `planTaskRead`: the task's own reader (`sessions.files.get`) within 256 KiB; a larger picture from the workspace reader (5 MiB) where the folder is established, otherwise from `sessions.files.assets` (1 MiB); recordings, videos, and stylesheets or scripts over 256 KiB from `sessions.files.assets` (1 MiB), and never audio or video from a repository. It never asks a reader the list's facts show will refuse, and never reads a file because a name matches. When a reader refuses, what follows comes from that refusal's own facts, not the list's: `afterTooLarge` takes the task reader's size and limit (a stylesheet or script goes on to the asset reader, up to its limit), `afterUnsupported` the type it detected (a picture a repository will not send for its type is `picture-type-not-sent`, not too large), and the workspace reader's refusal says which of its limits it applied. A `FileRead` is `content` (with the `reader`, `kind`, exact `bytes` and a SHA-256 `hash`: the gateway's for text it hashed, computed here otherwise), `cannot-show` with the `FileLimit` the file met and its facts, `missing`, or `failed` with the reason.

Content reaches the viewer in chunks sized to its channel (at most `MAX_CHUNK_BYTES`, 1,048,575 bytes, on the desktop), each a multiple of 3 bytes so that its base64 decodes by itself: the answer carries the first, and `readFileChunk` the rest. At most `MAX_FILE_TRANSFERS` (4) transfers are held at once, each at most `MAX_TRANSFER_BYTES` (5 MiB, the largest any reader sends); each is dropped when its last chunk is read, when its viewer releases it or goes away, or, once it has gone `FILE_TRANSFER_TTL_MS` (60 s) without a read, by the next transfer that starts or chunk read. Expiry is checked then, not on a timer, so an idle transfer can stay longer; it still counts against the four, and a new transfer drops it before it is refused. At most `MAX_FILE_READS` (4) lists and reads run at once; a fifth is refused. A list or page longer than the viewer's channel keeps what fits and says how many it left out (`omitted`, `nextOffset`).

A file tool's step carries `files` (`StepFiles`): the paths its arguments name, read as the gateway's own list reads them, and its result's `changed` and `created`. The views over a task's runs are pure: `fileMarks` (writing, this run, last run, from file-tool evidence only), `fileSource` and `fileChanges` (the steps that touched exactly that path), `commandsSince` (an `exec` started after the list was checked) `finishedChanges` (a count that grows when a change result lands, for the refetch) and `changesUnlisted` (a finished change a list does not hold yet, for the refetch after a history read). A tool step whose start the live stream missed takes its call from history's copy: its `argsText`, its `files`, and the raw payload `readStepRaw` returns, call and result together. A tool step whose run ended before its result arrived here is `unknown`, not `failed`: nothing established how it ended, it is no file's source, and history's finished copy replaces it, so a write whose result event was missed is still a done change and the file's source. `stepPatch` reads a change from a step's raw result: the live result's `patch`, or the numbered `diff`, which is all the gateway's history keeps.

## Provider accounts

`src/accounts.ts` holds the account screens' facts (`docs/design/bots.md`), and `src/accounts-engine.ts` reads and writes them on the client's connection. Nothing is read until a screen asks (`refreshAccounts`); after that a reconnect reads again.

- **Accounts as each bot sees them.** `models.authStatus {agentId, refresh: true}` for every listed bot, four at a time: an unrefreshed answer can list shared accounts as `saved`, so it is never asked for. An account is shared (`keptBy: null`) when any bot's view lists it as inherited, otherwise kept by the one bot whose own store has it. `kind` is `subscription` or `key` only for a sign-in Clawtrate started (recorded with the person's preferences, `users.prefs` key `clawtrate.account-kind.<profile id>`), else `gateway`. Labels come with admin reads only (`labels`).
- **Bindings.** Each bot's model as `config.get` holds it (`agents.list` drops the account suffix): `mode` `account`, `gateway` (its own model, no account) or `default-model`; its `fallbacks`; `suffixLost` when Clawtrate's own record (`clawtrate.bot-account.<bot>`) says it set an account that the model no longer names; `accountMissing`; the provider's stored order. `accountWord` gives the row's word; `retainedOrder` the one-account order a bot with no fixed account still has.
- **The lock's evidence** (`LockEvidence`): `matched` only for a stored order of exactly the bound account, still listed; `multi`, `other` (a one-account order naming another account: "Lock out of date"), `none`, `failed` (the read failed: the last confirmation and its time are kept), with `checkedAt`, `lastMatchAt` and `lostAt`. `checkLock` reads one bot again; the interface decides when (on opening the Account page, every 4 s after the lock command was copied, every 30 s otherwise), and the engine re-checks every locked bot of a provider after a sign-in it started.
- **Sign-ins.** `startSignIn` runs `models.authLogin` for `main` when its sign-ins land in the shared store (`mainShared`), else for the bot named, and follows `wizard.next` (which waits while the gateway polls, up to `SIGNIN_WAIT_MS`). Client notes are acknowledged; a choice step ends the sign-in. Stages: `starting`, `waiting` (a code and its link, or the gateway's own instruction), `entering` (a field), `checking`, `connected`, `failed`, `expired`, `cancelled`, `ended` (the connection dropped), `unconfirmed` (saved, not confirmed), `busy`; `saving` when the gateway refused to cancel. However it ended, `result` is read afterwards: the accounts added, where the first is visible, and the locks of the provider's bots (`kept` or `widened`).
- **Creating and changing.** `createBot` sends `agents.create` once, then the model with `fallbacks: []` (and the effort) in one `config.patch`, reads the bots back and gives the bot its first, empty task "Main" (`sessions.create`). A create that got no answer is never sent again: once connected, the bot list is read for the bot it may have made. A refused fallback write leaves `fallbacksUnwritten`. Every patch waits for the gateway to apply it.

**What the person types.** A code pasted into a sign-in and an API key are arguments of one request each. They are kept nowhere: not in the state, not in a field or collection of the engine, not in an error (`withoutSecret` takes them out of the gateway's answers; a key's error carries no `cause`). `accounts.test.ts` proves it for the state, the host's storage and log, every snapshot a viewer receives and every string the client object holds.

**Bounds.** 64 accounts, 32 sign-in methods, 64 key providers, 128 catalogue models (12 effort levels each), 32 bindings (16 order ids, 16 fallbacks each), one sign-in, one creation, one write. The engine's own records (kinds, what it set per bot, unwritten fallbacks) are at most 64 each and registered in `owners.ts`.

## Usage and warning budgets

`src/usage.ts` reads the gateway's figures and holds the budgets' rules; `src/usage-engine.ts` reads and writes them on the client's connection (`docs/design/controls.md`, sections 16 and 17; what the gateway returned is in `docs/decisions.md`).

- **Reports** (`readUsage`) are answers, never kept: the bot's or every bot's `usage.cost` for the period's days in the given time zone, its `updatedAt` and whether the gateway is still counting (`UsageFigure`); with `detail`, each task's share (`sessions.usage`, the largest `MAX_REPORT_TASKS`) and the usage by source (`UsageSources`), from at most `MAX_SCANNED_TASKS` task histories and `MAX_SENDER_TASKS` sending tasks. A cost is `estimate`, `partial` (`missingCostEntries`) or `unavailable`. At most `MAX_USAGE_REPORTS` (2) are read at once; one more is answered `{ busy: true }` (`UsageBusy`), not refused, and nothing waits for it: the page that asked says it is waiting and asks again while it is shown. A report belongs to the connection it started on: once that closes it asks nothing more, uses no answer, and fails, so no figure comes from another gateway.
- **Budgets** are the `clawtrate.budgets` user preference, read at every connect and on `users.prefs.changed`, and changed with a compare-and-set (`changeBudget`, `operator.write`; a host pinned read-only refuses it). `state.usage` holds them (`budgetsStatus` is `unavailable` for a connection with no durable user), each one's count for its current period (`counts`; `currentCount` gives a budget's count only for the period it is in now) and the providers' limits (`limits`, from `usage.status` at every connect and every 5 minutes). Counts are read when budgets change, every `COUNT_EVERY_MS` (60 s) while any is kept (`COUNT_COUNTING_MS`, 5 s, while the gateway is still counting one), and `COUNT_AFTER_RUN_MS` (31 s) after a budgeted bot's run ends.
- **Bounds.** 16 budgets and their counts, 16 providers with 8 windows each, in the state (`USAGE` in `state-bounds.ts`); the engine keeps no collection between events.

## Search

`src/search.ts` holds the gateway's part of the Cmd/Ctrl+K palette (`docs/design/search.md`) and keeps none of it: each answer goes to the viewer that asked, and the query is never logged. All three read at `operator.read`, at most `MAX_SEARCHES_IN_FLIGHT` (10) at once; past it a request is refused with an error to show.

- `searchMessages` sends `sessions.search {query, scope: {excludeCron, excludeSubagents, agentId?}, limit: 25}`, the task list's own filters, never `query` alone or `sessionKeys`. A result without its session key, message id or role is dropped, since it could not be opened; a snippet is cut at 500 characters. `truncated`, `indexing` and `archivedExcluded` belong to the reply that carries them.
- `searchRoutines` sends `cron.list {query, enabled: "all", limit: 50, offset}` and returns the page with `total`, `hasMore`, a `nextOffset` past this page or null, and `snapshotRevision` as `revision`.
- `searchFiles` searches through the bot's newest listed task: `sessions.files.list {sessionKey, search}` and `sessions.describe`. Names are returned only when that task's row has none of `spawnedWorkspaceDir`, `spawnedCwd`, `repositoryWorkspaceId` or `worktree` and the list returned a root (`establishFolder`); otherwise the answer is `unverified` or `no-root`. Only entries of kind `file` count, at most `MAX_FILE_HITS` (100) of them, with `returned` saying how many came back, so the largest answer fits a web viewer's result frame.

Bots, task titles, links and settings are matched by the interface over what it already holds.

## Where a bot runs and Machines

`src/machines.ts` reads what "Where a bot runs" and Settings, Machines show (`docs/design/controls.md` sections 14 and 15) and keeps none of it: each read is answered to the viewer that asked, with the time it was read, and the engine holds no collection. What the gateway returned for each method is in `docs/decisions.md`.

- `readPlacement` reads `config.get`, `agents.list`, `node.list`, `models.authStatus` and the bot's latest task's `tools.effective` (all `operator.read`), and with admin only `secrets.store.list` and, per enabled plugin, `plugins.inspect` then `plugins.credentials.inspect`. Everything is the gateway's settings as stored or what it reported, never an inference: `CommandPlace` holds the stored `tools.exec.host` and `.node` (an unknown host kept and marked), and a listed node only when its id is the stored one; `BrowserSettings` the stored tool lists, the gateway's browser switches and the computer plugin's profile. What the settings name (`inventory`) is inventory, never a permission; a list a tier cannot read is `{status: "needs-admin"}` or `"needs-pairing"`, and a failed read `"failed"`, never empty.
- `readMachines` reads the machines (`node.list`), each approvals file with admin (`exec.approvals.get`, `exec.approvals.node.get` for a connected node) and the paired devices with device access (`device.pair.list`).
- Every write is refused before anything is sent below its tier or on a host that only reads (`PlacementWriteError`). A command machine, a workspace and a machine's defaults need admin, and so does renaming or removing another device's or a machine's record; this device's own name needs device access. `setCommandMachine` sends the revision the page showed and answers whether the gateway reports it applied. `setMachineDefaults` reads the file again, refuses a hash other than `expectedHash`, and writes the whole file back with only its defaults changed. A removal is done when the whole listing read back lacks the id.
- Bounds: 16 machines, 32 devices, 32 names per inventory list, an approvals file's entries only for listed bots, names and ids of 128 characters, so the largest answer fits one result frame of the web host.

## The state

`ClawtrateState` (`src/types.ts`):

- `connection: ConnectionState`. `status` is `idle`, `connecting`, `pairing`, `connected`, `reconnecting` or `error`. `canWrite`, `canAnswer`, `canApprove` and `canAdmin` follow the scopes the gateway granted (`scopes`); a dropped connection clears them until the next hello. `upgrade: ScopeUpgradeState` tracks an access request and carries the request id and the approve command to show. `pairing` carries the same for pairing. `connectedAt` is the latest hello. Anything loaded before it is not yet known to be in sync.
- `discovery: DiscoveryState`, the bot and task lists. `partial` means the gateway listed more tasks than were read.
- `bots: Bot[]` and `tasksByBot: Record<botId, Task[]>`.
- `transcripts: Record<key, Transcript>`: one per task the client follows. On the web host a viewer's snapshot carries only the tasks that viewer has open (`viewerState` in `apps/desktop/src/web-host/server.ts`). A viewer that opens a task is sent a snapshot at once, before its open is answered, so a second tab, or a tab reloaded while another holds the task, gets its transcript although the host's state did not change. The Electron window receives the client's whole state.
- `unroutedApprovals: ApprovalCard[]`: pending approvals no followed task can show yet. `unroutedApprovalsOmitted` counts the ones not kept.
- `creations: TaskCreation[]`: task creations asked for and not yet settled.
- `accounts: AccountsState`: provider accounts, sign-in methods, each bot's binding and lock evidence, the sign-in and bot creation under way (see Provider accounts).
- `retention`: the estimated size of the state against its arithmetic bound. `near` is true past 80% of the bound.
- `usage`: warning budgets, their counts and the providers' limits (see Usage and warning budgets). Optional: a host that does not read them leaves it out.

`Transcript` is `TaskActivity` (`src/runs.ts`) plus the task's history:

- `status` (`loading`, `ready`, `error`), `items: TranscriptItem[]` (the last 200 history rows; a user row the gateway wrote itself, `provenance.kind: "internal_system"`, is a `system` item saying the gateway started or resumed a turn, never the person's words, and never settles an outgoing message), `hasMore`, `loadedAt` (the latest successful history load), `interSession` and `linkedRuns` (`src/cards.ts`).
- `live`: the active run's text, derived from `runs`, for a view that draws one streaming bubble.
- `runs: Run[]`. Each run has `state`, `steps: Step[]`, `pendingCards`, `closedCards`, the streaming `text`, `error`, `ending` and `attemptErrors`.

Key a step's view state (expansion, selection, a link) by `Step.id`. A tool step's id is `tool:<toolCallId>`, the gateway's own. A reasoning step's id is derived from its place in its run, never its text: the nearest tool call before it, or the run's start, and how many reasoning blocks came since (`reasoningStepId`; the run's `reasoningAnchor` and `nextReasoning` say where the next one is numbered from). A tool call the gateway sends with no id makes no step and does not move the anchor; a call id repeated within a run is one step, and it does not move the anchor either, so the reasoning after it goes on counting from the call before and no id is used twice (live and history alike). A reconciliation with history can change those places: history may hold a block the live stream never showed on its own, show one card's text as several blocks, or reveal a tool call the live stream missed, and then an id may vanish, appear, or name a different block than before. **The rule:** view state keyed by a reasoning step id (an open card, a selected raw view) is valid only while that run's `reasoningRevision` is unchanged. Remember the revision with the state; when the run's `reasoningRevision` changes, clear that run's reasoning view state. It never changes for tool steps. Clear it too whenever the task is reopened or a different history window replaces this one.

- `outbox: OutgoingMessage[]`, the user's messages until history holds them.
- `mcpTools`: the gateway's current map from a tool-server tool's effective name to its server and tool, read with `tools.effective` (`operator.read`) when the task's history loads and again on `plugins.changed`; at most 128. It is evidence of a call's tool before its result only: the gateway rebuilds it from its current catalog, which need not be what a running attempt captured, and a result's own `details.mcpServer` and `details.mcpTool` overrule it. One read of a task is in flight at a time: one asked for meanwhile is made once it answers, so a map from before a change cannot replace the one after it.
- `questions: QuestionCard[]` and `approvals: ApprovalCard[]` (`src/approvals.ts`), with `approvalAccess` and `approvalSources` saying whether the approval lists could be read at all. Each card keeps, as received, the records the gateway sent that settled it (`settledBy`: the `*.resolved` event, the reply to this client's request, or a read-back), one per source, and what this client sent to settle it (`sent`: method and parameters; the last 4 decisions for an approval, the answer or dismissal for a question). Each record is cut to 2,048 JSON characters; nothing is filled in where none arrived.
- `caughtUp`: set when the task was reloaded after an event gap or a reconnect.

`selectMessageCards` (`src/cards.ts`) derives the "Messaged <bot>" and MCP cards from a task's runs. It is a pure view and changes nothing in state.

## Reading an action

`src/actions.ts` reads a tool call as an action (`docs/design/conversation.md`, sections 7 and 8), and `src/action-feed.ts` lays a run's actions out. Both are pure and keep nothing; every word comes from one catalogue, `src/action-words.ts` (exported as `actionWords`), so a translation replaces that module alone. The iOS app uses the same functions.

- An `ActionCall` is a call as the reading takes it: its name, arguments, `status` (what the events established: `running`, `waiting`, `review`, `returned`, `stopped`, `cut-off`, or `unreturned` when its run ended otherwise with no result), the result's text, `isError` and `details`. `callFromStep(step, run)` and `callFromBlock(block, step, run)` build one from the engine's state, live or from a history item, and the reading (`lineOf`, `outcomeOf`, `readableOf`) reads each call through `withPayload` with its context, so a call reads the same live and from history (the result's own JSON under the details that were kept).
- `kindOf` gives the kind of 8.1 and the fold key (null: never folds); `outcomeOf` the outcome of 7.3: the event's status first, then an outcome the kind's adapter names more exactly, then any signal of the general reading (`payloadOutcome`, at either level of the payload), which outranks the adapter's Done and its fallback. Nothing reaches Done by default: Done needs the kind's positive evidence, and a payload that establishes nothing is Call made. `readingContextOf(transcript)` gives what the reading may know from the gateway: the name map, the built-in and plugin tools of the inventory (`Transcript.builtinTools`) and the bot's workspace root (`Transcript.workspaceRoot`, from `agents.files.list`). `lineOf` gives the line's words, state and accessible name; `foldLineOf` a fold's; `readableOf` the opened card's readable view, as data.
- `groupFeed(entries)` groups a run's ordered record (actions, reasoning, bubbles, cards and other breaks) into cards, folds and "Thought" lines, keyed by the gateway's tool call ids (a fold by its first member's). The live run and history go through it alike. `runLineOf` gives the run line; `phraseCall` the call whose running words the status line says.
- A step keeps what the reading needs even when its raw payload is too large to travel: `Step.args` and `Step.details` are bounded projections (`projectArgs`, `projectDetails`, at most `MAX_ACTION_FACTS_CHARS` each), and `Step.commandBearing` is the gateway's mark. A run keeps the text the model wrote beside a tool call in `Run.preambles` (`item` events of kind `preamble`), each placed before the tool step that follows it, by its call id (`beforeCall`).

## What each state establishes

Runs (`RunState`):

- `queued`: held by this client until the active run ends. It has not been sent.
- `running`: the gateway's events say the run is under way.
- `waiting`: the run holds a card in `pendingCards`, because its lifecycle reported `waiting-approval` or it asked a question. An approval record alone does not make a run `waiting`.
- `stopping`: Stop was pressed and `chat.abort` is on its way or unanswered. Stop aborts the one current run of the task (`runningRunId`): a steer's or a queued turn's own run id stands for the run it belongs to, and with two active runs that nothing ties together (an older run whose end a reconnect missed, beside the one the gateway runs now) Stop is withheld, and not offered, until the gateway establishes which is current. The run becomes `stopped` when the abort took, or `completed` with `finishedBeforeStop` when it finished first. Only the gateway's refusal of the abort puts the run back and sets `stopError`. An abort that was not sent, or whose answer a dropped connection lost, leaves the run `stopping`: once the connection is back it is aborted again if it still is, after as many drops as there are, until the gateway answers or the run's end arrives. The gateway cancels only a run it has registered: an abort that reaches it before it has taken the send stops nothing, with or without the run's id, and the turn then runs in full. So Stop on a run the gateway has not named yet (`bound: false`) sends nothing until the send's answer names the run, and then aborts that exact run. Every `chat.abort` names its run. The Stop is never forgotten when that answer is missing (no answer, a dropped connection, or an acceptance that names no run): the run stays `stopping` and unnamed, and the next history read settles it. If the gateway has it in flight under the send's id, it is named and stopped; if history holds its rows, the merge settles it; if nothing shows it, it is `stopped` with `outcomeKnown: false`, and a later read that finds it in flight still stops it. Meanwhile a message sent behind it is queued, and parked as `not-sent` once it stops.
- A send's answer can say the run is over already: `status: "timeout"` with `summary: "aborted"` (the gateway aborted the send before the turn ran; no event of it follows), `ok` or `error`. The run then settles from the answer: `stopped`, `completed` or `failed`.
- A steer's own run id (the send's answer while a run is active) is tentatively an alias of the run it was sent into (`steerAliases`). A steer the gateway joins to that run gets only a bare `chat final` under its own id, which shows nothing. A steer the gateway admits as a run of its own (it can, for instance when it races a Stop) shows lifecycle, text, tools or an error that ends it under its own id: the alias goes, and it is a run of its own, with its own history and anchor. History is never read through steer aliases.
- A turn the gateway ran from its queue carries two ids: the send's (its lifecycle, text and end) and the gateway's own (its `run_status`, and the rows history stores). `sessions.changed` names both, `runId` and `clientRunId`; from then on the gateway's id is a queue alias of the send's run (`queueAliases`, at most 16 per task), kept for as long as either id can arrive: its events, late ones included, update that run, and history rows under it are that run's. A reconnect that missed the pairing frame, or a transcript built from history alone, recovers it from history itself, whatever this client holds: a user row keyed `<send id>:user` followed by rows under an id the page has not shown before pairs the two. A steer's user row, followed by the rows of the run it was sent into, and an ordinary turn's, followed by rows under the send's own id, pair nothing. Until that row arrives (about a tenth of a second on the development gateway) the gateway's id can show as a run of its own with no steps or text; it goes when the alias is known. A `sessions.changed` row saying `end` or `error` for a run the task still shows as active, under either id, reads history again, so a run whose end did not reach this client under the id it knows is settled.
- `completed`, `stopped`, `failed`, `cancelled`: the gateway's terminal event, or history, said so. A history read whose rows for a run stop short of an end (a tool call last) does not end it while the gateway has a turn of the task in flight or queued: a steer into a run waiting on an approval or a question is held by OpenClaw 2026.10.6 as a queued turn of its own, which `chat.history` reports as the run in flight, while the run itself still waits. Only with nothing in flight or queued does such a run settle with `outcomeKnown: false`.
- A run this client stopped (Stop, a typed `/stop`, the stop after three timeouts) that ends as `stopped`, however that reached it (the abort's answer, the run's end event, history after a reconnect), also stops the runs of other bots its own `sessions_send` results name: `chat.abort` on each recipient's session, each recipient still identified by a retained run ID and session key, asked once more on the next connection when unanswered. `Run.stoppedWith` records each as the gateway answered: `bots` (stopped), `refused`, `unanswered`, `uncertain` (no run named), at most `MAX_STOPPED_NAMED` (8) of each with `omitted` counting the rest, and `helpers`, the helper runs a confirming abort's answer names besides the run. No process is stopped with a run: the gateway's process list does not say which run started one.
- After `TIMEOUTS_IN_A_ROW` (3) of a run's finished tool calls in a row timed out (`details.timedOut` or a `failureKind` of a timeout), this client stops it and marks `stoppedForTimeouts`. If the gateway refuses that stop, the mark becomes 0: the run goes on, it is not stopped for its timeouts again, and a later Stop's note is a plain stop's.
- `retry` is set while the gateway retries the model request by itself (`run_status` `retrying`, its `attempt` of `maxAttempts` and `reason`), and cleared when the model answers again. Only `reason: "rate_limit"` is a rate limit; the interface says any other reason as a plain retry, never as an outage the gateway did not report.
- `requestId` is the id of the `chat.send` frame that started a run this client sent. A failed run's `error.raw` names what the gateway sent that failed it (`holds`: the `chat-event`, the agent lifecycle event's `data`, or the `send-answer`) and its length; the content is never in the state. `readRunRaw` reads it when Raw is opened: `available` with the payload as received, `too-large` past `MAX_RAW_ENTRY_CHARS`, or `not-kept` (no longer kept, or, with `holds: null`, nothing was kept for this failure, which says nothing about what the gateway sent). A failure read from history takes the gateway's error row as its reason.
- `reportedStartAt` is when the gateway says the run started (its lifecycle start, or the history snapshot); null until it says. `startedAt` may be this client's own send time.
- `bound` is false until the gateway has named the run; until then `id` is this client's key. `outcomeKnown: false` means the run is known to have ended but nothing established how; its terminal state is a stand-in, and it always gives way: a later event of the run, or history that establishes its end, settles it as it really ended (a Stop asked of it still counts, so a run that finished first is `completed` with `finishedBeforeStop`).

A reply carries `replyToId`. A history item carries `messageId`, the gateway's id of the row whose text it shows, which reactions and replies name, and a reply's `replyTo` (`id`, the gateway's preview `text` and `sender`). `Transcript.reactions` holds, by message id, the reactions on the messages the transcript shows (at most 12 emoji each, most counted first; `mine` when this connection's person, as `users.self` names them, is among those who reacted): read with `session.reactions.list` after each history read and kept up by `session.reaction` events. Reactions never go backwards: a list asked for before a newer event, change or history page gives way to it and is asked for again (at most 3 times), an answer to `setReaction` older than an event about its message is not applied, and a message's reactions leave with the history page that showed it. A bot's turn of several rows has several bubbles, each with its row's id in its text block's `messageId`.

Outgoing messages (`OutgoingStatus`): `sending`, then `sent` once the gateway accepted it. The message leaves the outbox when history holds it. `checking` means no answer came, so whether the gateway took the message is unknown and history is being read. `unknown` means no answer came and the history read since holds no row with its key: whether the gateway took it is still not known, and it is never shown as accepted; retry (same key) and delete apply, and a later history row with its key settles it. `unconfirmed` means it was accepted (the gateway answered), its run ended, and no history row ties to it. `handled` means the gateway treated it as a command and started no run. `failed` and `cancelled` are what they say. `held` and `queued` have not been sent. `not-sent` is every message whose frame had not left when a Stop was confirmed: held, queued, or released and still waiting in the task's delivery chain. Nothing starts by itself after a stop, so it stays unsent until `retryMessage` sends it, as a message sent at that moment would go (a run starts with it, same key; with another run going, a steer into it; queued while one stops), or `deleteMessage` removes it. A Stop whose outcome nothing established (`outcomeKnown: false`) parks them the same way. This is decided per stopped run, at the change that stops it: another run being active, or ending later, does not release them, and a message sent after the stop, or sent again, is never parked by it. Whether a message has left is recorded in one place, `leftAt`: the time its `chat.send` frame was handed to the connection, null while the message waits in this client. Entering the delivery chain clears it, the send sets it, and the stop rule reads only it, never the status; a message whose frame left is not parked and settles as the gateway answers it. The outbox lives in the host's memory: a renderer reload keeps it, since the host holds the state, but a host restart loses it, every unsent status included. A retry reuses the message id as the idempotency key, so the gateway delivers it at most once. A message that came from the queue keeps `mode: "queue"` through every attempt until it starts or is removed: a refused start is `failed` with `queue` (the shelf's "Couldn't start"), and `retryMessage` on it starts it at once when no run is active, or queues it again behind the active run (held while a question is pending), so a second refusal reads the same as the first.

Questions: `pending`, `answered`, `dismissed`, `expired`, `cancelled` (the run was stopped), or `closed` (no longer pending on the gateway, and this client did not see how it ended).

Approvals: `pending`, `allowed`, `denied`, `expired`, `cancelled`, `closed`. `inferred` means the terminal status is this client's inference (expiry passed, or a reload no longer listed it); the gateway's own outcome replaces it. When the client makes that inference it reads the approval back once (`approval.get`, `operator.approvals`); the gateway's snapshot of a settled request gives its status, decision, resolution time and terminal `reason` (`user`, `timeout`, …), which replace the inference. The gateway keeps no reason of the kind "why the bot asked": `reason` is how it ended. `outcomeUnknown` means the gateway said the approval is settled but not how. `runEnded` means the approval is still pending after its run ended, and allowing it may still act.

Task creations: `creating`, `checking` (no answer; asked again with the same key), `failed` (refused; retry or dismiss), `unknown` (nothing establishes whether the task exists; a retry may create a second task), `created`.

Message cards: a tool start is the model's request, not a delivery, so a card is `started` until a result says more. `sentAt` is always null, because the gateway reports no delivery time. A late reply from another bot appears in `interSession` and is never attached to a card.

## Limits

- A viewer holds at most `MAX_VIEWER_OPEN_TASKS` (4) tasks open, and fewer when the host sets `maxOpenTasks`. It may have at most `MAX_VIEWER_PENDING_COMMANDS` (16) commands in flight.
- The client follows at most `MAX_TRACKED_TASKS` (8) tasks: open in some viewer, kept for unsent work after the last viewer closed them, or being created. The host may set fewer (`limits.trackedTasks`).
- Message text: at most `MAX_MESSAGE_CHARS` (32,000), never cut, refused if longer. One task's outbox holds at most 16 messages in any status. A new message past that is refused; nothing is dropped.
- Files: at most 20 per message; at most 64 files and 32 MiB waiting on the host, each kept for 15 minutes; images up to 6 MiB and other files up to 20 MiB, each less if the gateway says so (`hello-ok.policy.attachments`); the whole send within the gateway's frame limit. `connection.sendLimits` says all three, and the file count, as the gateway's current policy (read again at every connect). What a message may carry is computed in one place, `src/send-size.ts`: `chatSendParams` builds the request, `sendFrameBytes` is its exact size (its JSON with every escape, the reply id and a command chip's text, each file's base64, the frame around it), and `sendRefusal` checks the count, each file and the frame. The engine checks every send with it when it is made and again at delivery, so a message waiting for a reconnect meets the policy of the new connection; the composer checks a draft with the same function as it is drawn. More than 20 files are refused at `sendMessage` itself. Oversized sends throw `SendTooLargeError` before anything is sent. `releaseAttachments` lets the host drop files a viewer removed from its draft, so their room is free at once. Taking a message back (`takeBackMessage`) is all or nothing: its files are checked as one batch, bytes and count together, against what is left of those bounds before anything is cancelled or released. When they do not fit, the message stays exactly as it was, held or queued with its words and files, and the command is refused with `TAKE_BACK_NO_ROOM`, which says why in plain words. A restore never takes the waiting files past 64.
- The web bridge refuses a command frame over 64 KiB (`MAX_BRIDGE_FRAME_BYTES`). A command's answer on the web host must fit one result frame of `MAX_RESULT_CHARS` (262,144) JSON characters. An approval text too long for it is not given, so that approval stays deny-only for that viewer.
- Per task: 32 runs, 128 steps shared by its runs (older finished steps go first; `omittedSteps` counts them), 4 pending questions (`questionsOmitted`), 16 pending approvals (more wait in `unroutedApprovals`), the last 200 history rows. Earlier history pages are not loaded.
- Question cards show at most 8 options per question (`optionsOmitted` counts the rest) and 3 questions.
- At most 4 whole reads (`readStepRaw` from history, `readHistoryItem`, `readApprovalText`) run at once; a fifth is refused with an error to show.
- A host subscribes to the client's store (`client.store.subscribe`) at most `MAX_STORE_LISTENERS` (32) times at once; one more throws.
- A run this host started is stopped at the "Turn time limit", as Stop stops it (`stopping` until the gateway confirms, then `stopped` with `Run.turnLimit`; a refusal puts it back), 50 minutes (`DEFAULT_TURN_LIMIT_MS`) until the person chooses another with `setTurnLimit` (whole minutes, 1 to 1,440, kept in the host's storage and shown as `state.turnLimitMinutes`); a run already going is timed against a new limit from when it started. A run this host did not start has no timer. A request unanswered for 60 seconds fails locally.
- Not promised: a reasoning step's id once its run's `reasoningRevision` changed, or after its task is closed and reopened or read from a different history window; that a step's whole text can be read before history holds it; that history itself is uncut (`Step.truncated` and `TranscriptItem.truncated` mark what the gateway cut); delivery of a message whose status is `checking`, `unknown` or `unconfirmed`; any order or link between a late reply and the send it answers.

## Changes interface builders must adapt to

Since the guide first described the engine, these changes are not additive. Code written against the earlier surface has to change.

- `StepRead`, the answer of `readStepRaw`, has three more members: `cut-by-gateway`, `not-established` and `too-large-for-gateway`. An exhaustive `switch` on `status` must handle them. Only `available` carries the step's whole raw payload.
- `Run.reasoningAnchor` is a new required field, and `Run.nextReasoning` now counts the reasoning blocks since that anchor and starts again at 0 after each tool call; it used to grow for the whole run. Code that builds `Run` values must set both.
- `Run.reasoningRevision` is a new required field. View state keyed by a reasoning step id is valid only while it is unchanged (see "Key a step's view state" above).
- Reasoning step ids have a new form, `reasoning:<runId>:<anchor>:<n>`, with `%` and `:` escaped in the run id and the anchor, so no two places share an id whatever characters the gateway's ids hold, a lone surrogate included (ordinary ids read the same). They were always opaque; do not parse them.
- Removed exports: `EngineContext.ids` (the client-wide reasoning id allocator); `CLIENT_FOREIGN`, `VIEWER_FOREIGN` and `ATTACHMENT_FOREIGN`, replaced by `CLIENT_NOT_WALKED`, `VIEWER_NOT_WALKED` and `ATTACHMENT_NOT_WALKED`, records that give a reason for each property; `GATEWAY_HISTORY_RESPONSE_BYTES`. `HistoryMerge.fromHistory` is now a `Set<string>` of step ids, not a `Map` from step id to source id.
- New refusals a caller must handle: `client.store.subscribe` throws past `MAX_STORE_LISTENERS` (32) listeners, and `readApprovalText` now shares the gate of four concurrent whole reads with `readStepRaw` and `readHistoryItem`, so a fifth whole read of any kind is refused with an error to show.
- New in this round: the `not-established` and `too-large-for-gateway` results of `readStepRaw`, and `Run.reasoningRevision` with its rule.
- `StepStatus` has a new member, `unknown`: a tool step whose run ended before its result arrived. An exhaustive `switch` on it must handle it, and it is neither done nor failed. `STEP_CLOSED_BY_RUN_END` is gone with it.
- Additive since then: `Step.args`, `Step.details` and `Step.commandBearing`, `Run.preambles` (each anchored by `beforeCall`, the id of the call it came with), `Run.omittedTools`, `Run.omittedToolsAtEnd`, `Run.endFromRows`, `Step.omittedBefore`, `Step.rowTimes`, and `Transcript.builtinTools` and `Transcript.workspaceRoot`, all optional, so code that builds `Step` and `Run` values keeps compiling; a step without them is read from `argsText` and its result text alone. The worst case of a step and of a run grew with them (`docs/decisions.md`).
- `Step.files` is a new optional field on file-tool steps, and the `STEP` bound counts it; code that builds `Step` values need not set it. `ClawtrateBridge.save` is new and optional: a host that has it saves a file the viewer holds (the desktop app's save dialog); without it the interface downloads through the browser. The desktop host refuses more than `MAX_SAVE_BYTES` (the largest content a reader sends) and a second save while one dialog is open (`MAX_PENDING_SAVES`), and holds the bytes (`PendingSaves`) only until that dialog's save ends or its page goes.
- Since then: `stopRun` on a run the gateway has not named sends no `chat.abort` until the send's answer names it, and never sends one without a run id. `TaskActivity.queueAliases` is new and required: the gateway's own id of a queued turn, mapped to the send's run. A history user row the gateway wrote itself is a `system` item. A send's answer that says the run is over settles it.
- Additive: `ClawtrateState.usage`, optional, and the commands `readUsage`, `changeBudget`, `refreshUsage` and `listRoutines`.
- Additive: the machine commands above, and `requestAccess` takes `tier: "pairing"`; a granted device access is recorded with the token (`pairingHeld`).
- `ClawtrateState.accounts` and `ConnectionState.canAdmin` are new required fields; code that builds states must set them (`initialAccountsState`). `HostInfo.devGateway` may carry `cli`, how a command reaches the development instance (`openclaw --profile clawtrate-dev-<name>`), for the commands the interface shows. `requestAccess` takes an optional `tier`.
